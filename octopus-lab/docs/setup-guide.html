1 — Start Octopus Deploy
1

Configure Environment

PowerShell 
cd octopus-lab
Copy-Item .env.example .env

Edit .env and set:

# Required
SA_PASSWORD=YourStrong!Pass2024
ACCEPT_OCTOPUS_EULA=Y
ADMIN_USERNAME=admin
ADMIN_PASSWORD=OctoAdmin!2024
ADMIN_EMAIL=admin@localhost

# Paste your license key (base64)
OCTOPUS_SERVER_BASE64_LICENSE=...
2

Start Containers

PowerShell 
# Make sure dba-lab is running first
..\dba-lab.ps1 up

# Start Octopus
.\octopus-lab.ps1 up

Octopus takes ~2 minutes to initialize. Two containers start:

ContainerPortPurpose
octopus-db1400SQL Server Express for Octopus internal data
octopus-server8080Octopus Deploy web UI + API
Networking: Octopus containers join the dba-lab_dba-lab Docker network, so they can reach sql-dev, sql-staging, sql-prod-1 by hostname on port 1433.
2 — First-Time Octopus Setup
3

Login and Create API Key

  1. Open http://localhost:8080
  2. Login with ADMIN_USERNAME / ADMIN_PASSWORD from .env
  3. Go to Profile → API Keys → New API Key
  4. Copy the API key
  5. Add to .env as OCTOPUS_API_KEY=API-XXXXXXXXXX
API key format: Starts with API- followed by alphanumeric characters. This key authenticates all CLI and REST API calls.
Button grayed out? If the “New API Key” button is disabled in the UI, create the key via REST API instead:
Bash / Git Bash 
# 1. Login and save cookies
curl -s -c /tmp/octo-cookies -X POST \
  "http://localhost:8080/api/users/login" \
  -H "Content-Type: application/json" \
  -d '{"Username":"admin","Password":"YOUR_PASSWORD"}'

# 2. Extract CSRF token from cookies
CSRF=$(cat /tmp/octo-cookies | grep "Octopus-Csrf-Token" | awk '{print $NF}')

# 3. Create API key
curl -s -b /tmp/octo-cookies -X POST \
  "http://localhost:8080/api/users/Users-1/apikeys" \
  -H "Content-Type: application/json" \
  -H "X-Octopus-Csrf-Token: $CSRF" \
  -d '{"Purpose":"dba-lab automation"}'

The response contains "ApiKey": "API-XXXX..." — copy that value to your .env.

4 — Build dacpac from SSDT
5

Build the SSDT Projects

PowerShell (via CLI) 
.\octopus-lab.ps1 build
Or from Visual Studio 
Open ..\db\db.sln → Right-click Solution → Build Solution (Ctrl+Shift+B)

Produces the dacpac file:

ProjectOutputTarget Database
db..\db\bin\Release\db.dacpacAppDB
Compile-time validation. The build catches broken references, missing columns, invalid syntax, and FK violations before anything touches a database. This is the main advantage over raw SQL scripts.
5 — Package & Push to Octopus
6

Package dacpac into NuGet

PowerShell 
.\octopus-lab.ps1 pack

Creates versioned .nupkg files in artifacts/:

artifacts/
  DbaLab.AppDB.2026.06.18.1200.nupkg
Version format: yyyy.MM.dd.HHmm by default. Override with octo pack --version=1.0.0 for semantic versioning.
7

Push to Octopus Built-in Feed

PowerShell 
.\octopus-lab.ps1 push

Pushes all .nupkg files from artifacts/ to the Octopus built-in package feed. Packages are now available for releases.

Manual Alternative

If you prefer to package and push manually:

PowerShell 
# Package
octo pack `
    --id="DbaLab.AppDB" `
    --version="1.0.0" `
    --basePath="..\db\bin\Release" `
    --include="db.dacpac" `
    --format="nupkg" `
    --outFolder="artifacts"

# Push
octo push `
    --server="http://localhost:8080" `
    --apiKey=$env:OCTOPUS_API_KEY `
    --package="artifacts\DbaLab.AppDB.1.0.0.nupkg"
6 — Deployment Process

Configure Deployment Steps

In Octopus UI → Database Deployment project → Process, add these steps:

#Step NameTemplateWhat It Does
1Script AppDB ChangesRun a Scriptsqlpackage /Action:Script — generates diff, attaches as artifact for DBA review
2Publish AppDBRun a Scriptsqlpackage /Action:Publish — applies dacpac delta
4Run Post-DeployRun a ScriptExecutes idempotent migration scripts (seed data)
5Verify SchemaRun a ScriptQueries sys.tables/procedures/views, logs counts

Step 1: Script AppDB Changes (Diff Preview)

Package reference: DbaLab.AppDB

PowerShell Script Body 
$dacpac = "$($OctopusParameters['Octopus.Action.Package[DbaLab.AppDB].ExtractedPath'])\db.dacpac"
$server = $OctopusParameters['SqlServer.Host']
$port   = $OctopusParameters['SqlServer.Port']
$db     = $OctopusParameters['Database.Name']
$pass   = $OctopusParameters['SqlServer.Password']
$script = "$env:TEMP\AppDB_diff_$(Get-Date -Format 'yyyyMMdd_HHmmss').sql"

sqlpackage /Action:Script `
    /SourceFile:$dacpac `
    /TargetServerName:"$server,$port" `
    /TargetDatabaseName:$db `
    /TargetUser:sa `
    /TargetPassword:$pass `
    /TargetTrustServerCertificate:True `
    /OutputPath:$script `
    /p:BlockOnPossibleDataLoss=$($OctopusParameters['Deploy.BlockOnPossibleDataLoss'])

Write-Host "--- Generated diff script ---"
Get-Content $script | Select-Object -First 50
Write-Host "..."

New-OctopusArtifact -Path $script -Name "AppDB_diff.sql"
DBA review gate. The diff script is attached as an Octopus deployment artifact. Before promoting to Production, a DBA can download and review exactly what will change.

Step 2: Publish AppDB

Same package reference. This step applies the changes.

PowerShell Script Body 
$dacpac = "$($OctopusParameters['Octopus.Action.Package[DbaLab.AppDB].ExtractedPath'])\db.dacpac"
$server = $OctopusParameters['SqlServer.Host']
$port   = $OctopusParameters['SqlServer.Port']
$db     = $OctopusParameters['Database.Name']
$pass   = $OctopusParameters['SqlServer.Password']

Write-Host "Publishing $dacpac to $server,$port/$db..."

sqlpackage /Action:Publish `
    /SourceFile:$dacpac `
    /TargetServerName:"$server,$port" `
    /TargetDatabaseName:$db `
    /TargetUser:sa `
    /TargetPassword:$pass `
    /TargetTrustServerCertificate:True `
    /p:BlockOnPossibleDataLoss=$($OctopusParameters['Deploy.BlockOnPossibleDataLoss'])

if ($LASTEXITCODE -ne 0) { throw "AppDB publish failed!" }
Write-Host "AppDB published successfully."

Step 4: Post-Deploy Migrations

PowerShell Script Body 
$server = $OctopusParameters['SqlServer.Host']
$port   = $OctopusParameters['SqlServer.Port']
$pass   = $OctopusParameters['SqlServer.Password']
$db     = $OctopusParameters['Database.Name']

sqlcmd -S "$server,$port" -U sa -P $pass -d $db -No -b `
    -Q "
SET QUOTED_IDENTIFIER ON;
IF NOT EXISTS (SELECT 1 FROM [dbo].[Folder] WHERE [Name] = N'Root')
BEGIN
    DECLARE @uid UNIQUEIDENTIFIER;
    IF NOT EXISTS (SELECT 1 FROM [dbo].[User] WHERE [ExternalId] = N'SYSTEM')
    BEGIN
        SET @uid = NEWID();
        INSERT INTO [dbo].[User] ([Id],[ExternalId],[DisplayName],[Email],[Role])
        VALUES (@uid, N'SYSTEM', N'System', N'system@localhost', 255);
    END ELSE SELECT @uid = [Id] FROM [dbo].[User] WHERE [ExternalId] = N'SYSTEM';
    INSERT INTO [dbo].[Folder] ([Name],[ParentFolderId],[CreatedBy]) VALUES (N'Root', NULL, @uid);
    PRINT 'Root folder seeded';
END ELSE PRINT 'Root folder exists';
"

if ($LASTEXITCODE -ne 0) { Write-Warning "Post-deploy returned non-zero" }
else { Write-Host "Post-deploy complete." }

Step 5: Verify Schema

PowerShell Script Body 
$server = $OctopusParameters['SqlServer.Host']
$port   = $OctopusParameters['SqlServer.Port']
$pass   = $OctopusParameters['SqlServer.Password']
$db     = $OctopusParameters['Database.Name']

sqlcmd -S "$server,$port" -U sa -P $pass -d $db -No -b `
    -Q "
SELECT 'Tables:    ' + CAST(COUNT(*) AS VARCHAR) FROM sys.tables WHERE is_ms_shipped=0;
SELECT 'Procedures: ' + CAST(COUNT(*) AS VARCHAR) FROM sys.procedures;
SELECT 'Views:      ' + CAST(COUNT(*) AS VARCHAR) FROM sys.views WHERE is_ms_shipped=0;
"
7 — Create Release & Deploy
8

Create a Release

Octopus UI

Database Deployment project → Create Release → select package versions → Save.

Or via CLI 
octo create-release `
    --server="http://localhost:8080" `
    --apiKey=$env:OCTOPUS_API_KEY `
    --project="Database Deployment" `
    --version="1.0.0" `
    --packageVersion="1.0.0"
9

Deploy to Dev

PowerShell 
octo deploy-release `
    --server="http://localhost:8080" `
    --apiKey=$env:OCTOPUS_API_KEY `
    --project="Database Deployment" `
    --version="1.0.0" `
    --deployTo="Dev" `
    --waitForDeployment

Octopus runs all 5 steps against sql-dev:1433. Check the task log for step output and the diff artifact.

Production deploys to primary only. AG automatically replicates schema changes (DDL) to sql-prod-2. The diff script artifact from Step 1 provides the DBA review gate — download it before promoting to Production to see exactly what changes.
