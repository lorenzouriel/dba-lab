# Understanding a SELECT: What SQL Server Actually Does When You Hit F5

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

You write a SELECT. You hit F5. Data comes back. Simple enough.

But then a colleague asks why an alias you defined in SELECT can't be used in the WHERE clause, and you don't have a good answer. Or you wonder why a query with a GROUP BY runs slowly even though the result set is tiny. Or you write what looks like a perfectly logical filter and it silently returns the wrong rows.

These aren't edge cases. They're the result of not knowing what SQL Server actually does with your query — and in what order.

---

## The Six Clauses and What They Mean

A full SELECT statement has six clauses. You don't always use all six, but when you do, they mean very specific things.

```sql
SELECT
    column1,
    column2,
    aggregate_function(column3) AS alias
FROM table_name
WHERE filter_condition
GROUP BY column1, column2
HAVING aggregated_filter_condition
ORDER BY column1 ASC;
```

Let's walk through each one using SalesDB.

**FROM** — The data source. SQL Server starts here. Before it reads a single column, it needs to know which table (or joined set of tables) to work with.

**WHERE** — Row-level filter applied before any grouping. Filters which rows get into the result set. `WHERE order_date >= '2024-01-01'` eliminates rows from the start.

**GROUP BY** — Collapses multiple rows into groups. Every column in your SELECT that isn't inside an aggregate function must appear in GROUP BY.

**HAVING** — Filters *groups* after aggregation. WHERE can't reference aggregate results (`SUM`, `COUNT`, `AVG`). HAVING can.

**SELECT** — Chooses which columns to return and applies expressions or aliases. Despite appearing first in the written syntax, this runs late in the process.

**ORDER BY** — Sorts the final result set. The one clause that can reference aliases defined in SELECT, because it runs after SELECT.

---

## The Execution Order Problem

Here's the thing that surprises almost every developer at some point: **SQL Server does not execute your query in the order you write it.**

Writing order:
```
SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY
```

Execution order:
```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

This isn't an implementation quirk — it's the logical processing order defined by the SQL standard. And it explains a lot of behavior that otherwise seems arbitrary.

**Why can't you use a SELECT alias in WHERE?**

```sql
-- This fails:
SELECT
    customer_id,
    COUNT(*) AS order_count
FROM dbo.Orders
WHERE order_count > 5;   -- Error: Invalid column name 'order_count'
```

Because WHERE runs before SELECT. When WHERE is evaluated, `order_count` doesn't exist yet — the alias hasn't been computed.

**Why does HAVING exist at all?**

```sql
-- Wrong: you can't filter an aggregate in WHERE
SELECT
    customer_id,
    COUNT(*) AS order_count
FROM dbo.Orders
WHERE COUNT(*) > 5;   -- Error: aggregate not allowed in WHERE

-- Right: use HAVING, which runs after GROUP BY
SELECT
    customer_id,
    COUNT(*) AS order_count
FROM dbo.Orders
GROUP BY customer_id
HAVING COUNT(*) > 5;
```

HAVING exists precisely because WHERE runs before aggregation. If you need to filter on an aggregated value, you need a clause that runs after GROUP BY — and that's HAVING.

**Why can ORDER BY reference aliases but WHERE cannot?**

Because ORDER BY runs last. By the time ORDER BY executes, SELECT has already run and the aliases exist.

## A Complete Example With SalesDB

```sql
-- "Find customers with more than 3 orders placed in 2024,
-- sorted by their total order count descending"

SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(o.order_id) AS order_count
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
WHERE YEAR(o.order_date) = 2024
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING COUNT(o.order_id) > 3
ORDER BY order_count DESC;
```

Trace the execution order through this query:

1. **FROM + JOIN** — SQL Server loads `Customers` joined with `Orders` on `customer_id`
2. **WHERE** — Filters to only rows where `order_date` falls in 2024
3. **GROUP BY** — Collapses rows into one group per customer
4. **HAVING** — Drops any group with 3 or fewer orders
5. **SELECT** — Extracts `customer_id`, `first_name`, `last_name`, and `COUNT(order_id)` — and creates the `order_count` alias
6. **ORDER BY** — Sorts by `order_count` descending (the alias is now available)

## The Trap

**`SELECT *` — the lazy habit that costs you in production.**

Every developer has written `SELECT * FROM dbo.Orders` to check what's in a table. That's fine for exploration. The trap is leaving `SELECT *` in production code, reports, or stored procedures.

The problems:

- **Schema changes break you silently.** Add a new column to `Orders`, and every `SELECT *` consumer suddenly gets that column — which might overflow a fixed-width application field, break a downstream CSV export, or confuse a dashboard that was mapping columns by position.
- **Performance.** SQL Server has to fetch every column from disk and transmit it over the network, including large text or binary columns you don't need.
- **Ambiguity in joins.** `SELECT * FROM Orders o JOIN Customers c ON ...` returns multiple `customer_id` columns. Which one is which?

List your columns explicitly. It takes an extra 30 seconds now and saves an incident at 2am later.

---

## Key Takeaways

- **SQL has six core clauses** — `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY` — each with a distinct role
- **Writing order ≠ execution order** — SQL Server processes FROM first and SELECT late; this explains why WHERE can't reference SELECT aliases
- **WHERE filters rows; HAVING filters groups** — use WHERE to eliminate rows before aggregation, HAVING to filter aggregate results after
- **ORDER BY is the only clause that can use SELECT aliases** — because it runs after SELECT
- **Avoid `SELECT *` in production code** — explicit column lists protect you from schema changes and improve query performance
