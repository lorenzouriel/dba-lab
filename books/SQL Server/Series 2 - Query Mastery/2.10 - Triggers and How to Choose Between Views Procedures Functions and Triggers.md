# Triggers, and How to Choose Between Views, Procedures, Functions, and Triggers

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

Every growing SQL codebase hits the same symptoms. The same five-table join gets pasted into six reports. Business logic lives in the application tier, duplicated across three applications, slowly drifting out of sync. Some writes need validation and logging that nobody remembers to add consistently. SQL Server gives you four tools to pull that logic out of the app and into the database, where it lives once: views, stored procedures, functions, and triggers.

This series has already covered the first three in depth — views in 2.6, stored procedures in 2.7, functions in 2.8. What's missing is the fourth tool, and the framework that ties all four together. Triggers are the one object in this list that fires on its own, without being called — which makes them powerful and, if you're not careful, the thing you're debugging at 2 a.m. wondering why a row got an extra write nobody asked for.

---

## A One-Paragraph Recap

A **view** is a saved `SELECT` — no parameters, no data of its own, a security and readability boundary over a query you don't want re-typed. A **stored procedure** is a compiled batch of T-SQL that accepts parameters, runs multiple statements, and owns its own transaction — the natural home for "validate stock, insert the order, decrement inventory, all atomically." A **function** — scalar or table-valued — returns a value or a result set you can drop straight into a `SELECT`, `WHERE`, or `JOIN`; inline table-valued functions optimize like parameterized views, while scalar functions carry a row-by-row execution cost the optimizer can sometimes (not always) inline away. If any of that needs a refresher, 2.6, 2.7, and 2.8 cover the syntax and traps in detail. What none of those articles cover is the fourth object: the one that runs automatically.

---

## Triggers: Automatic, Powerful, and the Hardest to Debug

A trigger is a stored procedure that fires on its own when an event happens. You don't `EXEC` a trigger — SQL Server invokes it in response to something else. DML triggers respond to `INSERT`, `UPDATE`, and `DELETE`. DDL triggers respond to schema changes like `CREATE`, `ALTER`, and `DROP`. That automatic, invisible execution is the entire value proposition — and the entire risk.

### AFTER vs. INSTEAD OF

DML triggers come in two shapes, and picking the right one matters.

**AFTER triggers** (also called FOR triggers) run once the underlying modification has already landed in the table. They're the right choice for validation after the fact, cascading updates to related tables, and audit logging.

```sql
CREATE TRIGGER trg_LogPriceChanges
ON dbo.Products
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    IF UPDATE(unit_price)
        INSERT INTO dbo.PriceHistory (product_id, old_price, new_price, changed_at)
        SELECT d.product_id, d.unit_price, i.unit_price, GETDATE()
        FROM deleted AS d
        INNER JOIN inserted AS i ON d.product_id = i.product_id
        WHERE d.unit_price <> i.unit_price;
END;
```

**INSTEAD OF triggers** replace the original statement entirely. The `INSERT`, `UPDATE`, or `DELETE` you wrote never touches the table directly — the trigger body decides what actually happens. This is how you make an otherwise non-updatable view writable, or inject validation that must run *before* any row is committed.

```sql
CREATE TRIGGER trg_PreventCompletedOrderDelete
ON dbo.Orders
INSTEAD OF DELETE
AS
BEGIN
    SET NOCOUNT ON;

    IF EXISTS (SELECT 1 FROM deleted WHERE status = 'Completed')
    BEGIN
        THROW 50004, 'Completed orders cannot be deleted.', 1;
        RETURN;
    END

    DELETE o
    FROM dbo.Orders AS o
    INNER JOIN deleted AS d ON o.order_id = d.order_id;
END;
```

Notice that the `INSTEAD OF DELETE` trigger has to perform the delete itself for the rows it allows through — nothing happens automatically once you've told SQL Server to intercept the statement.

### DDL Triggers: Guarding the Schema, Not the Data

Everything above is a DML trigger — it fires on data changes. A **DDL trigger** fires on schema changes instead: `CREATE TABLE`, `ALTER TABLE`, `DROP INDEX`, and the like. They're less common than DML triggers, but they're the right tool when you need to prevent or log structural changes — blocking an accidental `DROP TABLE` in production, or recording who changed a table definition and when.

```sql
CREATE TRIGGER trg_PreventTableDrop
ON DATABASE
FOR DROP_TABLE
AS
BEGIN
    PRINT 'Table drops are disabled on this database. Contact a DBA to proceed.';
    ROLLBACK;
END;
```

DDL triggers scope to either `ON DATABASE` (fires for events in that database) or `ON ALL SERVER` (fires server-wide, useful for auditing login or server-configuration changes). They're a governance tool more than a business-logic tool — reach for them when the requirement is "nobody should be able to do X without going through a review," not as a substitute for proper permissions and change management.

### The `inserted` and `deleted` Pseudo-Tables

Every DML trigger has access to two special in-memory tables that hold the rows affected by the statement that fired it. `INSERT` populates `inserted`. `DELETE` populates `deleted`. `UPDATE` populates both — the old values land in `deleted`, the new values land in `inserted`. Matching a row across both by primary key, as in the price-change example above, is how you build a clean before/after audit record.

The critical mental model: these are **sets**, not single rows. A trigger fires once per statement, not once per row. If your trigger logic assumes exactly one row landed in `inserted`, it will work perfectly in testing and quietly produce wrong results the first time someone runs a batch `UPDATE` that touches 500 rows at once. Always write trigger logic as a set-based operation against `inserted`/`deleted`, the same way you'd write any other query.

The `UPDATE(column_name)` function, used inside the trigger body, tells you whether a specific column was targeted by the statement — regardless of whether the value actually changed. Pair it with a value comparison (`WHERE d.unit_price <> i.unit_price`, as above) if you only want to act when the value truly changed, not just when it was included in the `SET` clause.

### Recursion

A trigger that modifies a table can cause that same table's trigger to fire again, and if the logic isn't guarded, that becomes a loop. SQL Server's `RECURSIVE_TRIGGERS` database setting controls whether a trigger is allowed to fire itself indirectly through a chain of other triggers (it's off by default for *direct* recursion regardless of the setting, but indirect recursion through a different table's trigger is controlled by this option). Know the setting exists, know what your triggers touch downstream, and design against loops rather than relying on the recursion depth limit to save you — SQL Server does cap trigger nesting at 32 levels, but hitting that cap in production means something already went wrong upstream.

### Error Semantics

An unhandled error inside a trigger rolls back not just the trigger's own work but the entire triggering statement. That's usually what you want for a hard business rule (rejecting a delete on a completed order, as above), but it means a careless error in logging code can block a legitimate write. Use `THROW` deliberately when blocking the operation is the intent, and keep any non-critical trigger logic (like writing to an audit table) defensive — a failure to log shouldn't necessarily fail the original insert, depending on how strict your audit requirements are.

### Keep Them Minimal

A trigger executes *inside* the transaction of the statement that fired it. Slow trigger code doesn't run "in the background" — it adds directly to the latency of every `INSERT`, `UPDATE`, or `DELETE` against that table. A trigger that does a few extra sets of column comparisons and an insert into an audit table is fine. A trigger that calls out to complex multi-table logic, loops, or anything resembling application-tier work will throttle every write to the table, and because it's invisible in the calling code, it's one of the hardest kinds of slowdown to trace back to its source.

For genuinely heavy work — sending a notification, recalculating an aggregate across millions of rows — have the trigger drop a row into a queue table instead, and let a separate scheduled job process the queue asynchronously. The trigger's job is to capture that something happened, not to do everything that needs to happen as a result.

Document triggers deliberately. They execute where nobody's looking at the calling code. The next person debugging a mysterious extra write, or wondering why a `DELETE` didn't do what they expected, needs a way to discover that a trigger exists and why — a comment in the trigger body and a note wherever the table's schema is documented both help.

### Finding What's Already There

Before adding a trigger to a table, check what's already firing on it. `sys.triggers` lists every trigger in the database along with whether it's currently enabled:

```sql
SELECT
    t.name                              AS trigger_name,
    OBJECT_NAME(t.parent_id)            AS table_name,
    t.is_disabled,
    t.is_instead_of_trigger,
    m.definition
FROM sys.triggers AS t
INNER JOIN sys.sql_modules AS m ON t.object_id = m.object_id
WHERE t.parent_id = OBJECT_ID('dbo.Orders');
```

This is worth running before every schema change on a table you didn't design — a trigger doing validation or cascading logic is easy to miss if you only look at the table's columns and constraints.

## The Capability Grid

With all four objects covered, here's what actually separates them — worth keeping as a reference:

| Capability | Views | Procedures | Functions | Triggers |
|---|---|---|---|---|
| Accept parameters | No | Yes | Yes | No |
| Modify data | Limited | Yes | No | Yes |
| Return result sets | Yes | Yes | TVFs only | No |
| Use in SELECT / JOIN | Yes | No | Yes | No |
| Transaction control | No | Yes | No | Yes |
| Automatic execution | No | No | No | Yes |
| Plan caching | No | Yes | Varies | Yes |

---

## The Decision Framework

The grid is useful as a lookup, but the actual decision comes down to two questions: **can the query optimizer see inside this object, and does it need its own transaction control?**

- **Need it inside a `SELECT`, `WHERE`, or `JOIN`?** Reach for a function or a view. A parameterized result set means a table-valued function (inline if at all possible — it optimizes like a parameterized view). A single value means a scalar function. No parameters, just simplifying access to a join or hiding columns, means a view.
- **Need multi-statement logic, multi-table writes, and a transaction that either fully commits or fully rolls back?** That's a stored procedure. It's the default for anything that changes data in more than one place.
- **Need it to happen automatically on every write, no matter who or what performs the write?** That's a trigger — but only because "automatic" is a genuine requirement. If a stored procedure could do the same job by being called explicitly as part of a normal workflow, use the procedure. It's easier to test, easier to read, and easier to debug six months from now.

A few concrete mappings make this click: a five-table join reused across reports is a view. "Validate stock, insert the order, update inventory" is a stored procedure. A shipping-cost calculation from weight and destination is a scalar function (verify it inlines). "All orders for a customer in a date range" is a table-valued function. "Log every change to the price column, no matter which application makes the change" is a trigger — because the requirement is specifically that no caller can bypass the logging.

The mistake to avoid, in every direction, is picking by habit instead of by fit: scalar functions parked in a hot `WHERE` clause without checking whether they inline; triggers doing work a stored procedure should own, which trades visibility for automation you didn't actually need; views stacked on views until the optimizer can't reason about any of them; and a stored procedure where an inline table-valued function would have slotted directly into a query instead of forcing a round-trip through a temp table.

## Key Takeaways

- **Triggers fire automatically** — DML triggers respond to `INSERT`/`UPDATE`/`DELETE`, DDL triggers respond to schema changes; nothing calls them explicitly
- **AFTER runs post-write, INSTEAD OF replaces the statement** — use AFTER for logging and cascades, INSTEAD OF to make a view writable or to intercept and reject an operation before it happens
- **`inserted` and `deleted` hold sets, not single rows** — a trigger fires once per statement; always write trigger logic to handle multi-row batches correctly
- **Triggers run inside the triggering transaction** — slow trigger code slows every write to the table; offload heavy work to a queue table and an async job
- **Choose by optimizer visibility and transaction control** — function/view for composing into a query, procedure for multi-statement transactional writes, trigger only when automatic execution on every write is the actual requirement
