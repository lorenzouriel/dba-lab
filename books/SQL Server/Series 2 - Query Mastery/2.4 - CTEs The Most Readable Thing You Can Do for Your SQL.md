# CTEs: The Most Readable Thing You Can Do for Your SQL

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

You inherit a stored procedure. It's 150 lines. The FROM clause has a subquery, inside which there's another subquery, and somewhere in the middle of that second subquery is the actual logic you need to change. You're not sure where the calculation starts. You're not sure what the inner SELECT is doing. You start at the top, read to the bottom, and still don't understand what it's doing.

CTEs don't solve all SQL complexity — but they solve this kind. A CTE forces you to name your intermediate result, and named things are understandable things.

---

## What a CTE Is

A **Common Table Expression (CTE)** is a named temporary result set you define at the start of a query using the `WITH` keyword. You can then reference that name in the main query below it — as if it were a table.

```sql
WITH cte_name AS (
    -- This is the CTE body: any valid SELECT
    SELECT
        column1,
        column2
    FROM some_table
    WHERE some_condition
)
-- This is the outer query — it uses the CTE like a table
SELECT *
FROM cte_name;
```

The CTE exists only for the duration of the query. It's not stored anywhere. When the query finishes, it's gone. Think of it as giving a name to a piece of your query so you can refer to it cleanly.

---

## The Main Benefits

**Readability.** This is the primary reason to use a CTE. Naming an intermediate result forces you to think about what it represents — and communicates that to the next person who reads the code.

**Reuse within the same query.** A CTE defined once can be referenced multiple times in the outer query. The equivalent with a subquery would mean duplicating the logic every place you reference it.

**Debuggability.** Because a CTE is defined as a standalone block, you can highlight just the CTE body and run it independently to inspect its result before worrying about the outer query.

**Recursive queries.** CTEs are the only SQL construct that supports recursive queries (querying hierarchical data by having a CTE reference itself). Subqueries can't do this.

## Building a CTE on SalesDB

Let's build up a real example — "find each customer's total order value, but only for completed orders."

**Step 1: Write the inner logic first.**

```sql
SELECT
    o.customer_id,
    SUM(od.quantity * od.unit_price) AS total_value
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
WHERE o.status = 'Completed'
GROUP BY o.customer_id;
```

**Step 2: Wrap it in a CTE with a descriptive name.**

```sql
WITH completed_order_totals AS (
    SELECT
        o.customer_id,
        SUM(od.quantity * od.unit_price) AS total_value
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    WHERE o.status = 'Completed'
    GROUP BY o.customer_id
)
SELECT
    c.first_name,
    c.last_name,
    c.email,
    cot.total_value
FROM dbo.Customers AS c
INNER JOIN completed_order_totals AS cot ON c.customer_id = cot.customer_id
ORDER BY cot.total_value DESC;
```

The name `completed_order_totals` tells you exactly what the CTE contains before you read a single line of its body. That's the value.

---

## Multiple CTEs in One Query

You can chain CTEs by separating them with commas. Each CTE can reference the ones defined before it.

```sql
WITH completed_order_totals AS (
    SELECT
        o.customer_id,
        SUM(od.quantity * od.unit_price) AS total_value
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    WHERE o.status = 'Completed'
    GROUP BY o.customer_id
),
high_value_customers AS (
    SELECT
        customer_id,
        total_value
    FROM completed_order_totals
    WHERE total_value > 1000
)
SELECT
    c.first_name,
    c.last_name,
    hvc.total_value
FROM dbo.Customers AS c
INNER JOIN high_value_customers AS hvc ON c.customer_id = hvc.customer_id
ORDER BY hvc.total_value DESC;
```

Two CTEs, each named, each focused on one job. The outer query reads like a sentence: "Get me the customer details for high-value customers."

## Recursive CTEs

A recursive CTE references itself in its own definition. This is how SQL handles hierarchical data — org charts, category trees, bill of materials.

The structure requires two parts:
1. An **anchor member** — the base case (top of the hierarchy)
2. A **recursive member** — the part that joins back to the CTE itself (walk down the hierarchy)

```sql
-- Employee hierarchy: who reports to whom
-- Assuming a Employees table with employee_id, name, manager_id
WITH employee_hierarchy AS (
    -- Anchor: top-level employees (no manager)
    SELECT
        employee_id,
        name,
        manager_id,
        0 AS depth
    FROM dbo.Employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive: employees who report to someone already in the CTE
    SELECT
        e.employee_id,
        e.name,
        e.manager_id,
        eh.depth + 1
    FROM dbo.Employees AS e
    INNER JOIN employee_hierarchy AS eh ON e.manager_id = eh.employee_id
)
SELECT
    employee_id,
    name,
    depth
FROM employee_hierarchy
ORDER BY depth, employee_id;
```

SQL Server executes the anchor once, then repeatedly executes the recursive member until it produces no new rows. The `depth` column tracks how deep in the hierarchy each employee sits.

SQL Server adds a default recursion limit of 100 iterations. You can override with `OPTION (MAXRECURSION n)` — but if you're hitting that limit in production, it usually means a data cycle (A reports to B reports to A) rather than a genuinely deep hierarchy.

---

## The Trap

**CTEs are not materialized — they're re-evaluated.** A common misconception is that defining a CTE "caches" the result so it's computed once and reused cheaply. In most cases, SQL Server re-evaluates the CTE every time it's referenced. If you reference the same CTE twice in the outer query and the CTE is expensive, you're paying that cost twice.

```sql
WITH expensive_cte AS (
    -- Complex calculation over millions of rows
    SELECT customer_id, SUM(value) AS total
    FROM dbo.VeryLargeTable
    GROUP BY customer_id
)
-- This might evaluate expensive_cte twice
SELECT * FROM expensive_cte WHERE total > 1000
UNION ALL
SELECT * FROM expensive_cte WHERE total <= 1000;
```

For cases where you genuinely need a materialized intermediate result, use a temporary table (`#temp`) instead. The CTE gives you readability; the temp table gives you materialization. They solve different problems.

---

## Key Takeaways

- **CTEs use the `WITH` keyword and exist only for the query's lifetime** — they're not stored, not cached, not persistent
- **The main value is readability** — naming an intermediate result forces clarity and makes complex queries approachable
- **Multiple CTEs can be chained** — separate them with commas; each can reference earlier ones
- **Recursive CTEs walk hierarchies** — anchor member sets the base, recursive member walks down; SQL Server limits recursion to 100 by default
- **CTEs are not materialized** — if you reference a CTE multiple times and it's expensive, consider a temp table instead
