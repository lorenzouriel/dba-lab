# Wildcards in SQL: LIKE, PATINDEX, and When to Avoid Them

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

"Find all customers whose email ends in `.com`." Easy enough. "Find all product names that start with a number." A bit trickier. "Find every order note that contains a phone number." Now you need more than LIKE.

Wildcard searches are one of those things that look simple but hide enough complexity to cause real problems in production. The `%` pattern scan that works fine on 1,000 rows becomes the query that locks up a table with 10 million.

This article covers how wildcards work, when to use each one, and when to stop using them altogether.

---

## The Two Core Wildcards

SQL Server has two wildcard characters used with the `LIKE` operator.

**`%` (percent)** — matches zero or more characters of any kind.

```sql
-- Finds all customers whose email ends in '.com'
SELECT
    customer_id,
    first_name,
    email
FROM dbo.Customers
WHERE email LIKE '%.com';

-- Finds products with 'Pro' anywhere in the name
SELECT
    product_id,
    product_name
FROM dbo.Products
WHERE product_name LIKE '%Pro%';

-- Finds emails starting with 'a'
SELECT
    customer_id,
    email
FROM dbo.Customers
WHERE email LIKE 'a%';
```

**`_` (underscore)** — matches exactly one character, any character.

```sql
-- Finds product names that are exactly 5 characters long
SELECT
    product_id,
    product_name
FROM dbo.Products
WHERE product_name LIKE '_____';

-- Finds SKUs in the pattern 'A-###' (letter, dash, three digits)
SELECT
    product_id,
    product_name
FROM dbo.Products
WHERE product_name LIKE '[A-Z]-[0-9][0-9][0-9]';
```

---

## Two More Wildcards You Should Know

SQL Server supports two additional wildcards that are less commonly used but solve specific problems cleanly.

**`[character_list]`** — matches any single character from a specified set.

```sql
-- Finds products starting with A, B, or C
SELECT product_name
FROM dbo.Products
WHERE product_name LIKE '[ABC]%';

-- Finds products starting with any letter A through F
SELECT product_name
FROM dbo.Products
WHERE product_name LIKE '[A-F]%';
```

**`[^character_list]`** — matches any single character NOT in the specified set.

```sql
-- Finds products NOT starting with A, B, or C
SELECT product_name
FROM dbo.Products
WHERE product_name LIKE '[^ABC]%';
```

## PATINDEX: When You Need More Than a Boolean

`LIKE` tells you whether a pattern exists — it returns matching rows or not. `PATINDEX` tells you *where* the pattern occurs, returning the position of the first match (or 0 if not found).

```sql
-- Find customers whose email has a domain longer than 3 characters after the dot
-- PATINDEX returns the position of '.com' or similar pattern
SELECT
    customer_id,
    email,
    PATINDEX('%.____%', email) AS pattern_position
FROM dbo.Customers;

-- Filter: only rows where a digit appears in the product name
SELECT
    product_id,
    product_name,
    PATINDEX('%[0-9]%', product_name) AS first_digit_position
FROM dbo.Products
WHERE PATINDEX('%[0-9]%', product_name) > 0;
```

`PATINDEX` uses the same wildcard syntax as `LIKE` (`%`, `_`, `[character_list]`). The key difference: LIKE is a predicate (true/false), PATINDEX is a function (returns an integer position).

---

## Case Sensitivity

By default, `LIKE` comparisons are case-insensitive in SQL Server when using a case-insensitive collation (the default for most installations). So `LIKE '%pro%'` matches "Product", "PRO", and "pro".

If you need case-sensitive matching:

```sql
-- Explicit case-sensitive collation
SELECT product_name
FROM dbo.Products
WHERE product_name LIKE '%Pro%' COLLATE Latin1_General_CS_AS;
```

Check your database collation if you're getting unexpected matches or misses — collation rules affect LIKE results.

---

## The Trap

**Leading wildcards destroy index performance.** This is the most important thing to understand about wildcard queries.

When you write `WHERE email LIKE '%.com'`, SQL Server cannot use an index on `email` to satisfy this search. The pattern starts with `%`, which means "the match could start anywhere" — the database has no choice but to scan every row in the table.

Compare:

```sql
-- Index CANNOT be used — pattern starts with wildcard
WHERE email LIKE '%@gmail.com'

-- Index CAN be used — pattern anchored at the start
WHERE email LIKE 'ana%'
```

The second query can use a range scan on an index. The first cannot — it's a full table scan no matter what indexes you have.

This matters at scale. A leading-wildcard search on an unindexed 10-million-row table can take tens of seconds. On an indexed column, the trailing-wildcard version of the same pattern can complete in milliseconds.

If you genuinely need full-text pattern matching — searching for words anywhere inside long text fields — SQL Server's **Full-Text Search** feature (with `CONTAINS` and `FREETEXT`) is the right tool. LIKE with leading wildcards is not designed for that use case.

---

## Key Takeaways

- **`%` matches zero or more characters; `_` matches exactly one** — the two wildcards you'll use daily
- **`[char_list]` and `[^char_list]`** match or exclude specific character sets — useful for format validation patterns
- **`PATINDEX` returns the position of a match, not just whether it exists** — use it when you need to locate or extract pattern occurrences
- **Leading wildcards (`LIKE '%something'`) disable index seeks** — they cause full table scans; anchor your patterns at the start when possible
- **For real full-text search, use Full-Text Search with `CONTAINS`** — LIKE is not designed for searching within large text bodies at scale
