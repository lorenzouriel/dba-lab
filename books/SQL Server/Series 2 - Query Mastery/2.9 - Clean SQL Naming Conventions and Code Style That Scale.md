# Clean SQL: Naming Conventions and Code Style That Scale

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

"It works" is not the bar. Code that works but nobody can read costs time on every future change. SQL that works but uses inconsistent names, no formatting, and mixed conventions accumulates into a database where developers are afraid to touch anything because they can't tell what's doing what.

Clean SQL is not about aesthetics. It's about maintainability — the difference between a query that the next developer can extend in 20 minutes and one that requires an archaeology expedition to understand.

---

## Naming Conventions

Good names communicate intent without explanation. These conventions are the baseline — your team may adjust them, but the principle (consistency, clarity, predictability) should stay constant.

| Object | Convention | Example |
|--------|-----------|---------|
| Table | Singular noun, PascalCase or snake_case | `dbo.Customer`, `dbo.OrderDetail` |
| Column | snake_case | `first_name`, `total_amount`, `created_at` |
| Primary Key | `[entity_id]` | `customer_id`, `order_id` |
| Foreign Key | Same name as the referenced PK | `customer_id` in `Orders` references `customer_id` in `Customers` |
| Stored Procedure | `usp_[Verb][Entity]` | `usp_GetCustomerOrders`, `usp_CreateOrder` |
| View | `vw_[Entity][Purpose]` | `vw_OrderSummary`, `vw_CustomerActivity` |
| Index | `ix_[Table]_[Column(s)]` | `ix_Orders_customer_id` |
| Constraint (CHECK) | `ck_[Table]_[Rule]` | `ck_OrderDetails_quantity_positive` |
| Function | `fn_[Purpose]` | `fn_GetOrderTotal`, `fn_GetCustomerOrders` |

The FK naming convention matters more than it looks. If `Orders.customer_id` matches `Customers.customer_id` exactly, anyone reading the schema immediately knows how to join those tables. If they're named differently (`Orders.cust_id` or `Orders.client_key`), every join requires schema lookup.

## Code Formatting

Readable SQL isn't a style preference — it's what lets you catch a logic bug at a glance rather than after 20 minutes of staring.

**Capitalize all SQL keywords.**

```sql
-- Bad
select c.first_name, o.order_id from customers c inner join orders o on c.customer_id = o.customer_id where o.status = 'Pending';

-- Good
SELECT
    c.first_name,
    o.order_id
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
WHERE o.status = 'Pending';
```

**One clause per line, one column per line.**

```sql
SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(o.order_id) AS total_orders
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
WHERE c.created_at >= DATEADD(YEAR, -1, GETDATE())
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING COUNT(o.order_id) > 0
ORDER BY total_orders DESC;
```

**Align JOIN conditions on the ON keyword.** The join condition belongs on the same line as the JOIN or immediately below it — not buried after a long table alias.

**Use meaningful aliases.** `c` for Customers, `o` for Orders, `od` for OrderDetails, `p` for Products. Single-letter aliases are fine as long as they're predictable and consistent.

## The Rules That Actually Matter in Production

### Never `SELECT *` in Production Code

```sql
-- Bad: breaks when schema changes, transmits unnecessary data
SELECT * FROM dbo.Orders;

-- Good: explicit, stable, documents what you actually need
SELECT
    order_id,
    customer_id,
    order_date,
    status
FROM dbo.Orders;
```

`SELECT *` is fine for quick exploration. It's a liability in stored procedures, views, application queries, and ETL pipelines — anywhere the code persists and may be affected by schema changes.

### Comment the Why, Not the What

```sql
-- Bad: restates what the code already says
SELECT customer_id FROM dbo.Customers; -- Select customer ID from Customers

-- Good: explains the non-obvious constraint
-- Exclude test accounts (customer_id < 1000 reserved for QA environment)
SELECT customer_id
FROM dbo.Customers
WHERE customer_id >= 1000;
```

If the comment explains something that the code doesn't already communicate — a constraint, a business rule, a historical reason — it's worth writing. If it restates the code in English, delete it.

### Qualify Schema Names

```sql
-- Bad: which database object? Depends on user's default schema
SELECT * FROM Orders;

-- Good: unambiguous, consistent, avoids resolution errors
SELECT * FROM dbo.Orders;
```

Always prefix object names with the schema (`dbo.` in most SQL Server databases). This prevents silent failures when a user has a different default schema and avoids ambiguity in multi-schema databases.

### Don't Wrap Filter Columns in Functions

```sql
-- Bad: function on column destroys index usability
WHERE YEAR(order_date) = 2024

-- Good: range comparison uses index seek
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
```

Wrapping a column in a function in a WHERE clause means SQL Server can't use an index on that column. The query becomes a full table scan. Write range conditions instead.

### Use EXISTS Instead of COUNT for Existence Checks

```sql
-- Bad: counts all matching rows just to check if any exist
IF (SELECT COUNT(*) FROM dbo.Orders WHERE customer_id = @customer_id) > 0

-- Good: stops at the first match
IF EXISTS (SELECT 1 FROM dbo.Orders WHERE customer_id = @customer_id)
```

`EXISTS` short-circuits — as soon as one row matches, it returns true. `COUNT(*)` scans all matching rows before returning. The difference on large tables is significant.

### Keep Transactions Short

```sql
-- Pattern: validate outside the transaction, run DML inside
-- Don't put slow SELECTs or user waits inside a BEGIN TRANSACTION

BEGIN TRANSACTION;
BEGIN TRY
    INSERT INTO dbo.Orders (customer_id, order_date, status)
    VALUES (@customer_id, GETDATE(), 'Pending');

    INSERT INTO dbo.OrderDetails (order_id, product_id, quantity, unit_price)
    VALUES (SCOPE_IDENTITY(), @product_id, @quantity, @unit_price);

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    THROW;
END CATCH;
```

Every open transaction holds locks. Long-running transactions block other queries and cause contention. Do your validation before `BEGIN TRANSACTION`, do only the necessary DML inside, and commit as quickly as possible.

### Dynamic SQL: Parameterize or Don't Write It

If you need dynamic SQL, use `sp_executesql` with parameters — never string concatenation.

```sql
-- Bad: SQL injection vulnerability
DECLARE @sql NVARCHAR(MAX) = 'SELECT * FROM Orders WHERE status = ''' + @status + '''';
EXEC(@sql);

-- Good: parameterized dynamic SQL
DECLARE @sql NVARCHAR(MAX) = N'SELECT * FROM dbo.Orders WHERE status = @status_param';
EXEC sp_executesql @sql, N'@status_param VARCHAR(50)', @status_param = @status;
```

The first version lets a caller inject arbitrary SQL by passing `'; DROP TABLE Orders; --` as `@status`. The second doesn't — the parameter is typed data, never interpreted as SQL.

## Version Control and Deployment

Treat SQL like code, because it is.

- Store all schema objects (tables, procedures, views, functions) in version control
- Use migration tools (SSDT, Flyway, Liquibase, or even numbered `.sql` files) to track schema changes
- Never make schema changes directly in production without a tracked script
- Apply CI/CD pipelines to validate and deploy SQL changes

The database is part of your codebase. It should have the same traceability and deployment discipline as application code.

---

## Key Takeaways

- **Consistent naming is the foundation** — predictable object names eliminate lookup time and communicate intent
- **Format for the reader** — one clause per line, one column per line, capitalized keywords, qualified schema names
- **Never `SELECT *` in production code** — always list columns explicitly
- **Comment the why, not the what** — explain constraints, business rules, and non-obvious choices; delete everything else
- **Don't wrap filter columns in functions** — they destroy index performance; use range conditions instead
- **Parameterize dynamic SQL with `sp_executesql`** — string concatenation is a SQL injection vulnerability
