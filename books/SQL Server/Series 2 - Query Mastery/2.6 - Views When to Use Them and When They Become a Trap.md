# Views: When to Use Them and When They Become a Trap

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

A CTE lives for one query, then disappears. A subquery is embedded in the code that uses it. Neither is accessible to someone else without sharing the full query.

A view solves that problem. It's a stored query — saved in the database, queryable by name, accessible to any user or application with the right permissions. You write the logic once, store it, and consumers query it as if it were a table.

That sounds great. And it often is — until someone builds six views that each depend on three other views, and now you can't change a column in a base table without breaking half the reporting layer.

---

## What a View Is

A **view** is a named `SELECT` statement stored in the database. When you query a view, SQL Server executes the underlying SELECT and returns the result — the view itself stores no data.

```sql
-- Create a view: order summary with customer and product detail
CREATE VIEW dbo.vw_OrderSummary
AS
SELECT
    o.order_id,
    o.order_date,
    o.status,
    c.first_name,
    c.last_name,
    c.email,
    p.product_name,
    od.quantity,
    od.unit_price,
    od.quantity * od.unit_price AS line_total
FROM dbo.Orders AS o
INNER JOIN dbo.Customers AS c ON o.customer_id = c.customer_id
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id;
```

Once created, anyone with SELECT permission on the view can query it:

```sql
-- Query the view exactly like a table
SELECT
    first_name,
    last_name,
    order_id,
    line_total
FROM dbo.vw_OrderSummary
WHERE status = 'Completed'
ORDER BY order_date DESC;
```

## Creating, Altering, and Dropping Views

All three DDL commands follow the same pattern:

```sql
-- ALTER: modify the view definition
ALTER VIEW dbo.vw_OrderSummary
AS
SELECT
    o.order_id,
    o.order_date,
    o.status,
    c.first_name,
    c.last_name,
    c.email,
    p.product_name,
    p.category,           -- added this column
    od.quantity,
    od.unit_price,
    od.quantity * od.unit_price AS line_total
FROM dbo.Orders AS o
INNER JOIN dbo.Customers AS c ON o.customer_id = c.customer_id
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id;

-- DROP: remove the view entirely
DROP VIEW dbo.vw_OrderSummary;
```

A common pattern is `CREATE OR ALTER VIEW`, available in SQL Server 2016 SP1 and later — it creates the view if it doesn't exist, or replaces it if it does, without having to manage DROP/CREATE separately.

```sql
CREATE OR ALTER VIEW dbo.vw_OrderSummary
AS
-- updated definition
```

## The Three Legitimate Use Cases

**1. Access control.** Give application users or reporting tools access to a view, not to the base tables. The view shows exactly what they're supposed to see — no more, no less. A finance user can query `vw_CustomerOrders` without having any idea that `dbo.Orders`, `dbo.Customers`, and `dbo.Financials` exist.

```sql
-- A restricted view: customer-facing data only, no internal pricing
CREATE VIEW dbo.vw_CustomerOrderHistory
AS
SELECT
    o.order_id,
    o.order_date,
    o.status,
    p.product_name,
    od.quantity
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id;
-- Notice: no unit_price exposed here

GRANT SELECT ON dbo.vw_CustomerOrderHistory TO [customer_portal_user];
```

**2. Shared logic.** If five different stored procedures all need the same three-table join, putting that join in a view means changing it once propagates everywhere. The view becomes a reusable module.

**3. Simplified interfaces.** A reporting tool or BI system that needs a flat, wide table to build a dashboard doesn't need to know about normalization. A view that pre-joins the relevant tables hides the complexity.

---

## What Views Are Not Good For

**Parameterized filtering.** A view can't accept parameters. `SELECT * FROM dbo.vw_OrderSummary WHERE region = @region` is a filter applied *on top of* the view — the view already ran its underlying SELECT in full before your WHERE applies (in most cases). For parameterized queries over large tables, a stored procedure or table-valued function is the right tool.

**Complex business logic with branching.** Views can't contain IF statements, variables, or procedural code. They're pure SELECTs. Anything that requires conditional logic belongs in a stored procedure or function.

**Performance-critical high-frequency queries on large tables.** Standard views are not materialized — they re-execute the underlying SELECT every time they're queried. SQL Server does have **indexed views** (materialized views), which physically store the result, but they come with strict constraints on what the view can contain.

---

## The Trap

**View-on-view dependency chains.** This is how reporting layers rot over time. Someone creates a view. Someone else creates a view based on that view. A third person creates a view based on the second. Three months later, nobody knows what the base tables look like, changing anything breaks something upstream, and the "simple" query against `vw_FinalReportData` executes seven nested views and scans three million rows.

Signs you're in this situation:
- Views that reference other views in their definition
- Views with `SELECT *` in them (especially bad — adding a column to a base table invisibly changes what the view returns)
- Views nobody can explain without reading all the way down to the base tables

The discipline: views should reference base tables, not other views. One level of abstraction. If you need a second level, use a CTE inside a stored procedure instead — at least then the complexity is visible in one place.

---

## Key Takeaways

- **A view is a stored SELECT** — it stores the query definition, not the data; the data is retrieved each time the view is queried
- **Best uses: access control, shared join logic, simplified reporting interfaces** — let views hide complexity from consumers who don't need it
- **Views can't accept parameters** — use stored procedures or table-valued functions when you need filtering by variable input
- **Standard views are not cached** — they re-execute on every query; use indexed views for materialization, with strict constraints
- **Avoid view-on-view chains** — views should reference base tables; more than one level of view abstraction is a maintenance problem
