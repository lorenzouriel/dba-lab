# Stored Procedures: The Good, the Bad, and the Business Logic

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

Stored procedures get two completely different reputations depending on who you ask. Some developers love them — precompiled, parameterized, secure, reusable. Others avoid them — "business logic doesn't belong in the database."

Both camps are partially right, and both miss the point when they go to the extreme. Stored procedures are the right tool for specific jobs. The question isn't whether to use them — it's knowing when.

---

## What a Stored Procedure Is

A stored procedure is a named, saved block of T-SQL that can be executed by name, optionally with parameters. Unlike a view (which can only contain a SELECT), a stored procedure can contain any T-SQL — INSERT, UPDATE, DELETE, SELECT, variable declarations, IF/ELSE logic, loops, error handling, and transaction control.

```sql
-- Basic structure
CREATE PROCEDURE dbo.usp_GetCustomerOrders
    @customer_id INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        o.order_id,
        o.order_date,
        o.status,
        SUM(od.quantity * od.unit_price) AS order_total
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    WHERE o.customer_id = @customer_id
    GROUP BY o.order_id, o.order_date, o.status
    ORDER BY o.order_date DESC;
END;
```

Execute it:

```sql
EXEC dbo.usp_GetCustomerOrders @customer_id = 42;
```

---

## The Practical Benefits

**Pre-compilation and plan caching.** SQL Server compiles a stored procedure the first time it runs and caches the execution plan. Subsequent calls skip compilation and reuse the plan. For complex queries that run thousands of times, this matters.

**Parameterization prevents SQL injection.** Instead of building a query string in application code, you pass parameters to a procedure. The parameters are never interpreted as SQL syntax — they're data.

```sql
-- This is safe: @customer_id is a typed INT parameter, not a string
EXEC dbo.usp_GetCustomerOrders @customer_id = 42;
```

Compared to application code that builds a query string with string concatenation — where `42` could be replaced with `42; DROP TABLE Customers;` — stored procedures handle this safely by design.

**Centralized business logic.** If ten different applications need to insert an order, they all call the same procedure. Change the procedure once, and every caller gets the update. No coordination across applications, no risk of one caller using an outdated version of the logic.

**Access control.** You can grant EXECUTE on a procedure without granting SELECT, INSERT, UPDATE, or DELETE on the underlying tables. The application user doesn't need direct table access — they just call the procedure.

## A Production-Grade Example

A procedure that inserts a new order with validation and error handling:

```sql
CREATE PROCEDURE dbo.usp_CreateOrder
    @customer_id INT,
    @product_id  INT,
    @quantity    INT
AS
BEGIN
    SET NOCOUNT ON;

    -- Validate inputs
    IF NOT EXISTS (SELECT 1 FROM dbo.Customers WHERE customer_id = @customer_id)
    BEGIN
        THROW 50001, 'Customer not found.', 1;
    END;

    IF NOT EXISTS (SELECT 1 FROM dbo.Products WHERE product_id = @product_id AND stock >= @quantity)
    BEGIN
        THROW 50002, 'Insufficient stock or product not found.', 1;
    END;

    DECLARE @unit_price DECIMAL(10, 2);
    SELECT @unit_price = unit_price FROM dbo.Products WHERE product_id = @product_id;

    BEGIN TRANSACTION;
    BEGIN TRY
        -- Insert order header
        DECLARE @order_id INT;

        INSERT INTO dbo.Orders (customer_id, order_date, status)
        VALUES (@customer_id, GETDATE(), 'Pending');

        SET @order_id = SCOPE_IDENTITY();

        -- Insert order line
        INSERT INTO dbo.OrderDetails (order_id, product_id, quantity, unit_price)
        VALUES (@order_id, @product_id, @quantity, @unit_price);

        -- Reduce stock
        UPDATE dbo.Products
        SET stock = stock - @quantity
        WHERE product_id = @product_id;

        COMMIT TRANSACTION;

        SELECT @order_id AS new_order_id;
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;
```

This procedure validates inputs, runs three DML operations as a single transaction, and either commits all three or rolls back all three. None of this is possible in a view.

## Updating and Removing Procedures

```sql
-- ALTER: modify the procedure definition
ALTER PROCEDURE dbo.usp_GetCustomerOrders
    @customer_id INT,
    @status      VARCHAR(50) = NULL   -- added optional parameter with default
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        o.order_id,
        o.order_date,
        o.status,
        SUM(od.quantity * od.unit_price) AS order_total
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    WHERE o.customer_id = @customer_id
      AND (@status IS NULL OR o.status = @status)
    GROUP BY o.order_id, o.order_date, o.status
    ORDER BY o.order_date DESC;
END;

-- DROP: remove the procedure entirely
DROP PROCEDURE dbo.usp_GetCustomerOrders;
```

## Stored Procedures vs Views vs Functions

| | View | Stored Procedure | Table-Valued Function |
|---|---|---|---|
| Accepts parameters | No | Yes | Yes |
| Returns a table | Yes (always) | Optional | Yes (always) |
| Can use in FROM clause | Yes | No | Yes |
| Can contain DML | No | Yes | No (inline TVF) |
| Can contain transactions | No | Yes | No |
| Execute syntax | SELECT | EXEC | SELECT |

Views are for persistent, parameterless queries. Stored procedures are for parameterized logic that may involve data modification, transactions, or procedural flow. Functions are for parameterized, read-only logic that returns a table you can query inline.

---

## The Trap

**Stuffing everything into stored procedures.** The argument that "all business logic belongs in stored procedures" leads to a codebase where the database holds thousands of procedures, each doing slightly different things, that nobody fully understands and nothing can be changed without fear.

The practical guidelines:
- Put data integrity validation in the database (constraints, procedures) — close to the data
- Put business workflow, orchestration, and complex state management in the application layer — where it can be tested, versioned, and debugged
- Use procedures for frequently run, parameterized DML operations that benefit from plan caching and security encapsulation

The other trap: procedures that do too much. A 500-line procedure that handles 12 different scenarios based on parameter combinations is a nightmare to debug. Keep procedures focused — one purpose, predictable inputs, predictable outputs.

---

## Key Takeaways

- **Stored procedures are named, saved T-SQL blocks** — parameterized, precompiled, reusable, and securable
- **Always include `SET NOCOUNT ON`** — suppresses row-count messages that can confuse calling applications
- **Use TRY/CATCH with explicit transactions** — commit on success, rollback on any error, re-raise with THROW
- **Use THROW, not RAISERROR, for new code** — covered in depth in Series 3
- **Procedures provide security isolation** — grant EXECUTE without granting direct table access
- **Don't put everything in procedures** — complex business workflow belongs in the application layer; procedures are for data operations
