# SQL Server Functions: Scalar, Table-Valued, and When Each Kills Performance

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

SQL Server ships with hundreds of built-in functions. Most developers use maybe fifteen of them regularly and don't know the rest exist. That's fine — the 80/20 rule applies here harder than almost anywhere in SQL.

But there's a line past what built-in functions can do. When your query needs to encapsulate a business rule that returns a value, or filter data through logic that returns a table, that's when you write your own. User-defined functions (UDFs) are where SQL gets most powerful — and where the worst performance traps hide.

---

## The Built-in Functions You'll Actually Use

### Aggregate Functions

Aggregate functions collapse multiple rows into one value. They must appear in SELECT alongside a GROUP BY, or used in HAVING.

```sql
SELECT
    p.category,
    COUNT(*)                                  AS total_orders,
    SUM(od.quantity * od.unit_price)          AS total_revenue,
    AVG(od.unit_price)                        AS avg_unit_price,
    MIN(o.order_date)                         AS first_order,
    MAX(o.order_date)                         AS last_order
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id
GROUP BY p.category;
```

### Date and Time Functions

```sql
-- Current timestamp
SELECT GETDATE() AS now;                       -- 2024-05-13 21:06:24.240
SELECT GETUTCDATE() AS utc_now;

-- Add/subtract intervals
SELECT DATEADD(DAY, 30, o.order_date) AS due_date
FROM dbo.Orders AS o;

-- Difference between two dates
SELECT DATEDIFF(DAY, o.order_date, GETDATE()) AS days_since_order
FROM dbo.Orders AS o;

-- Extract parts
SELECT
    YEAR(order_date)  AS order_year,
    MONTH(order_date) AS order_month,
    DAY(order_date)   AS order_day
FROM dbo.Orders;

-- Format output (use sparingly — formatting belongs in the app layer)
SELECT FORMAT(GETDATE(), 'dd/MM/yyyy') AS formatted_date;
```

### String Functions

```sql
SELECT
    LEN(c.email)                         AS email_length,
    UPPER(c.last_name)                   AS last_name_upper,
    LOWER(c.email)                       AS email_lower,
    SUBSTRING(c.email, 1, CHARINDEX('@', c.email) - 1) AS email_username,
    REPLACE(p.product_name, 'Pro', 'Professional') AS product_name_expanded,
    LTRIM(RTRIM(c.first_name))           AS name_trimmed,
    CONCAT(c.first_name, ' ', c.last_name) AS full_name
FROM dbo.Customers AS c
CROSS JOIN dbo.Products AS p;
```

### Null-Handling Functions

```sql
-- COALESCE: return first non-null value from a list
SELECT
    order_id,
    COALESCE(shipping_address, billing_address, 'No address') AS delivery_address
FROM dbo.Orders;

-- ISNULL: replace null with a specific value (SQL Server-specific)
SELECT
    product_name,
    ISNULL(category, 'Uncategorized') AS category
FROM dbo.Products;
```

### Type Conversion

```sql
-- CAST: standard SQL conversion
SELECT CAST(unit_price AS INT) AS price_rounded_down FROM dbo.Products;
SELECT CAST('2024-01-15' AS DATE) AS parsed_date;

-- CONVERT: SQL Server extension, supports formatting styles
SELECT CONVERT(VARCHAR(10), GETDATE(), 101) AS us_date_format;  -- '05/13/2024'
```

## Window Functions: The Most Powerful Built-ins

Window functions compute values across a "window" of rows without collapsing them into groups. The `OVER()` clause defines the window.

```sql
-- Row number per customer (most recent order = 1)
SELECT
    o.customer_id,
    o.order_id,
    o.order_date,
    ROW_NUMBER() OVER (PARTITION BY o.customer_id ORDER BY o.order_date DESC) AS recency_rank
FROM dbo.Orders AS o;

-- Running total of revenue by date
SELECT
    o.order_date,
    od.quantity * od.unit_price AS line_total,
    SUM(od.quantity * od.unit_price) OVER (ORDER BY o.order_date) AS running_total
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id;

-- Compare each order's value to the previous one
SELECT
    o.order_id,
    o.order_date,
    SUM(od.quantity * od.unit_price) AS order_total,
    LAG(SUM(od.quantity * od.unit_price)) OVER (ORDER BY o.order_date) AS previous_order_total
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY o.order_id, o.order_date;
```

`ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `LAG()`, `LEAD()`, and aggregate functions with `OVER()` all belong in this category. They're invaluable for analytics, ranking, and sequential comparisons.

## User-Defined Functions

### Table-Valued Functions (TVFs)

A table-valued function returns a table. You call it in a FROM clause and treat the result like a regular table.

```sql
-- TVF: orders within a date range for a specific customer
CREATE FUNCTION dbo.fn_GetCustomerOrders
(
    @customer_id INT,
    @start_date  DATE,
    @end_date    DATE
)
RETURNS TABLE
AS
RETURN
(
    SELECT
        o.order_id,
        o.order_date,
        o.status,
        SUM(od.quantity * od.unit_price) AS order_total
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    WHERE o.customer_id = @customer_id
      AND o.order_date BETWEEN @start_date AND @end_date
    GROUP BY o.order_id, o.order_date, o.status
);
```

Usage:

```sql
SELECT *
FROM dbo.fn_GetCustomerOrders(42, '2024-01-01', '2024-12-31')
ORDER BY order_date;
```

This is an **inline TVF** (defined with `RETURNS TABLE AS RETURN (single SELECT)`). Inline TVFs are efficient — SQL Server treats them like a parameterized view and can optimize them fully.

### Scalar Functions

A scalar function returns a single value. You call it in a SELECT, WHERE, or any expression.

```sql
-- Scalar function: calculate revenue for a specific order
CREATE FUNCTION dbo.fn_GetOrderTotal
(
    @order_id INT
)
RETURNS DECIMAL(10, 2)
AS
BEGIN
    DECLARE @total DECIMAL(10, 2);

    SELECT @total = SUM(quantity * unit_price)
    FROM dbo.OrderDetails
    WHERE order_id = @order_id;

    RETURN ISNULL(@total, 0);
END;
```

Usage:

```sql
SELECT
    order_id,
    order_date,
    dbo.fn_GetOrderTotal(order_id) AS calculated_total
FROM dbo.Orders;
```

## The Trap

**Scalar UDFs in WHERE clauses and on large tables.** Scalar UDFs are row-by-row. When you call a scalar UDF in a SELECT over a million-row table, SQL Server calls the function a million times — one invocation per row. The function can't be parallelized before SQL Server 2019, and even with scalar UDF inlining in 2019+, the optimizer sometimes can't inline complex functions.

The performance difference is dramatic. The same logic written inline in the query typically runs 10–100x faster than wrapped in a scalar UDF.

```sql
-- SLOW: scalar UDF called once per row
SELECT
    order_id,
    dbo.fn_GetOrderTotal(order_id) AS total    -- 1M rows = 1M function calls
FROM dbo.Orders;

-- FAST: same logic inline
SELECT
    o.order_id,
    SUM(od.quantity * od.unit_price) AS total
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY o.order_id;
```

Use scalar UDFs for calculations over scalar inputs (formatting, business rule lookups, single-row transformations). Avoid them in WHERE clauses or in SELECTs over large result sets. When you need parameterized table-returning logic, use inline TVFs — they optimize far better.

---

## Key Takeaways

- **Built-in functions are the right first stop** — check the docs before creating a UDF; a system function for your need likely exists
- **Window functions use `OVER()`** — they compute across a window of rows without collapsing them; essential for ranking, running totals, and sequential comparisons
- **Inline TVFs are like parameterized views** — efficient and optimizable; the preferred UDF type for returning result sets
- **Scalar UDFs have a row-by-row execution cost** — avoid them in WHERE clauses and SELECTs over large tables; they don't parallelize well
- **`COALESCE` over `ISNULL`** — COALESCE is ANSI standard and handles multiple arguments; prefer it for portability
