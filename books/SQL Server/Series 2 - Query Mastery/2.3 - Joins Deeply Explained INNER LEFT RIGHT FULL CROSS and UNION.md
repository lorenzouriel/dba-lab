# Joins, Deeply Explained: INNER, LEFT, RIGHT, FULL, CROSS, and UNION

*Series 2 — Query Mastery | The SQL Server Deep Dive*

---

Joins are the move that separates SQL from spreadsheets. A spreadsheet stores data in one flat grid. A relational database stores it in related tables — and joins are how you bring those tables back together when you need to ask questions that span more than one.

Most developers learn INNER JOIN and stop there. That's enough to get by, but it's not enough to understand why a LEFT JOIN returns NULLs in unexpected places, or why a CROSS JOIN that seemed harmless on a small table just produced 2 million rows and killed the server.

---

## INNER JOIN: The Default

INNER JOIN returns only the rows where both tables have a matching value on the join condition. No match, no row — from either side.

```sql
-- Every order with its customer's name
-- Orders without a matching customer (shouldn't happen with FK, but hypothetically) won't appear
SELECT
    o.order_id,
    o.order_date,
    o.status,
    c.first_name,
    c.last_name
FROM dbo.Orders AS o
INNER JOIN dbo.Customers AS c ON o.customer_id = c.customer_id;
```

`INNER JOIN` and `JOIN` are identical — the INNER keyword is optional. Most style guides write it out for clarity.

Use INNER JOIN when you only want rows that have matches in both tables. In SalesDB, this means orders that have a valid customer. If your foreign key constraints are in place, every `Orders` row has a valid `customer_id`, so INNER JOIN and LEFT JOIN produce identical results here — but the intent reads differently.

---

## LEFT JOIN: All From the Left, Matched or Not

LEFT JOIN returns all rows from the left table, plus matching rows from the right table. Where there's no match on the right, SQL Server fills in NULL for all columns from the right table.

```sql
-- Every customer, whether they've ordered or not
SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    o.order_id,
    o.order_date
FROM dbo.Customers AS c
LEFT JOIN dbo.Orders AS o ON c.customer_id = o.customer_id;
```

Customers who have never placed an order appear in the result — with NULL for `order_id` and `order_date`. This is how you find records that *don't* have a counterpart in another table:

```sql
-- Customers who have never placed any order
SELECT
    c.customer_id,
    c.first_name,
    c.email
FROM dbo.Customers AS c
LEFT JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```

The "IS NULL after LEFT JOIN" pattern is one of the most useful in SQL. It's often faster and cleaner than `NOT IN` or `NOT EXISTS` for this use case.

---

## RIGHT JOIN: All From the Right

RIGHT JOIN is the mirror of LEFT JOIN — returns all rows from the right table, with NULLs for unmatched columns from the left.

```sql
-- All orders, including any that somehow reference a non-existent product
SELECT
    od.order_detail_id,
    od.quantity,
    p.product_name,
    p.unit_price
FROM dbo.OrderDetails AS od
RIGHT JOIN dbo.Products AS p ON od.product_id = p.product_id;
```

In practice, RIGHT JOIN is used rarely. Anything a RIGHT JOIN can express, a LEFT JOIN can express by swapping the table order. Most style guides prefer LEFT JOIN for consistency — it reads more naturally and avoids the mental flip.

---

## FULL JOIN: Everything From Both

FULL JOIN (or FULL OUTER JOIN) returns all rows from both tables. Where matches exist, columns are filled in from both sides. Where they don't, you get NULLs from whichever side has no match.

```sql
-- Full audit: all customers and all orders, matched where possible
SELECT
    c.customer_id,
    c.first_name,
    o.order_id,
    o.status
FROM dbo.Customers AS c
FULL JOIN dbo.Orders AS o ON c.customer_id = o.customer_id;
```

FULL JOIN is most useful for data reconciliation — "show me everything from both systems so I can see where they don't align." It's uncommon in application queries but valuable in ETL work and data audits.

---

## CROSS JOIN: The Cartesian Product

CROSS JOIN returns every combination of every row from the left table with every row from the right table. No join condition — just every row paired with every other row.

```sql
-- Every possible product-status combination (for generating test data or a reporting matrix)
SELECT
    p.product_name,
    s.status_name
FROM dbo.Products AS p
CROSS JOIN (VALUES ('Pending'), ('Processing'), ('Shipped'), ('Cancelled')) AS s(status_name);
```

The result row count is `(rows in left table) × (rows in right table)`. A CROSS JOIN between a 1,000-row table and a 1,000-row table produces 1,000,000 rows. On an accidentally large pair of tables, this can bring down a server.

Legitimate uses: generating a complete time-series grid when combined with a dates table, creating all combinations of product attributes for a configurator, building test data. The rest of the time, if you see a CROSS JOIN in production code, it's usually a mistake.

---

## Multiple JOINs in One Query

You can chain as many JOINs as needed. Each JOIN adds a table to the working result set.

```sql
-- Full order view: customer → order → order details → product
SELECT
    c.first_name,
    c.last_name,
    o.order_id,
    o.order_date,
    p.product_name,
    od.quantity,
    od.unit_price,
    od.quantity * od.unit_price AS line_total
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id
WHERE o.status = 'Completed'
ORDER BY o.order_date DESC;
```

Each JOIN is evaluated left to right. The result of the first JOIN becomes the input for the second. Think of it as building up a wider and wider row, one table at a time.

## UNION and UNION ALL: Stacking Results

UNION and UNION ALL combine the results of two queries *vertically* — stacking rows — rather than joining them horizontally. The columns in both queries must match in number and compatible data types.

```sql
-- UNION: combine two query results, deduplicate
SELECT customer_id, 'Active' AS segment
FROM dbo.Customers
WHERE created_at >= DATEADD(YEAR, -1, GETDATE())

UNION

SELECT customer_id, 'Legacy' AS segment
FROM dbo.Customers
WHERE created_at < DATEADD(YEAR, -1, GETDATE());
```

`UNION` removes duplicate rows from the combined result. `UNION ALL` keeps them all — and is significantly faster because it skips the deduplication step.

```sql
-- UNION ALL: combine and keep all rows including duplicates
SELECT order_id, 'Current' AS source FROM dbo.Orders
UNION ALL
SELECT order_id, 'Archive' AS source FROM dbo.OrdersArchive;
```

When to use which: if duplicates genuinely can't exist (different sources, different date ranges, mutually exclusive conditions), use `UNION ALL` — it's faster and signals to the reader that you know there are no duplicates. Use `UNION` only when you actually need deduplication.

---

## The Trap

**Joining on non-indexed columns multiplies your problem.** Every JOIN is a lookup operation. When you join `Orders.customer_id` to `Customers.customer_id`, SQL Server needs to find the matching row efficiently. If `customer_id` is indexed (and it is, as a primary key), that lookup is fast. If you're joining on a non-indexed column — a free-text field, an unindexed status, a computed expression — SQL Server has to scan.

The pattern that kills performance:

```sql
-- Joining on a function-wrapped column destroys index usability
JOIN dbo.Customers AS c ON LOWER(c.email) = LOWER(o.contact_email)
```

Both sides are wrapped in `LOWER()`, which means SQL Server can't use any index on `email` or `contact_email`. It has to evaluate the function on every row of every join.

Fix: store data consistently (lowercase emails in both tables), avoid wrapping join columns in functions, and index the columns you join on regularly.

---

## Key Takeaways

- **INNER JOIN returns only matched rows** — the most common join; no match means no row from either side
- **LEFT JOIN returns all rows from the left, NULLs for unmatched right** — use `WHERE right_table.id IS NULL` to find rows with no counterpart
- **RIGHT JOIN is LEFT JOIN with tables swapped** — prefer LEFT JOIN for consistency
- **FULL JOIN returns everything from both sides** — use for data reconciliation and audits, not routine queries
- **CROSS JOIN produces rows × rows** — useful for generating combinations, dangerous on large tables
- **UNION removes duplicates; UNION ALL keeps everything** — use UNION ALL when duplicates are known to be impossible
