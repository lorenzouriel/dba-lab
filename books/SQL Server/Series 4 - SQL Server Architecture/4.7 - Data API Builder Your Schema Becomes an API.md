# Data API Builder: Your Schema Becomes an API

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

Modern apps don't open raw SQL connections; they consume REST and GraphQL. Building those layers by hand means controllers, DTOs, auth plumbing, and deploy infrastructure. Data API Builder (DAB) deletes that work: point a config file at your database and it generates secure, scalable REST and GraphQL endpoints from the schema, with zero backend code.

The shift that matters is where the logic goes. It's not in application code anymore — it's in configuration, which means the same discipline you'd apply to a CI/CD pipeline applies directly: source control the config, keep secrets out of it, merge per environment. And because the endpoints are generated, the engineering judgment moves to the edges: introspection, query depth, stored-procedure auth context, relationship fan-out, and polling versus push for change capture. This article walks the whole surface, with working config.

---

## The Configuration File

Everything starts here. Four sections: `$schema` (validation and IntelliSense), `data-source` (connection), `runtime` (host behavior), `entities` (what you expose).

```json
{
  "$schema": "https://github.com/Azure/data-api-builder/releases/download/v1.1.7/dab.draft.schema.json",
  "data-source": {
    "database-type": "mssql",
    "connection-string": "@env('DATABASE_CONNECTION_STRING')",
    "options": { "set-session-context": true }
  },
  "runtime": {
    "rest":    { "enabled": true, "path": "/api" },
    "graphql": { "enabled": true, "path": "/graphql", "allow-introspection": false },
    "host": {
      "cors": { "origins": ["https://myapp.azurewebsites.net"], "allow-credentials": true },
      "mode": "production"
    },
    "cache": { "enabled": true, "ttl-seconds": 5 }
  },
  "entities": {}
}
```

Two lines carry weight. `@env('...')` keeps the connection string out of the file and out of source control — the same rule as pipeline secrets. And `set-session-context: true` flows the caller's identity into SQL via `SESSION_CONTEXT()`, which is exactly what row-level-security predicates read, so this is the hook that makes RLS and audit work behind DAB. Also note `allow-introspection` off in production: leaving it on lets clients enumerate your schema, the same exposure you'd close on any GraphQL endpoint.

Manage it with the CLI so the JSON stays valid and PR diffs stay clean:

```bash
dab init --database-type mssql --connection-string "@env('DATABASE_CONNECTION_STRING')" --host-mode development
dab add Product --source dbo.Products --permissions "anonymous:read"
```

For multiple environments, keep a base `dab-config.json` and layer overrides (`dab-config.production.json`) that contain only what differs; DAB merges them, environment winning:

```bash
dab start --config dab-config.production.json
```

## Entities: Shaping REST and GraphQL

An entity maps a database object to the API. Name, source, and permissions are the minimum:

```json
"Product": {
  "source": { "object": "dbo.Products", "type": "table" },
  "permissions": [ { "role": "anonymous", "actions": ["read"] } ]
}
```

That exposes `dbo.Products` at `/api/Product` for REST and as `product`/`products` in GraphQL. `type` is `table`, `view`, or `stored-procedure`, and each has different capabilities — tables do full CRUD, views read, procedures execute.

**Field mappings** decouple your API names from column names, so you present a clean contract without touching the schema:

```json
"mappings": { "ProductID": "id", "ProductName": "name", "Price": "price", "StockQuantity": "stockQuantity" }
```

**Caching, pagination, and filtering** come for free per entity. Cache with a TTL sized to the data's volatility — long for a catalog, short or off for live inventory. Pagination is cursor-based: REST uses `$first`/`$after`, GraphQL uses `first`/`after` with `hasNextPage`/`endCursor`.

```
GET /api/products?$first=10&$after=eyJQcm9kdWN0SUQiOjEwfQ==
GET /api/products?$filter=price gt 100 and stockQuantity gt 0
```

Filtering is OData-style for REST and typed input for GraphQL, with `gt`/`lt`/`eq`/`contains`/`startsWith` generated automatically per field type. No config needed. For logic that won't fit the operators, wrap it in a view or procedure and expose that.

**Relationships** are what make GraphQL worth it, mapping foreign keys so clients traverse in one query:

```json
"relationships": {
  "orders": {
    "cardinality": "many",
    "target.entity": "Order",
    "source.fields": ["CustomerID"],
    "target.fields": ["CustomerID"]
  }
}
```

```graphql
query { customers { items { firstName orders { orderDate amount } } } }
```

**REST endpoints** follow convention: `GET /api/Product` lists, `GET /api/Product/id/123` fetches, `POST` creates, `PUT`/`PATCH` update, `DELETE` deletes, with `/id/` marking the key (chain segments for composite keys: `/api/OrderDetail/orderId/100/productId/50`). You can rename the path and disable verbs, which is real defense in depth — turning off `PUT` prevents full-record replacement and the accidental data loss that comes with it:

```json
"rest": {
  "enabled": true, "path": "/products",
  "methods": { "get": true, "post": true, "put": false, "patch": true, "delete": true }
}
```

**GraphQL** runs through one endpoint. Set custom type names, mark an entity `query` or `mutation`, and cap complexity with `depth-limit` so a deeply nested query can't hammer the database — the same DoS concern as introspection:

```json
"runtime": {
  "graphql": {
    "enabled": true, "path": "/graphql",
    "allow-introspection": false, "depth-limit": 8,
    "multiple-mutations": { "create": { "enabled": true } }
  }
}
```

## Views, Stored Procedures, and Deeper Relationships

**Views** expose computed or joined data read-only. The one required extra is `key-fields`, because DAB can't infer a primary key from a view:

```json
"CustomerOrderSummary": {
  "source": { "object": "dbo.CustomerOrderSummary", "type": "view", "key-fields": ["CustomerID"] },
  "rest": { "enabled": true, "path": "/customer-summary" },
  "graphql": { "enabled": true, "operation": "query" },
  "permissions": [ { "role": "anonymous", "actions": ["read"] } ]
}
```

**Stored procedures** are the flexibility escape hatch: parameters, custom logic, multiple result sets. Map the parameters and grant `execute`. Read procedures use `operation: query`; write procedures use `operation: mutation`:

```json
"CreateOrder": {
  "source": {
    "object": "dbo.CreateOrder", "type": "stored-procedure",
    "parameters": { "CustomerID": "customerId", "ProductID": "productId", "Quantity": "quantity" }
  },
  "rest": { "enabled": true, "methods": { "post": true } },
  "graphql": { "enabled": true, "operation": "mutation" },
  "permissions": [ { "role": "authenticated", "actions": ["execute"] } ]
}
```

The security detail worth flagging: a procedure runs with the database connection's permissions, not the caller's. So authorization has to live inside the procedure or ride on `SESSION_CONTEXT()` (the `set-session-context` hook again). The generated API tells you who's calling; the procedure has to enforce what they're allowed to do.

Relationships let one GraphQL query walk `dbo.Orders` to `dbo.Customers` to `dbo.OrderDetails` to `dbo.Products` in a single round trip instead of N requests. Worth knowing at a senior level: DAB resolves each relationship level, so wide-and-deep queries fan out into multiple database calls, which is exactly why `depth-limit` and per-entity caching exist. Many-to-many relationships go through the junction table as an explicit chain (`Products` → `ProductSuppliers` → `Suppliers`), one extra level in the query that keeps the model honest.

## Deployment

DAB ships as a container, so hosting is about picking the Azure surface.

**Azure Container Apps** (serverless, scale-to-zero) is the natural fit. Build an image from the official base and deploy with the secret referenced, never inlined:

```dockerfile
FROM mcr.microsoft.com/azure-databases/data-api-builder:latest
COPY dab-config.json /App/dab-config.json
ENV DATABASE_CONNECTION_STRING=""
ENV ASPNETCORE_URLS="http://+:5000"
EXPOSE 5000
```

```bash
az containerapp create \
  --name dab-api --resource-group myResourceGroup --environment myContainerAppEnv \
  --image myregistry.azurecr.io/dab-api:v1 --target-port 5000 --ingress external \
  --secrets database-conn="<connection-string>" \
  --env-vars DATABASE_CONNECTION_STRING=secretref:database-conn
```

Better still, enable the Container App's managed identity and grant it Azure SQL access, which eliminates the stored credential entirely — the same passwordless move as any well-run security or CI/CD setup.

**Azure App Service** suits teams already there, with slots and the Key Vault reference syntax pulling secrets at runtime:

```bash
az webapp config appsettings set --name dab-api --resource-group myResourceGroup \
  --settings DATABASE_CONNECTION_STRING="@Microsoft.KeyVault(SecretUri=https://myvault.vault.azure.net/secrets/db-connection)"
```

**Azure Static Web Apps** has DAB built in as "database connections," configured through `staticwebapps.database.config.json` with routes under `/data-api/`. Simplest when the API backs a static frontend, but note the limitations — stored-procedure support is restricted.

Automate it like any container. The GitHub Actions workflow builds, pushes to ACR, and updates the Container App, triggered only on config or Dockerfile changes:

```yaml
on:
  push:
    branches: [main]
    paths: ['dab-config*.json', 'Dockerfile']
# ... docker build/push to ACR, then:
- uses: azure/container-apps-deploy-action@v1
  with:
    resourceGroup: myResourceGroup
    containerAppName: dab-api
    imageToDeploy: ${{ secrets.ACR_LOGIN_SERVER }}/dab-api:${{ github.sha }}
```

Bake the environment in with a Dockerfile `ARG ENVIRONMENT` and per-env config, and wire health probes so the platform restarts bad instances. Make the readiness probe hit a real endpoint so it verifies database connectivity, not just that the process is up:

```json
{ "type": "readiness", "httpGet": { "path": "/api/Product?$first=1", "port": 5000 }, "periodSeconds": 10 }
```

## Observability with Azure Monitor

Set one environment variable and DAB starts emitting to Application Insights — request, dependency (the SQL it issues), exception, and custom telemetry:

```
APPLICATIONINSIGHTS_CONNECTION_STRING="InstrumentationKey=...;IngestionEndpoint=https://region.in.applicationinsights.azure.com/"
```

The dashboards you actually want are KQL. API health at a glance:

```kusto
requests
| where timestamp > ago(24h)
| summarize RequestCount = count(), AvgDuration = avg(duration),
            P95Duration = percentile(duration, 95),
            FailureRate = countif(success == false) * 100.0 / count()
```

The most useful query for a DBA is dependency tracking, because it surfaces the exact SQL DAB runs and how long it takes, which connects straight back to query-tuning work: slow dependencies here are your missing-index and bad-plan candidates.

```kusto
dependencies
| where type == "SQL" and timestamp > ago(1h)
| summarize CallCount = count(), AvgDuration = avg(duration), FailureCount = countif(success == false) by data
| top 20 by AvgDuration desc
```

Container logs go to Log Analytics (`ContainerAppConsoleLogs_CL`), alerts fire on error rate or p95 latency (`az monitor metrics alert create ... --condition "avg requests/failed > 5"`), and `traceparent` headers give end-to-end distributed traces across client, API, and database. Watch CPU, memory, network, and replica count, and autoscale on them. Configure alerts sparingly at first to avoid alert fatigue, then tighten thresholds to your real baseline.

## Closing the Loop: Event-Driven Change Capture

The final piece is the database pushing changes out, not just answering reads. Three native mechanisms, with a real tradeoff between them:

| | CDC | Change Tracking | Change Event Streaming |
|---|---|---|---|
| Captures changed values | yes | no | yes |
| Polling required | yes | yes | no (push) |
| History | yes | limited | stream only |
| Setup | moderate | low | moderate |

**Change Data Capture** reads the log into change tables with full before/after state — the choice for audit and sync. It needs SQL Server Agent for its capture/cleanup jobs.

```sql
EXEC sys.sp_cdc_enable_db;
EXEC sys.sp_cdc_enable_table
    @source_schema = 'dbo', @source_name = 'Orders',
    @role_name = NULL, @capture_instance = 'dbo_Orders', @supports_net_changes = 1;

DECLARE @from_lsn binary(10) = sys.fn_cdc_get_min_lsn('dbo_Orders'),
        @to_lsn   binary(10) = sys.fn_cdc_get_max_lsn();
SELECT * FROM cdc.fn_cdc_get_all_changes_dbo_Orders(@from_lsn, @to_lsn, 'all');  -- __$operation = the DML type
```

**Change Tracking** is the lightweight sibling: it records which rows changed, not the values, and it's what the Azure Functions SQL trigger binding uses.

```sql
ALTER DATABASE [YourDatabase] SET CHANGE_TRACKING = ON (CHANGE_RETENTION = 2 DAYS, AUTO_CLEANUP = ON);
ALTER TABLE dbo.Orders ENABLE CHANGE_TRACKING;
```

```csharp
[FunctionName("OrderChangedTrigger")]
public static void Run(
    [SqlTrigger("[dbo].[Orders]", "SqlConnectionString")] IReadOnlyList<SqlChange<Order>> changes,
    ILogger log)
{
    foreach (var change in changes)
    {
        log.LogInformation($"{change.Operation} on Order {change.Item.OrderId}");
        if (change.Operation == SqlChangeOperation.Update) ProcessOrderUpdate(change.Item);
    }
}
```

The trigger delivers batches (`SqlChange<T>`), which is efficient when many rows change at once, and the connection string comes from Key Vault, not the function code.

**Change Event Streaming** is the newest, and the one to reach for at high volume: it pushes committed changes straight to Event Hubs, no polling, sub-second, scaling to millions of events per second.

```sql
CREATE EVENT STREAMING GROUP MyOrderStream
WITH (TARGET_TYPE = 'eventhub', TARGET_NAME = 'orders-eventhub', TARGET_CONNECTION = '<event-hub-connection-string>');
ALTER EVENT STREAMING GROUP MyOrderStream ADD TABLE dbo.Orders;
```

Choose by requirement: CDC when you need before/after history and batch sync is fine; Change Tracking plus Functions when you need real-time reactions to current values in an event-driven microservice; CES when you need sub-second latency at streaming volume. And they compose — CDC for the audit trail while Functions triggers fire the real-time notifications is a common and sensible pairing. If you already run an external log-based CDC pipeline (Debezium-style into Kafka), CES is the native push equivalent and worth weighing against the operational cost of the external stack for SQL-Server-only sources.

## Key Takeaways

- **DAB turns a config file into your API surface** — REST and GraphQL are generated from `entities` in the JSON config, not hand-written controllers, so the config deserves the same review rigor as application code
- **`@env()` and `set-session-context` are the two lines that matter most** — secrets stay out of source control, and caller identity flows into `SESSION_CONTEXT()` for row-level security
- **Stored procedures run as the connection's identity, not the caller's** — authorization has to live inside the procedure or ride on session context; DAB doesn't do it for you
- **`allow-introspection: false` and `depth-limit` are your GraphQL exposure controls** — both close off ways a client can over-fetch schema information or force expensive fan-out queries
- **CDC, Change Tracking, and Change Event Streaming solve different change-capture problems** — before/after history, lightweight row-changed signals, and sub-second push, respectively, and they can be combined
- **Observability is one environment variable away** — Application Insights dependency tracking on the SQL DAB issues is the fastest way to spot missing indexes and bad plans surfaced through the API layer
