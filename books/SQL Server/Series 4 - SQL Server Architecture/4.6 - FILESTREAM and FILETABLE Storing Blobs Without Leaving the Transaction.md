# FILESTREAM and FILETABLE: Storing Blobs Without Leaving the Transaction

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

Product photos, PDFs, video files, scanned documents — every application eventually has to decide where large unstructured files live relative to the database. Cram them into a `VARBINARY(MAX)` column and every backup, every buffer pool page, every query touching that table gets heavier, even when nobody asked for the blob. Store them purely on a file share instead and you've traded that problem for a worse one: the file and the database row describing it can drift out of sync, because nothing ties their lifecycles together.

SQL Server's answer is to let the two live in different places — the database and the filesystem — while keeping them inside the same transaction. That's what this article covers: **FILESTREAM**, which stores BLOBs in the filesystem under full transactional control, and **FILETABLE**, which builds a folder-and-file view on top of FILESTREAM so file data can be browsed and manipulated with ordinary file semantics. (Full-text indexing and search — the other major "working with unstructured text" feature in SQL Server — is covered separately in `Series 6 - AI Stuff\Full Text, Vector Search and Hybrid`; this article is about storing and accessing the blobs themselves, not searching their text content.)

---

## FILESTREAM: BLOBs in the Filesystem, Transactions in the Database

FILESTREAM lets SQL Server store large binary objects — documents, images, audio, video — directly in the NTFS or ReFS filesystem instead of inside the database's data pages, while still integrating them fully with the database. The row in your table doesn't hold the file bytes; it holds a pointer to where the file lives on disk, managed by SQL Server.

That distinction — file bytes on the filesystem, but the *relationship* between file and row still governed by the database engine — is the entire value proposition. You get:

- **Read performance for large files.** The filesystem is what filesystems are good at: streaming large sequential reads. Pulling a 200 MB video through the buffer pool as an in-row `VARBINARY(MAX)` value competes with your OLTP data for cache; FILESTREAM data bypasses that entirely.
- **Scalability for genuinely large unstructured datasets.** Filesystem storage handles large volumes of blob data more gracefully than trying to keep it all inside `.mdf`/`.ndf` files, which grow unmanageably large and slow down backups that don't need to touch the blobs every time.
- **Full transactional consistency anyway.** This is the part that a naive "store the path in a column" approach can't give you. FILESTREAM data participates in the same transactions, the same backups, and the same concurrency control as the rest of the database.

### Enabling FILESTREAM

FILESTREAM has to be turned on at two levels before you can use it: the SQL Server instance, and the specific database.

```sql
-- Enable FILESTREAM at the instance level
EXEC sp_configure 'filestream access level', 2;  -- 2 = full T-SQL and Win32 access
RECONFIGURE;
```

(This also requires enabling FILESTREAM in SQL Server Configuration Manager at the OS level — the `sp_configure` call alone isn't sufficient on a fresh instance.)

A database that will hold FILESTREAM data needs a filegroup marked `CONTAINS FILESTREAM`. Unlike an ordinary filegroup (covered in `Series 4.5`), a FILESTREAM filegroup doesn't point at a data file — it points at a folder, called a **FILESTREAM data container**, where the actual blob files get written by SQL Server.

```sql
CREATE DATABASE MediaDB
ON PRIMARY (
    NAME = MediaDB,
    FILENAME = 'C:\MediaDB\Data\MediaDB.mdf'
),
FILEGROUP MediaFileStreamGroup CONTAINS FILESTREAM (
    NAME = MediaFileStreamData,
    FILENAME = 'C:\MediaDB\Data\MediaFileStreamData'
)
LOG ON (
    NAME = MediaDB_Log,
    FILENAME = 'C:\MediaDB\Log\MediaDB_Log.ldf'
)
WITH FILESTREAM (NON_TRANSACTED_ACCESS = FULL, DIRECTORY_NAME = N'MediaDBDir');
```

### Using FILESTREAM in a Table

A FILESTREAM column is declared as `VARBINARY(MAX) FILESTREAM` on a table that also has a `ROWGUIDCOL` column — SQL Server needs a globally unique identifier per row to track the file on disk.

```sql
CREATE TABLE dbo.ProductImages (
    ProductID   INT NOT NULL,
    ImageID     UNIQUEIDENTIFIER ROWGUIDCOL NOT NULL UNIQUE
                    DEFAULT NEWID(),
    ImageData   VARBINARY(MAX) FILESTREAM,
    FileName    NVARCHAR(255),
    UploadedAt  DATETIME2 DEFAULT GETUTCDATE(),
    CONSTRAINT FK_ProductImages_Products
        FOREIGN KEY (ProductID) REFERENCES dbo.Products(ProductID)
) FILESTREAM_ON MediaFileStreamGroup;
```

From the application's side, this reads and writes almost like any other column — `INSERT` the binary data, `SELECT` it back — through T-SQL, .NET's `SqlFileStream` API for streaming access, or any client library that speaks SQL Server's protocol. What's different is what happens underneath: a normal `VARBINARY(MAX)` write goes through the buffer pool like any other page; a FILESTREAM write goes to the filesystem, but the transaction that performs it doesn't commit until both the metadata row and the file write are durable — the same all-or-nothing guarantee as any other transaction.

That transactional guarantee is why FILESTREAM data is included in ordinary SQL Server backups. There's no separate "also remember to back up the file share" step — restoring the database restores the FILESTREAM container along with the `.mdf` and `.ldf`, at the same point in time, with the same recovery mechanism covered in `Series 5.1`. Concurrency control (locking, isolation levels) applies to FILESTREAM data the same way it applies to any other column, so two transactions writing to the same row's blob are still serialized correctly.

### When to Reach for FILESTREAM

FILESTREAM makes sense when files are large (the general guidance is objects consistently above roughly 1 MB), read-heavy, and need to stay transactionally tied to relational metadata — a document management system where "the file" and "the record describing the file" must never go out of sync. It's the wrong tool for small blobs (a few KB profile thumbnail is often cheaper to just leave as in-row `VARBINARY(MAX)`) and for scenarios where the files genuinely don't need database transaction semantics at all — plain blob storage is simpler in that case.

## FILETABLE: A Folder, Seen Two Ways at Once

FILETABLE builds directly on FILESTREAM to solve a narrower, very practical problem: sometimes what you actually want isn't a table with a blob column — you want a folder on disk that you can drag-and-drop files into using Windows Explorer, *and* query with T-SQL as if it were a normal relational table. FILETABLE gives you both views of the same data simultaneously.

Under the hood, a FILETABLE is a special table type with a fixed, predefined schema — you don't design its columns — that maps onto a hierarchical folder structure, exposed through a Windows file share by SQL Server's FILESTREAM subsystem. Every row is a file or a directory; the schema tracks name, path, creation time, modification time, and the file's FILESTREAM content, alongside a `path_locator` value that encodes the file's position in the hierarchy.

### Creating a FILETABLE-Enabled Database and Table

Because FILETABLE depends on FILESTREAM, the database needs the same FILESTREAM filegroup setup, plus `CONTAINMENT = PARTIAL` to support the non-transactional file-share access pattern FILETABLE relies on.

```sql
CREATE DATABASE DocumentStoreDB
CONTAINMENT = PARTIAL
ON PRIMARY (
    NAME = DocumentStoreDB,
    FILENAME = 'C:\DocumentStoreDB\Data\DocumentStoreDB.mdf'
),
FILEGROUP DocsFileStreamGroup CONTAINS FILESTREAM (
    NAME = DocsFileStreamData,
    FILENAME = 'C:\DocumentStoreDB\Data\DocsFileStreamData'
)
LOG ON (
    NAME = DocumentStoreDB_Log,
    FILENAME = 'C:\DocumentStoreDB\Log\DocumentStoreDB_Log.ldf'
)
WITH FILESTREAM (NON_TRANSACTED_ACCESS = FULL, DIRECTORY_NAME = N'DocumentStoreDir');

USE DocumentStoreDB;

CREATE TABLE dbo.ProductDocuments AS FILETABLE;
```

That single `CREATE TABLE ... AS FILETABLE` statement is the whole schema definition — SQL Server generates the fixed columns (`name`, `path_locator`, `file_stream`, `creation_time`, `last_modified_time`, and more) for you.

### Reading and Writing Through Two Doors

The point of FILETABLE is that both access paths stay in sync automatically, because they're the same underlying data.

**Through the filesystem**, a user or another application can browse to the FILETABLE's UNC share (`\\ServerName\DocumentStoreDir\ProductDocuments\`) and drag files in with Explorer, exactly like any network folder. No T-SQL required for that path at all.

**Through T-SQL**, the same files show up as rows, queryable and insertable like any table:

```sql
-- List every file under the FILETABLE, newest first
SELECT name, file_type, cached_file_size, creation_time
FROM dbo.ProductDocuments
WHERE is_directory = 0
ORDER BY creation_time DESC;

-- Insert a file directly via T-SQL instead of the file share
DECLARE @FileTableDirectory NVARCHAR(MAX);
SELECT @FileTableDirectory = [file_stream].GetFileNamespace()
FROM dbo.ProductDocuments;  -- namespace root, not row-specific data

DECLARE @FileName NVARCHAR(255) = 'spec-sheet.pdf';
DECLARE @FileData VARBINARY(MAX) = 0x255044462D312E34...;  -- actual file bytes

INSERT INTO dbo.ProductDocuments (name, file_stream)
VALUES (@FileName, @FileData);
```

Whichever door you use, the change is transactional and consistent from the database's point of view, and — like plain FILESTREAM — FILETABLE data is included in standard SQL Server backups, so restoring the database restores the folder hierarchy along with everything else. Access to the data, whether through T-SQL or the file share, is governed by the same SQL Server security model (logins, permissions) as any other table, so you don't lose access control by exposing a folder view.

### When to Reach for FILETABLE

FILETABLE earns its keep specifically when non-database tools and users need direct filesystem-style access to the same files your application manages relationally — a document repository where both a line-of-business app *and* office staff dragging files from a network share need to hit the same underlying store without a sync process between them. If nothing outside your application ever needs raw file-share access, plain FILESTREAM (or even a `VARBINARY(MAX)` column for smaller files) is simpler and has less operational surface area than standing up the file-share integration FILETABLE requires.

## Key Takeaways

- **FILESTREAM stores BLOBs on the filesystem but keeps them inside SQL Server's transactions** — the file write and the metadata row commit or roll back together, with the same durability guarantee as any other change
- **It requires enabling FILESTREAM at both the instance and database level**, and a dedicated `CONTAINS FILESTREAM` filegroup pointing at a data container folder rather than a data file
- **FILESTREAM data is included in ordinary backups and behaves under normal locking** — there's no separate blob-storage backup process or weakened consistency model to manage
- **Use FILESTREAM for large, read-heavy blobs that must stay transactionally tied to relational metadata** — small blobs are often simpler as in-row `VARBINARY(MAX)`
- **FILETABLE builds on FILESTREAM to expose the same data as both a folder (via a Windows file share) and a table (via T-SQL)** simultaneously, kept in sync because they're the same underlying storage
- **FILETABLE is worth the extra setup specifically when non-database tools need raw filesystem access** to the same files the application manages relationally — otherwise plain FILESTREAM is the simpler choice
