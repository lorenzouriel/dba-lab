# SQL Server Query Store: The Flight Recorder for Your Database

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

A deployment goes out on Friday afternoon. By Monday morning, a key report that used to run in 3 seconds now takes 45. The query hasn't changed. The data volume hasn't spiked. But something changed — and without the right tooling, figuring out what requires guesswork, log archaeology, and luck.

Query Store is what makes that investigation trivial instead of painful. It records the execution history of every query — which plans were used, when they changed, and how performance shifted — and stores all of it inside your database.

---

## What Query Store Is

Introduced in SQL Server 2016, Query Store is a **persistent performance history** built directly into the database engine. It continuously captures:

- Every query that executes
- Every execution plan the optimizer chose for each query
- Runtime statistics for each plan: duration, CPU, I/O, memory grants, and execution count

Unlike Dynamic Management Views (DMVs), which reset when SQL Server restarts and only reflect the current runtime state, Query Store data **survives restarts**. You can look back days or weeks and see exactly how a specific query performed over time.

---

## Enabling Query Store

Query Store is configured per database:

```sql
-- Enable Query Store
ALTER DATABASE SalesDB
SET QUERY_STORE = ON;

ALTER DATABASE SalesDB
SET QUERY_STORE (OPERATION_MODE = READ_WRITE);
```

Once enabled, SQL Server automatically starts collecting data. No additional configuration is required to begin capturing.

In SSMS, navigate to: **Database → Query Store → Reports** for visual dashboards including:
- Top Resource Consuming Queries
- Regressed Queries
- Overall Resource Consumption
- Queries with Forced Plans

---

## The Three Data Layers

Query Store collects and correlates three distinct types of information:

**1. Query Text** — the exact SQL statement that executed. Each unique query text gets a `query_id`.

**2. Execution Plans** — every distinct plan SQL Server generated for a given query. One query can have multiple plans over time if plan changes occur. Each plan gets a `plan_id`.

**3. Runtime Statistics** — aggregated performance data per (query, plan) combination over configurable time intervals. Captures duration, CPU time, logical reads, memory grants, and execution count.

---

## Configuration

```sql
ALTER DATABASE SalesDB
SET QUERY_STORE (
    OPERATION_MODE = READ_WRITE,            -- Collect and serve data
    CLEANUP_POLICY = (STALE_QUERY_THRESHOLD_DAYS = 30),  -- Retain 30 days of data
    DATA_FLUSH_INTERVAL_SECONDS = 900,       -- Flush to disk every 15 minutes
    MAX_STORAGE_SIZE_MB = 1000,              -- Max 1GB for Query Store data
    QUERY_CAPTURE_MODE = AUTO               -- Only capture relevant queries
);
```

**Key settings:**

| Setting | Recommendation |
|---------|---------------|
| `STALE_QUERY_THRESHOLD_DAYS` | 30–90 days for most workloads |
| `MAX_STORAGE_SIZE_MB` | 500–2000MB; monitor via sys.database_query_store_options |
| `QUERY_CAPTURE_MODE` | `AUTO` filters out trivial queries; `ALL` captures everything |
| `DATA_FLUSH_INTERVAL_SECONDS` | 900 (15 min) is a reasonable default |

Check current space usage:

```sql
SELECT
    current_storage_size_mb,
    max_storage_size_mb,
    readonly_reason,
    actual_state_desc
FROM sys.database_query_store_options;
```

If Query Store hits its storage limit, it switches to `READ_ONLY` mode and stops collecting. Monitor this proactively.

## The Core Use Case: Diagnosing a Regression

A query runs fine for months, then suddenly slows down after a deployment or statistics update. Query Store lets you pinpoint the exact moment performance changed and which plan change caused it.

**Step 1: Find the regressed query.**

In SSMS, open the **Regressed Queries** report under your database's Query Store folder. It shows queries whose average duration has increased significantly in recent time periods.

Or query directly:

```sql
-- Find queries with significant performance regressions
SELECT
    q.query_id,
    qt.query_sql_text,
    rs_recent.avg_duration    AS recent_avg_duration_us,
    rs_baseline.avg_duration  AS baseline_avg_duration_us,
    rs_recent.avg_duration / rs_baseline.avg_duration AS regression_ratio
FROM sys.query_store_query AS q
INNER JOIN sys.query_store_query_text AS qt ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan AS p ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats AS rs_recent
    ON p.plan_id = rs_recent.plan_id
INNER JOIN sys.query_store_runtime_stats AS rs_baseline
    ON p.plan_id = rs_baseline.plan_id
WHERE rs_recent.last_execution_time > DATEADD(HOUR, -24, GETDATE())
  AND rs_baseline.last_execution_time < DATEADD(HOUR, -24, GETDATE())
  AND rs_recent.avg_duration > rs_baseline.avg_duration * 2   -- 2x slower
ORDER BY regression_ratio DESC;
```

**Step 2: Compare the old and new plans.**

In the Regressed Queries report, you can select a query and see the execution plans side-by-side — the plan that was running before the regression and the new one SQL Server switched to.

**Step 3: Force the better plan.**

```sql
-- Force a specific plan for a specific query
-- Get query_id and plan_id from the Query Store reports or sys.query_store_plan
EXEC sp_query_store_force_plan
    @query_id = 123,
    @plan_id  = 456;
```

Forcing a plan locks SQL Server into using that specific execution plan regardless of statistics, schema changes, or optimizer decisions. This is a temporary stabilization while you investigate the root cause — it's not a permanent fix.

```sql
-- Unforce a plan when the underlying issue is resolved
EXEC sp_query_store_unforce_plan
    @query_id = 123,
    @plan_id  = 456;
```

## Finding Top Resource Consumers

```sql
-- Top 10 queries by average CPU time
SELECT TOP 10
    q.query_id,
    qt.query_sql_text,
    rs.avg_cpu_time        AS avg_cpu_us,
    rs.avg_duration        AS avg_duration_us,
    rs.avg_logical_io_reads,
    rs.count_executions
FROM sys.query_store_query AS q
INNER JOIN sys.query_store_query_text AS qt ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan AS p ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats AS rs ON p.plan_id = rs.plan_id
ORDER BY rs.avg_cpu_time DESC;
```

This surfaces optimization candidates: queries that run frequently and consume the most CPU or I/O are the highest-impact targets.

## Automatic Plan Correction (SQL Server 2022+)

SQL Server 2022 and Azure SQL Database can automatically revert to a better-performing plan when a regression is detected — no manual intervention required.

```sql
-- Enable automatic plan correction
ALTER DATABASE SalesDB
SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON);
```

With this enabled, Query Store continuously monitors for plan regressions. When a query's performance degrades due to a plan change, SQL Server automatically forces the previously better plan and flags the action in `sys.dm_db_tuning_recommendations`.

---

## What Query Store Solves That DMVs Don't

| Capability | DMVs | Query Store |
|-----------|------|------------|
| Survives restarts | No | Yes |
| Historical comparison | No | Yes (configurable retention) |
| Per-plan performance breakdown | Partial | Yes |
| Plan forcing | No | Yes |
| Automatic regression correction | No | Yes (SQL 2022+) |

DMVs like `sys.dm_exec_query_stats` are useful for real-time diagnostics. Query Store is useful for trend analysis, regression investigation, and anything that requires persistence across restarts.

---

## The Trap

**Query Store filling up and going read-only.** When the storage limit is hit, Query Store switches to read-only mode — it stops collecting new data until space is freed. If you're not monitoring this, you'll discover the problem after it's already happened, when the data you needed for a regression investigation was never captured.

Set up a monitoring job that checks `sys.database_query_store_options` weekly. If `current_storage_size_mb` is approaching `max_storage_size_mb`, either increase the limit or reduce the retention threshold.

Also: don't set `QUERY_CAPTURE_MODE = ALL` in high-throughput OLTP environments without testing the space impact first. Capturing every trivial query can fill the store quickly.

---

## Key Takeaways

- **Query Store is a persistent performance history** — unlike DMVs, data survives restarts; you can look back days or weeks
- **Three data layers: query text, plans, and runtime stats** — correlated by `query_id` and `plan_id`; multiple plans can exist for one query
- **Regressed Queries is the primary diagnostic workflow** — find what changed, compare old vs. new plans, force the better plan
- **`sp_query_store_force_plan` is a stabilization tool** — forces a known-good plan while you fix the root cause; use `sp_query_store_unforce_plan` when resolved
- **Automatic plan correction (SQL Server 2022+)** — `FORCE_LAST_GOOD_PLAN` lets SQL Server revert regressions automatically
- **Monitor storage usage** — Query Store goes read-only when full; check `sys.database_query_store_options` regularly
