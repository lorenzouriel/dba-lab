# How SQL Server Processes Your Query: Parsing, Optimization, Plan Caching, and Parallelism

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

The previous article covered SQL Server's three-layer architecture. This one goes deeper into the Relational Engine — specifically what happens to a query between the moment it arrives and the moment execution starts. Plan caching, parameter sniffing, parameterization, and parallel execution are all internal behaviors that directly affect performance in ways that aren't obvious from the query text itself.

Understanding these mechanics helps you explain why the second execution of a procedure is faster than the first, why the same query can perform differently for different parameter values, and why some queries don't parallelize even on a 32-core server.

---

## Execution Plan Caching

After the Query Optimizer produces an execution plan, SQL Server stores it in the **plan cache** (part of the Buffer Pool). On the next execution of the same query, SQL Server checks the cache before recompiling.

**Plan reuse requires two things to match:**
1. The query text must be identical
2. The SET options of the connection must be identical

SET options like `ANSI_NULLS`, `QUOTED_IDENTIFIER`, and `ARITHABORT` affect how queries behave. A connection using SSMS may default to different SET options than an application using ORM-generated SQL. The same query text from two different callers with different SET options produces two separate cached plans.

```sql
-- These may produce separate plans despite identical SQL
-- (if called with different ANSI_NULLS settings)
SELECT order_id FROM dbo.Orders WHERE status = 'Pending';
SELECT order_id FROM dbo.Orders WHERE status = 'Pending';
```

Object names also affect plan matching:

```sql
SELECT * FROM Person;           -- Different plan entry
SELECT * FROM Person.Person;    -- Different plan entry (fully qualified)
SELECT * FROM Person.Person;    -- Reuses previous plan
```

Fully qualifying object names (`schema.table`) improves plan cache efficiency.

## Stored Procedures and Plan Reuse

Stored procedures are the natural home of plan caching. SQL Server compiles a stored procedure's execution plan on the **first call** and stores it in the plan cache. All subsequent calls with the same connection SET options reuse that plan — no recompilation, no optimizer overhead.

```sql
-- First call: compiled and cached
EXEC dbo.usp_GetCustomerOrders @customer_id = 10;

-- Second call: plan reused from cache
EXEC dbo.usp_GetCustomerOrders @customer_id = 20;
```

The plan cache is dynamic — plans are evicted under memory pressure (using a cost-based LRU algorithm). Schema changes (`ALTER TABLE`, `DROP INDEX`), statistics updates, and explicit commands flush specific plans or the entire cache.

```sql
-- Flush all cached plans (use with care in production)
DBCC FREEPROCCACHE;

-- Flush plans for a specific database
ALTER DATABASE SalesDB CLEAR PROCEDURE_CACHE;

-- Mark a specific procedure's plan for recompilation
EXEC sp_recompile 'dbo.usp_GetCustomerOrders';
```

## Parameterization: Fewer Plans, Better Reuse

When an application submits different literal values in otherwise identical queries, SQL Server may compile a separate plan for each:

```sql
-- These may compile as two separate plans
SELECT * FROM dbo.Products WHERE category = 'Electronics';
SELECT * FROM dbo.Products WHERE category = 'Clothing';
```

**Parameterized queries** replace literals with parameters. SQL Server compiles one plan and reuses it regardless of the parameter value:

```sql
-- sp_executesql with explicit parameters: one plan, many executions
EXEC sp_executesql
    N'SELECT * FROM dbo.Products WHERE category = @category',
    N'@category VARCHAR(100)',
    @category = 'Electronics';
```

**Simple parameterization** happens automatically for the simplest query patterns — SQL Server internally converts `WHERE category = 'Electronics'` into `WHERE category = @P1`. It doesn't apply to complex queries.

**Forced parameterization** makes SQL Server parameterize more queries automatically:

```sql
ALTER DATABASE SalesDB SET PARAMETERIZATION FORCED;
```

This is useful for OLTP systems where application code submits many nearly-identical queries with varying literals, causing plan cache bloat. Beware of edge cases — forced parameterization can produce suboptimal plans for queries involving indexed views, partitioned views, or computed column indexes.

## Parameter Sniffing

Parameter sniffing is what happens when the Query Optimizer compiles a plan for a stored procedure using the *first* parameter values it receives. The compiled plan is then cached and reused for all subsequent calls — regardless of whether those parameter values have similar or very different selectivity.

```sql
-- Customer 1 has 5 orders → optimizer chooses Nested Loops, fast for small sets
EXEC dbo.usp_GetCustomerOrders @customer_id = 1;

-- Plan is now cached. Customer 50000 has 500,000 orders.
-- Same Nested Loops plan runs → potentially catastrophic for large sets
EXEC dbo.usp_GetCustomerOrders @customer_id = 50000;
```

This is parameter sniffing working against you: the plan that's optimal for small inputs is terrible for large inputs, and the optimizer doesn't know, because it sniffed the wrong values at compile time.

**Mitigation options:**

```sql
-- OPTION (RECOMPILE): recompile on every execution using current parameter values
-- High accuracy, but compilation overhead on each call
CREATE PROCEDURE dbo.usp_GetCustomerOrders @customer_id INT
AS
    SELECT order_id, order_date, status
    FROM dbo.Orders
    WHERE customer_id = @customer_id
    OPTION (RECOMPILE);

-- OPTIMIZE FOR UNKNOWN: compile a plan based on average statistics instead of sniffed values
CREATE PROCEDURE dbo.usp_GetCustomerOrders @customer_id INT
AS
    SELECT order_id, order_date, status
    FROM dbo.Orders
    WHERE customer_id = @customer_id
    OPTION (OPTIMIZE FOR (@customer_id UNKNOWN));
```

SQL Server 2022 introduced **Parameter Sensitive Plan (PSP) optimization**, which allows multiple cached plans for the same query — one for low-cardinality inputs, one for high-cardinality inputs, automatically.

## Recompilation

Plans are sometimes recompiled automatically — when they become stale or invalid. Triggers for recompilation:

- Schema changes to referenced objects (`ALTER TABLE`, `DROP INDEX`)
- Significant data volume changes (approximately 20% of rows modified)
- Statistics updates
- `sp_recompile` called on the object
- `WITH RECOMPILE` in the procedure or query

Since SQL Server 2005, recompilation is **statement-level**, not batch-level. If one statement in a 10-statement procedure triggers recompilation, only that statement is recompiled — the rest continue using cached plans.

## Parallel Query Execution

For queries that process large amounts of data, SQL Server can split work across multiple CPU cores using **parallel execution**. The optimizer decides whether parallelism is worth the overhead based on the estimated cost of the query.

When parallelism is used, the execution plan includes **exchange operators** that manage data flow between threads:

- **Distribute Streams** — sends data to multiple threads based on a key
- **Repartition Streams** — redistributes data across threads for joins or aggregation
- **Gather Streams** — combines parallel outputs into a single result stream

**Degree of Parallelism (MAXDOP)** controls how many CPUs a parallel operation can use:

```sql
-- Query-level MAXDOP hint
SELECT
    customer_id,
    COUNT(*) AS order_count
FROM dbo.Orders
GROUP BY customer_id
OPTION (MAXDOP 4);

-- Server-level setting
EXEC sp_configure 'max degree of parallelism', 8;
RECONFIGURE;
```

`MAXDOP = 0` means "use all available CPUs." A common production recommendation is to set MAXDOP to the number of physical cores per NUMA node, with a cap of 8.

**What prevents parallelism:**

Some constructs force serial execution for a query or part of it:
- Scalar UDFs (without inlining in SQL Server 2019+)
- Multi-statement table-valued functions (MSTVFs)
- Dynamic cursors
- Recursive CTEs
- Remote queries via linked servers

When a plan is forced to run serially, the execution plan shows `NonParallelPlanReason`. This is an actionable signal — if a critical query is prevented from parallelizing by a scalar UDF, rewriting the UDF as an inline TVF can unlock parallelism.

## Checking the Plan Cache

```sql
-- Find top 10 most expensive cached plans
SELECT TOP 10
    qs.total_elapsed_time / qs.execution_count AS avg_elapsed_us,
    qs.execution_count,
    SUBSTRING(qt.text, qs.statement_start_offset/2 + 1,
        (CASE WHEN qs.statement_end_offset = -1
              THEN LEN(CONVERT(NVARCHAR(MAX), qt.text)) * 2
              ELSE qs.statement_end_offset END - qs.statement_start_offset)/2 + 1
    ) AS query_text,
    qp.query_plan
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
ORDER BY avg_elapsed_us DESC;
```

## Key Takeaways

- **Plan caching avoids recompilation** — plans are stored in the Buffer Pool and reused when query text and SET options match; stored procedures are the best vehicle for reliable plan reuse
- **Parameter sniffing can help or hurt** — the optimizer compiles a plan for the first parameter values seen; skewed data distributions can cause the cached plan to perform poorly for other inputs
- **Use `sp_executesql` for parameterized dynamic SQL** — parameterization reduces plan cache bloat and protects against SQL injection
- **`OPTION (RECOMPILE)` trades CPU for accuracy** — useful for queries with highly variable cardinality; generates a fresh plan per execution
- **Scalar UDFs block parallelism** — rewrite as inline TVFs to allow parallel execution in critical analytical queries
