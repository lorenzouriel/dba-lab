# System Databases, Files, and Filegroups

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

Every SQL Server instance has databases you never created. Before your first `CREATE DATABASE` runs, four system databases are already sitting there, quietly doing the work that makes the instance function at all. Most developers never look at them until something breaks — `tempdb` fills the drive at 2 AM, a restore fails because `msdb` lost job history, or a new database inherits settings nobody remembers configuring. Understanding what these databases do, and how your own databases are physically laid out on disk, turns those incidents from mysteries into two-minute diagnoses.

---

## The Four System Databases

When SQL Server starts, it doesn't go looking for your application databases first — it reads its own configuration from a small set of system databases that exist on every instance, whether you asked for them or not.

### master: The Instance's Memory

The `master` database is the one you cannot lose without losing the instance. It stores the metadata about the instance itself — not about any single database's data, but about the *server*: what databases exist and where their files live, what logins are allowed to connect, what linked servers are configured, and instance-wide configuration settings.

This is why `master` corruption is a full-blown emergency rather than an inconvenience. When SQL Server starts up, one of its first acts is reading `master` to figure out what other databases exist and where to find them. If `master` is gone or corrupt, the instance doesn't know it has a `dbo.Orders` table anywhere — it doesn't know it has *any* databases, even if the data files are sitting untouched on disk. This is also why `master` gets backed up after every meaningful instance-level change (new login, new linked server, new database) rather than on a data-driven schedule — its content changes with *administration*, not with application traffic.

### model: The Template Nobody Remembers Setting

The `model` database is the blueprint SQL Server copies every time you run `CREATE DATABASE`. Whatever exists in `model` — a table, a stored procedure, a specific recovery model, a default filegroup setting — gets stamped into every new database from that point forward.

This is the mechanism behind a specific kind of confusion: a DBA adds a standard audit table or a default `CHECK` constraint pattern to `model`, and six months later a new hire is confused why every freshly created database already has an `AuditLog` table nobody wrote a migration for. It's not magic — it's `model` doing exactly what it's designed to do. The practical use is deliberate: if every database in your shop should start with the same recovery model, the same default filegroup, or a standard set of administrative objects, put them in `model` once instead of scripting them into every `CREATE DATABASE` you'll ever run.

### msdb: The Automation Database

`msdb` is where SQL Server Agent, and SQL Server's own operational history, live. Backup and restore history, SQL Server Agent job definitions, job step history, alerts, operators, and maintenance plan metadata are all stored here.

This is the database people don't think about until they need it. "When did we last back up this database, and did it succeed?" — that's a query against `msdb.dbo.backupset` and `msdb.dbo.backupmediafamily`. "Why didn't last night's index maintenance job run?" — that's `msdb.dbo.sysjobhistory`. If `msdb` is corrupted or restored to a stale point, your Agent jobs may still be scheduled but SQL Server Agent's bookkeeping about *what already ran and when* becomes unreliable, which is a quiet way to end up with duplicate runs or silently skipped maintenance.

### tempdb: The Workspace Nobody Owns

`tempdb` is the odd one out among the four: it is recreated from scratch every time the SQL Server service restarts. Nothing in it is meant to survive a restart, because everything in it is, by design, temporary.

`tempdb` holds explicit temporary objects your code creates (`#TempTable`, `@TableVariable`), but it also silently absorbs a huge amount of engine-internal work you never asked for directly: intermediate results for sort and hash operations that spill past available memory, worktables for cursors, the row-versioning store used by `READ_COMMITTED_SNAPSHOT` and `SNAPSHOT` isolation, and the version store for online index rebuilds. This is why `tempdb` contention is one of the most common "SQL Server is slow" root causes that has nothing to do with your query's own table — a poorly-sized `tempdb`, or one with too few data files relative to concurrent load, becomes a bottleneck for workloads that never explicitly touch a temp table. Its size and file configuration can and should be tuned to the workload, which is why production installations routinely configure multiple equally-sized `tempdb` data files rather than accepting the single-file default.

## Data Files and Log Files: What Actually Lives on Disk

Every database — system or user — is physically backed by at least two kinds of files, and understanding the split explains most of what SQL Server's storage architecture is built around.

**Data files** hold the actual data and database objects: tables, indexes, stored procedures, views — everything that isn't the record of *how it changed*. Every database has exactly one **primary data file**, using the `.mdf` extension, which also stores the internal system tables that describe the rest of the database's structure. A database can additionally have any number of **secondary data files**, using the `.ndf` extension, used to spread data across multiple physical disks, multiple filegroups, or simply to keep a single file from growing unmanageably large.

```sql
CREATE DATABASE SalesDB
ON (
    NAME = 'SalesDB_Data',
    FILENAME = 'C:\Data\SalesDB.mdf',
    SIZE = 100MB,
    MAXSIZE = UNLIMITED,
    FILEGROWTH = 10%
);
```

**Log files** hold the transaction log — the record of every change made to the database, including transactions, rollbacks, and the internal steps needed to make crash recovery possible. Every database has exactly one active log file, using the `.ldf` extension (large systems sometimes add secondary log files for space management, but there's still one logical, sequential log stream). As `Series 4.1` covered, this is the file the Log Manager writes to *before* the corresponding change touches the data file — Write-Ahead Logging. If you lose the log file for a database using the Full recovery model without a recent backup, you lose the ability to recover any change since the last data backup, even if the `.mdf` is perfectly intact.

```sql
CREATE DATABASE SalesDB
ON (
    NAME = 'SalesDB_Log',
    FILENAME = 'C:\Logs\SalesDB.ldf',
    SIZE = 50MB,
    MAXSIZE = UNLIMITED,
    FILEGROWTH = 5%
);
```

The practical rule that follows from this split: data files and log files should live on physically separate storage whenever the deployment allows it. Data file I/O is largely random (index seeks jump all over the file); log file I/O is almost entirely sequential (each new log record appends to the end). Mixing them on the same disk means the sequential log writes get interrupted by random data reads, which slows down both.

## Filegroups: Grouping Data Files for a Purpose

A **filegroup** is a logical container for one or more data files. It doesn't hold data itself — it's an administrative grouping that lets you control *where* specific tables, indexes, or partitions physically land, without every object having to know which individual file it's in.

Every database starts with a `PRIMARY` filegroup, which contains the primary data file and, unless you say otherwise, every table and index you create. You can add more filegroups and assign secondary data files to them:

```sql
ALTER DATABASE SalesDB
ADD FILEGROUP FG_Archive;

ALTER DATABASE SalesDB
ADD FILE (
    NAME = 'FG_Archive_File1',
    FILENAME = 'C:\Data\FG_Archive.ndf',
    SIZE = 100MB,
    MAXSIZE = UNLIMITED,
    FILEGROWTH = 10MB
)
TO FILEGROUP FG_Archive;
```

Filegroups are how you put cold, rarely-queried data (say, `dbo.Orders` history older than three years) on cheaper, slower storage while keeping hot data on fast disks — the same mechanism partitioning (covered in `Series 4.4`) leans on when a partition scheme maps date ranges to specific filegroups. Autogrowth on each file can be set in flat MB or as a percentage, and a maximum size cap prevents a runaway process from filling the entire volume.

Once a filegroup exists, you can make it the default target for new objects that don't explicitly specify a filegroup. This is a database-level setting, not a per-object one:

```sql
USE SalesDB;

ALTER DATABASE SalesDB
MODIFY FILEGROUP FG_Archive DEFAULT;
```

After this runs, any `CREATE TABLE` or `CREATE INDEX` that doesn't name a filegroup explicitly lands in `FG_Archive` instead of `PRIMARY`. This is an easy setting to forget you changed — six months later someone runs a plain `CREATE TABLE` expecting it on `PRIMARY` with the fast disks, and it silently lands on the archive filegroup instead. Document a default filegroup change the same way you'd document any schema change.

## Backing Up and Restoring a Single Filegroup

On a large, multi-filegroup database, backing up everything every night isn't always practical — a 5 TB database with 4.9 TB of cold archive data and 100 GB of active data doesn't need the archive portion backed up nightly if it never changes. SQL Server allows backing up and restoring individual filegroups, which is the mechanism behind **piecemeal restores**: getting the critical, actively-used filegroup back online fast, and restoring the rest afterward.

**Backing up a specific filegroup** uses the `FILEGROUP` option on `BACKUP DATABASE`:

```sql
BACKUP DATABASE SalesDB
FILEGROUP = 'FG_Archive'
TO DISK = 'C:\Backups\SalesDB_Archive.bak';
```

**Restoring a specific filegroup** requires the `PARTIAL` option on `RESTORE DATABASE`, which tells SQL Server you're intentionally restoring only part of the database rather than expecting a complete, consistent whole in one step:

```sql
RESTORE DATABASE SalesDB
FILEGROUP = 'FG_Archive'
FROM DISK = 'C:\Backups\SalesDB_Archive.bak'
WITH PARTIAL, RECOVERY;
```

If there are additional filegroups to bring back, repeat the `RESTORE DATABASE` statement for each one, pointing at its own backup file:

```sql
RESTORE DATABASE SalesDB
FILEGROUP = 'FG_Reporting'
FROM DISK = 'C:\Backups\SalesDB_Reporting.bak'
WITH PARTIAL, RECOVERY;
```

If the database uses the Full or Bulk-Logged recovery model — covered in depth in `Series 5.1` — transaction log backups taken since the filegroup backup also need to be restored, so that the filegroup you just brought back is rolled forward to a point consistent with the rest of the database:

```sql
RESTORE LOG SalesDB
FROM DISK = 'C:\Backups\SalesDB_Log.trn'
WITH RECOVERY;
```

Sequencing matters here more than in a full database restore. Restoring filegroups out of order, or skipping a required log backup in the chain, leaves the database in a state where some filegroups are ahead of others in time — which SQL Server won't silently paper over. Piecemeal restore is a real recovery strategy for very large databases, but it demands the same discipline as any multi-step recovery plan: know your backup chain before the incident, not during it.

## Key Takeaways

- **`master` holds the instance's own metadata** — logins, linked servers, and the list of every database and where its files live; losing it without a recent backup means the instance doesn't know it has any databases at all
- **`model` is the template for every new database** — objects and settings placed here are copied into every future `CREATE DATABASE`, which is either a useful standardization tool or a source of confusing surprises depending on whether it's documented
- **`msdb` is SQL Server Agent's and the backup subsystem's memory** — job history, schedules, and backup/restore history all live here; corrupt or stale `msdb` undermines your confidence in "did the job actually run?"
- **`tempdb` rebuilds on every restart and absorbs far more than explicit temp tables** — sort/hash spills, row versioning, and cursor worktables all land there, making it a common hidden bottleneck
- **Data files (`.mdf`/`.ndf`) and log files (`.ldf`) have fundamentally different I/O patterns** — random for data, sequential for the log — which is the reason to separate them physically when possible
- **Filegroups let you control physical placement without rewriting every object** — hot data on fast storage, cold data on cheap storage, tied together with a default filegroup setting that's easy to forget was changed
- **Filegroup-level backup and restore (piecemeal restore) is how very large databases recover critical data fast** — but it requires strict sequencing of filegroup backups and log backups to reach a consistent state
