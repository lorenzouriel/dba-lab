# SQL Server Architecture: Protocol Layer, Relational Engine, and Storage Engine

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

You write a SELECT, hit F5, and data appears. That 200ms round-trip involves more moving parts than most developers ever think about — authentication, protocol negotiation, parsing, optimization, plan compilation, buffer management, disk I/O, and transmission back to your client. Each step touches a different component of SQL Server's internal architecture.

Understanding this architecture doesn't just satisfy curiosity. It's the foundation for understanding why queries are fast or slow, how transactions survive crashes, and what "query optimization" actually means inside the engine.

---

## Three Layers

SQL Server's architecture divides into three main layers, each with a distinct responsibility:

```text
Client Application
       │ (TDS protocol)
       ▼
┌─────────────────────┐
│   Protocol Layer    │  ← Connection management, authentication, TDS
└─────────────────────┘
       │
       ▼
┌─────────────────────┐
│  Relational Engine  │  ← Parsing, optimization, execution planning
└─────────────────────┘
       │
       ▼
┌─────────────────────┐
│   Storage Engine    │  ← Buffer pool, transactions, disk I/O
└─────────────────────┘
       │
       ▼
  Data Files (.mdf)
  Log Files (.ldf)
```

---

## Protocol Layer: The Front Door

The Protocol Layer handles everything before SQL Server sees your query. It manages client connections, authentication, and message framing.

**Three supported protocols:**

| Protocol | When it's used |
|----------|---------------|
| **Shared Memory** | Client and server are on the same machine — fastest, local only |
| **Named Pipes** | Client and server on the same LAN — legacy protocol |
| **TCP/IP** | Client and server anywhere — the standard for all networked connections |

All three protocols share the same underlying message format: **TDS (Tabular Data Stream)**. TDS is Microsoft's wire protocol that defines how SQL queries, results, errors, and metadata are packaged and transmitted. When your ORM sends a query, SSMS submits a batch, or an application calls a stored procedure — it's all TDS packets over one of these three transports.

The Protocol Layer also handles connection pooling coordination, session establishment, and login authentication (SQL Server auth or Windows/Integrated auth).

## Relational Engine: Where Queries Become Plans

The Relational Engine is the core of SQL Server's query processing. It has three sequential components:

### 1. CMD Parser (Command Parser)

The first thing SQL Server does with your query text is parse it. The CMD Parser:
- Checks syntax (missing commas, invalid keywords, unbalanced parentheses)
- Validates object references (does `dbo.Orders` exist? Does the column `customer_id` exist in that table?)
- Produces a **parse tree** (also called a syntax tree) — an internal tree structure representing the logical structure of the query

If your query has a typo or references a nonexistent column, this is where you get the error. Nothing leaves the CMD Parser until the query is syntactically and semantically valid.

### 2. Query Optimizer

The Query Optimizer receives the parse tree and produces an **execution plan** — a step-by-step set of physical operations that SQL Server will use to execute the query.

This is where most of the interesting (and consequential) work happens:
- Evaluating possible join orders (for a 4-table query, there are dozens of possible join sequences)
- Choosing join algorithms (Nested Loops vs. Merge vs. Hash — see Series 3)
- Deciding whether to use an index seek or a table scan based on cardinality estimates
- Estimating the cost of each possible plan and choosing the one with the lowest estimated cost

The optimizer doesn't find the perfect plan — it finds a good plan within a time budget. For complex queries with many tables, trying every possible plan combination is computationally infeasible, so the optimizer uses heuristics and statistics to prune the search space.

```sql
-- See the estimated execution plan without executing the query
SET SHOWPLAN_TEXT ON;
GO
SELECT c.first_name, COUNT(o.order_id) AS order_count
FROM dbo.Customers c
LEFT JOIN dbo.Orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name;
GO
SET SHOWPLAN_TEXT OFF;
```

### 3. Query Executor

The Query Executor takes the chosen execution plan and runs it. It coordinates with the Storage Engine to read and write data, manages operator-level execution (sort, join, aggregate), and routes SELECT operations to the Buffer Manager and DML operations to the Transaction Manager.

## Storage Engine: Where Data Actually Lives

The Storage Engine handles the physical reality: pages, disk, memory, locks, and logs.

### Access Manager

The Access Manager is the interface between the Relational Engine and the physical storage layer. It routes operations:
- **SELECT** operations → Buffer Manager (read from cache or disk)
- **Non-SELECT** (INSERT, UPDATE, DELETE) → Transaction Manager

### Buffer Manager (Buffer Pool)

The Buffer Pool is SQL Server's in-memory data cache. It holds 8KB data pages that were recently read from disk. When the Query Executor needs a data page:

1. **Check Buffer Pool** — if the page is already in memory (a "cache hit"), return it immediately
2. **Hard parse / cold read** — if not in memory (a "cache miss"), read it from disk, load it into the Buffer Pool, then return it

This is why the same query runs faster on the second execution: the first execution populated the Buffer Pool with the relevant pages. Subsequent executions find them in memory.

The Buffer Manager also manages:
- **Plan Cache** — stores compiled execution plans for reuse
- **Data Cache** — the data pages themselves
- **Dirty Pages** — pages modified in memory but not yet written to disk

### Transaction Manager

The Transaction Manager enforces ACID properties for all write operations. It contains two sub-components:

**Lock Manager** — controls concurrency. When a transaction modifies a row, the Lock Manager acquires locks on that row (and potentially the page and table) to prevent other transactions from reading or modifying it until the first transaction commits or rolls back. The Lock Manager coordinates lock escalation, deadlock detection, and isolation level enforcement.

**Log Manager** — implements Write-Ahead Logging (WAL). Every modification is recorded in the transaction log (`LDF` file) *before* the change is applied to the data file (`MDF`). This is the mechanism that enables durability and crash recovery — if the server restarts, the Log Manager replays committed transactions from the log.

## The Full Flow: F5 to Result Set

Following a SELECT from client to result:

```text
1. Client sends SQL batch (TDS packet over TCP/IP)
2. Protocol Layer: validates connection, routes to Relational Engine
3. CMD Parser: syntax check, produces parse tree
4. Query Optimizer: evaluates execution plans, selects lowest-cost plan
5. Query Executor: executes plan, requests data pages from Access Manager
6. Buffer Manager: checks buffer pool → cache hit returns immediately,
   cache miss reads from MDF, loads into pool
7. Results returned to Query Executor → Relational Engine → Protocol Layer
8. TDS packets with result rows sent back to client
```

For a DML operation, step 6 also involves the Transaction Manager logging the change to the LDF before modifying the buffer pool pages.

## The Trap

**Assuming "the database is slow" without knowing which layer.** Performance problems in SQL Server are layer-specific:

- **Slow query, fast hardware** → usually a Relational Engine problem: bad execution plan, missing index, parameter sniffing issue
- **Fast query, slow overall response** → may be Protocol Layer / network: TDS packet fragmentation, connection pool exhaustion
- **High I/O, query performance degrading over time** → Storage Engine: Buffer Pool pressure (not enough memory), index fragmentation, checkpoint pressure
- **Blocking and deadlocks** → Transaction Manager: Lock Manager contention

Knowing the architecture turns "the database is slow" into "which component is the bottleneck" — a much more actionable question.

---

## Key Takeaways

- **Three layers: Protocol, Relational Engine, Storage Engine** — each with distinct responsibilities; performance problems are layer-specific
- **TDS is the wire protocol** — all client-server communication uses Tabular Data Stream regardless of the transport (TCP/IP, Named Pipes, Shared Memory)
- **The Query Optimizer produces execution plans** — it estimates costs and picks the best available plan, not necessarily the optimal one; execution plan quality determines query performance
- **The Buffer Pool is the performance multiplier** — hot data in memory avoids disk I/O; plan cache avoids recompilation
- **Write-Ahead Logging is how durability works** — the log file is written before the data file; crashed transactions are recovered from the log on restart
