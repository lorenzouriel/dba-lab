# Specialized Table Types: Temporal, Ledger, In-Memory, Graph, and Columnstore

*Series 4 — SQL Server Architecture | The SQL Server Deep Dive*

---

You can rewrite a C# service on a Friday afternoon and nobody notices. Change a table from rowstore to columnstore, bolt temporal history onto a live table, or swap an `IDENTITY` column for a `SEQUENCE`, and you're scheduling a maintenance window, rebuilding multi-GB structures, and explaining why the orders table was locked for two hours.

That asymmetry is the whole point of this article. Table design decisions outlive your application code, and most of them are cheap to get right at design time and expensive to fix in production. The specialized table types covered here — temporal, ledger, in-memory, graph, columnstore — aren't optimizations you sprinkle on later. They change how data is stored, validated, and queried at the engine level. Pick a plain table when you needed audit history, and you're hand-rolling triggers and a shadow history table. Pick `IDENTITY` when you needed cross-table numbering, and you're patching the gap in the application tier.

The framing throughout: decide the foundation before you pour the concrete.

---

## Platform First: It Changes What You Can Use

Before any `CREATE TABLE`, know where the database lives. The same T-SQL runs across four Azure platforms, but their management boundaries and feature sets differ, and that affects design.

**SQL Server on Azure VMs (IaaS).** You own the instance, the engine config, and the OS. Maximum compatibility and control — specific SQL Server versions, OS-level access, full say over Always On AG or FCI replica placement. The SQL IaaS Agent extension hands you automated backups, patching windows, Key Vault integration, and `tempdb` configuration from the portal. Choose this when you need something PaaS won't give you.

**Azure SQL Managed Instance (PaaS).** Near 100% surface-area compatibility with SQL Server Enterprise, always on the latest engine, auto-patched. You keep instance-level features that single databases drop: SQL Server Agent, Service Broker, linked servers, cross-database three-part-name queries, Database Mail. The Managed Instance link rides distributed availability groups to sync from on-prem SQL Server to Azure in near real time — read offload, DR, low-downtime migrations. In-Memory OLTP is available in the Business Critical tier.

**Azure SQL Database (PaaS).** Fully managed single database. Hyperscale removes the single-node storage ceiling — storage grows as needed, you pay for what you use, read replicas scale out reads. Serverless pauses compute when idle and resumes on connection, so design for retry logic and avoid long transactions that block autopause. Built-in HA carries a 99.99% SLA, and intelligent query processing will recommend or auto-create indexes and auto-correct plan regressions.

**SQL database in Microsoft Fabric.** Azure SQL Database engine under the hood, but every operational table auto-mirrors into OneLake as Delta Parquet. No ETL, no triggers — inserts/updates/deletes replicate to a read-only SQL analytics endpoint, so heavy reporting hits the Parquet copy and never touches live OLTP. You get three-part-name queries across warehouses, lakehouses, and other Fabric SQL databases, plus auto-indexing and built-in RAG/semantic search hooks.

The mental model that matters: PaaS draws the line below the database layer. Azure runs the servers, network, OS patches, and engine updates. You own tables, indexes, constraints, and data — that's where your time should go.

## Data Type Sizing: The Decisions That Bite Later

Tables look like the boring part of the schema. They're where most long-term performance is won or lost, because data types and sizing are baked in before a single row lands — changing a column type on a large table means a rebuild.

A few choices are worth slowing down for:

- **`DECIMAL`, never `FLOAT`, for money.** `FLOAT` introduces rounding error you can't fix without recomputing every dependent value. `Amount DECIMAL(10,2)` is exact; financial code should never gamble on binary floating point.
- **`INT` over `UNIQUEIDENTIFIER` for keys when an `INT` fits.** A GUID primary key is 16 bytes vs. 4, which roughly triples index size and slows every join. Use a GUID when you genuinely need distributed uniqueness, not by reflex.
- **`DATETIME2` over legacy `DATETIME`.** Better precision, and 6–8 bytes vs. the old type's overhead.
- **`VARCHAR` vs. `NVARCHAR`.** `NVARCHAR` costs 2 bytes per character for Unicode. If the data is provably ASCII-only, `VARCHAR` halves string storage. On a 30-character name across 10 million rows, that's roughly 300 MB. Use `NVARCHAR` for international data; use `VARCHAR` when storage matters and the data stays ASCII.

Sizing isn't academic. An extra 50 bytes per row on a table taking 100 million transactions a day is 5 GB/day — about 1.8 TB a year of waste, plus proportional backup time and I/O. The rough estimate is straightforward: sum fixed-length columns, estimate the average for variable-length ones, add about 7 bytes of row overhead.

```sql
CREATE TABLE dbo.Customers (
    CustomerID   INT,              -- 4 bytes
    FirstName    NVARCHAR(50),     -- ~40 bytes avg
    LastName     NVARCHAR(50),     -- ~40 bytes avg
    SignupDate   DATE,             -- 3 bytes
    LifetimeValue DECIMAL(10,2)    -- 5 bytes
);
-- ~92 bytes + ~7 overhead = ~99 bytes/row -> 1M rows ≈ 94 MB
```

A well-formed table puts these principles together: a narrow `IDENTITY` surrogate key, right-sized strings, `NOT NULL` where data is mandatory, and `DEFAULT`s that keep nulls out and reduce application boilerplate.

```sql
CREATE TABLE dbo.Products (
    ProductID     INT PRIMARY KEY IDENTITY(1,1),
    ProductName   NVARCHAR(100) NOT NULL,
    Category      NVARCHAR(50)  NOT NULL,
    Price         DECIMAL(10,2) NOT NULL,
    StockQuantity INT NOT NULL DEFAULT 0,
    LastRestocked DATETIME2 DEFAULT GETUTCDATE()
);
```

## Rowstore vs. Columnstore, and What's Actually Happening Underneath

`Series 3.1 - Indexes Deeply Explained` already covers clustered vs. non-clustered indexes, the basic rowstore/columnstore distinction, and fragmentation in depth — start there for the fundamentals of how `CREATE INDEX` and `CREATE CLUSTERED COLUMNSTORE INDEX` work. What's worth adding here is what happens *inside* a columnstore index once data starts landing in it, because that mechanism is exactly why the "don't use columnstore for X" rules exist.

Columnstore data lands in **rowgroups** of up to roughly 1,048,576 rows, with each column compressed separately as a **segment**. But new rows don't go straight into columnar format. A small insert first lands in a rowstore structure called the **deltastore** — an ordinary B-tree, not columnar at all. Once a delta rowgroup accumulates around **102,400 rows**, a background process called the **tuple-mover** compresses it into columnar format and closes it into a proper compressed rowgroup. Bulk loads of 102,400 rows or more skip the deltastore entirely and go straight to columnar compression.

This mechanism explains the practical rules:

- **High-frequency single-row updates fragment columnstore.** Columnstore doesn't update rows in place — a modification marks the old row deleted in its compressed rowgroup and inserts a new version (often into the deltastore). Enough of this and you end up with rowgroups full of `deleted_rows`, which is wasted space the engine still has to scan past.
- **Single-row lookups favor rowstore.** A seek against a B-tree nonclustered index is still faster than decompressing a columnar segment to pull one row.
- **Small tables don't pay off.** Under roughly a million rows, rowgroups can't fill enough to make the compression and scan-elimination benefits worth the overhead. Use columnstore for fact tables, reporting databases, and historical data in the millions of rows.

Two flavors, same underlying mechanism:

- **Clustered columnstore (CCI)** *becomes* the table's storage — all data is columnar, no separate rowstore copy. Use it when analytics is the primary workload.
- **Nonclustered columnstore (NCCI)** is a columnar copy layered alongside the existing rowstore table. The optimizer picks per query, so you keep fast single-row OLTP access on the base table and get columnar scans for analytics on the same data — the HTAP (hybrid transactional/analytical processing) move.

```sql
-- analytics-first table
CREATE CLUSTERED COLUMNSTORE INDEX CCI_OrderDetails ON dbo.OrderDetails;

-- analytics layered on top of an OLTP table
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Products_Analytics
    ON dbo.Products(Price, StockQuantity, Category, ProductName);
```

Watch columnstore health through `sys.dm_db_column_store_row_group_physical_stats`. A high `deleted_rows` count, or a pile of small open rowgroups that never made it past the tuple-mover, means fragmentation. `ALTER INDEX ... REORGANIZE` forces compression and cleanup.

```sql
SELECT OBJECT_NAME(object_id) AS TableName,
       state_desc, total_rows, deleted_rows,
       size_in_bytes / 1024 / 1024 AS SizeMB
FROM sys.dm_db_column_store_row_group_physical_stats
WHERE object_id = OBJECT_ID('dbo.OrderDetails');
```

## Specialized Table Types: Pick the Engine Feature Instead of Rebuilding It

This is the heart of the "design it now" argument. Each of the following replaces something you'd otherwise build by hand, and each carries one dominant tradeoff.

**In-memory (memory-optimized) tables** keep data in RAM with lock-free optimistic concurrency, eliminating disk-I/O latency for workloads like 10k+ TPS order processing, session state at scale, or hot reference caches. Durability still comes from the transaction log on disk, so committed data survives a restart. The cost: data size is bounded by available RAM, and there's no `VARCHAR(MAX)`, `NVARCHAR(MAX)`, or `VARBINARY(MAX)` support.

```sql
CREATE TABLE dbo.OrderCache (
    OrderID    INT PRIMARY KEY NONCLUSTERED,
    CustomerID INT,
    OrderDate  DATETIME2,
    Amount     DECIMAL(10,2),
    INDEX IX_CustomerID NONCLUSTERED (CustomerID)
) WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);
```

**Temporal tables** track full row history automatically. You write normal `INSERT`/`UPDATE`/`DELETE` statements, and the engine stores prior versions in a linked history table with validity periods, no triggers required. This is your answer to "what was this customer's tier on January 1st?", compliance audit trails, and automated Type 2 slowly-changing dimensions, with zero application code. The cost: storage roughly doubles.

```sql
CREATE TABLE dbo.Customers (
    CustomerID    INT PRIMARY KEY,
    CustomerName  NVARCHAR(100),
    Tier          NVARCHAR(50),
    SysStartTime  DATETIME2 GENERATED ALWAYS AS ROW START,
    SysEndTime    DATETIME2 GENERATED ALWAYS AS ROW END,
    PERIOD FOR SYSTEM_TIME (SysStartTime, SysEndTime)
) WITH (SYSTEM_VERSIONING = ON);

SELECT * FROM dbo.Customers
FOR SYSTEM_TIME AS OF '2026-01-01'
WHERE CustomerID = 1;
```

**External tables** let you query data where it lives — Parquet or CSV in a data lake, blob storage — without ETL. Good for lake integration, exploring raw data before importing, and federating database tables with external files. The cost: network latency and file parsing make them slower than native tables, they're mostly read-only, and indexing is limited.

```sql
CREATE EXTERNAL TABLE dbo.ExternalOrderData (
    OrderID INT, CustomerID INT,
    OrderAmount DECIMAL(10,2), OrderDate DATE
) WITH (LOCATION = '/raw/orders/', DATA_SOURCE = DataLakeSource, FILE_FORMAT = ParquetFormat);
```

**Ledger tables** give you cryptographic, tamper-evident records — blockchain-style hashing that chains row modifications so auditors can independently verify nothing was altered after the fact. Updatable ledgers allow DML while tracking every change (a history table plus a tamper-proof chain); append-only ledgers allow inserts only, for truly immutable logs. This is for banking, supply-chain provenance, clinical trial data, voting records. Verify integrity with `sys.database_ledger_transactions` and `sp_verify_database_ledger`.

```sql
CREATE TABLE dbo.OrderAuditLog (
    LogID INT PRIMARY KEY IDENTITY,
    EventDescription NVARCHAR(500),
    EventTimestamp DATETIME2
) WITH (LEDGER = ON, APPEND_ONLY = ON);
```

**Graph tables** model nodes and edges natively, so "friends of friends" and multi-hop traversals stop being join nightmares. Use them for genuinely connected, read-heavy relationship queries — social graphs, bill-of-materials, org charts with arbitrary depth. Don't use them for simple parent-child relationships (a foreign key is fine) or stable, highly structured schemas. The cost is the `MATCH` syntax learning curve.

```sql
CREATE TABLE Person AS NODE;
CREATE TABLE Manages AS EDGE;

SELECT p1.name, p2.name
FROM Person p1, Manages, Person p2
WHERE MATCH (p1-(Manages)->p2) AND p1.id = 1;
```

The honest summary: in-memory needs RAM, temporal doubles storage, external adds latency, ledger blocks deletion, graph needs new syntax. All five are painful to retrofit onto a live table — which is the reason to choose them during design, not after the fact.

## Constraints: Enforce Rules Where They Can't Be Bypassed

Application validation is optional from the database's point of view. A bulk import, an ad-hoc script, or a second application that skips your validation layer can all write garbage. Constraints enforce rules at the engine on every `INSERT`/`UPDATE`/`DELETE`, so they're the one source of truth that can't be routed around.

The mapping from problem to constraint is direct: orphaned records → `FOREIGN KEY`, duplicates → `UNIQUE`, invalid values → `CHECK`, missing critical data → `NOT NULL`. The classic failure mode is a missing `UNIQUE (Email)` on `dbo.Customers` — customers get registered three times, marketing sends triplicate emails, trust erodes. One constraint at design time prevents the whole class of problem.

Two details worth keeping straight. `UNIQUE` permits a single `NULL` (unlike `PRIMARY KEY`, which forbids nulls entirely). And `CHECK` evaluates `NULL` as `UNKNOWN`, not `FALSE`, so `CHECK (MyColumn = 10)` still lets `NULL` through unless you also add `NOT NULL`. Name your `DEFAULT` constraints explicitly (`DF_Orders_CreatedDate`) so they're consistent across environments instead of getting system-generated names that differ everywhere.

```sql
CREATE TABLE dbo.Orders (
    OrderID    INT PRIMARY KEY,
    OrderDate  DATE,
    Amount     DECIMAL(10,2),
    CHECK (Amount >= 0),
    CHECK (OrderDate <= GETDATE())
);
```

**Identity vs. sequence** is a real fork, not a style preference. `IDENTITY` is perfect when you want auto-numbering for one table and nothing more. Reach for a `SEQUENCE` when you need to share one number series across multiple tables, get the next value *before* the insert, reserve a block of numbers at once (`sp_sequence_get_range`), cycle or restart at a boundary, or change the increment after creation. The catch: sequence values aren't auto-protected or auto-unique (add a `UNIQUE` constraint if you need it), and a number is consumed whether the transaction commits or rolls back, so expect gaps.

```sql
CREATE SEQUENCE dbo.OrderNumber
    START WITH 1000 INCREMENT BY 1
    MINVALUE 1000 MAXVALUE 999999 NO CYCLE;

DECLARE @Next INT = NEXT VALUE FOR dbo.OrderNumber;  -- value obtained before the insert
```

## JSON Columns: Structure Where You Can, Flexibility Where You Must

Some data refuses a fixed schema. A shirt has size and color, a laptop has CPU and screen size, a book has an author. You either create dozens of mostly-empty columns, split into many tables, or store the common fields as typed columns and the variable part as JSON.

SQL Server 2025 adds a native `json` type stored in binary form: faster reads (already parsed), faster writes (modify a value without rewriting the whole document), better compression than the old `NVARCHAR(MAX)` approach. Older versions still use `NVARCHAR(MAX)`. Read with `JSON_VALUE` (scalar) and `JSON_QUERY` (object/array). Because the `json` type can't be an index key directly, index a computed column that extracts the hot path instead.

```sql
CREATE TABLE dbo.ProductAttributes (
    ProductID  INT PRIMARY KEY,
    Attributes JSON NOT NULL
);

-- index a frequently queried property via a computed column
ALTER TABLE dbo.ProductAttributes ADD ColorValue AS JSON_VALUE(Attributes, '$.color');
CREATE INDEX IX_Color ON dbo.ProductAttributes(ColorValue);
```

The discipline that keeps this from turning into a schemaless mess: typed columns for anything with a consistent shape, JSON only for the genuinely variable parts, `CHECK (JSON_PATH_EXISTS(...) = 1)` to enforce required keys, and indexed computed columns on the paths you actually query. JSON complements relational design; it doesn't replace it.

## Partitioning: Powerful, and Close to Irreversible

Partitioning splits one logical table into physical segments the engine can maintain, archive, and query independently. Done right on a 1.2 TB `dbo.Orders` table, date-filtered queries (typically 90% of the workload) improve 10–20x via partition elimination, index rebuilds drop from six hours to twenty minutes per partition, and archiving old data goes from a four-hour `DELETE` lock to a near-instant metadata switch.

Done wrong, it's worse than no partitioning at all, and the fix is rebuilding a multi-terabyte table. So the partition key is the decision. The good key shows up in the `WHERE` clause of 80%+ of queries, distributes data evenly (no single partition holding 90% of rows), aligns with your archival cadence, and doesn't change after insert. Date columns hit all four for time-series data, which is why range-by-date dominates in practice.

Three components: a partition function (the boundaries), a partition scheme (boundaries mapped to filegroups, usually all to `PRIMARY` unless you're doing tiered storage), and the table built on the scheme. Put the partition column in the primary key so the clustered index aligns with the partitions.

```sql
CREATE PARTITION FUNCTION PF_OrderDate (DATETIME2)
    AS RANGE RIGHT FOR VALUES ('2024-01-01','2024-04-01','2024-07-01','2024-10-01');

CREATE PARTITION SCHEME PS_OrderDate
    AS PARTITION PF_OrderDate ALL TO ([PRIMARY]);

CREATE TABLE dbo.Orders (
    OrderID    INT NOT NULL,
    OrderDate  DATETIME2 NOT NULL,
    CustomerID INT,
    Amount     DECIMAL(10,2),
    CONSTRAINT PK_Orders PRIMARY KEY (OrderID, OrderDate)
) ON PS_OrderDate(OrderDate);
```

Keep indexes **aligned** — same partition scheme as the table. Aligned indexes enable partition switching, independent rebuilds, and better elimination; nonaligned indexes can't switch and aren't supported past 1,000 partitions. Manage the lifecycle with `$PARTITION` to inspect distribution, `SPLIT RANGE` to add a boundary as data grows, and `MERGE RANGE` to roll old data out.

The two mistakes to avoid: over-partitioning (target millions of rows per partition, not thousands, or the overhead eats the benefit), and partitioning a table whose queries scan everything or filter on scattered columns (every partition gets read, and you've made it slower, not faster).

One consequence that only shows up once you've partitioned: the partition column climbs into the primary key, and every relationship that points at the table inherits it. A composite foreign key like `dbo.OrderDetails` referencing `dbo.Orders(OrderID, OrderDate)` — instead of just `OrderID` — exists purely because `Orders` is partitioned on `OrderDate`. Decide partitioning early, or you're reworking foreign keys across the schema later.

## Key Takeaways

- **Platform choice comes first** — Azure VM, Managed Instance, SQL Database, or Fabric SQL database each draw the ownership line differently, and that affects which features (Agent, linked servers, In-Memory OLTP) are even available
- **Data type sizing compounds** — `DECIMAL` over `FLOAT` for money, right-sized `VARCHAR`/`NVARCHAR`, and narrow keys are cheap now and expensive to fix after the table has billions of rows
- **Columnstore internals explain the rules** — the deltastore buffers small inserts until ~102,400 rows trigger the tuple-mover to compress them into a rowgroup; this is why frequent single-row updates fragment columnstore and small tables don't benefit
- **Specialized table types replace hand-built plumbing** — temporal replaces manual history tables, ledger replaces bolt-on tamper-evidence, in-memory replaces disk-latency workarounds, graph replaces recursive join chains — each is expensive to retrofit
- **Constraints are the only validation that can't be bypassed** — `CHECK`, `UNIQUE`, `FOREIGN KEY`, and `NOT NULL` enforce rules at the engine regardless of which application or script is writing
- **Partitioning is fast and nearly permanent in the same breath** — the partition key becomes part of the primary key and propagates into every foreign key that references the table
