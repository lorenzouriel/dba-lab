# SQL Server Data Security and Compliance, Layer by Layer

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

Defense in depth is only useful if you can say, per layer, exactly which adversary it stops and which one it lets straight through. Transparent Data Encryption is for the person who steals a backup file — it does nothing against a valid login. Dynamic Data Masking hides values on a screen and folds instantly to anyone who can write a `WHERE` clause. Treating either as "the security layer" is how systems end up compliant on paper and exposed in practice.

This article walks seven layers of SQL Server data security, in order of how they actually compose in a real system: three flavors of encryption, masking, row-level security, permissions and identity, auditing, and — because it's 2026 — securing the AI and API surfaces that now sit on top of the database. For each layer, the goal is the same: name the attacker it stops, name the gap it leaves, and show the T-SQL that gets it running.

---

## Layer 1: Encryption, Three Flavors, Three Adversaries

Encryption is not one control. It's three, and conflating them is how teams end up with TDE enabled and a false sense of security against threats it was never designed to stop.

### Transparent Data Encryption (TDE): the stolen-backup attacker

TDE encrypts the data files, the log, and backups at rest. It's transparent to applications — no code changes — because SQL Server decrypts automatically on read. That's also its limitation: TDE does nothing against someone who can connect with valid permissions. It exists for one scenario — a drive, a backup file, or a decommissioned server ends up somewhere it shouldn't.

```sql
-- 1) Database master key in master, protecting the server certificate
USE master;
GO
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'S0me-Strong-DMK-P@ss!';
GO

-- 2) Server certificate that protects the database encryption key
CREATE CERTIFICATE TDE_Cert
    WITH SUBJECT = 'TDE Certificate for production';
GO

-- 3) BACK UP THE CERTIFICATE IMMEDIATELY. Without this file and private key,
--    a TDE backup CANNOT be restored on another server. This is the #1 TDE disaster.
BACKUP CERTIFICATE TDE_Cert
    TO FILE = 'C:\Secure\TDE_Cert.cer'
    WITH PRIVATE KEY (
        FILE = 'C:\Secure\TDE_Cert.pvk',
        ENCRYPTION BY PASSWORD = 'Cert-Backup-P@ss!'
    );
GO

-- 4) Create the database encryption key (DEK) and turn TDE on
USE SalesDB;
GO
CREATE DATABASE ENCRYPTION KEY
    WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE TDE_Cert;
GO
ALTER DATABASE SalesDB SET ENCRYPTION ON;
GO
```

Confirm the state (3 means fully encrypted):

```sql
SELECT DB_NAME(database_id) AS DatabaseName,
       encryption_state,            -- 0 none, 1 unencrypted, 2 in progress, 3 encrypted
       encryption_state_desc,
       percent_complete,
       key_algorithm, key_length
FROM sys.dm_database_encryption_keys;
```

Restoring a TDE-encrypted backup on a second server requires recreating the certificate first:

```sql
USE master;
GO
CREATE CERTIFICATE TDE_Cert
    FROM FILE = 'C:\Secure\TDE_Cert.cer'
    WITH PRIVATE KEY (
        FILE = 'C:\Secure\TDE_Cert.pvk',
        DECRYPTION BY PASSWORD = 'Cert-Backup-P@ss!'
    );
GO
-- RESTORE DATABASE ... now succeeds
```

On Azure SQL Database and Managed Instance, TDE is on by default with a service-managed key; you can switch to customer-managed keys (BYOK) via Key Vault. On Fabric, it's on by default and fully managed. TDE is a lost-media and compliance control — nothing more, nothing less.

### Always Encrypted: the DBA / engine-never-sees-plaintext attacker

Always Encrypted is the only control on this list that defends against a privileged DBA. The engine only ever handles ciphertext; the client driver performs encryption and decryption using keys the engine itself cannot read.

```sql
-- Column master key (CMK): metadata pointing at the real key in Key Vault
CREATE COLUMN MASTER KEY CMK_Prod
WITH (
    KEY_STORE_PROVIDER_NAME = 'AZURE_KEY_VAULT',
    KEY_PATH = 'https://kv-prod.vault.azure.net/keys/CMK_Prod/0123abcd'
);
GO

-- Column encryption key (CEK), stored encrypted under the CMK
CREATE COLUMN ENCRYPTION KEY CEK_Prod
WITH VALUES (
    COLUMN_MASTER_KEY = CMK_Prod,
    ALGORITHM = 'RSA_OAEP',
    ENCRYPTED_VALUE = 0x01700000016C006F00...   -- generated by tooling/driver
);
GO

CREATE TABLE dbo.Customers (
    CustomerID int PRIMARY KEY,

    -- DETERMINISTIC: same plaintext -> same ciphertext. Enables =, JOIN, GROUP BY,
    -- and WHERE equality. Requires a BIN2 collation for string columns.
    -- Cost: equal values are visibly equal, so frequency analysis is possible.
    NationalID char(11) COLLATE Latin1_General_BIN2
        ENCRYPTED WITH (ENCRYPTION_TYPE = DETERMINISTIC,
                        ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256',
                        COLUMN_ENCRYPTION_KEY = CEK_Prod),

    -- RANDOMIZED: strongest, leaks nothing, but supports NO query operations
    CreditLimit money
        ENCRYPTED WITH (ENCRYPTION_TYPE = RANDOMIZED,
                        ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256',
                        COLUMN_ENCRYPTION_KEY = CEK_Prod)
);
```

Two things trip people up. First, you cannot write literals into encrypted columns from plain T-SQL — the driver has to encrypt parameter values, so inserts and equality filters must go through parameterized commands with `Column Encryption Setting=Enabled` in the connection string:

```sql
-- Works only as a parameterized command with Always Encrypted enabled on the connection:
DECLARE @nid char(11) = @NationalID_param;   -- driver encrypts the parameter
SELECT CustomerID, CreditLimit
FROM dbo.Customers
WHERE NationalID = @nid;                      -- equality OK because DETERMINISTIC
```

Second, when the list of permitted operations is too short — no ranges, no `LIKE` — the answer is Always Encrypted with secure enclaves, which runs limited computations inside a protected region and adds `ENCLAVE_COMPUTATIONS` to the CMK, unlocking range comparisons, pattern matching, and in-place re-encryption. Inspect what's configured:

```sql
SELECT * FROM sys.column_master_keys;
SELECT * FROM sys.column_encryption_keys;
SELECT c.name AS ColumnName, c.encryption_type_desc,
       c.encryption_algorithm_name, k.name AS CEK
FROM sys.columns c
JOIN sys.column_encryption_keys k
     ON c.column_encryption_key_id = k.column_encryption_key_id
WHERE c.object_id = OBJECT_ID('dbo.Customers');
```

### Column-level (cell) encryption: explicit key control, manual everything

When Always Encrypted doesn't fit and you want to `GRANT`/`DENY` decryption rights yourself, encrypt individual cells with a symmetric key.

```sql
-- Key chain: DB master key -> certificate -> symmetric key
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'DMK-P@ss!';
CREATE CERTIFICATE Cert_PII WITH SUBJECT = 'PII cell encryption';
CREATE SYMMETRIC KEY SymKey_PII
    WITH ALGORITHM = AES_256
    ENCRYPTION BY CERTIFICATE Cert_PII;
GO

-- Encrypt on write. The third argument is an authenticator that binds the
-- ciphertext to a row value (here CustomerID), preventing copy/paste of
-- ciphertext between rows.
OPEN SYMMETRIC KEY SymKey_PII DECRYPTION BY CERTIFICATE Cert_PII;

INSERT INTO dbo.Customers (CustomerID, CardNumber_enc)
VALUES (1,
        ENCRYPTBYKEY(KEY_GUID('SymKey_PII'),
                     CONVERT(varbinary, '4111-1111-1111-1111'),
                     1, CONVERT(varbinary, 1)));   -- authenticator = CustomerID

CLOSE SYMMETRIC KEY SymKey_PII;
GO

-- Decrypt on read, matching the authenticator
OPEN SYMMETRIC KEY SymKey_PII DECRYPTION BY CERTIFICATE Cert_PII;

SELECT CustomerID,
       CONVERT(varchar(20),
               DECRYPTBYKEY(CardNumber_enc, 1, CONVERT(varbinary, CustomerID))) AS CardNumber
FROM dbo.Customers;

CLOSE SYMMETRIC KEY SymKey_PII;
GO
```

Control decryption precisely by gating the key itself:

```sql
GRANT VIEW DEFINITION ON SYMMETRIC KEY::SymKey_PII TO PaymentsRole;
DENY  CONTROL        ON SYMMETRIC KEY::SymKey_PII TO ReportingRole;
```

The cost: application code changes everywhere, and because `ENCRYPTBYKEY` output is non-deterministic (random IV each time), you cannot seek on the ciphertext. If you need to *look up* an encrypted value, store a keyed hash alongside it for equality search while keeping the reversible ciphertext for retrieval:

```sql
ALTER TABLE dbo.Customers ADD CardNumber_hash varbinary(32);
-- deterministic hash for searching (salt/pepper it in real systems)
UPDATE dbo.Customers
SET CardNumber_hash = HASHBYTES('SHA2_256', CONVERT(varbinary, '4111-1111-1111-1111'))
WHERE CustomerID = 1;
CREATE INDEX IX_Customers_CardHash ON dbo.Customers(CardNumber_hash);
```

Compose the layers rather than picking one: TDE as the baseline for everything at rest, Always Encrypted (or cell encryption) reserved for the few columns that must stay opaque even to the engine.

## Layer 2: Dynamic Data Masking — Useful, But Not a Boundary

Dynamic Data Masking (DDM) rewrites values in query results while the real data sits untouched on disk. Four built-in functions cover most cases:

```sql
CREATE TABLE dbo.Customers (
    CustomerID int PRIMARY KEY,
    FullName   varchar(100),
    Email      varchar(100) MASKED WITH (FUNCTION = 'email()'),                        -- jXXX@XXXX.com
    Phone      varchar(20)  MASKED WITH (FUNCTION = 'partial(3, "-XXX-XX", 2)'),        -- 206-XXX-XX89
    CardNumber varchar(19)  MASKED WITH (FUNCTION = 'partial(0, "XXXX-XXXX-XXXX-", 4)'), -- XXXX-XXXX-XXXX-9012
    Income     decimal(18,2) MASKED WITH (FUNCTION = 'random(10000, 100000)'),          -- random per query
    SSN        char(11)     MASKED WITH (FUNCTION = 'default()')                        -- XXXX
);
```

Add and drop masks on existing columns, and inspect what's masked across the database:

```sql
ALTER TABLE dbo.Customers ALTER COLUMN DateOfBirth ADD MASKED WITH (FUNCTION = 'default()');
ALTER TABLE dbo.Customers ALTER COLUMN DateOfBirth DROP MASKED;

SELECT t.name AS TableName, c.name AS ColumnName, mc.masking_function
FROM sys.masked_columns mc
JOIN sys.columns c ON mc.object_id = c.object_id AND mc.column_id = c.column_id
JOIN sys.tables  t ON mc.object_id = t.object_id;
```

`UNMASK` controls who sees the real values, and since SQL Server 2022 it's granular down to the column:

```sql
GRANT UNMASK TO ComplianceOfficer;                          -- everything
GRANT UNMASK ON SCHEMA::Sales TO SalesManager;               -- schema scope
GRANT UNMASK ON dbo.Customers TO CustomerService;             -- table scope
GRANT UNMASK ON dbo.Customers(Phone) TO TelemarketingTeam;    -- column scope
REVOKE UNMASK ON dbo.Customers(Phone) FROM TelemarketingTeam;
```

Here's why masking is not a security boundary, made concrete. Masking operates at the presentation layer — the real value still drives predicate evaluation. A masked user can binary-search a salary out of the column without ever seeing it directly:

```sql
-- The user sees only random()/XXXX in the SELECT list, but these still
-- evaluate against the TRUE value, so the truth leaks one bit at a time:
SELECT COUNT(*) FROM dbo.Customers WHERE Income > 50000;   -- true/false on real data
SELECT COUNT(*) FROM dbo.Customers WHERE Income > 75000;   -- narrow the range, repeat
```

And there's a direct bypass: a user with `SELECT` plus `ALTER` on the table can simply remove the mask. Manage `ALTER` carefully, and treat DDM as accidental-exposure reduction for dev/test environments and support staff — with encryption or row-level security underneath anything that must actually stay protected. In Fabric, the same masks are configured via T-SQL through the SQL analytics endpoint.

## Layer 3: Row-Level Security — the Per-Row Boundary

Row-Level Security (RLS) has two pieces: a schema-bound inline table-valued function that acts as a predicate returning 1 or 0, and a security policy that binds it to tables. Two patterns cover most real designs.

```sql
CREATE SCHEMA Security;
GO

-- (a) Multitenant via session context
CREATE FUNCTION Security.fn_TenantPredicate(@TenantID int)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN
    SELECT 1 AS ok
    WHERE @TenantID = CAST(SESSION_CONTEXT(N'TenantID') AS int);
GO

-- (b) User/role based
CREATE FUNCTION Security.fn_SalesRepPredicate(@SalesRepID int)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN
    SELECT 1 AS ok
    WHERE @SalesRepID = DATABASE_PRINCIPAL_ID()
       OR IS_MEMBER('SalesManagers') = 1;
GO
```

The application sets context right after authentication:

```sql
EXEC sp_set_session_context @key = N'TenantID', @value = 42, @read_only = 1;
```

Bind the predicate with a policy. Use **filter** predicates to silently hide rows, and **block** predicates so a user can't insert or update a row they'd then be unable to see:

```sql
CREATE SECURITY POLICY Security.TenantPolicy
ADD FILTER PREDICATE Security.fn_TenantPredicate(TenantID) ON dbo.Orders,
ADD FILTER PREDICATE Security.fn_TenantPredicate(TenantID) ON dbo.OrderDetails
WITH (STATE = ON);

CREATE SECURITY POLICY Security.SalesPolicy
ADD FILTER PREDICATE Security.fn_SalesRepPredicate(SalesRepID) ON dbo.Customers,
ADD BLOCK  PREDICATE Security.fn_SalesRepPredicate(SalesRepID) ON dbo.Customers AFTER INSERT,
ADD BLOCK  PREDICATE Security.fn_SalesRepPredicate(SalesRepID) ON dbo.Customers AFTER UPDATE
WITH (STATE = ON);
```

Hierarchical access — managers see their reports' data — is a recursive-CTE predicate. Same recursion shape as any org-chart walk, with the same cost warning: it runs per query on large tables.

```sql
CREATE FUNCTION Security.fn_HierarchyPredicate(@OwnerID int)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN
    WITH Reports AS (
        SELECT EmployeeID, ManagerID
        FROM dbo.Employees
        WHERE EmployeeID = DATABASE_PRINCIPAL_ID()
        UNION ALL
        SELECT e.EmployeeID, e.ManagerID
        FROM dbo.Employees e
        JOIN Reports r ON e.ManagerID = r.EmployeeID
    )
    SELECT 1 AS ok
    WHERE @OwnerID IN (SELECT EmployeeID FROM Reports);
GO
```

Manage and inspect policies directly:

```sql
ALTER SECURITY POLICY Security.TenantPolicy WITH (STATE = OFF);   -- temporarily disable to troubleshoot
ALTER SECURITY POLICY Security.TenantPolicy
    ADD FILTER PREDICATE Security.fn_TenantPredicate(TenantID) ON dbo.Products;
ALTER SECURITY POLICY Security.TenantPolicy
    DROP FILTER PREDICATE ON dbo.Orders;

SELECT p.name AS PolicyName, p.is_enabled,
       o.name AS TargetTable, pred.predicate_definition
FROM sys.security_policies p
JOIN sys.security_predicates pred ON p.object_id = pred.object_id
JOIN sys.objects o ON pred.target_object_id = o.object_id;
```

RLS applies transparently through views and stored procedures, so there's no path around it once it's bound. Keep predicates cheap, and watch for row existence leaking through error-based side channels — a constraint violation on a row the user "can't see" still tells them it exists.

## Layer 4: Permissions, Roles, and Passwordless Identity

This series already covers the basic DCL verbs — `GRANT`, `REVOKE`, `DENY` — in [1.5 — DDL, DML, DCL, TCL](../Series%201%20-%20SQL%20and%20Database%20Foundations/1.5%20-%20DDL%20DML%20DCL%20TCL%20The%20Four%20SQL%20Dialects%20Youre%20Already%20Using.md). What's worth adding here is how those verbs compose at scale: schema-level grants, role design, and identity that doesn't depend on a password anyone can leak.

Grant at the schema level so future objects are automatically covered, and build roles around job function rather than individual users:

```sql
GRANT SELECT  ON SCHEMA::Sales   TO SalesAnalyst;     -- includes tables added later
GRANT EXECUTE ON SCHEMA::Reports TO ReportingUsers;

CREATE ROLE DataReaders;
CREATE ROLE DataWriters;
GRANT SELECT ON SCHEMA::dbo TO DataReaders;
GRANT INSERT, UPDATE, DELETE ON SCHEMA::dbo TO DataWriters;
ALTER ROLE DataReaders ADD MEMBER JohnSmith;
ALTER ROLE DataWriters ADD MEMBER AppService;
ALTER ROLE DataReaders ADD MEMBER DataWriters;          -- nest: writers also read
```

Schema separation gives each team a clean, isolated grant surface instead of a tangle of per-table permissions:

```sql
CREATE SCHEMA Sales AUTHORIZATION dbo;
CREATE SCHEMA HR    AUTHORIZATION dbo;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::Sales TO SalesTeam;
GRANT CONTROL ON SCHEMA::HR TO HRAdministrators;
```

Passwordless is the modern default. Entra identities and managed identities mean there's no secret sitting in a connection string for someone to leak:

```sql
CREATE USER [app-service-identity] FROM EXTERNAL PROVIDER;  -- managed identity
CREATE USER [developer@contoso.com] FROM EXTERNAL PROVIDER; -- Entra user
CREATE USER [DataAnalystsGroup]    FROM EXTERNAL PROVIDER;  -- Entra group
ALTER ROLE db_datareader ADD MEMBER [developer@contoso.com];
ALTER ROLE db_datawriter ADD MEMBER [app-service-identity];
-- connection string: Authentication=Active Directory Managed Identity;Encrypt=True;TrustServerCertificate=False;
```

Least privilege is verified, not assumed — audit the actual result:

```sql
-- Everything granted to one principal
SELECT prin.name AS Principal, perm.permission_name, perm.state_desc, obj.name AS ObjectName
FROM sys.database_permissions perm
JOIN sys.database_principals prin ON perm.grantee_principal_id = prin.principal_id
LEFT JOIN sys.objects obj ON perm.major_id = obj.object_id
WHERE prin.name = 'SalesAnalyst';

-- Effective permissions for the current user on a specific object
SELECT * FROM sys.fn_my_permissions('Sales.Orders', 'OBJECT');

-- Role membership map
SELECT r.name AS RoleName, m.name AS MemberName
FROM sys.database_role_members rm
JOIN sys.database_principals r ON rm.role_principal_id = r.principal_id
JOIN sys.database_principals m ON rm.member_principal_id = m.principal_id;
```

`sys.fn_my_permissions` is the single most useful query in this section — it answers "what can this specific principal actually do here?" instead of forcing you to reconstruct the answer from stacked role memberships.

## Layer 5: Auditing — Accountability That Survives a Compromise

[5.4 — SQL Audit](5.4%20-%20SQL%20Audit%20Track%20Every%20Change%20Every%20User%20Every%20Time.md) already covers the mechanics of `CREATE SERVER AUDIT`, `CREATE SERVER AUDIT SPECIFICATION`, and `CREATE DATABASE AUDIT SPECIFICATION` in depth, along with `sys.fn_get_audit_file` and the forensic queries you'd run against it — that's where to go for the full setup syntax. What's worth adding here is what's genuinely different in an Azure SQL context, and the two design rules that separate audit logs that hold up under compliance review from audit logs that just consume disk.

In Azure SQL, audit data can be routed to Blob storage, Log Analytics, or Event Hubs. With Log Analytics, you query the result in KQL rather than T-SQL:

```kusto
AzureDiagnostics
| where Category == "SQLSecurityAuditEvents"
| where TimeGenerated > ago(7d)
| where action_name_s == "SELECT"
| summarize Count = count() by client_ip_s, server_principal_name_s
| order by Count desc
```

Two design rules matter more than the choice of destination. First, pick a focused set of action groups — `BATCH_COMPLETED_GROUP` is a firehose that both hurts performance and buries the signal you actually need under noise. Second, store the logs separate from the database, ideally on immutable storage, so an attacker who compromises the database itself can't rewrite the record of what they did. Alert on failed logins, off-hours permission changes, and access-volume anomalies — an audit log nobody reviews is evidence after the fact, not a control. Fabric routes audit data through Purview for unified coverage across the workspace.

## Layer 6: Securing AI Service Endpoints

Calling Azure OpenAI or Azure ML directly from the database introduces three threats at once: data exfiltration via crafted prompts, runaway per-call cost, and model probing by anyone with `EXECUTE` rights. Authenticate with managed identity — never a stored key sitting in a credential object waiting to be dumped.

```sql
-- Database-scoped credential backed by the SQL resource's managed identity
CREATE DATABASE SCOPED CREDENTIAL AzureOpenAICredential
WITH IDENTITY = 'Managed Identity',
     SECRET = '{"resourceId": "https://cognitiveservices.azure.com/"}';

CREATE EXTERNAL DATA SOURCE AzureOpenAI
WITH (TYPE = REST,
      LOCATION = 'https://my-aoai.openai.azure.com',
      CREDENTIAL = AzureOpenAICredential);
GO
```

Wrap the call in a procedure, log every invocation for cost and anomaly detection, and gate `EXECUTE` to a dedicated role rather than leaving it open:

```sql
CREATE TABLE dbo.AIEndpointLog (
    LogID int IDENTITY PRIMARY KEY,
    CallTimestamp datetime2 DEFAULT SYSUTCDATETIME(),
    CallerPrincipal nvarchar(128) DEFAULT ORIGINAL_LOGIN(),
    EndpointName nvarchar(256),
    InputLength int,
    ResponseStatus int,
    DurationMs int
);
GO

CREATE PROCEDURE dbo.GetEmbedding
    @InputText nvarchar(max),
    @Embedding nvarchar(max) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @start datetime2 = SYSUTCDATETIME(), @response nvarchar(max);

    EXEC sp_invoke_external_rest_endpoint
        @url        = 'https://my-aoai.openai.azure.com/openai/deployments/text-embedding/embeddings?api-version=2024-02-01',
        @method     = 'POST',
        @payload    = N'{"input":"' + STRING_ESCAPE(@InputText, 'json') + N'"}',
        @credential = AzureOpenAICredential,
        @response   = @response OUTPUT;

    INSERT INTO dbo.AIEndpointLog (EndpointName, InputLength, ResponseStatus, DurationMs)
    VALUES ('text-embedding', LEN(@InputText), 200,
            DATEDIFF(millisecond, @start, SYSUTCDATETIME()));

    SET @Embedding = JSON_VALUE(@response, '$.data[0].embedding');
END;
GO

CREATE ROLE AIFeatureUsers;
GRANT EXECUTE ON dbo.GetEmbedding TO AIFeatureUsers;
ALTER ROLE AIFeatureUsers ADD MEMBER [app-service-identity];
```

Catch abuse before it turns into a surprise bill:

```sql
SELECT CallerPrincipal, COUNT(*) AS Calls, AVG(DurationMs) AS AvgMs
FROM dbo.AIEndpointLog
WHERE CallTimestamp > DATEADD(hour, -1, SYSUTCDATETIME())
GROUP BY CallerPrincipal
HAVING COUNT(*) > 100
ORDER BY Calls DESC;
```

In Fabric, AI access is governed by workspace roles and capacity, not by database-level credentials.

## Layer 7: Securing Data API Endpoints — GraphQL, REST, MCP

These are doors opened on purpose, and each has its own failure mode. A Data API Builder configuration defines authentication, per-entity permissions, and field-level exposure in one place:

```json
{
  "runtime": {
    "rest":    { "enabled": true },
    "graphql": { "enabled": true, "path": "/graphql", "allow-introspection": false }
  },
  "authentication": {
    "provider": "AzureAD",
    "jwt": { "audience": "api://my-api", "issuer": "https://login.microsoftonline.com/{tenant}/v2.0" }
  },
  "entities": {
    "Order": {
      "source": "dbo.Orders",
      "permissions": [
        { "role": "authenticated", "actions": ["read"],
          "fields": { "include": ["OrderID","OrderDate","Status"],
                      "exclude": ["InternalNotes","CostPrice"] } },
        { "role": "admin", "actions": ["*"] }
      ]
    },
    "Product": {
      "source": "dbo.Products",
      "rest": { "enabled": true, "path": "/products" },
      "permissions": [
        { "role": "anonymous",
          "actions": [ { "action": "read", "policy": { "database": "@item.IsPublic eq true" } } ] },
        { "role": "inventory-manager", "actions": ["create","read","update"] }
      ]
    }
  }
}
```

For **GraphQL**, disable introspection in production so the schema can't be enumerated by an attacker probing the API, set field-level includes/excludes so a column like `CostPrice` never leaves even for authenticated reads, and cap query depth and complexity to blunt nested-query denial-of-service attempts. For **REST**, the equivalent is role permissions layered with database policy filters — anonymous callers see only rows where `IsPublic` is true, for example.

**MCP** deserves the tightest leash of the three, because an AI agent may attempt operations a human user never would, and prompt injection is squarely in scope as an attack vector:

```json
{
  "mcpServers": {
    "sqlDatabase": {
      "transport": "stdio",
      "authentication": { "type": "azure-identity", "scope": "https://database.windows.net/.default" },
      "security": {
        "allowedOperations": ["read"],
        "deniedTables": ["dbo.Passwords", "dbo.APIKeys"],
        "maxRowsReturned": 1000
      }
    }
  }
}
```

On validating AI-generated SQL before execution: a `LIKE '%INSERT%'` blocklist is fragile — comments, casing, and encoding tricks slip straight past it. Validate against an **allowlist** of permitted objects and operations instead. A sketch that combines a read-only guard with an explicit table allowlist:

```sql
CREATE PROCEDURE mcp.ExecuteValidatedRead
    @GeneratedQuery nvarchar(max)
AS
BEGIN
    SET NOCOUNT ON;

    -- 1) Read-only guard
    IF EXISTS (SELECT 1 WHERE @GeneratedQuery LIKE '%INSERT%'
                            OR @GeneratedQuery LIKE '%UPDATE%'
                            OR @GeneratedQuery LIKE '%DELETE%'
                            OR @GeneratedQuery LIKE '%DROP%'
                            OR @GeneratedQuery LIKE '%MERGE%'
                            OR @GeneratedQuery LIKE '%EXEC%')
        THROW 50403, 'Write or exec operations are not permitted.', 1;

    -- 2) Allowlist: every base table referenced must be in mcp.AllowedTables
    --    (use sys.dm_exec_describe_first_result_set / real parsing in production;
    --     this illustrates the allowlist posture)
    IF EXISTS (
        SELECT 1
        FROM STRING_SPLIT(@GeneratedQuery, ' ') s
        WHERE s.value LIKE 'dbo.%'
          AND s.value NOT IN (SELECT TableName FROM mcp.AllowedTables)
    )
        THROW 50403, 'Query references a table outside the allowlist.', 1;

    EXEC sp_executesql @GeneratedQuery;
END;
GO
```

If you already run a read-only, multi-engine MCP setup, you have most of this posture in place already — the denied-tables list, the row cap, and allowlist validation are what turn "read-only by convention" into "read-only by enforcement."

## Key Takeaways

- **Match each control to the attacker it stops** — TDE stops stolen media, Always Encrypted stops a privileged DBA, masking stops accidental on-screen exposure, RLS stops wrong-row access, permissions stop the front door, auditing catches what happens after
- **Masking is not access control** — the real value still drives predicate evaluation, so range queries can binary-search a masked value out one bit at a time; anyone with `ALTER` can drop the mask entirely
- **RLS applies transparently through views and procedures** — there's no path around a bound security policy, but watch for row-existence leaks through constraint errors
- **Grant at the schema level and build roles by job function** — individual per-table grants don't scale and don't survive personnel turnover cleanly
- **Passwordless identity removes an entire class of leaked-secret incidents** — `CREATE USER ... FROM EXTERNAL PROVIDER` with managed identities and Entra groups should be the default, not the exception
- **Verify permissions, don't assume them** — `sys.fn_my_permissions` answers "what can this principal actually do" directly, instead of requiring you to reconstruct it from role memberships
- **AI and API endpoints are new attack surface, not exceptions to old rules** — managed identity over stored keys, allowlists over blocklists, and logging every AI call for cost and anomaly detection
- **Security is the composition, not any single layer** — the cheapest moment to design it in is while deciding which column holds the sensitive data, not after an incident
