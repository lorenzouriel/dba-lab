# Capacity Planning, Scaling, and Storage Design for SQL Server

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

Capacity planning done wrong fails in one of two directions, and both are expensive. Overprovision and you're paying for CPU, memory, and storage nobody uses — a quiet, ongoing tax that rarely gets questioned because nothing is actually broken. Underprovision and the failure mode is loud: autogrow events stacking up during a Black Friday traffic spike, a data file expanding in small increments while every write transaction stalls waiting for the extend to finish, at 2 AM, with the business watching the dashboard turn red in real time.

Good capacity planning is what keeps you out of both situations. It's not a one-time sizing exercise done at deployment — it's a recurring discipline of measuring current workload, projecting growth, and making deliberate decisions about scaling and storage before the system forces the decision on you. This article covers how to think about scale-up versus scale-out, the mechanics of a capacity planning process, storage design principles for new databases, and the RAID and OS-level configuration choices that determine how far your storage will actually take you.

---

## Scale Up vs. Scale Out

There are two fundamentally different ways to give SQL Server more room to grow, and picking the wrong one for your workload shape means either overpaying or hitting a wall you can't easily engineer around.

**Scaling up (vertical scaling)** means adding more capacity to a single server — more CPU cores, more RAM, faster or more storage. It's the simpler option operationally: no architectural changes, no data distribution logic, just a bigger box. It works well for workloads with limited parallelism, where a single well-resourced instance can absorb the entire load. Most OLTP systems in the small-to-mid range live comfortably here, and it's usually the first lever to pull because it requires no application changes.

**Scaling out (horizontal scaling)** means distributing the workload across multiple SQL Server instances rather than growing one instance indefinitely. This is the right direction for workloads with high parallelism or that decompose naturally into independent pieces — read replicas fanning out reporting load, sharding a large multi-tenant database across instances by tenant, or separating OLTP and analytical workloads onto dedicated servers. It's more complex to build and operate, but it's the only path once a single server's ceiling — physical or economic — has been reached.

In practice, most systems scale up until vertical scaling stops being cost-effective or a single point of contention (usually I/O or a single writer bottleneck) becomes unavoidable, and only then start scaling out. Deciding this in advance, rather than reactively, is part of what capacity planning is for.

## The Capacity Planning Process

Capacity planning is a cycle, not a checklist you complete once. The steps below form that cycle, and the discipline is revisiting them on a schedule rather than only when something breaks.

**Start with the current workload.** Before projecting anything forward, understand what's happening now: CPU usage, memory pressure, disk I/O patterns, and — just as important — when the peaks happen. A system that's fine on average but saturates every day at 9 AM has a different capacity problem than one under constant, even load.

**Measure size and estimate growth.** Know the current size of data and log files, and build a growth estimate from historical trends rather than guesswork. A table that's grown 15% per quarter for the last two years is a much better predictor of next year's size than an assumption. Combine this with business projections — a planned marketing push or new customer onboarding will move the growth curve in ways historical data alone won't show.

**Put monitoring and alerting in front of the numbers, not behind them.** Track CPU, memory, disk space, and query performance continuously, and set alert thresholds well before resources are actually exhausted — you want the alert to arrive while there's still time to act, not as a postmortem. This is what turns capacity planning from a quarterly spreadsheet exercise into something that catches problems while they're still cheap to fix.

**Decide autogrow policy deliberately.** Autogrow should exist as a safety net, not as the primary growth mechanism. Configure it with a sensible fixed size or percentage — small enough that a single autogrow event doesn't stall the system for too long, large enough that you're not triggering autogrow every few minutes during a load spike. For performance-critical databases, preallocate space manually ahead of expected growth and schedule manual growth events during maintenance windows, so the cost of extending a file is never paid during peak traffic.

**Be cautious about shrinking.** Shrinking reclaims space, but it fragments indexes and costs I/O to perform — the same tradeoff covered in this series' discussion of `AUTO_SHRINK`. Reserve shrinking for genuine, permanent reductions in data volume, not as a routine housekeeping task.

**Keep index maintenance and statistics current as part of the same cycle.** A capacity plan that only tracks raw size misses half the picture — fragmented indexes and stale statistics degrade performance independently of how much free space is on disk.

**Review regularly and document what you find.** Capacity planning has a shelf life; a review done six months ago on a system that's since changed shape is not a review you can trust today. Documenting autogrow settings, growth projections, and past maintenance decisions means the next review — possibly done by someone else — starts from data instead of institutional memory.

**Treat backup and restore as part of capacity, not separate from it.** Backup storage grows with the database, restore time grows with backup size, and both need to be sized and tested as deliberately as the primary data files.

**Loop in stakeholders.** Application developers and business owners know about upcoming launches, migrations, or feature changes that will move the growth curve before it shows up in the metrics. Capacity planning done in isolation from the people driving the roadmap is always reacting a step late.

## Storage Design for New Databases

Storage decisions made at database creation time are expensive to unwind later, which makes them worth getting right up front rather than treating as an afterthought.

Start by understanding the actual workload shape: is it read-heavy or write-heavy, mostly sequential scans or highly random point lookups, OLTP with many small fast transactions or analytical with fewer large ones? This shapes almost every decision that follows. From there, estimate real capacity needs — not just current data volume, but growth over the planning horizon plus space for backups and any archival retention.

I/O performance requirements follow from workload shape: throughput and latency needs driven by concurrent user count, query complexity, and how data is typically retrieved. A reporting database serving a handful of analysts with long-running scans has very different I/O needs than an OLTP system serving thousands of short transactions per second.

Redundancy and availability belong in the storage design from day one — RAID configuration, backup strategy, and failover mechanisms are not things to retrofit after a disk failure teaches the lesson the hard way.

**Separate data and log files onto different physical disks or disk arrays.** Data files see largely random I/O; log files are written sequentially. Mixing them on the same spindles means the sequential log-write pattern gets interrupted by random data I/O, hurting both. This is one of the oldest and still most relevant pieces of SQL Server storage advice.

**Use storage tiering where it fits the access pattern.** Not all data is accessed equally — frequently queried recent data belongs on faster storage, while older, rarely-touched data can live on slower, cheaper storage without a noticeable performance cost. Combined with partitioning large tables (covered in depth elsewhere in this series), tiering lets you control cost without sacrificing performance where it matters.

## RAID Configurations

RAID choice is a tradeoff between raw performance, redundancy, and cost — and the right answer depends entirely on what the database is being used for.

**RAID 0 (striped, no redundancy)** spreads data across multiple disks for maximum performance, but a single disk failure loses everything. There's no scenario in production SQL Server where the performance gain justifies zero fault tolerance — this is a benchmark configuration, not a production one.

**RAID 1 (mirrored)** writes the same data to two or more disks, giving strong redundancy and often improved read performance, at the cost of slightly slower writes and using half your raw capacity. A reasonable choice for log files, where sequential write performance matters and the volume is comparatively small.

**RAID 5 (striped with parity)** balances performance and redundancy with better storage efficiency than mirroring, but write performance suffers from the parity calculation overhead, and it's vulnerable to data loss if a second disk fails during a rebuild. Reasonable for read-heavy workloads where storage efficiency matters more than write throughput.

**RAID 6 (striped with dual parity)** extends RAID 5 with tolerance for two simultaneous disk failures, at the cost of even slower writes than RAID 5. Worth considering for large arrays where rebuild times are long enough that a second failure during rebuild is a realistic risk.

**RAID 10 (mirrored and striped)** combines RAID 1 and RAID 0, delivering both high performance and strong redundancy at the cost of needing more disks for the same usable capacity. This is the standard recommendation for performance-critical SQL Server data files where both read and write throughput matter — the extra hardware cost is usually justified by the workload it's protecting.

As a rule of thumb: RAID 10 for high-performance data files, RAID 1 for log files, and RAID 5/6 where storage efficiency and cost outweigh raw write performance.

## OS Disk Configuration

A handful of OS-level settings consistently make a measurable difference for SQL Server storage performance, and they're cheap to get right at setup time:

- **64 KB allocation unit size** when formatting volumes hosting SQL Server data and log files — this aligns with how SQL Server allocates extents and avoids the overhead of the smaller default allocation unit size.
- **Instant File Initialization** — lets SQL Server skip zeroing new data file space, dramatically speeding up database creation, file growth, and restores. (This applies to data files only; log files must always be zero-initialized for durability reasons.)
- **High Performance power plan** — Windows' default balanced power plan can throttle CPU frequency in ways that hurt latency-sensitive database workloads.
- **Antivirus exclusions on SQL Server data, log, and backup paths** — real-time scanning of files SQL Server is actively writing adds latency and, in rare cases, can interfere with file locking.
- **Lock Pages in Memory** — prevents the OS from paging out SQL Server's buffer pool under memory pressure, which is critical for keeping performance predictable on memory-constrained hosts.
- **Appropriately sized paging file** — even with Lock Pages in Memory enabled, the OS still needs adequate page file space for its own operations.
- **Correct Windows security policy and permissions** on the service account running SQL Server, scoped to what's actually needed.

None of these individually is dramatic, but together they remove a set of avoidable performance taxes that otherwise get misdiagnosed as query or index problems months later.

## Key Takeaways

- **Scale up first, scale out when you have to** — vertical scaling is simpler and covers most workloads; horizontal scaling is for high-parallelism workloads or once a single server's ceiling is reached
- **Capacity planning is a recurring cycle** — assess workload, estimate growth from real trends, monitor continuously, and review on a schedule, not just when something breaks
- **Autogrow is a safety net, not a growth strategy** — preallocate space and schedule manual growth during maintenance windows for performance-critical databases
- **Separate data and log files onto different physical disks** — random data I/O and sequential log I/O interfere with each other when combined
- **RAID 10 for data files, RAID 1 for logs** is the standard starting point; RAID 5/6 trade write performance for storage efficiency
- **OS-level tuning (64 KB allocation units, Instant File Initialization, Lock Pages in Memory, AV exclusions) removes avoidable performance taxes** that otherwise get misdiagnosed as application or query problems
