# Automating Disaster Recovery with dbatools

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

Disaster recovery plans are written once and forgotten — until the disaster. Then they get tested in the worst possible conditions: under pressure, with incomplete information, and a business waiting for its data back. The ones that work are the ones that have been practiced, scripted, and automated enough that execution is mechanical rather than improvisational.

dbatools is a free, open-source PowerShell module that reduces "migrate or recover an entire SQL Server instance" from a multi-hour manual process to a few dozen lines of script. This article covers what dbatools does well, the spectrum of DR options it supports, and a complete server-level backup and recovery routine you can adapt and run.

---

## The DR Options Spectrum

SQL Server disaster recovery isn't one technology — it's a spectrum based on how fast you need to recover and how much you're willing to spend:

| Approach | Complexity | Cost | Recovery Time |
|----------|-----------|------|--------------|
| Backup/Restore | Low | Low | Hours |
| Log Shipping | Medium | Low | Minutes to hours |
| Database Mirroring | Medium | Medium | Minutes (deprecated) |
| Failover Clustering | High | High | Seconds to minutes |
| Always On Availability Groups | High | High | Seconds |
| Geo-replicated Distributed AGs | Very High | Very High | Near-zero |

The simplest approach that meets your RTO/RPO is usually the right one. For many teams, **scheduled backups + offsite copy via Robocopy** covers 90% of realistic scenarios. dbatools automates this end cleanly.

## Installing dbatools

dbatools installs from the PowerShell Gallery:

```powershell
# Install for all users (requires admin)
Install-Module dbatools

# Install for current user (no admin needed)
Install-Module dbatools -Scope CurrentUser
```

Every command has built-in documentation:

```powershell
Get-Help Restore-DbaDatabase -Detailed
Get-Help Export-DbaInstance -Examples
```

To explore what's available:

```powershell
# Find all backup-related commands
Get-Command -Name *backup* -Module dbatools -Type Function

# Find all export commands
Get-Command -Name *export* -Module dbatools -Type Function
```

## Exporting Server-Level Objects

Before migrating or recovering a SQL Server instance, you need more than database files. You need the server-level configuration: logins, SQL Agent jobs, linked servers, Database Mail profiles, sp_configure settings. dbatools exports all of these as executable T-SQL scripts.

```powershell
$sourceInstance = 'WAVES\SQLWAVES'
$exportPath     = '\\WAVES\Backups\SQLWAVES\InstanceExport'

# Export everything: jobs, logins, linked servers, configs, mail profiles
Export-DbaInstance -SqlInstance $sourceInstance -Path $exportPath -Force
```

What this creates in `$exportPath`:

- `logins.sql` — all SQL and Windows logins with hashed passwords
- `jobs.sql` — all SQL Agent job definitions
- `linkedservers.sql` — linked server definitions (note: passwords stored in clear text — protect this file)
- `configurations.sql` — all `sp_configure` settings
- `dbmail.sql` — Database Mail accounts and profiles

These scripts are the "server skeleton" — restoring databases without them gives you data but not a functional instance.

You can also export individual objects:

```powershell
# Export just the SQL Agent jobs
Get-DbaAgentJob -SqlInstance $sourceInstance | Export-DbaScript -Path C:\Temp\jobs.sql

# Export logins with hashed passwords
Export-DbaLogin -SqlInstance $sourceInstance -Path C:\Temp\logins.sql

# Export Database Mail profiles
Get-DbaDbMailProfile -SqlInstance $sourceInstance | Export-DbaScript -Path C:\Temp\mail.sql
```

## Full Instance Backup

Back up all databases — including system databases — from the source instance:

```powershell
$backupPath = '\\WAVES\Backups\SQLWAVES\DatabaseBackups'

Backup-DbaDatabase `
    -SqlInstance      $sourceInstance `
    -Path             $backupPath `
    -Type             Full `
    -CompressBackup `
    -IncludeSystemDbs
```

`-IncludeSystemDbs` captures `master`, `msdb`, and `model` — critical for a full server recovery. `msdb` contains job history, backup history, and Database Mail configuration. Without it, restoring only user databases leaves you rebuilding server configuration by hand.

---

## Restoring to the Target Instance

Restore all databases from the backup path to the target instance:

```powershell
$targetInstance = 'WAVES\SQLWAVES2'

Get-ChildItem -Path $backupPath -Directory |
    Restore-DbaDatabase -SqlInstance $targetInstance -WithReplace
```

dbatools automatically discovers backup files, sorts them into the correct restore order (Full → Differential → Log), and applies them in sequence. The `-WithReplace` flag overwrites existing databases if they already exist on the target.

For generating restore scripts without executing them (useful for review or manual execution):

```powershell
Get-ChildItem -Path $backupPath -Directory |
    Restore-DbaDatabase -SqlInstance $targetInstance -OutputScriptOnly -WithReplace |
    Out-File -FilePath C:\Temp\restore.sql
```

## Applying Exported Server Objects

After databases are restored, run the exported scripts to recreate server-level objects:

```powershell
Get-ChildItem -Path $exportPath -Filter *.sql | ForEach-Object {
    Write-Host "Executing: $($_.FullName)"
    Invoke-DbaQuery -SqlInstance $targetInstance -File $_.FullName
}
```

Run the scripts in this order to avoid dependency failures:
1. `configurations.sql` — server settings
2. `logins.sql` — logins (jobs and linked servers may depend on them)
3. `linkedservers.sql` — linked server definitions
4. `dbmail.sql` — Database Mail profiles
5. `jobs.sql` — SQL Agent jobs (may reference mail profiles and linked servers)

## Complete DR Script

```powershell
$sourceInstance = 'WAVES\SQLWAVES'
$targetInstance = 'WAVES\SQLWAVES2'
$exportPath     = '\\WAVES\Backups\SQLWAVES\InstanceExport'
$backupPath     = '\\WAVES\Backups\SQLWAVES\DatabaseBackups'

# Step 1: Export server-level objects as scripts
Export-DbaInstance -SqlInstance $sourceInstance -Path $exportPath -Force

# Step 2: Back up all databases including system
Backup-DbaDatabase -SqlInstance $sourceInstance -Path $backupPath `
    -Type Full -CompressBackup -IncludeSystemDbs

# Step 3: Restore databases to target instance
Get-ChildItem -Path $backupPath -Directory |
    Restore-DbaDatabase -SqlInstance $targetInstance -WithReplace

# Step 4: Apply server-level scripts to target
Get-ChildItem -Path $exportPath -Filter *.sql | ForEach-Object {
    Invoke-DbaQuery -SqlInstance $targetInstance -File $_.FullName
}

# Step 5: Validate
Test-DbaLastBackup -SqlInstance $targetInstance
Get-DbaAgentJob    -SqlInstance $targetInstance
Get-DbaLogin       -SqlInstance $targetInstance
```

`Test-DbaLastBackup` is one of the most valuable dbatools commands — it actually restores each database to a temporary location, runs DBCC CHECKDB, and reports whether the backup is restorable. This is automated restore testing.

## Log Shipping with dbatools

For near-real-time replication using log shipping:

```powershell
$params = @{
    Source                           = 'localhost\sql2016'
    Destination                      = 'localhost\sql2017'
    Database                         = 'SalesDB'
    BackupNetworkPath                = '\\localhost\backups'
    BackupScheduleFrequencyType      = 'Daily'
    BackupScheduleFrequencyInterval  = 1
    CopyScheduleFrequencyType        = 'Daily'
    CopyScheduleFrequencyInterval    = 1
    CompressBackup                   = $true
    GenerateFullBackup               = $true
    Force                            = $true
}

Invoke-DbaDbLogShipping @params
```

When a failover is needed:

```powershell
Invoke-DbaDbLogShipRecovery -SqlInstance localhost\sql2017 -Database SalesDB
```

## The Trap

**Running DR scripts for the first time during an actual disaster.** Scripts that have never been tested have bugs. Paths that worked in development may not be accessible from the recovery server. Service accounts may lack permissions on the backup share. The target SQL Server version may have subtle compatibility differences.

The right time to discover these problems is during a planned drill, not at 2 AM with stakeholders waiting.

Build a quarterly DR drill into your schedule:

1. Take a full backup of a non-critical production database
2. Run the full DR script against a spare or dev instance
3. Run `Test-DbaLastBackup` and verify the restored database passes CHECKDB
4. Record the actual time from "start" to "database operational"

That elapsed time is your actual RTO — not the theoretical one in your SLA document.

## Key Takeaways

- **dbatools automates full server-level DR** — `Export-DbaInstance` captures server configuration, `Backup-DbaDatabase` captures data, `Restore-DbaDatabase` applies it to a target instance
- **Server-level objects matter as much as databases** — logins, jobs, linked servers, and mail profiles are captured by `Export-DbaInstance` and must be applied to the target after database restore
- **`-IncludeSystemDbs` is essential for full instance recovery** — `msdb` contains job history, backup history, and Database Mail configuration
- **`Test-DbaLastBackup` provides automated restore testing** — it restores each database to a temp location and validates it; run this regularly, not just after something breaks
- **Log shipping with `Invoke-DbaDbLogShipping` enables near-real-time replication** — failover via `Invoke-DbaDbLogShipRecovery` when needed
- **DR scripts must be tested before you need them** — run quarterly drills; time the recovery; fix path and permission issues in a safe environment
