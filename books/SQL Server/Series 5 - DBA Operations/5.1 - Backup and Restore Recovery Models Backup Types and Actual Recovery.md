# Backup and Restore: Recovery Models, Backup Types, and Actual Recovery

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

A database corruption happens at 2 AM on a Saturday. The on-call engineer gets paged. The first question everyone asks is: "When was the last backup?" The second question is: "Can we actually restore from it?"

Those are different questions. Many teams find out the hard way that having backups and being able to restore from them are not the same thing. Backups taken with the wrong recovery model, never tested, or applied in the wrong order can leave you with an unusable database at exactly the moment you need it most.

This article covers how SQL Server's backup system actually works — recovery models, backup types, restore sequences, and the policies that separate teams who recover in minutes from teams who spend hours hoping.

---

## Recovery Models: The Foundation

SQL Server's recovery model controls what gets logged, how much log you need to retain, and what recovery options you have when something goes wrong. Every database has one, and it determines everything else about your backup strategy.

### Simple Recovery Model

The transaction log is automatically truncated after each checkpoint. You can back up the database (Full or Differential), but you **cannot** take log backups — there's nothing to capture.

```sql
ALTER DATABASE SalesDB SET RECOVERY SIMPLE;
```

**What you get:** Minimal log storage, simple backup strategy.

**What you give up:** Point-in-time recovery. If the database fails at 2:47 PM and your last Full backup was at midnight, you lose everything from midnight to 2:47 PM.

**Best for:** Development databases, data warehouses that are rebuilt from source, non-critical systems where some data loss is acceptable.

### Full Recovery Model

Every transaction is fully logged and retained until a log backup captures it. This enables point-in-time recovery — you can restore to any specific moment in the past.

```sql
ALTER DATABASE SalesDB SET RECOVERY FULL;
```

**What you get:** Point-in-time recovery. If something goes wrong at 2:47 PM, you can restore to 2:46 PM.

**What you give up:** The log grows continuously until a log backup runs. You must take regular log backups or the log file grows unbounded.

**Best for:** Production OLTP databases, any system where data loss is measured in minutes or seconds.

### Bulk-Logged Recovery Model

A hybrid: bulk operations (bulk insert, SELECT INTO, index rebuilds) are minimally logged, reducing their I/O overhead. All other transactions are fully logged.

```sql
ALTER DATABASE SalesDB SET RECOVERY BULK_LOGGED;
```

The catch: during periods of bulk operations, point-in-time recovery is not available. If the log backup that covers a bulk operation is needed for recovery, SQL Server requires the original data files.

**Best for:** Temporarily switching to during large data loads in a Full-recovery database, then switching back immediately after.

## Backup Types

Recovery models determine what's possible. Backup types determine what you actually capture.

### Full Backup

A complete snapshot of the database at the moment the backup runs. Self-contained — a full backup alone is sufficient to restore the database to the point the backup completed.

```sql
BACKUP DATABASE SalesDB
TO DISK = 'C:\Backups\SalesDB_Full_20260513.bak'
WITH COMPRESSION, STATS = 10;
```

`STATS = 10` reports progress every 10%. `COMPRESSION` reduces backup size, often significantly.

### Differential Backup

Captures all pages changed since the **last Full backup**. Not incremental (not since the last differential) — always cumulative since the last Full.

```sql
BACKUP DATABASE SalesDB
TO DISK = 'C:\Backups\SalesDB_Diff_20260513.bak'
WITH DIFFERENTIAL, COMPRESSION, STATS = 10;
```

A differential backup is faster to take than a Full and faster to restore than applying many log backups. The tradeoff: it grows larger over time as more pages change since the last Full.

### Log Backup

Captures the transaction log since the last log backup. Only available in Full or Bulk-Logged recovery models. Enables point-in-time recovery and keeps the log from growing indefinitely.

```sql
BACKUP LOG SalesDB
TO DISK = 'C:\Backups\SalesDB_Log_20260513_0200.bak'
WITH COMPRESSION, STATS = 10;
```

Log backups form a chain. Each backup depends on the previous one. A gap in the chain — a missing log backup — breaks point-in-time recovery up to that gap.

### Copy-Only Backup

A Full backup that doesn't affect the backup chain. A regular Full backup resets the differential baseline, meaning any existing differentials become invalid. Copy-Only backups are standalone — they're used for one-off copies, migrations, or testing without disrupting the production backup schedule.

```sql
BACKUP DATABASE SalesDB
TO DISK = 'C:\Backups\SalesDB_CopyOnly_20260513.bak'
WITH COPY_ONLY, COMPRESSION;
```

## The Restore Sequence

Restoring a database requires applying backups in the correct order. Each step except the last must use `WITH NORECOVERY` — this keeps the database in a restoring state, allowing subsequent backups to be applied.

The final step uses `WITH RECOVERY`, which brings the database online.

### Full Restore Only

```sql
-- Restore and bring online immediately
RESTORE DATABASE SalesDB
FROM DISK = 'C:\Backups\SalesDB_Full_20260513.bak'
WITH RECOVERY;
```

### Full + Differential + Log Restore

```sql
-- Step 1: Apply Full backup (leave in restoring state)
RESTORE DATABASE SalesDB
FROM DISK = 'C:\Backups\SalesDB_Full_20260513.bak'
WITH NORECOVERY;

-- Step 2: Apply Differential backup (leave in restoring state)
RESTORE DATABASE SalesDB
FROM DISK = 'C:\Backups\SalesDB_Diff_20260513.bak'
WITH NORECOVERY;

-- Step 3: Apply each Log backup in order (leave in restoring state)
RESTORE LOG SalesDB
FROM DISK = 'C:\Backups\SalesDB_Log_20260513_0200.bak'
WITH NORECOVERY;

RESTORE LOG SalesDB
FROM DISK = 'C:\Backups\SalesDB_Log_20260513_0400.bak'
WITH NORECOVERY;

-- Step 4: Bring the database online
RESTORE DATABASE SalesDB WITH RECOVERY;
```

### Point-in-Time Restore

With Full recovery and log backups, you can stop recovery at a specific moment:

```sql
RESTORE LOG SalesDB
FROM DISK = 'C:\Backups\SalesDB_Log_20260513_1400.bak'
WITH STOPAT = '2026-05-13 13:47:00', RECOVERY;
```

This is how you recover to the moment before a bad deployment or accidental DELETE.

### Post-Restore Integrity Check

After any restore, verify the database is structurally sound before putting it back in production:

```sql
DBCC CHECKDB (SalesDB) WITH NO_INFOMSGS;
```

A successful restore is not the same as a healthy database. Run CHECKDB.

## Backup Policy Templates

The right backup policy depends on your Recovery Point Objective (RPO — how much data loss is acceptable) and Recovery Time Objective (RTO — how long recovery can take).

### Batch / Non-Critical Systems (RPO: hours)

```
Weekly  : Full backup
Daily   : Differential backup
Hourly  : Log backup (if Full recovery; else skip)
```

### Near Real-Time (RPO: 30 minutes)

```
2x Weekly : Full backup
3x Daily  : Differential backup
Hourly    : Log backup
```

### Mission-Critical (RPO: minutes)

```
Daily           : Full backup
Every 3 hours   : Differential backup
Every 15–30 min : Log backup
```

Match your policy to your actual RPO requirement. Over-backing up wastes storage and I/O. Under-backing up means you discover the gap when it's too late.

## Checking Backup History

SQL Server records every backup in `msdb`. Use this to verify your backup schedule is actually running:

```sql
SELECT
    d.name                  AS database_name,
    b.type                  AS backup_type,
    b.backup_start_date,
    b.backup_finish_date,
    b.backup_size / 1048576 AS size_mb,
    b.physical_device_name
FROM msdb.dbo.backupset AS b
INNER JOIN msdb.dbo.backupmediafamily AS bmf
    ON b.media_set_id = bmf.media_set_id
INNER JOIN sys.databases AS d
    ON b.database_name = d.name
WHERE b.backup_start_date > DATEADD(DAY, -7, GETDATE())
ORDER BY b.backup_start_date DESC;
```

If this query shows gaps in your expected backup schedule, investigate before something breaks.

## The Trap

**Never testing restores.** Backups that have never been tested are backups that may not work. Common failure modes discovered only during an actual emergency:

- Backup files written to a local drive that wasn't replicated — the files are on a server that's now corrupted
- Log chain broken because a manual ad-hoc backup reset the differential baseline unexpectedly
- Database restored successfully but DBCC CHECKDB reveals corruption that was already in the backup
- NORECOVERY/RECOVERY sequence applied incorrectly, bringing the database online before all logs were applied

The standard for a backup policy is not "we take backups." It's "we have a tested restore procedure that we've run at least quarterly, and we know exactly how long recovery takes."

Schedule a restore test. Run it against a non-production server. Time it.

## Key Takeaways

- **Recovery model determines what recovery is possible** — Simple allows Full/Differential only; Full enables point-in-time via log backups; Bulk-Logged trades PITR for bulk operation efficiency
- **Backup types serve different roles** — Full is the baseline; Differential is cumulative since last Full; Log is incremental and maintains the chain for PITR; Copy-Only is standalone and doesn't affect the chain
- **Restore order matters** — Full → Differential → Logs in sequence; every step but the last uses `WITH NORECOVERY`; final step uses `WITH RECOVERY` to bring database online
- **STOPAT enables point-in-time recovery** — restore to the minute before a bad event when log backups are in place
- **Run DBCC CHECKDB after every restore** — a successful restore doesn't guarantee a healthy database
- **Test restores on a schedule** — untested backups are not reliable backups; know your RTO before you need it
