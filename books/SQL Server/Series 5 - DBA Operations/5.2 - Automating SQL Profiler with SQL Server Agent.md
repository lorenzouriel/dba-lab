# Automating SQL Profiler with SQL Server Agent

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

SQL Server Profiler is the tool every DBA reaches for when something starts running slow. You open it, configure a trace, watch queries scroll by, and look for the slow ones. It works. But it has a problem: it requires someone to be sitting there watching it.

Performance problems don't schedule themselves for business hours. The query that's killing your system at 3 AM isn't going to wait around for you to launch the GUI. What you need is a trace that runs automatically, captures what you care about, and stores the results so you can analyze them the next morning.

This article covers how to replace interactive Profiler sessions with a stored procedure that creates and manages traces programmatically using the `sp_trace_*` system procedures — then wire it up to a SQL Server Agent job so it runs on a schedule.

---

## Why sp_trace_* Instead of Profiler

SQL Server Profiler is a GUI wrapper around the same server-side trace infrastructure exposed by `sp_trace_create`, `sp_trace_setevent`, and `sp_trace_setstatus`. The difference is that the GUI runs client-side and requires an active connection. The server-side trace runs entirely within SQL Server, with no client dependency, and writes to a file you control.

The result: you can schedule it, automate it, and review it after the fact — without anyone needing to watch it live.

---

## Building the Automated Trace Procedure

The following procedure creates a server-side trace that captures completed batches and RPC calls, filters to queries taking more than 30 seconds, and writes results to a `.trc` file:

```sql
CREATE OR ALTER PROCEDURE dbo.usp_AutomaticallyProfiler
    @TraceFilePath NVARCHAR(500) = N'C:\Traces\AutoTrace',
    @MaxFileSizeMB BIGINT        = 50,
    @StopAfterMinutes INT        = 60
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @TraceId   INT;
    DECLARE @StopTime  DATETIME = DATEADD(MINUTE, @StopAfterMinutes, GETDATE());
    DECLARE @ReturnVal INT;

    -- Create the trace file
    EXEC @ReturnVal = sp_trace_create
        @TraceId    OUTPUT,
        @options    = 2,                  -- 2 = rollover when file reaches max size
        @tracefile  = @TraceFilePath,
        @maxfilesize = @MaxFileSizeMB,
        @stoptime   = @StopTime;

    IF @ReturnVal <> 0
    BEGIN
        RAISERROR('sp_trace_create failed with code %d', 16, 1, @ReturnVal);
        RETURN;
    END

    -- Event 10: RPC:Completed (stored procedure calls)
    EXEC sp_trace_setevent @TraceId, 10, 1,  1;  -- TextData
    EXEC sp_trace_setevent @TraceId, 10, 12, 1;  -- SPID
    EXEC sp_trace_setevent @TraceId, 10, 13, 1;  -- Duration
    EXEC sp_trace_setevent @TraceId, 10, 14, 1;  -- StartTime
    EXEC sp_trace_setevent @TraceId, 10, 15, 1;  -- EndTime
    EXEC sp_trace_setevent @TraceId, 10, 16, 1;  -- Reads
    EXEC sp_trace_setevent @TraceId, 10, 17, 1;  -- Writes
    EXEC sp_trace_setevent @TraceId, 10, 18, 1;  -- CPU

    -- Event 12: SQL:BatchCompleted (ad-hoc queries and batches)
    EXEC sp_trace_setevent @TraceId, 12, 1,  1;
    EXEC sp_trace_setevent @TraceId, 12, 12, 1;
    EXEC sp_trace_setevent @TraceId, 12, 13, 1;
    EXEC sp_trace_setevent @TraceId, 12, 14, 1;
    EXEC sp_trace_setevent @TraceId, 12, 15, 1;
    EXEC sp_trace_setevent @TraceId, 12, 16, 1;
    EXEC sp_trace_setevent @TraceId, 12, 17, 1;
    EXEC sp_trace_setevent @TraceId, 12, 18, 1;

    -- Filter: Duration > 30 seconds (duration is in microseconds)
    -- 30 seconds = 30,000,000 microseconds
    -- Comparison value 4 = greater than or equal to
    EXEC sp_trace_setfilter @TraceId, 13, 0, 4, 30000000;

    -- Start the trace
    EXEC sp_trace_setstatus @TraceId, 1;
END;
```

The column numbers (1, 12, 13, etc.) correspond to standard trace columns:

| Column # | Column Name |
|----------|------------|
| 1 | TextData |
| 12 | SPID |
| 13 | Duration |
| 14 | StartTime |
| 15 | EndTime |
| 16 | Reads |
| 17 | Writes |
| 18 | CPU |

The filter on column 13 (Duration) with comparison 4 (`>=`) and value `30000000` means: only capture queries running 30 seconds or longer. Adjust this threshold based on what counts as "slow" in your environment.

## Reading the Trace Output

Once the trace has run and the file exists, query it directly in T-SQL using `fn_trace_gettable`:

```sql
-- Read the trace file into a queryable rowset
SELECT
    TextData,
    Duration / 1000             AS duration_ms,
    CPU,
    Reads,
    Writes,
    StartTime,
    EndTime,
    SPID
FROM fn_trace_gettable(N'C:\Traces\AutoTrace.trc', DEFAULT)
ORDER BY Duration DESC;
```

`DEFAULT` as the second argument tells SQL Server to read all rollover files (`.trc`, `_1.trc`, `_2.trc`, etc.) if the trace rolled over due to file size limits. This gives you the full dataset regardless of how many files were created.

## Cleaning Up After the Trace

Trace files accumulate. A scheduled cleanup prevents the trace directory from filling up over time:

```sql
-- Delete trace files older than 7 days
-- Requires xp_cmdshell (enable carefully; consider SQL Agent OS steps instead)
EXEC xp_cmdshell 'forfiles /P "C:\Traces" /M "*.trc" /D -7 /C "cmd /c del @file"';
```

A cleaner approach is to handle deletion via a SQL Agent job step that runs an OS command, keeping `xp_cmdshell` disabled.

---

## Wiring It to SQL Server Agent

The value of this approach is automation — a trace that captures slow queries overnight without anyone watching. Set this up as a SQL Server Agent job:

**Job: AutoTrace — Nightly Slow Query Capture**

```
Step 1: Start Trace
  Type: Transact-SQL script
  Command: EXEC dbo.usp_AutomaticallyProfiler
             @TraceFilePath = N'C:\Traces\AutoTrace',
             @MaxFileSizeMB = 100,
             @StopAfterMinutes = 480;  -- 8 hours

Schedule: Daily at 10:00 PM
```

**Job: AutoTrace — Cleanup**

```
Step 1: Delete old trace files
  Type: Operating System (CmdExec)
  Command: forfiles /P "C:\Traces" /M "*.trc" /D -7 /C "cmd /c del @file"

Schedule: Weekly on Sunday at 2:00 AM
```

With both jobs in place, you get 8 hours of slow-query capture every night and automatic cleanup of files older than a week.

## Checking Active Traces

Verify what traces are currently running:

```sql
SELECT
    id          AS trace_id,
    status,     -- 0=stopped, 1=running
    path        AS trace_file,
    max_size,
    stop_time,
    rowcounts   AS rows_captured
FROM sys.traces;
```

To stop a specific trace manually:

```sql
-- Stop trace with ID 2
EXEC sp_trace_setstatus 2, 0;  -- 0 = stop

-- Close and delete it from memory
EXEC sp_trace_setstatus 2, 2;  -- 2 = close
```

Always close traces you stop — a stopped-but-not-closed trace still holds a handle on the trace file.

## The Trap

**Running a trace with no duration filter on a busy OLTP system.** Capturing every `SQL:BatchCompleted` event on a server processing thousands of queries per second generates trace files in the gigabytes within minutes, adds I/O overhead, and produces so much data it's useless for analysis.

Always filter. At minimum, filter on Duration. On very busy systems, also filter on Database ID to scope to the database you care about:

```sql
-- Filter: DatabaseID = 7 (find your database ID with SELECT DB_ID('SalesDB'))
EXEC sp_trace_setfilter @TraceId, 3, 0, 0, 7;  -- Column 3, comparison 0 (=), value 7
```

Also: server-side traces are deprecated in favor of Extended Events (`sys.server_event_sessions`). Extended Events are more efficient and have more filtering options. For new tooling, build on Extended Events. The `sp_trace_*` approach described here is still widely used, well-understood, and useful to know — but Extended Events is the direction Microsoft has invested in for SQL Server 2012 onward.

---

## Key Takeaways

- **`sp_trace_create` starts server-side traces without a GUI connection** — the trace runs inside SQL Server and writes to a file, with no client dependency
- **Filter by Duration to avoid noise** — duration is in microseconds; 30 seconds = 30,000,000; only capture what's actually slow
- **`fn_trace_gettable` reads trace files into T-SQL queries** — sort by Duration, CPU, or Reads to find the worst offenders overnight
- **Always close stopped traces** — `sp_trace_setstatus 0` stops; `sp_trace_setstatus 2` closes and frees the file handle
- **Wire to SQL Agent for unattended capture** — schedule overnight trace runs, analyze results in the morning, and clean up old files automatically
- **Extended Events is the modern alternative** — `sp_trace_*` works and is widely understood, but Extended Events is more efficient for new tooling
