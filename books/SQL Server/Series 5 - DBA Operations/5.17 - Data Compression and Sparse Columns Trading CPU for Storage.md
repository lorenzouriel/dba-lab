# Data Compression and Sparse Columns: Trading CPU for Storage

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

Storage is cheap until it isn't — until the database is large enough that disk cost, backup time, and I/O throughput all start moving together, and every gigabyte saved on disk is a gigabyte less to read, write, and back up. SQL Server's built-in data compression is one of the more underused levers for this: it can shrink table and index storage substantially with a single `ALTER` statement, no application changes required. The cost isn't free — it's CPU, paid every time a compressed page is read or written — but for most OLTP and reporting workloads, that trade is a good one.

This article covers how row and page compression actually work under the hood, how to measure the savings before committing to them, the commands to apply and check compression, and a related but distinct feature — sparse columns — which optimizes storage for a completely different problem: tables with a lot of NULLs.

---

## How Row Compression Works

Row compression changes how SQL Server physically stores row data on a page, without changing the logical data type or requiring any query rewrite. Two mechanisms do the work.

For fixed-length data types — `CHAR`, `INT`, `DATETIME`, and similar — SQL Server normally reserves the full fixed width on disk regardless of the actual value stored. Row compression switches these to a variable-length storage format internally: an `INT` column holding the value `5` is stored using only the bytes actually needed to represent `5`, not the full 4 bytes it would otherwise occupy. The column is still logically an `INT` as far as every query and application is concerned — this is purely a storage-layer optimization.

For variable-length types like `VARCHAR`, row compression removes trailing spaces and unused padding that would otherwise be stored.

The net effect: tables with a high proportion of fixed-length columns, or columns where actual values are frequently much smaller than the declared width (small integers in a `BIGINT` column, short strings in a wide `VARCHAR`), see the largest gains from row compression. A table of mostly `VARCHAR` columns already storing near-full-width strings will see much less benefit, because there's less wasted space to reclaim.

```sql
-- Enable row compression on a table (rebuilds it)
ALTER TABLE dbo.Orders
REBUILD WITH (DATA_COMPRESSION = ROW);
```

## How Page Compression Works

Page compression is a superset of row compression — it applies everything row compression does, then adds two additional layers of compression that operate across the whole page rather than within a single row.

**Prefix compression** looks for a common prefix shared across values in the same column, across all rows on the page, and stores that prefix once, replacing each row's copy of it with a short reference back to the shared prefix. **Dictionary compression** goes further, looking for any repeated values anywhere on the page — not limited to a single column or a shared prefix pattern — and replacing repeated occurrences with references into a page-level dictionary.

This is why page compression tends to perform much better than row compression on tables with repetitive data: status codes, foreign keys with a small number of distinct values, dates clustered in narrow ranges. A table like `dbo.OrderDetails`, where a handful of `ProductID` values repeat across thousands of rows, is exactly the shape of table page compression is built for.

```sql
-- Enable page compression on a table (rebuilds it)
ALTER TABLE dbo.OrderDetails
REBUILD WITH (DATA_COMPRESSION = PAGE);
```

Compression can also be applied at the index level rather than the whole table, and scoped to specific partitions:

```sql
-- Apply page compression to a specific index
ALTER INDEX IX_OrderDetails_ProductID ON dbo.OrderDetails
REBUILD PARTITION = ALL WITH (DATA_COMPRESSION = PAGE);

-- Apply page compression to a specific partition only
ALTER TABLE dbo.OrderDetails
REBUILD PARTITION = 1 WITH (DATA_COMPRESSION = PAGE);
```

Partition-level compression is useful in a tiered storage strategy — older, less frequently accessed partitions can carry heavier compression (and absorb its CPU cost less often, since they're read less), while actively written partitions stay at row compression or uncompressed to keep write overhead low.

Compression can also be set at the filegroup level, so every object placed in that filegroup inherits the setting, which is a convenient way to enforce a compression policy for an entire tier of storage without setting it table by table.

## Estimating Savings Before You Commit

Compression isn't free to apply — rebuilding a large table or index takes time and resources — so it's worth estimating the payoff first rather than compressing everything reflexively.

```sql
EXEC sp_estimate_data_compression_savings
    'dbo', 'OrderDetails', NULL, NULL, 'PAGE';
```

This runs the compression algorithm against a sample of the actual data and reports the estimated size before and after, for both the current object and the requested compression type, without actually changing anything. Running it for both `ROW` and `PAGE` on the same object gives a direct comparison of which is worth the CPU tradeoff for that specific table.

To check what compression is currently applied — useful both before deciding what to change and afterward to confirm it took effect:

```sql
SELECT
    OBJECT_NAME(i.object_id) AS TableName,
    i.name                   AS IndexName,
    p.data_compression_desc  AS CompressionType
FROM sys.indexes AS i
JOIN sys.partitions AS p
    ON i.object_id = p.object_id AND i.index_id = p.index_id
WHERE i.type_desc IN ('CLUSTERED', 'NONCLUSTERED')
  AND OBJECT_NAME(i.object_id) = 'OrderDetails';
```

## The Storage-vs-CPU Tradeoff

The core tradeoff is straightforward to state and easy to get wrong in practice: compression reduces storage footprint and, often, I/O (fewer pages to read means fewer physical reads for the same logical data), but it costs CPU every time a compressed page has to be decompressed for a read or recompressed for a write.

For read-heavy, I/O-bound workloads — reporting tables, historical partitions, anything where disk throughput is the bottleneck and CPU has headroom — this trade is usually a clear win: fewer physical reads outweigh the decompression cost, and total query time often improves rather than degrades. For write-heavy, CPU-bound OLTP tables already running hot on processor time, adding compression overhead to every insert and update can turn a storage win into a throughput loss. There's no universal answer — it has to be evaluated per table, which is exactly what `sp_estimate_data_compression_savings` and a CPU-headroom check are for.

A few practical notes that affect the decision:

- **Row compression is the safer default starting point** — smaller CPU cost, still meaningful savings, and a reasonable choice when you're not sure page compression's extra overhead is worth it for a given table.
- **Data type mix matters** — tables dominated by fixed-length numeric and date columns compress better than tables of long, low-repetition text.
- **Backups aren't compressed by default just because the data is** — compressed data on disk and compressed backups are separate settings; if backup size matters, enable backup compression explicitly as well.
- **Monitor and revisit** — data patterns change, and a compression choice that made sense a year ago may not be optimal today. Periodically re-run the savings estimate as data grows or shifts.

## Sparse Columns: A Different Problem, A Different Tool

Sparse columns solve a related but distinct problem: tables where a column is `NULL` in the overwhelming majority of rows. A normal column reserves storage space regardless of whether the value is `NULL`; a sparse column skips storage entirely for `NULL` values, at the cost of slightly more overhead for the rows that do have a value.

```sql
CREATE TABLE dbo.Products
(
    ProductID       INT PRIMARY KEY,
    ProductName     NVARCHAR(100) NOT NULL,
    DiscontinuedNote NVARCHAR(MAX) SPARSE NULL,
    SeasonalTag     NVARCHAR(50) SPARSE NULL
);
```

Internally, non-`NULL` sparse column values are stored in a separate structure, with a pointer from the main row back to that value — so a row where `DiscontinuedNote` and `SeasonalTag` are both `NULL` pays essentially nothing for either column. This makes sparse columns a good fit for tables with many optional, rarely-populated attributes — product tables with dozens of category-specific fields where any given product only uses a handful of them, for instance — rather than trying to model that shape with a wide table of mostly-`NULL` regular columns, or splitting it into multiple joined tables.

Sparse columns are not a general-purpose optimization — they only pay off when a large majority of values are genuinely `NULL`. Applying `SPARSE` to a column that's populated most of the time adds overhead without the storage benefit that justifies it.

When a table has many sparse columns, querying them individually can get unwieldy. A **column set** collapses all sparse columns in a table into a single untyped XML column, giving a way to select or update the whole group at once:

```sql
CREATE TABLE dbo.Products
(
    ProductID        INT PRIMARY KEY,
    ProductName      NVARCHAR(100) NOT NULL,
    DiscontinuedNote NVARCHAR(MAX) SPARSE NULL,
    SeasonalTag      NVARCHAR(50) SPARSE NULL,
    AllSparseAttrs    XML COLUMN_SET FOR ALL_SPARSE_COLUMNS
);
```

Querying `AllSparseAttrs` returns only the sparse columns that actually have non-`NULL` values for that row, as XML — convenient for applications that need to work generically with a variable set of optional attributes without knowing every possible column name in advance.

## Key Takeaways

- **Row compression uses variable-length storage for fixed types and strips trailing space from variable-length types** — biggest wins on tables with many fixed-length or overallocated columns
- **Page compression adds prefix and dictionary compression on top of row compression** — biggest wins on tables with repetitive values, like foreign keys or status codes
- **`sp_estimate_data_compression_savings` estimates the payoff without changing anything** — run it for both ROW and PAGE before committing
- **Compression trades storage and I/O for CPU** — a clear win for read-heavy, I/O-bound workloads; evaluate carefully for CPU-bound, write-heavy OLTP tables
- **Compression can be scoped to a table, index, partition, or filegroup** — useful for tiering older partitions more aggressively than actively written ones
- **Backup compression is a separate setting from data compression** — enable it explicitly if backup size matters
- **Sparse columns eliminate storage cost for `NULL` values** — effective only when a large majority of values in the column are genuinely `NULL`
- **Column sets group sparse columns into a single queryable XML column** — useful when a table has many optional, sparsely populated attributes
