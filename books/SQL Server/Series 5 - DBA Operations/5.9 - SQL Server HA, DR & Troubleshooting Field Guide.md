# SQL Server HA, DR & Troubleshooting Field Guide
### High Availability · Disaster Recovery · Failover & Recovery Troubleshooting

The companion to the monitoring/performance guide. Same posture: what you actually run and decide, not a feature tour. The discipline here is different from performance work — HA/DR is about **surviving failure with a known, tested recovery path**, so the recurring theme is "you don't have HA/DR until you've tested the failover and the restore."

T-SQL and PowerShell throughout. On-prem WSFC/AG focus with the cloud variations called out.

---

## Part 0 — The Framing: RTO, RPO, and Choosing a Strategy

Every HA/DR decision flows from two numbers. Pin them down before touching any technology:

- **RTO (Recovery Time Objective)** — how long you can be *down*. The clock from outage to service restored. Drives your HA choice.
- **RPO (Recovery Point Objective)** — how much *data* you can lose, measured in time. "15 minutes of RPO" means losing up to 15 minutes of committed transactions is acceptable. Drives your backup/replication frequency.

A third, often forgotten: **RLO (Recovery Level Objective)** — the granularity you must recover to (whole instance? one database? a single table at a point in time?).

The distinction that trips people up: **HA ≠ DR.** High Availability keeps you running through *local* failures (a node dies, a disk fails) with automatic, fast failover — usually same datacenter, shared or synchronized storage. Disaster Recovery is surviving the loss of the *whole site* (datacenter gone, region down) — usually asynchronous, geographically distant, often a manual decision to fail over because you don't auto-fail-over across a continent on a transient network blip. You need both; they solve different problems.

### The decision matrix

| Requirement | Technology | RTO | RPO | Notes |
|---|---|---|---|---|
| Auto-failover, local, zero data loss | **AG (synchronous)** or **FCI** | seconds–minutes | 0 | AG = separate storage; FCI = shared storage |
| Cross-site DR, some data loss OK | **AG (asynchronous)** | minutes (manual) | seconds–minutes | the standard modern DR pattern |
| Cheap DR, simple, no clustering | **Log Shipping** | minutes–hours | = log backup interval | battle-tested, low-tech, no WSFC needed |
| Read-scale offload | **AG readable secondaries** | n/a | n/a | reporting off the secondary |
| Whole-instance protection incl. SQL Agent/logins | **FCI** | seconds | 0 | protects instance-level objects AGs don't |
| Last line of defense, any disaster | **Backups** | hours | = log backup interval | non-negotiable; underpins everything |

Backups are the floor under all of it. AGs and FCIs reduce *downtime*; only backups protect against corruption, accidental `DELETE`, ransomware, and "someone dropped the table." An AG faithfully replicates your `DROP TABLE` to every secondary in milliseconds. **HA technologies are not a backup.**

# PART 1 — FOUNDATIONS

Everything in DR rests on recovery models and the backup chain. Get these wrong and your fancy AG won't save you.

## 1.1 Recovery Models

The recovery model controls how the transaction log behaves and what restore options you have.

| Model | Log behavior | Point-in-time restore? | Use when |
|---|---|---|---|
| **Full** | Log retained until backed up | **Yes** | Production OLTP — anything where RPO < "last full/diff" |
| **Bulk-logged** | Bulk ops minimally logged | Partial (not during bulk ops) | Temporary, during large bulk loads, to shrink log impact |
| **Simple** | Log auto-truncates at checkpoint | **No** | Dev/test, data warehouses you can reload, or where RPO = last full/diff |

```sql
-- Check the model for every database
select name, recovery_model_desc, log_reuse_wait_desc
from sys.databases
order by name;

alter database [YourDB] set recovery full;
```

`log_reuse_wait_desc` is the column to know: it tells you *why* the log can't truncate. The classic value `LOG_BACKUP` means "you're in FULL recovery and haven't backed up the log" — the #1 cause of a transaction log eating the disk. If it says `ACTIVE_TRANSACTION`, something's holding a long transaction open. `AVAILABILITY_REPLICA` means an AG secondary hasn't hardened the log yet.

**The trap:** switching a database to FULL recovery and *not* backing up the log. The log grows forever because nothing truncates it. FULL recovery without log backups gives you all the disk consumption and none of the point-in-time benefit — the worst of both worlds.

## 1.2 Backup Types & the Backup Chain

Three backup types compose into a recovery strategy:

- **Full** — the entire database. The baseline every restore starts from.
- **Differential** — everything changed *since the last full*. Cumulative (each diff contains all prior diffs' changes since the full), so you only ever restore the *latest* diff. Shrinks restore time vs. replaying all logs.
- **Transaction log** — every log record since the last log backup. The chain that gives you **point-in-time** recovery and the smallest RPO. Only available in FULL/bulk-logged.

```sql
-- Full
backup database [YourDB]
to disk = N'\\backup\YourDB\full.bak'
with compression, checksum, stats = 5;

-- Differential
backup database [YourDB]
to disk = N'\\backup\YourDB\diff.bak'
with differential, compression, checksum, stats = 5;

-- Transaction log
backup log [YourDB]
to disk = N'\\backup\YourDB\log_001.trn'
with compression, checksum, stats = 5;
```

Always use **`CHECKSUM`** (verifies page integrity during backup — catches corruption at backup time, not at the 3 a.m. restore) and **`COMPRESSION`** (smaller, faster, cheaper — the CPU cost is almost always worth it). Consider **`VERIFYONLY`** as a follow-up step or `RESTORE VERIFYONLY` to confirm the backup is restorable.

**The backup chain** is the unbroken sequence: `full → (diff) → log → log → log …`. A point-in-time restore replays the chain to your target time. Anything that **breaks the chain** invalidates your ability to restore past that break:
- Switching to SIMPLE recovery (even briefly) truncates the log and breaks the chain — you must take a new full afterward.
- A log backup taken outside your normal job (e.g., an ad-hoc `BACKUP LOG` someone ran to a random path) — that file is now part of the chain and you need it.
- `BACKUP LOG ... WITH TRUNCATE_ONLY` (deprecated, removed) — historically the chain-killer.

```sql
-- Inspect the chain history for a database
select
    bs.database_name,
    bs.backup_start_date,
    bs.type,                       -- D=full, I=diff, L=log
    bs.first_lsn,
    bs.last_lsn,
    bs.backup_size / 1048576.0 as size_mb,
    bmf.physical_device_name
from msdb.dbo.backupset as bs
inner join msdb.dbo.backupmediafamily as bmf
    on bs.media_set_id = bmf.media_set_id
where bs.database_name = N'YourDB'
order by bs.backup_start_date desc;
```

The LSN columns are how restore stitches the chain: each backup's `first_lsn`/`last_lsn` must connect to the next. A gap means a missing backup.

## 1.3 Restore Sequences & Point-in-Time

Restore is the part nobody practices until they need it. The sequence for a full point-in-time recovery:

```sql
-- 1. Restore the full WITH NORECOVERY (leaves DB ready for more restores)
restore database [YourDB]
from disk = N'\\backup\YourDB\full.bak'
with norecovery, replace;

-- 2. Restore the latest differential WITH NORECOVERY
restore database [YourDB]
from disk = N'\\backup\YourDB\diff.bak'
with norecovery;

-- 3. Restore each log backup in order WITH NORECOVERY...
restore log [YourDB]
from disk = N'\\backup\YourDB\log_001.trn'
with norecovery;

-- 4. ...until the final log, where you STOPAT the target time and RECOVER
restore log [YourDB]
from disk = N'\\backup\YourDB\log_002.trn'
with recovery, stopat = N'2026-06-25T14:32:00';
```

The mechanics that matter:
- **`NORECOVERY`** leaves the database in "restoring" state, able to accept more backups. **`RECOVERY`** (the default) runs recovery, rolls back uncommitted transactions, and brings it online — *do this only on the last step*. Recover too early and you must start over.
- **`STOPAT`** gives point-in-time precision down to the moment. Use it to recover to just before a bad `DELETE`. (For more surgical recovery there's `STOPATMARK`/`STOPBEFOREMARK` against named transaction marks.)
- **`REPLACE`** overwrites an existing database — use deliberately.
- **`MOVE`** relocates files when restoring to a different server/path: `with move 'YourDB_data' to 'D:\...\YourDB.mdf', move 'YourDB_log' to 'L:\...\YourDB.ldf'`.

**Tail-log backup** — before restoring over a damaged-but-online database, capture the tail of the log to minimize loss:

```sql
backup log [YourDB]
to disk = N'\\backup\YourDB\tail.trn'
with norecovery, no_truncate;   -- no_truncate works even if the DB is damaged
```

This grabs the transactions since your last log backup, shrinking RPO to near-zero. The restore sequence then ends by applying this tail.

### Specialized restores

- **Page restore** — restore individual corrupt pages (from 823/824 errors or `DBCC CHECKDB`) without restoring the whole database, online in Enterprise. `restore database [DB] page = '1:57' from disk = ... with norecovery;` then apply logs. Huge RTO win when only a few pages are damaged on a large DB.
- **Piecemeal / partial restore** — bring a database online filegroup by filegroup, PRIMARY first, so critical data is available while the rest restores. For very large databases where full restore RTO is unacceptable.
- **File/filegroup restore** — restore just the damaged filegroup, not the whole DB.

# PART 2 — DISASTER RECOVERY

## 2.1 Designing a Backup Strategy

The strategy is dictated by RPO and RTO, not by habit. Work backwards:

- **RPO drives log backup frequency.** RPO of 15 min → log backups every ≤15 min. RPO of 5 min → every 5 min. The log backup interval *is* your worst-case data loss (plus tail-log if recoverable).
- **RTO drives full/diff frequency.** More frequent fulls/diffs = fewer logs to replay = faster restore. A daily full + every-few-hours diff + frequent logs is the common OLTP shape.

A typical production cadence:
- Full: nightly (or weekly full + daily diff for very large DBs)
- Differential: every 4–12 hours
- Log: every 5–15 minutes

**Don't hand-roll this.** Use **Ola Hallengren's Maintenance Solution** — it's the de facto standard, handles backup, integrity checks, and index maintenance with sane defaults, verification, and cleanup. Rolling your own backup jobs is a classic way to discover a gap at the worst time.

Other essentials:
- **Store backups off the production host** — a backup on the same disk that died is no backup. Off-box, ideally off-site (or to cloud, below).
- **Run `RESTORE VERIFYONLY`** or, better, periodic real test restores. A backup you've never restored is a hope, not a backup.
- **Back up `master`, `msdb`, `model`** — system databases hold logins, jobs, and config. People back up user DBs and forget these, then can't rebuild the instance.
- **Record the `dedicated_admin_connection` / encryption keys** — if you use TDE, back up the certificate and private key *separately and securely*. Lose the cert, lose the ability to restore the encrypted backup. This has ended careers.

```sql
-- Back up the TDE certificate — do this and store it somewhere safe and separate
backup master key to file = N'\\secure\masterkey.key'
    encryption by password = N'<strong>';
backup certificate TDE_Cert to file = N'\\secure\tde_cert.cer'
    with private key (
        file = N'\\secure\tde_cert.pvk',
        encryption by password = N'<strong>'
    );
```

## 2.2 Backup to URL (Azure Blob)

Your stack includes Azure — native backup to blob storage is the clean DR-offsite path:

```sql
-- Credential using a SAS token (scoped to the container)
create credential [https://youracct.blob.core.windows.net/backups]
with identity = 'SHARED ACCESS SIGNATURE',
    secret = '<sas-token-without-leading-?>';

backup database [YourDB]
to url = N'https://youracct.blob.core.windows.net/backups/YourDB_full.bak'
with compression, checksum, stats = 5;
```

This gets backups off-site automatically with geo-redundant storage handling the replication. On AWS the analogous pattern is backup to a local path with an agent/lifecycle policy pushing to S3, or using RDS/managed backups if you're on a managed instance.

## 2.3 Testing DR — The Part Everyone Skips

A DR plan you haven't executed is fiction. The mandatory discipline:

1. **Test restores on a schedule** — automate restoring last night's backups to a scratch server and running `DBCC CHECKDB` on the result. This validates the backups *and* the corruption-free state in one move.
2. **Run a full DR drill** — actually fail over to the DR site, run the app against it, measure your *real* RTO. The first drill always surfaces something: a missing login, a hardcoded connection string, a firewall rule, an unbacked-up `msdb` job.
3. **Document the runbook** — exact steps, in order, that someone *other than you* can execute at 3 a.m. while you're unreachable. RTO includes the time to figure out what to do; a good runbook collapses that.
4. **Track orphaned users after restore** — restoring a DB to a different instance leaves users whose SIDs don't match server logins. Fix with `ALTER USER ... WITH LOGIN = ...` (the modern replacement for `sp_change_users_login`).

# PART 3 — HIGH AVAILABILITY TECHNOLOGIES

## 3.1 Always On Availability Groups (the flagship)

The modern HA/DR workhorse (Enterprise; **Basic AGs** in Standard with limits). An AG replicates a *set of databases* across replicas, with automatic failover and readable secondaries.

### Architecture

- **WSFC (Windows Server Failover Cluster)** underpins it — AGs require a cluster for health detection and failover arbitration, but unlike FCI they use **non-shared storage** (each replica has its own copy). On Linux, Pacemaker plays the cluster role.
- **Replicas** — one **primary** (read/write) and up to 8 **secondaries**. Each holds a full synchronized copy of the AG databases.
- **Availability mode** per replica:
  - **Synchronous-commit** — the primary waits for the secondary to *harden* (write to its log) before committing. **Zero data loss**, enables **automatic failover**. Costs commit latency proportional to network round-trip — keep sync replicas close (same site/low-latency).
  - **Asynchronous-commit** — primary commits without waiting. **Near-zero RPO but not zero** (some in-flight loss possible). Manual failover only. This is your *cross-region DR* mode.
- **Listener** — a virtual network name + IP the application connects to. It follows the primary on failover, so the app reconnects transparently without a config change. Multi-subnet listeners (`MultiSubnetFailover=True` in the connection string) handle cross-site IPs.
- **Failover types:**
  - *Automatic* — requires sync-commit + the secondary in SYNCHRONIZED state + healthy. Seconds of RTO.
  - *Manual (planned)* — clean failover with no data loss (waits for sync).
  - *Forced (manual, with data loss)* — for async replicas in a real disaster; you accept the RPO gap.

### Readable secondaries

Secondaries can serve **read-only** traffic — offload reporting, backups, and `DBCC CHECKDB` off the primary. Route via the listener with `ApplicationIntent=ReadOnly` and **read-only routing** configured. Caveats worth knowing:
- Reads on the secondary see data as of the **redo** point — slight lag, not the live primary.
- Read workloads on the secondary get automatic snapshot isolation, which generates **row versions in the secondary's tempdb** — size tempdb accordingly.
- **Backups can run on secondaries** (copy-only full, and log backups) — useful, but the backup chain spans replicas, so coordinate.

### Setup (T-SQL skeleton)

```sql
-- Prereqs: WSFC up, HADR enabled on each instance, endpoints created, DBs in FULL recovery
-- with an initial full+log backup restored WITH NORECOVERY to each secondary.

-- Enable the feature (each instance, then restart SQL service)
-- (done via SQL Server Configuration Manager or:)
-- ALTER SERVER CONFIGURATION SET HADR CLUSTER CONTEXT = ...

-- Create the mirroring endpoint on each replica
create endpoint [Hadr_endpoint]
    state = started
    as tcp (listener_port = 5022)
    for database_mirroring (role = all, encryption = required algorithm aes);

-- Create the AG on the primary
create availability group [AG_Prod]
with (automated_backup_preference = secondary)
for database [YourDB1], [YourDB2]
replica on
    N'SQLNODE1' with (
        endpoint_url = N'TCP://SQLNODE1.domain.com:5022',
        availability_mode = synchronous_commit,
        failover_mode = automatic,
        seeding_mode = automatic,
        secondary_role (allow_connections = read_only)
    ),
    N'SQLNODE2' with (
        endpoint_url = N'TCP://SQLNODE2.domain.com:5022',
        availability_mode = synchronous_commit,
        failover_mode = automatic,
        seeding_mode = automatic,
        secondary_role (allow_connections = read_only)
    ),
    N'SQLNODE3' with (   -- DR replica, different site
        endpoint_url = N'TCP://SQLNODE3.dr.com:5022',
        availability_mode = asynchronous_commit,
        failover_mode = manual,
        seeding_mode = automatic
    );

-- On each secondary, join:
alter availability group [AG_Prod] join;
alter availability group [AG_Prod] grant create any database;   -- for automatic seeding

-- Create the listener
alter availability group [AG_Prod]
add listener N'AGProdListener' (
    with ip ((N'10.0.1.50', N'255.255.255.0')),
    port = 1433
);
```

**`seeding_mode = automatic`** is the modern convenience — SQL streams the database to the secondary over the endpoint, no manual backup/restore. Great for reasonable-sized DBs; for very large ones, manual seeding (backup/restore with NORECOVERY) over a fast path may still be faster.

### AG variants worth knowing

- **Basic AGs** (Standard edition) — one primary, one secondary, single database, no readable secondary, no read-only routing. A two-node cheap HA option.
- **Contained AGs** (2022+) — replicate `master`/`msdb` system objects (logins, jobs, linked servers) *with* the AG, solving the long-standing pain that AGs don't sync instance-level objects. A genuinely big quality-of-life improvement.
- **Distributed AGs** — an AG of AGs, spanning two separate WSFC clusters (even cross-OS, cross-region). The standard pattern for multi-region DR and for migrations.
- **Read-scale AGs** (clusterless) — AGs without WSFC, for pure read-scale-out with no automatic failover. Manual failover only.

## 3.2 Failover Cluster Instances (FCI)

The older, instance-level HA model. Two+ nodes share **common storage** (SAN, Storage Spaces Direct); the SQL Server *instance* runs on one node at a time and fails over to another. The key differences from AG:

- **Protects the entire instance** — logins, SQL Agent jobs, `msdb`, linked servers, everything — because there's one set of databases on shared storage that simply re-mounts on the surviving node. AGs (pre-contained) don't replicate these.
- **Shared storage is a single point of failure** for the data — FCI protects against *node* failure, not *storage* failure. That's why FCI is frequently combined with an AG (FCI for local HA, AG to a DR site for storage/site redundancy).
- **No readable secondary** — the passive node isn't serving anything; it's standby.
- Failover re-mounts storage and restarts the instance on the new node — RTO is seconds to a couple of minutes (recovery of in-flight transactions on startup).

Choose FCI when you need instance-level protection and have shared storage; choose AG when you need readable secondaries, non-shared storage, or cross-site DR. Combine them when you need both.

## 3.3 Log Shipping

The low-tech, rock-solid option. Three jobs on a schedule: **backup** the log on the primary → **copy** it to the secondary → **restore** it on the secondary (in NORECOVERY or STANDBY). No WSFC, no cluster, no shared storage — just SQL Agent jobs and a file share.

- **RPO** = your log backup interval. **RTO** = manual (bring the secondary online, repoint the app).
- **STANDBY mode** makes the secondary **read-only between restores** — a cheap reporting copy, though reads are kicked off during each log restore.
- No automatic failover, no listener — failover is a manual procedure (recover the secondary, redirect connections, ship logs back the other way to re-establish protection).

It's unglamorous and it works. Good for DR to a site where you don't want clustering complexity, for many-database scenarios, or as a secondary safety net alongside an AG. The failure modes are simple and the troubleshooting is just "which of the three jobs broke."

## 3.4 Database Mirroring (legacy)

Deprecated since 2012, but you'll still encounter it. One principal, one mirror, optional witness for automatic failover. High-safety (sync) or high-performance (async) modes — conceptually the precursor to AGs but per-database and limited to one mirror. **Don't build new on it**; migrate existing mirroring to AGs. Knowing it exists matters mainly for inherited environments.

## 3.5 Replication (distribution, not HA)

Transactional/merge/snapshot replication moves data between servers, but it's a **data distribution** tool, not an HA/DR technology — it replicates selected articles, not the whole database with guaranteed consistency for failover. Use it for read-scale to specific subscribers, data integration, or partial replication. Don't confuse it with HA: it has no failover, no automatic recovery semantics, and replicating a subset of tables doesn't give you a recoverable database. Mentioned here mainly so you don't reach for it expecting HA.

## 3.6 Comparison Matrix

| | AG (sync) | AG (async) | FCI | Log Shipping | Mirroring |
|---|---|---|---|---|---|
| Auto failover | Yes | No | Yes | No | Yes (w/ witness) |
| Data loss (RPO) | Zero | Near-zero | Zero | = log interval | Zero/near-zero |
| Storage | Non-shared | Non-shared | **Shared** | Non-shared | Non-shared |
| Readable secondary | Yes | Yes | No | STANDBY (read) | No (snapshot only) |
| Protects instance objects | No¹ | No¹ | **Yes** | No | No |
| Cross-site DR | Limited (latency) | **Yes** | No (shared storage) | Yes | Yes |
| Edition | Enterprise² | Enterprise² | Std/Ent | Std/Ent | Deprecated |
| Requires WSFC | Yes³ | Yes³ | Yes | No | No |

¹ unless Contained AG (2022+). ² Basic AG in Standard. ³ unless clusterless read-scale AG.

# PART 4 — TROUBLESHOOTING HA/DR

The diagnostic surface is different from performance work — you're chasing replication lag, failed failovers, broken chains, and quorum problems. The HADR DMVs and the cluster log are your instruments.

## 4.1 The Core HADR DMVs

```sql
-- Replica health: role, sync state, connection
select
    ag.name as ag_name,
    ar.replica_server_name,
    ars.role_desc,                    -- PRIMARY / SECONDARY
    ars.operational_state_desc,
    ars.connected_state_desc,         -- CONNECTED / DISCONNECTED
    ars.synchronization_health_desc,  -- HEALTHY / PARTIALLY_HEALTHY / NOT_HEALTHY
    ar.availability_mode_desc,
    ar.failover_mode_desc
from sys.availability_groups as ag
inner join sys.availability_replicas as ar
    on ag.group_id = ar.group_id
inner join sys.dm_hadr_availability_replica_states as ars
    on ar.replica_id = ars.replica_id;

-- Per-database sync detail — this is where lag and queues live
select
    db_name(drs.database_id) as database_name,
    ar.replica_server_name,
    drs.synchronization_state_desc,   -- SYNCHRONIZED / SYNCHRONIZING / NOT SYNCHRONIZING
    drs.synchronization_health_desc,
    drs.is_primary_replica,
    drs.log_send_queue_size,          -- KB not yet sent to secondary (DR exposure)
    drs.log_send_rate,
    drs.redo_queue_size,              -- KB received but not yet replayed (failover delay)
    drs.redo_rate,
    drs.last_commit_time,             -- compare across replicas to see lag in time
    drs.secondary_lag_seconds
from sys.dm_hadr_database_replica_states as drs
inner join sys.availability_replicas as ar
    on drs.replica_id = ar.replica_id
order by database_name, ar.replica_server_name;
```

The two queue columns are the heart of AG troubleshooting:
- **`log_send_queue_size`** — data on the primary not yet sent to the secondary. This is your **RPO exposure** — if the primary dies now, this is what you lose (on async). Growing = network or secondary can't keep up.
- **`redo_queue_size`** — data received by the secondary but not yet replayed into its database. This is your **RTO exposure on failover** — the secondary must drain this redo queue before it's fully caught up. A large redo queue means a slow failover.

## 4.2 Synchronization & Latency Issues

When a secondary falls behind (`SYNCHRONIZING` that won't reach `SYNCHRONIZED`, or growing queues):

**Diagnose by which queue is growing:**
- **`log_send_queue` growing** → the primary can't ship logs fast enough. Causes: network bandwidth/latency between replicas, the secondary's log disk can't harden fast enough (back to `WRITELOG`-style I/O analysis on the secondary), or the endpoint is throttled. Check network throughput and the secondary's log file latency.
- **`redo_queue` growing** → logs arrive but the secondary can't *replay* them fast enough. The redo thread is single-threaded-ish per database (parallel redo helps on modern versions but has limits). Causes: secondary undersized (CPU/IO), heavy read workload on the secondary contending with redo, or a long-running read query on the secondary blocking redo (a notorious one — a big report on the readable secondary can *stall redo* and balloon the queue).

```sql
-- Is a long-running query on the secondary blocking redo?  Check waits there:
select session_id, wait_type, wait_time, blocking_session_id
from sys.dm_exec_requests
where wait_type like '%PARALLEL_REDO%'
    or command like '%DB STARTUP%';
```

**Sync-commit latency on the primary** — if writes suddenly got slow after adding a sync replica, look for `HADR_SYNC_COMMIT` waits on the primary. That's the primary waiting for the secondary to harden. Cause is network round-trip or the secondary's log disk. The fix is either faster network/disk or moving that replica to async (accepting the RPO change).

## 4.3 Failover Troubleshooting

**Automatic failover didn't happen when it should have.** Checklist:
- Was the replica in **synchronous-commit** *and* **SYNCHRONIZED** (not just SYNCHRONIZING)? Auto-failover requires SYNCHRONIZED. A secondary that fell behind to SYNCHRONIZING is *not eligible* — this is the most common "why didn't it fail over" answer.
- Is `failover_mode = automatic` on *both* the primary and the target secondary?
- Is the WSFC quorum healthy? No quorum → no failover decision (4.4).
- Check the **flexible failover policy** / health-check timeout — `HealthCheckTimeout`, `FailureConditionLevel`. A too-lenient `FailureConditionLevel` won't trigger on conditions you'd expect to fail over.

```sql
-- Manual planned failover (no data loss — run ON THE TARGET SECONDARY)
alter availability group [AG_Prod] failover;

-- Forced failover WITH DATA LOSS (async replica, real disaster — run on the target)
alter availability group [AG_Prod] force_failover_allow_data_loss;
```

After a **forced failover with data loss**, the old primary (when it returns) is in a `NOT SYNCHRONIZING`/suspended state — you must **resume** data movement, and it may need reseeding if the LSNs diverged. Plan for that; a forced failover isn't clean.

**Where to look when failover misbehaves:** the SQL error log on both replicas, the **WSFC cluster log**, and the AG dashboard in SSMS (it surfaces health and the failover-readiness state visually). Generate the cluster log:

```powershell
# Dump the Windows cluster log for the last hour, in local time
Get-ClusterLog -TimeSpan 60 -Destination C:\Temp -UseLocalTime
# AG/cluster resource state:
Get-ClusterResource | Where-Object { $_.ResourceType -like '*SQL*' }
Get-ClusterGroup
```

## 4.4 WSFC & Quorum

The cluster underneath has to agree on who's alive. **Quorum** is the voting mechanism that prevents **split-brain** (two nodes both thinking they're primary). Each node can have a vote, plus a **witness** (disk, file share, or **cloud/Azure witness**) that breaks ties.

The principle: the cluster stays up only while a **majority of votes** is reachable. Lose quorum → the cluster shuts down to protect data integrity, and your AG goes offline even if a perfectly good node is sitting there. This surprises people: a *network partition* or losing the wrong combination of nodes can take the whole thing down despite healthy SQL instances.

Practical rules:
- **Odd vote count.** With an even number of nodes, add a witness to make it odd. Two-node cluster → always add a witness (you have effectively no fault tolerance without one).
- **Dynamic quorum** (Server 2012 R2+) auto-adjusts votes as nodes leave — generally leave it on; it improves survivability.
- For multi-site, **node weight** matters — don't let the DR site's votes accidentally let it win quorum and fail over on a WAN blip. Configure vote weights so a primary-site outage is a *deliberate* decision.
- **Cloud witness** (Azure blob) is the clean modern tiebreaker for multi-site/cloud, replacing a fragile file-share witness.

```powershell
# Inspect quorum config and node votes
Get-ClusterQuorum
Get-ClusterNode | Select-Object Name, State, DynamicWeight, NodeWeight
# (NodeWeight 0 = no vote; DynamicWeight = current effective vote)
```

When the AG is "down" but SQL looks fine, **check quorum first** — frequently the databases are healthy and the cluster has simply lost its majority.

## 4.5 Readable Secondary Issues

- **Stale reads / lag** — reads reflect the redo point, not the live primary. If users complain of missing recent data, check `redo_queue_size` and `secondary_lag_seconds`. The data isn't lost; it's queued.
- **Reads blocking redo** — covered in 4.2; long reports on the secondary can stall redo. Consider whether that workload belongs there.
- **tempdb pressure on the secondary** — read workloads get forced snapshot isolation → version store in the secondary's tempdb. Size it like a primary.
- **Statistics on read-only secondaries** — the optimizer can't create permanent stats on a read-only DB, so it uses **temporary statistics** in tempdb. Usually fine, but a reason secondary query plans can differ from the primary's.
- **Read-only routing not working** — connections with `ApplicationIntent=ReadOnly` land on the primary anyway. Verify the read-only routing *list* and *URL* are configured on each replica, and that the connection string hits the **listener** (not a node directly).

## 4.6 Backup & Restore Failures

**Broken backup chain** — restore fails with "the log in this backup set begins at LSN X, which is too recent" or "too early." Means a missing backup between two you have. Diagnose with the `msdb.backupset` LSN query (1.2) — find the gap where one backup's `last_lsn` doesn't connect to the next's `first_lsn`. Recovery: you can only restore up to the break; everything after needs a fresh full to re-baseline.

**Restore is slow / RTO blown** — too many log backups to replay (take more frequent diffs), no instant file initialization (grant the SQL service account **Perform Volume Maintenance Tasks** so data file creation during restore skips zeroing — log files still zero), or restoring uncompressed backups over a slow path.

**`RESTORE` fails on a different server** — orphaned users (4.x in DR testing), missing logins, mismatched file paths (use `MOVE`), edition/version downgrade (you can't restore a newer-version or higher-edition-feature backup to an older/lower one), or a different collation.

**Corruption found at restore** — if `RESTORE` or post-restore `DBCC CHECKDB` finds corruption and `CHECKSUM` was *off* during backup, the corruption may have been silently backed up. This is the argument for `WITH CHECKSUM` on every backup and `DBCC CHECKDB` on test-restored copies — you want to find corruption *before* it's your only copy.

```sql
-- Verify a backup is restorable without actually restoring
restore verifyonly from disk = N'\\backup\YourDB\full.bak' with checksum;

-- Inspect what's inside a backup file (files, LSNs, recovery state)
restore headeronly from disk = N'\\backup\YourDB\full.bak';
restore filelistonly from disk = N'\\backup\YourDB\full.bak';
```

## 4.7 Logs & Sources for HA/DR

Where the answers live, by problem:
- **AG sync/failover** → SQL error log on both replicas (logs role changes, lease/health-check timeouts, redo errors), the **AG dashboard** in SSMS, `sys.dm_hadr_*` DMVs, and the **AlwaysOn_health** Extended Events session (the AG equivalent of `system_health` — it auto-captures AG state changes, failovers, and errors).
- **Cluster/quorum** → **WSFC cluster log** (`Get-ClusterLog`), Windows **System** event log (cluster service, network), `Get-Cluster*` cmdlets.
- **Backup/restore** → SQL error log (backup/restore messages land here), `msdb.dbo.backupset` / `restorehistory`, the job history if run via Agent.
- **Corruption** → SQL error log (823/824/825), `DBCC CHECKDB` output, `suspect_pages` table:

# APPENDIX B — Runbook: AG Manual Failover (planned)

```
1. Confirm target secondary is SYNCHRONIZED + HEALTHY:
   query sys.dm_hadr_database_replica_states (redo_queue near 0)
2. Confirm no excessive log_send/redo queue (would mean data not caught up)
3. Notify / enter maintenance window (apps will reconnect via listener)
4. On the TARGET secondary:
     alter availability group [AG] failover;
5. Verify new primary role + databases online + listener resolves to new primary
6. Confirm old primary flipped to secondary and is SYNCHRONIZING/SYNCHRONIZED
7. Validate app connectivity through the listener
8. Document time taken (your real RTO)
```

# APPENDIX C — Runbook: DR Restore (point-in-time)

```
1. Identify the recovery target time (e.g., just before the bad DELETE)
2. Locate the chain: last full + last diff before target + all logs up to target
   (verify LSN continuity via msdb.backupset)
3. If source DB still online: take a TAIL-LOG backup (WITH NORECOVERY, NO_TRUNCATE)
4. Restore full         WITH NORECOVERY, REPLACE  (MOVE files if different paths)
5. Restore latest diff  WITH NORECOVERY
6. Restore each log     WITH NORECOVERY (in order)
7. Final log / tail:    WITH RECOVERY, STOPAT = '<target time>'
8. Post-restore: DBCC CHECKDB, fix orphaned users, validate data at target time
9. Repoint app / re-establish HA protection (reseed AG secondaries from new primary)
```

---

*The throughline: HA reduces downtime, DR survives disasters, backups are the floor under both — and none of it is real until you've tested the failover and the restore. The DMVs that matter most are `log_send_queue_size` (your RPO exposure) and `redo_queue_size` (your failover RTO). When the AG is down but SQL looks healthy, check quorum first.*
