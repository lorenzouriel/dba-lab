# Auditing SQL Server on AWS RDS

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

The T-SQL for SQL Server Audit doesn't change when you move to RDS — `CREATE SERVER AUDIT`, `CREATE SERVER AUDIT SPECIFICATION`, and `CREATE DATABASE AUDIT SPECIFICATION` work exactly as covered earlier in this series (5.4). What changes is everything around that T-SQL: how the audit gets turned on in the first place, where the files actually live, and how you get at them once RDS has rotated them out of instance reach. RDS is a managed service, and managed means you don't have filesystem access or `sysadmin`-level control over the underlying OS — so the mechanics of standing up an audit look different even though the audit objects themselves are identical.

This article is the RDS-specific companion to 5.4. If you haven't read that one, the audit concepts — server audits, server audit specifications, database audit specifications — are explained there. Here, the focus is entirely on what's different when the instance is running on RDS instead of on-prem or an EC2 self-managed box.

---

## The S3 and IAM Prerequisite

On-prem, a `CREATE SERVER AUDIT ... TO FILE` statement just needs a filesystem path SQL Server's service account can write to. On RDS, there's no filesystem you control — audit files ultimately need a home in S3, which means the S3 bucket and the IAM permissions to write to it have to exist before the audit will work.

The IAM role needs a trust policy that allows the `rds.amazonaws.com` service principal to assume it, plus a permissions policy granting `s3:PutObject`, `s3:GetObject`, `s3:ListBucket`, and `s3:GetBucketLocation` scoped to the target bucket. In practice, you rarely hand-write this: the RDS console will offer to create both the bucket and the IAM role automatically when you attach the audit option in the next step, which is the easiest path unless your organization requires IAM resources to be provisioned through its own pipeline (Terraform, CloudFormation, etc.).

---

## The Option Group Mechanism

This is the part that trips people up coming from on-prem SQL Server: RDS SQL Server doesn't use parameter groups to enable auditing. Parameter groups control instance-level configuration values, but SQL Server Audit on RDS is switched on through an **Option Group** instead, using the `SQLSERVER_AUDIT` option.

The workflow is:

1. Create (or modify) an Option Group and add the `SQLSERVER_AUDIT` option — this is where you configure the S3 bucket and IAM role from the prerequisite step above.
2. Attach the option group to the RDS instance.

Attaching the option group does **not** require a reboot, but there's a version floor to be aware of: the instance needs to be running SQL Server 2016 SP1 or later for both server-level and database-level audit specifications to be available on non-Enterprise editions. Below that, some audit capabilities are Enterprise-only, same as on-prem.

Once the option group is attached, the plumbing between SQL Server Audit and S3 is in place, and you create the actual audit objects the normal way — via T-SQL.

---

## Creating the Audit Objects

The syntax matches 5.4 almost exactly, with one forced difference: the file path.

```sql
USE master;
GO

CREATE SERVER AUDIT [Audit-YourInstance]
TO FILE (
    FILEPATH            = N'D:\rdsdbdata\SQLAudit\',  -- fixed path, cannot be changed on RDS
    MAXSIZE             = 100 MB,
    RESERVE_DISK_SPACE  = OFF
)
WITH (
    QUEUE_DELAY = 1000,
    ON_FAILURE  = CONTINUE
);
GO

ALTER SERVER AUDIT [Audit-YourInstance] WITH (STATE = ON);
GO
```

On-prem, `FILEPATH` is your choice. On RDS, it isn't — `D:\rdsdbdata\SQLAudit\` is the fixed, non-configurable location RDS manages internally, and audit files written there get rolled to S3 automatically in the background once the option group is active. You don't choose the path, and you don't manage the S3 upload yourself; RDS handles both.

The server and database audit specifications are unchanged from 5.4:

```sql
-- Server-level: capture logins and failures
CREATE SERVER AUDIT SPECIFICATION [ServerAuditSpec-YourInstance]
FOR SERVER AUDIT [Audit-YourInstance]
    ADD (FAILED_LOGIN_GROUP),
    ADD (SUCCESSFUL_LOGIN_GROUP)
WITH (STATE = ON);
GO

-- Database-level: capture actual statements (roughly equivalent to log_statement = all)
USE SalesDB;
GO

CREATE DATABASE AUDIT SPECIFICATION [DbAuditSpec-SalesDB]
FOR SERVER AUDIT [Audit-YourInstance]
    ADD (SCHEMA_OBJECT_ACCESS_GROUP)
WITH (STATE = ON);
GO
```

`SCHEMA_OBJECT_ACCESS_GROUP` is the closest equivalent to "log every statement" — it captures DML and DDL against objects broadly. It's also the single biggest volume driver in SQL Server Audit on any platform, RDS included, so scope it down to specific tables (`ADD (SELECT, INSERT, UPDATE, DELETE ON dbo.Customers BY PUBLIC)`, as shown in 5.4) rather than the whole schema unless you genuinely need full coverage and have sized the storage for it.

## Reading Audit Data: The Two-Phase Pattern

This is the other real difference from on-prem auditing: because RDS periodically closes and rolls audit files off to S3, where you look for audit data depends on whether the file is still local or has already rolled over.

**Phase one — query on-instance, before rollover.** While a `.sqlaudit` file is still active on the instance's local path, you can query it directly with the standard system function:

```sql
SELECT event_time, action_id, session_id, server_principal_name,
       database_name, object_name, statement, succeeded
FROM sys.fn_get_audit_file('D:\rdsdbdata\SQLAudit\*.sqlaudit', DEFAULT, DEFAULT)
ORDER BY event_time DESC;
```

RDS also exposes an equivalent wrapper function that some environments prefer to use consistently, since it works the same way whether or not you're relying on the exact instance path:

```sql
SELECT * FROM msdb.dbo.rds_fn_get_audit_file('D:\rdsdbdata\SQLAudit\*.sqlaudit', DEFAULT, DEFAULT);
```

**Phase two — query historical files after rollover.** Once RDS closes a file and uploads it to S3 (as a zip archive), it's no longer reachable from `sys.fn_get_audit_file` pointed at the instance path — it's out of the instance's reach entirely. To read historical audit data at that point, download the archive from S3, unzip it, and place it somewhere accessible to a machine with SSMS or `sqlcmd` — then run the same `sys.fn_get_audit_file` query, just pointed at the local file path instead of the RDS path.

This two-phase pattern is the operational reality of RDS auditing: recent activity is queryable in place, but anything that's rolled over requires a retrieve-then-query step. If you need to run audit queries regularly against a rolling window of history — for a compliance report, say — it's worth building a small process that pulls new files from S3 on a schedule rather than doing it manually each time someone asks for a report.

## Key Takeaways

- **The T-SQL is identical to on-prem** — `CREATE SERVER AUDIT`, server and database audit specifications work exactly as covered in 5.4; nothing about the syntax changes on RDS
- **RDS requires an S3 bucket and IAM role before auditing works** — the trust policy must allow `rds.amazonaws.com` to assume the role, with `PutObject`/`GetObject`/`ListBucket`/`GetBucketLocation` on the bucket
- **Auditing is enabled through an Option Group with `SQLSERVER_AUDIT`, not a parameter group** — this is the single biggest structural difference from on-prem
- **The audit file path is fixed** (`D:\rdsdbdata\SQLAudit\`) and not configurable — RDS manages the rollover to S3 automatically
- **Non-Enterprise editions need SQL Server 2016 SP1+** for full server- and database-level audit specification support
- **Reading audit data is a two-phase pattern** — query in place with `sys.fn_get_audit_file` or `rds_fn_get_audit_file` before rollover; download, unzip, and query locally after files land in S3
- **`SCHEMA_OBJECT_ACCESS_GROUP` is the biggest volume driver** — scope database audit specifications to specific tables unless full coverage is genuinely required
