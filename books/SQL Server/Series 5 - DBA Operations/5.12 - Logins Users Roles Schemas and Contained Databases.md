# Logins, Users, Roles, Schemas, and Contained Databases

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

"Who has access to this database?" sounds like a simple question until you try to answer it precisely. Is a login the same thing as access? Does removing someone from Active Directory actually remove their access to SQL Server? Why does the same person sometimes need two separate objects created — one at the server level, one at the database level — just to run a query?

The confusion almost always traces back to one distinction that gets glossed over early and never properly explained: a **login** gets you into the SQL Server instance, and a **user** gets you into a specific database. They are not the same object, they are not automatically linked, and understanding the gap between them is the foundation for everything else in this article — roles, schemas, and contained databases all exist to organize identity and access around that core split.

This article covers identity and grouping in SQL Server: how principals authenticate, how they're organized into roles at both the database and server level, how schemas group objects and simplify permission management, and how contained databases change the picture entirely by removing the server-level dependency altogether. The actual grant/revoke/deny verbs — the mechanics of *giving* permission once someone exists — are already covered in [1.5 — DDL, DML, DCL, TCL](../Series%201%20-%20SQL%20and%20Database%20Foundations/1.5%20-%20DDL%20DML%20DCL%20TCL%20The%20Four%20SQL%20Dialects%20Youre%20Already%20Using.md). This article is about who exists and what group they belong to before any grant ever runs.

## Windows Authentication vs. SQL Server Authentication

SQL Server supports two authentication modes, and the choice between them shapes everything downstream — how credentials are managed, what a connection string looks like, and how much of the identity problem you're outsourcing to the operating system.

**Windows Authentication** (also called Integrated Security) leverages the Windows domain's own security infrastructure. A user who is already authenticated to the domain doesn't need to remember or type a separate SQL Server password — SQL Server trusts the Windows token. This gives you single sign-on and centralizes credential policy (password complexity, expiration, lockout) in one place: Active Directory. It's the default recommendation for any environment where users and applications already live inside a Windows domain.

```sql
-- 1) Create the login at the server level, sourced from a Windows account
CREATE LOGIN [YourDomain\YourWindowsUser] FROM WINDOWS;

-- 2) Create the corresponding user inside the target database
USE YourDatabase;
CREATE USER [YourDomain\YourWindowsUser] FOR LOGIN [YourDomain\YourWindowsUser];
```

**SQL Server Authentication** requires a login name and password managed entirely inside SQL Server, independent of any Windows account. It's the necessary option when a client isn't part of the domain — a non-Windows application, a cross-platform driver, a SaaS integration — but it also means SQL Server itself now owns password policy and credential storage.

```sql
-- 1) Create a SQL Server login with its own password
CREATE LOGIN YourSQLLogin WITH PASSWORD = 'YourPassword';

-- 2) Create the corresponding user inside the target database
USE YourDatabase;
CREATE USER YourSQLLogin FOR LOGIN YourSQLLogin;
```

Notice the two-step pattern repeats in both cases: **create the login** (server-level, controls whether you can connect to the instance at all), then **create the user** (database-level, controls what you can do once connected to a specific database). A login with no corresponding user in a database can authenticate to the server but has no access inside that database. A user without a matching login — an "orphaned user" — can happen after a database restore on a different server, and it's one of the most common post-migration support tickets a DBA fields. The fix is `ALTER USER ... WITH LOGIN = ...` to re-link the orphaned user to an existing login, or creating the missing login outright.

## Database Roles: Grouping Access Inside One Database

A database role is a named group of database users. Instead of granting permissions to twelve individuals one at a time, you grant permissions to a role once, then add and remove members as people join or leave. When someone's job changes, you change their role membership — you don't hunt down and re-grant a dozen individual permissions.

### Built-in database roles

SQL Server ships with a set of fixed database roles that cover the common access patterns out of the box:

| Role | Grants |
|---|---|
| `db_owner` | Full control over the database, including configuration changes |
| `db_datareader` | Read access to all user tables |
| `db_datawriter` | Insert, update, delete on all user tables |
| `db_ddladmin` | Run any DDL — create, alter, drop objects |
| `db_securityadmin` | Manage role membership and permissions |
| `db_accessadmin` | Add or remove users from the database |
| `db_backupoperator` | Back up the database |

These cover the extremes well — a reporting account that only ever needs `db_datareader`, an ETL service account that needs `db_datareader` plus `db_datawriter` — but they're coarse. `db_owner` in particular is a common over-grant: it's convenient during development and dangerous in production, because it hands out configuration control alongside data access. Reach for a custom role before defaulting a real user into `db_owner`.

### Custom database roles

Custom roles let you group users around what your application actually needs, rather than around SQL Server's built-in categories.

```sql
USE YourDatabase;

-- Create a role scoped to a specific function
CREATE ROLE AppAdmins;

-- Add members
EXEC sp_addrolemember 'AppAdmins', 'AdminUser1';
EXEC sp_addrolemember 'AppAdmins', 'AdminUser2';

-- Grant only what the role actually needs
GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.Customers TO AppAdmins;
```

The design principle that makes roles worth the setup cost is least privilege combined with separation of duties: define roles around functional areas (order processing, reporting, customer support) rather than around individuals, grant each role only what its function requires, and review membership periodically as people's jobs change. A role nobody has audited in two years is exactly where over-privileged access quietly accumulates.

## Server Roles: Grouping Access Across the Whole Instance

Server roles are the same idea one level up — instead of grouping access to objects inside one database, they group permissions that apply across the entire SQL Server instance: creating databases, managing logins, configuring server-wide settings.

### Built-in server roles

| Role | Grants |
|---|---|
| `sysadmin` | Full control over the entire instance — every action, every database |
| `serveradmin` | Configure server-wide settings |
| `securityadmin` | Manage logins and their properties |
| `dbcreator` | Create, alter, and drop databases at the instance level |
| `setupadmin` | Add or remove linked servers |
| `processadmin` | Manage SQL Server processes |
| `diskadmin` | Manage disk files |
| `bulkadmin` | Run `BULK INSERT` |

`sysadmin` is the SQL Server equivalent of root — treat membership the same way you'd treat domain admin: a short, known, regularly reviewed list, never a default for a service account that only needs to read data.

### Custom server roles

```sql
-- Create a custom server role
CREATE SERVER ROLE MonitorRole;

-- Add logins
ALTER SERVER ROLE MonitorRole ADD MEMBER MonitorUser1;
ALTER SERVER ROLE MonitorRole ADD MEMBER MonitorUser2;

-- Grant server-wide permissions scoped to the role's actual purpose
GRANT VIEW ANY DEFINITION TO MonitorRole;
GRANT VIEW SERVER STATE TO MonitorRole;
```

This is the pattern for a monitoring tool, a DevOps pipeline account, or any identity that needs visibility across the instance without needing `sysadmin`. `ALTER SERVER ROLE ... DROP MEMBER` reverses membership the same way `sp_droprolemember` does at the database level.

## Schemas: Containers for Objects, Not Just Naming Prefixes

A schema is a namespace inside a database — a container for tables, views, and procedures that also happens to double as a natural permission boundary. `dbo.Customers` and `dbo.Orders` both live in the `dbo` schema; a reporting team's objects might live in a `Reports` schema instead, kept entirely separate.

```sql
CREATE SCHEMA Sales;
CREATE SCHEMA HR;
```

Objects are created inside a schema explicitly:

```sql
CREATE TABLE Sales.Orders (
    OrderID int PRIMARY KEY,
    CustomerID int,
    OrderDate date
);
```

The reason schemas matter for security specifically — beyond organization — is that permissions can be granted at the schema level and automatically apply to every object inside it, including objects created later:

```sql
GRANT SELECT, INSERT, UPDATE ON SCHEMA::Sales TO SalesTeam;
GRANT CONTROL ON SCHEMA::HR TO HRAdministrators;
```

A new table added to `Sales` tomorrow is covered by that `SalesTeam` grant automatically — nobody has to remember to re-grant access on every new object. This is the practical reason production schemas are usually organized by team or subject area rather than left as one flat `dbo` namespace.

Ownership can also move between principals without touching the objects themselves:

```sql
ALTER AUTHORIZATION ON SCHEMA::Sales TO new_owner;
```

## Contained Databases: Removing the Server-Level Dependency

Everything so far assumes the login-then-user two-step: a server-level login that authenticates to the instance, and a database-level user that maps to it. A **contained database** breaks that dependency on purpose. Instead of relying on a server-level login, a contained database stores user authentication information — including passwords, for SQL authentication — entirely within the database itself.

This solves a specific, recurring pain point: moving a database between servers. With a normal database, a restore on a new server routinely produces orphaned users, because the logins that used to exist on the old server don't exist on the new one. A contained database carries its own authentication with it, so the same restore just works — the users authenticate against information stored in the database, not against server-level logins that may or may not be present.

Creating a contained user looks similar to a normal user, but it's created directly with credentials rather than mapped to an existing login:

```sql
USE YourContainedDatabase;
CREATE USER ContainedUser WITH PASSWORD = 'YourPassword';
```

Enabling containment is a two-part configuration. First, the server itself has to allow contained databases:

```sql
sp_configure 'contained database authentication', 1;
RECONFIGURE;
```

Then the individual database's containment level is set — `PARTIAL` is the level currently supported, `NONE` is the default (uncontained):

```sql
ALTER DATABASE YourContainedDatabase
SET CONTAINMENT = PARTIAL;
```

Contained databases are the right fit for scenarios built around portability and isolation: databases that migrate frequently between environments, multi-tenant SaaS platforms where each tenant's database should be self-sufficient, and Azure SQL Database, where the platform-managed nature of the service makes server-level logins a poor fit in the first place — Azure SQL Database uses contained users by default for exactly this reason.

The trade-off is worth naming plainly: contained authentication information lives inside database backups. A backup of a contained database carries usernames and password hashes with it, which changes who needs access to backup files and where those files can safely be stored.

## Key Takeaways

- **Login gets you into the server; user gets you into a database** — they are separate objects, and a login without a matching user has no database access, while a user without a matching login is orphaned (common after cross-server restores)
- **Windows Authentication centralizes credential management in Active Directory**; **SQL Server Authentication is necessary for non-domain clients** but puts SQL Server in charge of password policy
- **Database roles group users inside one database** — prefer custom, function-scoped roles over defaulting real users into `db_owner`
- **Server roles group permissions across the whole instance** — `sysadmin` deserves the same scrutiny as domain admin; use custom server roles for scoped needs like monitoring
- **Schemas are a permission boundary, not just a naming convention** — granting at the schema level automatically covers objects added later, which is why production schemas are usually organized by team or subject area
- **Contained databases store authentication inside the database itself**, eliminating orphaned users after a restore and making the platform-managed model that Azure SQL Database defaults to
