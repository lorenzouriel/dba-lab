# SQL Audit: Track Every Change, Every User, Every Time

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

A row in the accounts table changes. The value is wrong. The business wants to know who changed it, when, and what it was before. Without auditing in place, the answer is "we don't know" — and that answer has a way of ending conversations with auditors, compliance teams, and occasionally regulators.

SQL Server Audit is the built-in mechanism for tracking exactly this: who accessed what data, who changed which objects, and what happened to sensitive tables. It's not optional if you operate under GDPR, LGPD, HIPAA, SOX, or ISO 27001 — and it's good practice regardless.

This article covers SQL Server Audit's three-layer architecture, how to configure auditing for the scenarios that actually matter, and how to query the audit logs for forensic analysis.

---

## Three Layers of SQL Server Audit

SQL Server Audit is structured in three objects, each serving a distinct purpose:

```text
┌──────────────────────────────────────┐
│         Server Audit Object          │  ← Where logs go (file, event log, app log)
└──────────────────────────────────────┘
                    │
       ┌────────────┴───────────┐
       ▼                        ▼
┌──────────────────┐   ┌──────────────────────┐
│  Server Audit    │   │  Database Audit       │
│  Specification   │   │  Specification        │
└──────────────────┘   └──────────────────────┘
  Server-level events    Database-level events
  (logins, permissions)  (SELECT, INSERT, DELETE
                          on specific objects)
```

**1. Server Audit** — defines the destination: a file on disk, the Windows Application Event Log, or the Security Event Log. This is where audit records are written.

**2. Server Audit Specification** — defines server-level events to capture: failed logins, permission changes, server-level configuration changes.

**3. Database Audit Specification** — defined per database; captures data-level events: SELECT, INSERT, UPDATE, DELETE on specific tables or schemas.

## Creating a Server Audit

Start with the audit object — the container that defines where logs go:

```sql
-- Create the audit (write to a file)
CREATE SERVER AUDIT SalesDB_Audit
TO FILE (
    FILEPATH        = 'C:\Audits\',
    MAXSIZE         = 100 MB,
    MAX_ROLLOVER_FILES = 10,
    RESERVE_DISK_SPACE = OFF
)
WITH (
    QUEUE_DELAY     = 1000,     -- milliseconds before flush to disk
    ON_FAILURE      = CONTINUE  -- CONTINUE or SHUTDOWN if audit fails
);

-- Audits start disabled; enable explicitly
ALTER SERVER AUDIT SalesDB_Audit WITH (STATE = ON);
```

`ON_FAILURE = SHUTDOWN` is the strict compliance option — if audit logging fails, SQL Server stops to prevent unaudited activity. `CONTINUE` is the operational choice — auditing failures don't bring down the server. Which is correct depends on your compliance requirements.

## Database Audit Specification

Capture data-access events on specific tables or schemas:

```sql
-- Scope to the SalesDB database
USE SalesDB;
GO

CREATE DATABASE AUDIT SPECIFICATION SalesDB_DataAccess_Audit
FOR SERVER AUDIT SalesDB_Audit
ADD (SELECT, INSERT, UPDATE, DELETE
     ON dbo.Customers BY PUBLIC),
ADD (SELECT, INSERT, UPDATE, DELETE
     ON dbo.Orders BY PUBLIC),
ADD (SELECT, INSERT, UPDATE, DELETE
     ON dbo.OrderDetails BY PUBLIC)
WITH (STATE = ON);
```

`BY PUBLIC` captures activity from all users. You can narrow to a specific login or role:

```sql
ADD (SELECT ON dbo.Customers BY [AppServiceAccount])
```

For broad coverage without listing every table:

```sql
-- Audit all objects in the schema
ADD (SELECT, INSERT, UPDATE, DELETE
     ON SCHEMA::dbo BY PUBLIC)
```

## Server Audit Specification

Capture server-level security events — failed logins, permission grants, role membership changes:

```sql
CREATE SERVER AUDIT SPECIFICATION Server_Security_Audit
FOR SERVER AUDIT SalesDB_Audit
ADD (FAILED_LOGIN_GROUP),         -- All failed login attempts
ADD (LOGIN_CHANGE_PASSWORD_GROUP), -- Password changes
ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP), -- Server role changes
ADD (DATABASE_PERMISSION_CHANGE_GROUP) -- Database permission changes
WITH (STATE = ON);
```

`FAILED_LOGIN_GROUP` is particularly valuable for security monitoring — repeated failures against the same account are a brute-force signal.

## Reading Audit Logs

Audit records are read using `sys.fn_get_audit_file`:

```sql
-- Read all audit events from the audit directory
SELECT
    event_time,
    action_id,
    succeeded,
    server_principal_name   AS login_name,
    database_name,
    object_name,
    statement,
    client_ip
FROM sys.fn_get_audit_file('C:\Audits\SalesDB_Audit_*.sqlaudit', DEFAULT, DEFAULT)
ORDER BY event_time DESC;
```

The wildcard pattern (`*.sqlaudit`) captures all rollover files. The two `DEFAULT` arguments specify offset position — leave them as `DEFAULT` to read all records.

## Common Forensic Queries

**Who accessed the Customers table in the last 24 hours?**

```sql
SELECT
    event_time,
    action_id,
    server_principal_name AS login_name,
    statement,
    client_ip
FROM sys.fn_get_audit_file('C:\Audits\SalesDB_Audit_*.sqlaudit', DEFAULT, DEFAULT)
WHERE object_name = 'Customers'
  AND event_time > DATEADD(HOUR, -24, GETUTCDATE())
ORDER BY event_time DESC;
```

**Failed login attempts (brute force detection):**

```sql
SELECT
    event_time,
    server_principal_name AS attempted_login,
    client_ip,
    statement
FROM sys.fn_get_audit_file('C:\Audits\SalesDB_Audit_*.sqlaudit', DEFAULT, DEFAULT)
WHERE action_id = 'LGIF'  -- LGIF = Login Failed
ORDER BY event_time DESC;
```

**All DML changes to a sensitive table:**

```sql
SELECT
    event_time,
    action_id,            -- 'SL'=SELECT, 'IN'=INSERT, 'UP'=UPDATE, 'DL'=DELETE
    server_principal_name AS login_name,
    database_name,
    schema_name,
    object_name,
    statement
FROM sys.fn_get_audit_file('C:\Audits\SalesDB_Audit_*.sqlaudit', DEFAULT, DEFAULT)
WHERE object_name = 'Customers'
  AND action_id IN ('IN', 'UP', 'DL')
ORDER BY event_time DESC;
```

## Common Action IDs

| action_id | Event |
|-----------|-------|
| `SL` | SELECT |
| `IN` | INSERT |
| `UP` | UPDATE |
| `DL` | DELETE |
| `EX` | EXECUTE |
| `LGIS` | Login Succeeded |
| `LGIF` | Login Failed |
| `LGLO` | Logout |

## Compliance Context

SQL Server Audit is the mechanism that satisfies audit trail requirements under:

- **GDPR/LGPD** — track who accessed personal data (Customers table) and when
- **SOX** — demonstrate that financial data changes have a traceable owner
- **HIPAA** — log access to protected health information
- **ISO 27001** — maintain access logs as part of access control evidence

The combination of `FAILED_LOGIN_GROUP` (detecting unauthorized access attempts) and DML auditing on sensitive tables (detecting unauthorized data access) covers the two most common audit requirements.

---

## The Trap

**Auditing everything without a retention and review process.** Audit files grow continuously. On a busy OLTP system auditing all SELECT activity, you can fill gigabytes per day. Audit files that are never reviewed provide compliance evidence but no operational value.

Two practices make auditing useful rather than just present:

1. **Scope your audit.** Don't capture SELECT on every table unless you need it. Focus on: sensitive tables (personal data, financial data), DDL changes, failed logins, and permission changes. These are the events that matter for both compliance and security.

2. **Schedule regular reviews.** At minimum, query `FAILED_LOGIN_GROUP` weekly. Repeated failures against the same account from the same IP are actionable. Audit logs sitting unread are not a security control — they're just evidence after the fact.

Also: protect the audit files. A user with access to delete the `.sqlaudit` files can remove evidence. Store audit files on a separate drive with restricted permissions, or configure auditing to write to the Windows Security Event Log (requires local admin; harder to tamper with without leaving traces).

## Key Takeaways

- **Three-layer architecture** — Server Audit (destination), Server Audit Specification (server events), Database Audit Specification (data events); all three must be enabled separately
- **`ON_FAILURE = SHUTDOWN` vs `CONTINUE`** — SHUTDOWN is strict compliance (server stops if audit fails); CONTINUE is operational (audit failure doesn't halt SQL Server)
- **`sys.fn_get_audit_file` reads all rollover files** — use wildcard pattern `*.sqlaudit` to capture the full history; filter by `action_id`, `object_name`, or `event_time`
- **`LGIF` action_id for failed logins** — repeated failures from the same IP are a brute-force signal worth automated alerting
- **Scope the audit to what matters** — sensitive tables, DDL changes, failed logins; auditing everything generates noise and fills storage fast
- **Protect audit files** — write to a restricted path or to the Security Event Log; audit records that can be deleted aren't reliable compliance evidence
