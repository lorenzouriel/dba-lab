# CI/CD for SQL: Treat the Database Like Code

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

The manual database deployment is a familiar horror. Someone writes a script, emails it to the DBA, waits for a maintenance window, and if it goes wrong there's no rollback because nobody recorded the exact schema state before the change. Meanwhile three developers editing three features overwrite each other, a 2 a.m. hotfix lands in production but never makes it into the repo, and the next deployment silently reverts it during peak hours.

SQL Database Projects fix this by making the database declarative: you version every object, build it into one artifact, and let tooling compute the change. But the same mechanism that makes it powerful is what makes the guardrails mandatory. SqlPackage deploys by diffing your project against the live database and generating whatever `ALTER`/`CREATE`/`DROP` closes the gap — and it does not respect changes it can't see. Read the whole pipeline as: preview that diff, gate that diff, test that diff.

---

## The Foundation: Projects, .dacpac, and SqlPackage

A SQL database project is your database in file form — one `.sql` file per object, each declaring its desired end state. That's the opposite of migration scripts. You don't accumulate a chain of `ALTER`s and pray they run in order; you maintain the final shape and let the tooling calculate the difference at deploy time.

Use the **SDK-style** format (`Microsoft.Build.Sql`) for anything new. It brings .NET 8+ and cross-platform builds (so Linux CI runners work), NuGet package references for database references, and default globbing so any `.sql` file in the folder is picked up automatically. SDK-style is GA in VS Code and in preview in Visual Studio 2022; note that Visual Studio 2026 supports only the original project format.

```bash
dotnet new sqlproj -n SalesDbProject
```

Drop objects in as files, one declaration each, using the series' canonical schema:

```sql
-- Tables/Customers.sql
CREATE TABLE [dbo].[Customers]
(
    [CustomerID] INT NOT NULL PRIMARY KEY,
    [FirstName]  NVARCHAR(50)  NOT NULL,
    [LastName]   NVARCHAR(50)  NOT NULL,
    [Email]      NVARCHAR(100) NULL
);
```

The build is the safety net. It validates every object reference and checks T-SQL against the target platform set in the `.sqlproj`. Reference a column that doesn't exist and the build fails; use a SQL Server 2025 function while targeting `Sql140` (2017) and the build catches it before it ever reaches a server. Output is a `.dacpac`, a compiled model of the whole schema.

```bash
dotnet build SalesDbProject.sqlproj      # produces bin/Debug/SalesDbProject.dacpac
```

SqlPackage takes it from there. Install it as a cross-platform global tool and publish:

```bash
dotnet tool install --global microsoft.sqlpackage

sqlpackage /Action:Publish \
    /SourceFile:bin/Debug/SalesDbProject.dacpac \
    /TargetConnectionString:"Server=myserver.database.windows.net;Database=SalesDB;Authentication=Active Directory Default"
```

The behavior that matters: for a new database, SqlPackage walks the dependency graph and creates objects in order (referenced tables before the foreign keys that point at them); for an existing database, it diffs and emits only the needed `ALTER`s — two missing columns become one `ALTER TABLE` with both. It's idempotent, so a fifth deploy of the same `.dacpac` changes nothing, and you can fan one `.dacpac` out across a fleet of tenant databases. Before touching production, preview the diff:

```bash
sqlpackage /Action:Script       /SourceFile:...dacpac /TargetConnectionString:"..." /OutputPath:deploy-script.sql
sqlpackage /Action:DeployReport /SourceFile:...dacpac /TargetConnectionString:"..." /OutputPath:report.xml
```

`Script` gives you the exact T-SQL that would run; `DeployReport` gives an XML summary of every `CREATE`, `ALTER`, and `DROP`. Review one before you push.

## Source Control and Reference Data

Because a project is just `.sql` files and a `.sqlproj`, it drops straight into Git, and Git tracks it at the object level — a commit that touches the `Orders` table and one stored procedure shows exactly those two files, not a monolithic migration script.

```bash
cd SalesDbProject
git init
git add .
git commit -m "Initial commit of database project"
```

Group files by object type and keep build artifacts out of the repo:

```
SalesDbProject/
├── SalesDbProject.sqlproj
├── Tables/ Views/ StoredProcedures/
├── Scripts/PreDeployment/  Scripts/PostDeployment/
└── PostDeploy.sql
```

```gitignore
bin/
obj/
*.dacpac
*.user
```

The `.dacpac` is rebuilt on every CI run, so there's no reason to track it. Now the data problem: status codes, lookup tables, region lists, and defaults are as essential as the schema, and they belong in the project. That's what pre- and post-deployment scripts are for. A project supports exactly one of each, declared in the `.sqlproj`:

```xml
<ItemGroup>
    <PreDeploy  Include="prep-db.sql" />
</ItemGroup>
<ItemGroup>
    <PostDeploy Include="PostDeploy.sql" />
</ItemGroup>
```

One script doesn't mean one giant file. Fan out with SQLCMD `:r` includes:

```sql
-- PostDeploy.sql
:r .\Scripts\PostDeployment\seed-order-statuses.sql
:r .\Scripts\PostDeployment\seed-regions.sql
:r .\Scripts\PostDeployment\seed-app-settings.sql
```

Each referenced file must be excluded from the build (or the compiler treats it as a schema object and fails), which is the `Build Remove` + `None Include` pair:

```xml
<ItemGroup>
    <Build Remove="Scripts\PostDeployment\seed-order-statuses.sql" />
    <None  Include="Scripts\PostDeployment\seed-order-statuses.sql" />
</ItemGroup>
```

And because post-deploy runs on every deployment, plain `INSERT`s fail on the second run with duplicate keys. Make seed data idempotent with `MERGE`:

```sql
MERGE INTO [dbo].[OrderStatuses] AS target
USING (VALUES
    (1, N'Pending'), (2, N'Processing'), (3, N'Shipped'),
    (4, N'Delivered'), (5, N'Cancelled')
) AS source ([StatusID], [StatusName])
ON target.[StatusID] = source.[StatusID]
WHEN MATCHED THEN
    UPDATE SET [StatusName] = source.[StatusName]
WHEN NOT MATCHED THEN
    INSERT ([StatusID], [StatusName]) VALUES (source.[StatusID], source.[StatusName]);
```

To confirm what actually got bundled, rename the built `.dacpac` to `.zip` and extract it; a single combined `.sql` per script type holds the merged content.

## Branching, Pull Requests, and Conflicts

The workflow is the standard one, and it works cleanly here precisely because of one-file-per-object: feature branch per change, merge to `main` through PRs, keep `main` deployable.

```bash
git checkout -b feature/add-customer-email
git add .
git commit -m "Add Email column to Customers table"
git push origin feature/add-customer-email
```

The PR diff shows the exact T-SQL that changed, which makes review real rather than a slog through a 500-line migration. The review questions worth asking every time: does the change break existing queries or procedures, are the names consistent, does it need a matching post-deploy update, and does it cause data loss or require a migration path. Wire the project build in as a PR check (a Build Validation branch policy in Azure DevOps, a `pull_request` workflow in GitHub) so a broken reference is caught before merge, not after.

Conflicts are usually two developers editing the same `CREATE TABLE` — one adding `Phone`, one adding `ShippingAddress`. Resolve, stage, commit:

```bash
git checkout feature/add-customer-phone
git pull origin main
# edit Tables/Customers.sql to include both columns
git add Tables/Customers.sql
git commit -m "Resolve merge conflict: include both Phone and ShippingAddress columns"
```

The non-obvious rule: a clean text merge does not mean a valid schema. If one branch renamed a column and another added a procedure referencing the old name, Git merges silently and the project is broken. Always rebuild after resolving:

```bash
dotnet build SalesDbProject.sqlproj
```

Keep branches short-lived so they don't diverge into painful merges.

## Schema Drift: Where "Respect What Exists" Is Literal

Your project says `Customers` has 12 columns. Production has 13, because someone added `LoyaltyTier` through SSMS during an incident and never told the repo. The danger isn't the drift itself — it's the next deploy: SqlPackage diffs, sees a column the project doesn't declare, and drops it. The tooling only respects what's committed, so drift detection is how you make it respect the hotfix too.

Detect drift with schema comparison, which holds any two of {live database, project, `.dacpac`} side by side and groups differences as Create/Alter/Delete. The direction is the whole trick: compare **database to project** to find drift, **project to database** to preview a deploy — same tool, different direction. Tune it to cut noise: ignore whitespace, ignore column order, block on possible data loss, and commit the settings as an `.scmp` so the team runs identical comparisons.

When you find drift, decide who's right. If the hotfix was correct, bring it into the project via schema compare's cherry-pick (accept the index, ignore the monitoring agent's temp table). For automation, extract the live schema to files and let Git report the delta:

```bash
rm -rf SalesDbProject
sqlpackage /Action:Extract \
    /SourceConnectionString:"{connection string}" \
    /TargetFile:SalesDbProject \
    /p:ExtractTarget=SchemaObjectType

git status --porcelain | wc -l          # your automated drift count
```

Then preview before applying anything. `DeployReport` is the one to parse in a pipeline, because it names the dangerous operations — `TableDataMotion`, column drops, clustered index rebuilds — so you can alert on them:

```xml
<DeploymentReport xmlns="http://schemas.microsoft.com/sqlserver/dac/DeployReport/2012/02">
    <Alerts />
    <Operations>
        <Operation Name="Create"><Item Value="[dbo].[Orders].[IX_Orders_CustomerID]" Type="SqlIndex" /></Operation>
        <Operation Name="Alter"><Item Value="[dbo].[Customers]" Type="SqlTable" /></Operation>
    </Operations>
</DeploymentReport>
```

For comparing two artifacts (validating an SSDT-to-SDK conversion, or confirming a pipeline produced the expected `.dacpac`), `DacpacVerify` diffs everything, including pre/post scripts, SQLCMD variables, references, and objects:

```bash
dotnet tool install -g microsoft.dacpacverify
dacpacverify before.dacpac after.dacpac
```

The goal isn't zero drift — it's catching drift before the next deploy turns a hotfix into an outage.

## CI/CD Pipelines

Two stages: build once into a `.dacpac`, then deploy that same artifact through dev, staging, and prod. Building once kills "works in dev, breaks in prod," because the file that passed staging is byte-for-byte the file that hits production.

GitHub Actions, using `azure/sql-action` for the deploy:

```yaml
# .github/workflows/sql-deploy.yml
name: Build and Deploy SQL Project
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Build SQL project
      run: dotnet build ./SalesDbProject.sqlproj -o ./output
    - name: Upload dacpac artifact
      uses: actions/upload-artifact@v4
      with:
        name: dacpac
        path: ./output/SalesDbProject.dacpac

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
    - name: Download dacpac artifact
      uses: actions/download-artifact@v4
      with:
        name: dacpac
    - name: Install SqlPackage
      run: dotnet tool install -g microsoft.sqlpackage
    - uses: azure/login@v2
      with:
        client-id:       ${{ secrets.AZURE_CLIENT_ID }}
        tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
        subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
    - uses: azure/sql-action@v2.3
      with:
        connection-string: ${{ secrets.AZURE_SQL_CONNECTION_STRING }}
        path: './SalesDbProject.dacpac'
        action: 'publish'
```

`azure/sql-action` handles `.dacpac`, `.sqlproj`, and `.sql`, and supports SQL auth, Entra ID, and service principals. If the database has firewall rules, pairing `azure/login` with `azure/sql-action` adds a temporary firewall rule for the runner's IP during deploy and removes it afterward.

Azure DevOps, the equivalent with `SqlAzureDacpacDeployment`:

```yaml
# azure-pipelines.yml
trigger: [main]
pool: { vmImage: 'windows-latest' }

steps:
- task: DotNetCoreCLI@2
  inputs:
    command: 'build'
    projects: './SalesDbProject.sqlproj'
    arguments: '-o $(Build.ArtifactStagingDirectory)'
- task: PublishBuildArtifacts@1
  inputs:
    PathtoPublish: '$(Build.ArtifactStagingDirectory)/SalesDbProject.dacpac'
    ArtifactName: 'dacpac'
- task: SqlAzureDacpacDeployment@1
  inputs:
    azureSubscription: 'your-service-connection'
    AuthenticationType: 'server'
    ServerName: 'your-server.database.windows.net'
    DatabaseName: 'SalesDB'
    SqlUsername: '$(SqlUser)'
    SqlPassword: '$(SqlPassword)'
    deployType: 'DacpacTask'
    DeploymentAction: 'Publish'
    DacpacFile: '$(Build.ArtifactStagingDirectory)/SalesDbProject.dacpac'
```

On Linux agents, or when you want full control, skip the task and call SqlPackage directly:

```yaml
- script: dotnet tool install --global microsoft.sqlpackage
  displayName: 'Install SqlPackage'
- script: |
    sqlpackage /Action:Publish \
      /SourceFile:$(Build.ArtifactStagingDirectory)/SalesDbProject.dacpac \
      /TargetConnectionString:"$(ConnectionString)"
  displayName: 'Deploy database'
```

**Secrets.** A connection string in YAML is a breach waiting to happen. Use GitHub repository or environment secrets (`${{ secrets.NAME }}`, with environment secrets scoped so prod credentials only reach prod jobs), or better, skip passwords entirely with OpenID Connect: `azure/login` authenticates via federated credentials using `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and `AZURE_SUBSCRIPTION_ID`, with nothing to rotate or leak. For centralized management, pull secrets from Azure Key Vault at deploy time and rotate on a schedule.

**Deployment controls.** A pipeline that pushes to prod on every commit with no review is reckless for schema changes. Gate it with environment protection rules (required reviewers, wait timers, deployment-branch restrictions so only `main` reaches prod), branch policies (minimum reviewers, build validation, comment resolution, auto-included reviewers), and `CODEOWNERS` so the database team sees every SQL change:

```
# .github/CODEOWNERS
/SalesDbProject/  @db-team
*.sql             @db-team @dba-lead
```

In Azure DevOps, a branch control check on the service connection locks production credentials to pipelines running in `main`'s context, so a feature-branch pipeline retargeted at prod is simply refused.

## Testing

Three layers, each catching what the previous can't. **Build validation** (the `dotnet build` you already run) proves structural validity — syntax and references. **Unit tests** prove logic — does a procedure return the right result for a known input. **Integration tests** prove objects work together end to end, and cost the most because they need a live instance.

SSDT unit tests follow pre-test / test / post-test (set up data, run the operation, clean up), then validate with test conditions: Row Count, Scalar Value, Expected Schema, plus Data Checksum, Empty/Not Empty ResultSet, and Execution Time. A test that a placed order updates a customer's year-to-date total:

```sql
-- Pre-test: set up a customer, clear prior data
DECLARE @CustomerID INT;
INSERT INTO [dbo].[Customers] (FirstName, LastName) VALUES (N'Test', N'Customer');
SET @CustomerID = SCOPE_IDENTITY();
DELETE FROM [dbo].[Orders] WHERE [CustomerID] = @CustomerID;

-- Test: place an order, verify YTDOrders
DECLARE @RC INT;
EXECUTE @RC = [dbo].[usp_PlaceNewOrder] @CustomerID, 100, GETDATE(), 'O';

SELECT [YTDOrders] FROM [dbo].[Customers] WHERE [CustomerID] = @CustomerID;
-- pair with a Scalar Value condition expecting 100
```

You also need negative tests: canceling an already-shipped order should raise an error, not silently succeed. Mark the generated C# test with `ExpectedSqlException`, and it passes only when the procedure throws with the matching severity and state:

```csharp
[TestMethod()]
[ExpectedSqlException(Severity = 16, MatchFirstError = false, State = 1)]
public void dbo_usp_CancelOrder_FilledOrder_Test()
```

Integration tests want a dedicated database, auto-deployed from the project before each run, reset to a known state, with connection strings externalized so local and CI point at different targets — and never pointed at production. Wire the whole thing into the pipeline so a red test blocks the deploy:

```yaml
# Azure DevOps
- task: VSTest@2
  inputs:
    testAssembly: '**\*Tests.dll'
    searchFolder: '$(System.DefaultWorkingDirectory)'
```

```yaml
# GitHub Actions
- name: Run database unit tests
  run: dotnet test ./SalesDbProjectTests/SalesDbProjectTests.csproj
```

A failing test stops the pipeline before the change reaches staging or production, which is the entire point.

## Key Takeaways

- **A SQL database project is declarative** — one file per object, desired end state, and SqlPackage computes the diff at deploy time instead of you maintaining a chain of migration scripts
- **The `.dacpac` diff will drop what it doesn't know about** — always preview with `Script` or `DeployReport` before deploying to production
- **Build once, deploy everywhere** — the same `.dacpac` that passed staging is the byte-for-byte artifact that reaches production
- **Schema drift is the real danger** — detect it with schema comparison or a scheduled `Extract` + `git status --porcelain`, and decide deliberately whether the drift belongs in the project
- **Seed data must be idempotent** — post-deployment scripts run on every deploy, so use `MERGE`, not plain `INSERT`
- **Gate production with environment protection, branch policies, and `CODEOWNERS`** — and prefer OpenID Connect over stored credentials wherever the platform supports it
- **Three testing layers catch different failures** — build validation (structure), unit tests (logic), integration tests (objects working together)
