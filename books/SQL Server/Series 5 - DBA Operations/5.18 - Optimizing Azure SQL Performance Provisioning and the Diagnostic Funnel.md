# Optimizing Azure SQL Performance: Provisioning and the Diagnostic Funnel

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

"The database is slow" is four different questions wearing one coat. Is it under-provisioned? Are queries scanning instead of seeking? Are writers blocking each other? Did the optimizer pick a bad plan at 2 a.m.? Each question lives at a different layer, and guessing the layer is how you spend a day tuning the wrong thing.

Azure SQL adds a wrinkle the on-premises troubleshooting playbook doesn't cover: before any query-level diagnosis, there's a provisioning ceiling and a set of database-scoped defaults that shape everything downstream. This article covers that ceiling in depth — it's the part of the performance story that's genuinely different in Azure SQL — and then walks the rest of the diagnostic funnel at a summary level, pointing to the articles in this series that already cover DMVs, execution plans, Query Store, and blocking/deadlocks in full depth.

---

## The Diagnostic Funnel

Work top-down, outside in: get the ceiling right, get the concurrency defaults right, then use DMVs to find expensive queries, execution plans to understand why, Query Store to catch regressions over time, and blocking/deadlock tooling to resolve contention. Six layers, each answering a different question:

1. **Provisioning** — is the tier and compute ceiling right for the workload?
2. **Concurrency** — are the isolation-level defaults appropriate?
3. **Expensive queries** — which queries are worth investigating?
4. **Execution plans** — why is a specific query slow?
5. **Query Store** — did something regress since the last deploy?
6. **Blocking and deadlocks** — is contention actively hurting throughput right now?

The bulk of this article lives in layer 1, because that's where Azure SQL differs most from a box you manage yourself.

## Layer 1: The Ceiling — Provisioning and Database Settings

### vCore vs. DTU

Azure SQL Database offers two resource models. **DTU** (Database Transaction Unit) bundles CPU, memory, and I/O into a single blended number — simple to reason about, but opaque when you need to know which resource is actually constrained. **vCore** exposes cores, memory, and storage as separate, direct dials. It maps cleanly onto physical CPU/RAM for migration sizing, and it supports reserved capacity pricing and Azure Hybrid Benefit for licensing savings.

For new work, vCore is the recommendation: higher ceilings, finer-grained scaling, and more pricing flexibility. DTU still shows up in legacy databases, but there's little reason to provision new workloads on it.

### The Three Service Tiers

Within the vCore model, three service tiers trade off latency, storage, and cost differently:

| | General Purpose | Business Critical | Hyperscale |
|---|---|---|---|
| Storage | Remote (Blob) | Local SSD | Decoupled + local SSD cache |
| Latency | 5–10 ms | 1–2 ms | Low (cached) |
| Max IOPS/vCore | 320 | 4,000 | ~5,500 |
| Max storage | 4 TB | 4 TB | 128 TB |
| Replicas | 1, no read replica | 3 + 1 free readable replica | 0–4 configurable |

**General Purpose** covers most workloads — it's the default choice unless you have a specific reason to move off it. **Business Critical** buys sub-2-ms latency and a free readable replica, at roughly 2.7x the cost of General Purpose for the same vCore count; reach for it when latency-sensitive OLTP or read-replica offloading justifies the premium. **Hyperscale** removes the storage and scaling ceiling entirely — up to 128 TB, and you can scale compute without copying data, which matters for databases that are growing fast or need near-instant scale-up.

Compute within any tier is either **provisioned** (fixed vCores, predictable cost, predictable performance) or **serverless** (autoscale within a min/max range, per-second billing, and autopause when idle — available on General Purpose). Serverless is a good fit for dev/test databases and bursty workloads; provisioned is the right default for steady production traffic.

That's the ceiling. Most of the day-to-day performance wins live in the database-scoped settings underneath it — things you change without touching the tier at all.

### MAXDOP

Caps the number of threads a single query can use. Azure SQL defaults to 8, which is right for the widest range of workloads. The one hard rule: never set it to `0` in production, because one analytical query can then grab every scheduler and starve the checkout transaction sitting behind it.

```sql
ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 8;
ALTER DATABASE SCOPED CONFIGURATION FOR SECONDARY SET MAXDOP = 4;  -- a read replica can differ

-- per-query override when one report needs to run single-threaded
SELECT c.CustomerID, SUM(o.TotalAmount)
FROM dbo.Customers AS c
JOIN dbo.Orders AS o ON o.CustomerID = c.CustomerID
GROUP BY c.CustomerID
OPTION (MAXDOP 1);
```

### Automatic Tuning

Catches plan regressions without anyone watching the dashboard. `FORCE_LAST_GOOD_PLAN` is on by default in Azure SQL and reverts a regressed plan to the prior fast one automatically. The index-management options (`CREATE_INDEX`, `DROP_INDEX`) are off by default and should stay off until you've reviewed a few of their recommendations — automatically dropping an index that looked unused but backs an infrequent month-end report is the kind of surprise you want to catch in review, not in production. Every automatic change runs through a validation window (30 minutes to 72 hours) and auto-reverts if it makes things worse.

```sql
ALTER DATABASE CURRENT
SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON,
                      CREATE_INDEX = OFF,
                      DROP_INDEX = OFF);
```

### Compatibility Level

Gates which intelligent query processing features the optimizer is allowed to use. Level 150 introduced batch mode on rowstore, table-variable deferred compilation, and scalar UDF inlining. Level 160 added parameter-sensitive plan optimization and cardinality-estimation feedback. Level 170 adds optional parameter plan optimization. Microsoft never auto-upgrades this setting — a database created years ago is still running on whatever level it was created with, silently missing every optimizer improvement shipped since.

```sql
SELECT name, compatibility_level FROM sys.databases WHERE name = DB_NAME();

ALTER DATABASE CURRENT SET COMPATIBILITY_LEVEL = 170;  -- baseline in test, compare, then prod
```

Move up deliberately, with a Query Store baseline captured first — a compatibility-level bump changes cardinality estimation and can shift plans for queries that were previously stable.

### OPTIMIZE_FOR_AD_HOC_WORKLOADS

A product search with dozens of filter combinations generates a distinct, single-use plan for every combination, and those single-use plans fill the plan cache and evict the ones that actually matter. With this setting on, the engine stores only a small stub on a query's first execution and compiles the full plan on the second — so one-off queries stop paying full plan-cache rent.

```sql
ALTER DATABASE SCOPED CONFIGURATION SET OPTIMIZE_FOR_AD_HOC_WORKLOADS = ON;
```

### Accelerated Database Recovery and the Persistent Version Store

Accelerated Database Recovery (ADR) is always on in Azure SQL and can't be disabled. It keeps recovery time constant regardless of transaction size, makes rollback near-instant, and moves the version store into the database itself — the **persistent version store (PVS)** — rather than `tempdb`.

The trade-off shows up on write-heavy workloads, where every row version gets logged into the PVS. Watch its size, and keep transactions short so cleanup can keep up:

```sql
SELECT persistent_version_store_size_kb / 1024.0 AS pvs_mb
FROM sys.dm_tran_persistent_version_store_stats;
-- compare against total database size; a sudden spike usually means a long-running
-- or aborted transaction that's preventing version cleanup
```

## Layer 2: Concurrency — What's Different in Azure SQL

Isolation levels aren't covered elsewhere in this series, so it's worth naming the three classic anomalies before the Azure-specific behavior. **Dirty read**: you act on another transaction's uncommitted value, which then rolls back. **Nonrepeatable read**: you read the same row twice in one transaction and get two different values. **Phantom read**: you re-run a range query and rows have appeared that weren't there before.

| Level | Dirty | Nonrepeatable | Phantom | Reader/writer blocking |
|---|---|---|---|---|
| READ UNCOMMITTED | Yes | Yes | Yes | No |
| READ COMMITTED (default) | No | Yes | Yes | Yes |
| REPEATABLE READ | No | No | Yes | Yes |
| SERIALIZABLE | No | No | No | Yes (range locks) |
| READ COMMITTED SNAPSHOT | No | Yes | Yes | No |
| SNAPSHOT | No | No | No | No (update conflicts instead) |

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;             -- session-level

ALTER DATABASE CURRENT SET READ_COMMITTED_SNAPSHOT ON;    -- makes READ COMMITTED use row versioning (RCSI)
ALTER DATABASE CURRENT SET ALLOW_SNAPSHOT_ISOLATION ON;   -- enables explicit SNAPSHOT
```

Here's what's specific to Azure SQL: **RCSI is on by default**, so readers never block writers out of the box. And **optimized locking** — also on by default — cuts writer-writer contention through transaction-ID locking and lock-after-qualification, releasing row and page locks as each row is updated instead of holding them until commit. Both of these are engine defaults you inherit for free; on-prem SQL Server requires you to opt in explicitly.

The practical posture: take the defaults. Step up to `SNAPSHOT` when one transaction runs several queries that all need to see the same point-in-time view (a balance report, for instance). Reserve `SERIALIZABLE` for phantom-sensitive logic — reconciliation, inventory reservation — and accept that it reintroduces the deadlocks the other levels avoid. `SNAPSHOT` raises an update conflict (error 3960) instead of silently clobbering a concurrent write, so make sure the calling code handles that error.

The cleaner fix for the classic oversell scenario, though, isn't a heavier isolation level at all — it's not reading-then-writing in the first place. Make the decrement atomic and let the predicate do the guarding:

```sql
UPDATE dbo.Products
SET StockCount = StockCount - 1
WHERE ProductID = 42 AND StockCount > 0;   -- the predicate is the guard

IF @@ROWCOUNT = 0
    THROW 50010, 'Out of stock', 1;        -- nobody ends up with a negative count
```

Whatever isolation level you land on, keep transactions short. A transaction held open across a user prompt or an external API call holds locks and PVS space, and concurrency grinds to a halt around it.

For the full blocking-chain and deadlock-graph diagnostic toolkit — head-blocker queries, wait-type triage, `system_health` Extended Events deadlock extraction — see [5.8 — SQL Server DBA Field Guide] and [5.10 — SQL Server Troubleshooting Cheat Sheet]. That ground won't be repeated here.

## Layer 3: Finding Expensive Queries

DMVs tell you which queries are even worth opening a plan for. The aggregate view, ranked by average CPU:

```sql
SELECT TOP 10
    qs.total_worker_time / qs.execution_count AS avg_cpu_time,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count AS avg_logical_reads,
    SUBSTRING(st.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
              ELSE qs.statement_end_offset END - qs.statement_start_offset)/2)+1) AS query_text
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
ORDER BY avg_cpu_time DESC;
```

Weigh average cost against execution count — a heavy query that runs once a day matters less than a moderate one running thousands of times an hour. Re-sort by `avg_logical_reads` to surface I/O hogs, which usually points at a missing index.

The missing-index DMVs rank optimization opportunities across the whole workload:

```sql
SELECT mid.statement AS table_name,
       mid.equality_columns, mid.inequality_columns, mid.included_columns,
       migs.avg_total_user_cost * migs.avg_user_impact *
           (migs.user_seeks + migs.user_scans) AS improvement_measure
FROM sys.dm_db_missing_index_groups AS mig
JOIN sys.dm_db_missing_index_group_stats AS migs ON migs.group_handle = mig.index_group_handle
JOIN sys.dm_db_missing_index_details AS mid ON mig.index_handle = mid.index_handle
ORDER BY improvement_measure DESC;
```

These are suggestions, not directives — they only reflect what's currently in the plan cache, and every proposed index trades read speed against write overhead. Test before shipping. For the deeper treatment of index design and query-optimization technique, see [3.1 — Indexes Deeply Explained] and [3.4 — 10 Query Optimization Techniques That Actually Work].

## Layer 4: Reading Execution Plans

An execution plan is the optimizer's chosen strategy, picked by lowest estimated cost. The **estimated** plan is compile-time only; the **actual** plan adds real row counts, timings, memory grants, and warnings — that's where the truth lives.

```sql
SET STATISTICS XML ON;   -- or "Include Actual Execution Plan" in SSMS
-- run the query
SET STATISTICS XML OFF;
```

At a glance, the things worth checking: scan vs. seek (a scan isn't automatically wrong on a small table), estimated-vs-actual row divergence (a sign of stale statistics), key lookups (fixable with an `INCLUDE`d index), and implicit conversions (a silent type mismatch that turns a seek into a scan):

```sql
-- column is varchar; passing nvarchar (N'...') forces a column-wide convert -> scan
WHERE ProductNumber = N'BK-1234';   -- bad
WHERE ProductNumber = 'BK-1234';    -- sargable, uses the index
```

This series already covers execution-plan reading and index design in depth in [3.1 — Indexes Deeply Explained] and [3.4 — 10 Query Optimization Techniques That Actually Work] — treat this section as the pointer, not the destination.

## Layer 5: Query Store for Regressions

[4.3 — SQL Server Query Store: The Flight Recorder for Your Database] already covers the Regressed Queries workflow, `sp_query_store_force_plan` / `sp_query_store_unforce_plan`, and `FORCE_LAST_GOOD_PLAN` in full. Two things from that toolkit are worth adding here because they didn't come up there.

**Query Store hints.** You can attach a hint to a query without touching application code, overriding any hard-coded statement hints or plan guides:

```sql
EXEC sp_query_store_set_hints @query_id = 42, @query_hints = N'OPTION (RECOMPILE)';                        -- fight parameter sniffing
EXEC sp_query_store_set_hints @query_id = 42, @query_hints = N'OPTION (MAXDOP 1, MAX_GRANT_PERCENT = 10)';
EXEC sp_query_store_clear_hints @query_id = 42;
```

**The read-only trap.** Query Store silently flips to `READ_ONLY` when it fills up, and stops collecting new data — including, in Azure SQL, the data that feeds Query Performance Insight in the portal. You won't notice until you need the history that was never captured.

```sql
SELECT actual_state_desc, desired_state_desc,
       current_storage_size_mb, max_storage_size_mb, readonly_reason
FROM sys.database_query_store_options;

ALTER DATABASE CURRENT SET QUERY_STORE (MAX_STORAGE_SIZE_MB = 1024);
```

Make checking Regressed Queries a post-deploy habit; force a plan as the immediate stopgap, then fix the root cause with an index, a stats update, or a rewrite.

## Layer 6: Resolving Contention

Because RCSI removes reader-writer blocking by default in Azure SQL, what you actually hit here is writer-writer contention. The persistent culprits are the ones RCSI and ADR can't paper over: a long-running query holding locks, a sleeping session with an uncommitted transaction, or an orphaned connection from a crashed client. Set `XACT_ABORT ON` so a runtime error auto-rolls-back instead of leaving locks held indefinitely:

```sql
SET XACT_ABORT ON;   -- runtime error => automatic rollback, no half-open transaction holding locks
```

## Key Takeaways

- **vCore is the modern resource model** — three service tiers (General Purpose, Business Critical, Hyperscale) trade off latency, storage, and cost differently; General Purpose covers most workloads
- **MAXDOP should never be 0 in production** — Azure SQL's default of 8 is right for most workloads; override per-query when needed
- **Automatic tuning catches regressions passively** — `FORCE_LAST_GOOD_PLAN` is on by default; leave the index-management options off until you've reviewed their recommendations
- **Compatibility level gates optimizer features and never auto-upgrades** — move up deliberately with a Query Store baseline first
- **RCSI and optimized locking are on by default in Azure SQL** — readers don't block writers, and writer-writer contention is reduced automatically; the classic oversell bug is best fixed with an atomic `UPDATE ... WHERE` guard, not a heavier isolation level
- **Accelerated Database Recovery is always on** — constant-time recovery and near-instant rollback, paid for by watching the persistent version store on write-heavy workloads
- **Query Store can silently go read-only when full** — monitor `sys.database_query_store_options` and set `MAX_STORAGE_SIZE_MB` deliberately
