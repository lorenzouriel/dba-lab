# The SQL Server Maintenance Playbook: Performance, Recovery, and Reliability

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

A database that runs flawlessly in January can be sluggish by June and broken by December — not because anything was done wrong, but because nothing was done at all. Indexes fragment. Statistics go stale. Corruption accumulates silently. Backups pile up without anyone verifying they work. And one day, something that should take 200ms takes 20 seconds, and nobody knows why.

Maintenance is what prevents that drift. Not reactive firefighting when something breaks — proactive, scheduled work that keeps the system in the condition it needs to be in to perform and recover reliably.

This playbook defines the what, when, and why of SQL Server maintenance: the schedule, the SLAs that drive it, and the automation that makes it repeatable without manual effort.

---

## SLAs Drive Everything

Maintenance isn't one-size-fits-all. The frequency of backups, the aggressiveness of index maintenance, and the depth of integrity checks should all be proportional to the cost of losing or degrading the data they protect.

Define SLAs before building your maintenance schedule:

| Tier | Database Type | RTO | RPO |
|------|--------------|-----|-----|
| Tier 1 | Production OLTP | ≤ 1 hour | ≤ 15 minutes |
| Tier 2 | Critical Reporting | ≤ 4 hours | ≤ 1 hour |
| Tier 3 | Archival / Historical | ≤ 24 hours | ≤ 24 hours |

**RTO (Recovery Time Objective):** How long can the business wait for the database to be back online?

**RPO (Recovery Point Objective):** How much data loss is acceptable? If the RPO is 15 minutes, you need log backups running at most every 15 minutes.

These numbers are not technical decisions — they're business decisions. The job of the DBA is to build a maintenance plan that meets the agreed SLAs, not to define them unilaterally.

## The Maintenance Schedule

### Daily

| Task | Schedule | Purpose |
|------|----------|---------|
| Transaction log backup | Every 5–15 min (Full recovery) | Enables PITR; prevents unbounded log growth |
| Differential backup | Every 4–12 hours | Reduces restore time vs applying many logs |
| Full backup | Nightly | Baseline restore point |
| Health checks | Continuous | Alert on job failures, disk space, error log |

```sql
-- Using Ola Hallengren's DatabaseBackup (recommended)
EXEC dbo.DatabaseBackup
    @Databases   = 'USER_DATABASES',
    @BackupType  = 'LOG',
    @Verify      = 'Y',
    @Compress    = 'Y';

EXEC dbo.DatabaseBackup
    @Databases   = 'USER_DATABASES',
    @BackupType  = 'FULL',
    @Verify      = 'Y',
    @Compress    = 'Y';
```

### Weekly

| Task | Schedule | Purpose |
|------|----------|---------|
| CHECKDB (physical only) | Every Sunday | Fast corruption detection focused on I/O and page structure |
| Index maintenance | Saturday | Rebuild/reorganize fragmented indexes |
| Statistics update | Saturday (after index maintenance) | Ensure optimizer has accurate row count estimates |

```sql
-- Fast integrity check (physical only)
EXEC dbo.DatabaseIntegrityCheck
    @Databases     = 'USER_DATABASES',
    @CheckCommands = 'CHECKDB',
    @PhysicalOnly  = 'Y',
    @LogToTable    = 'Y';

-- Index optimization (respects fragmentation thresholds)
EXEC dbo.IndexOptimize
    @Databases           = 'USER_DATABASES',
    @FragmentationLevel1 = 5,
    @FragmentationLevel2 = 30;

-- Statistics update
EXEC sp_updatestats;
```

### Monthly

- Full `DBCC CHECKDB` (logical + physical) — deep integrity check that takes longer but catches logical corruption `PHYSICAL_ONLY` misses
- Test restores — verify at least one database per tier can be recovered to the target RTO
- Review backup history — check `msdb.dbo.backupset` for gaps or missed jobs

### Quarterly

- Review index design — remove unused indexes (query `sys.dm_db_index_usage_stats`), evaluate fill factors
- Apply SQL Server patches — test in non-production first
- Review capacity trends — data file growth, log file growth, tempdb usage patterns

## Index Maintenance: The Fragmentation Thresholds

Indexes fragment over time as INSERT, UPDATE, and DELETE operations scatter data across pages. Fragmented indexes cause more I/O per query and degrade execution plan quality.

SQL Server provides two operations to address this:

| Fragmentation Level | Action | Notes |
|--------------------|--------|-------|
| < 5% | None | Overhead of maintenance exceeds benefit |
| 5–30% | `REORGANIZE` | Online, low-resource, incremental |
| > 30% | `REBUILD` | High-resource, optionally online (Enterprise only) |

```sql
-- Reorganize (online, low resource)
ALTER INDEX [IX_Orders_CustomerID] ON dbo.Orders REORGANIZE;

-- Rebuild (higher resource, online on Enterprise)
ALTER INDEX [IX_Orders_CustomerID] ON dbo.Orders
REBUILD WITH (ONLINE = ON);
```

`ONLINE = ON` requires Enterprise or Developer edition. On Standard edition, rebuilds are offline — they acquire a schema modification lock, blocking all access to the table for the duration. Schedule accordingly.

**Checking current fragmentation:**

```sql
SELECT
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name                     AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') AS ips
INNER JOIN sys.indexes AS i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 5
  AND ips.page_count > 500
ORDER BY ips.avg_fragmentation_in_percent DESC;
```

The `page_count > 500` filter avoids flagging tiny indexes where fragmentation doesn't matter in practice.

## Statistics: Keeping the Optimizer Informed

The Query Optimizer's plan quality depends on how accurately it estimates row counts. Those estimates come from statistics. Stale statistics — statistics that no longer reflect the actual data distribution — lead to bad plans and unexpected performance degradation.

SQL Server's auto-update trigger fires when approximately `500 + 20% of rows` in a table have changed. For a 10-million-row table, that's 2 million changes before statistics auto-update. Between auto-updates, the optimizer may be working from outdated cardinality data.

For critical tables, update statistics manually with a full scan:

```sql
-- Full scan: most accurate, most expensive
UPDATE STATISTICS dbo.Orders WITH FULLSCAN;

-- Sampled (faster, less accurate for skewed distributions)
UPDATE STATISTICS dbo.Orders WITH SAMPLE 30 PERCENT;
```

A weekly statistics update run after index maintenance is good practice. Index rebuilds also update statistics (with full scan), so tables that got rebuilt don't need a separate statistics update.

## DBCC CHECKDB: The Integrity Foundation

`DBCC CHECKDB` checks the structural integrity of every page in the database. It detects corruption that backups will replicate silently — if corruption exists and you back it up, you're now backing up corrupted data.

```sql
-- Full integrity check (logical + physical)
DBCC CHECKDB (SalesDB) WITH NO_INFOMSGS;

-- Physical-only (faster, finds I/O and page header corruption)
DBCC CHECKDB (SalesDB) WITH PHYSICAL_ONLY, NO_INFOMSGS;
```

**Recommended schedule:**
- Weekly `PHYSICAL_ONLY` — fast, catches hardware and I/O-related corruption early
- Monthly full `CHECKDB` — catches logical consistency issues (foreign key violations, allocation errors)
- Always after restoring a database before putting it back in production

For Very Large Databases (VLDBs) where full `CHECKDB` takes hours, run `PHYSICAL_ONLY` weekly and full `CHECKDB` monthly — or use `CHECKFILEGROUP` to distribute the check across multiple maintenance windows.

## Automation with Ola Hallengren's Solution

The industry standard for SQL Server maintenance automation is Ola Hallengren's free, open-source `MaintenanceSolution.sql`. It installs three stored procedures — `DatabaseBackup`, `DatabaseIntegrityCheck`, and `IndexOptimize` — with parameters for every common maintenance scenario.

**Complete SQL Agent job schedule using Ola Hallengren:**

| Job | Schedule | Command |
|-----|----------|---------|
| Transaction Log Backup | Every 15 min | `EXEC dbo.DatabaseBackup @Databases='USER_DATABASES', @BackupType='LOG', @Verify='Y', @Compress='Y'` |
| Full Backup | Daily 02:00 | `EXEC dbo.DatabaseBackup @Databases='USER_DATABASES', @BackupType='FULL', @Verify='Y', @Compress='Y'` |
| CHECKDB Physical Only | Sunday 03:00 | `EXEC dbo.DatabaseIntegrityCheck @Databases='USER_DATABASES', @CheckCommands='CHECKDB', @PhysicalOnly='Y', @LogToTable='Y'` |
| CHECKDB Full | 1st Sunday/month | `EXEC dbo.DatabaseIntegrityCheck @Databases='USER_DATABASES', @CheckCommands='CHECKDB', @PhysicalOnly='N', @LogToTable='Y'` |
| Index Maintenance | Saturday 01:00 | `EXEC dbo.IndexOptimize @Databases='USER_DATABASES', @FragmentationLevel1=5, @FragmentationLevel2=30` |
| Statistics Update | Saturday 04:00 | `EXEC dbo.IndexOptimize @Databases='USER_DATABASES', @UpdateStatistics='ALL', @OnlyModifiedStatistics='Y'` |

The `@LogToTable='Y'` parameter writes execution history to a table (`dbo.CommandLog`) so you can query what ran, when, and whether it succeeded.

## The Trap

**"We have backups" without "we have tested restores."** This appears in every DBA article about maintenance because it happens constantly. Backups that have never been restored are theoretical backups. The only backup you can trust is one you've actually restored and verified.

A maintenance plan that includes backups but not restore tests is incomplete. Schedule at minimum one restore test per quarter per tier. Time it. Compare the actual recovery time against your RTO. If the recovery takes three hours and your Tier 1 RTO is one hour, your plan doesn't meet your SLA — and you want to discover that in a drill, not an outage.

The other common failure: **maintenance running but nobody reviewing the results**. Index maintenance that fails silently still gets marked "done" in the Agent history. Build a monitoring query into your weekly review:

```sql
-- Check recent maintenance job outcomes
SELECT
    j.name        AS job_name,
    jh.run_date,
    jh.run_time,
    CASE jh.run_status
        WHEN 1 THEN 'Succeeded'
        WHEN 0 THEN 'Failed'
        WHEN 3 THEN 'Cancelled'
    END           AS outcome,
    jh.message
FROM msdb.dbo.sysjobs AS j
INNER JOIN msdb.dbo.sysjobhistory AS jh
    ON j.job_id = jh.job_id
WHERE jh.step_id = 0
  AND jh.run_date >= CAST(CONVERT(VARCHAR, DATEADD(DAY, -7, GETDATE()), 112) AS INT)
  AND j.name LIKE '%Backup%'
   OR j.name LIKE '%CHECKDB%'
   OR j.name LIKE '%Index%'
ORDER BY jh.run_date DESC, jh.run_time DESC;
```

## Key Takeaways

- **SLAs define the schedule** — RTO and RPO requirements drive backup frequency, CHECKDB cadence, and how aggressively you maintain indexes; agree these numbers with stakeholders before building the plan
- **Daily: backups; weekly: CHECKDB + index maintenance + statistics** — this cadence balances coverage against maintenance window cost for most production systems
- **Fragmentation thresholds: < 5% nothing, 5–30% REORGANIZE, > 30% REBUILD** — `REORGANIZE` is always online; `REBUILD WITH ONLINE=ON` requires Enterprise edition
- **CHECKDB `PHYSICAL_ONLY` weekly, full monthly** — `PHYSICAL_ONLY` is fast and catches hardware-level corruption; full CHECKDB catches logical consistency issues
- **Ola Hallengren's solution is the standard** — `DatabaseBackup`, `DatabaseIntegrityCheck`, and `IndexOptimize` cover all three maintenance domains with production-tested logic
- **Review maintenance results, don't just schedule them** — query `msdb.dbo.sysjobhistory` weekly; a job that runs and fails silently provides no protection
