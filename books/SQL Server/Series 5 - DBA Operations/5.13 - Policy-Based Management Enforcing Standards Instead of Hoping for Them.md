# Policy-Based Management: Enforcing Standards Instead of Hoping for Them

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

One SQL Server instance is easy to keep standards-compliant. You know it, you set it up, you remember the quirks. Twenty instances is a different problem entirely — some provisioned two years ago by someone who's left, some spun up in a hurry for a project deadline, some quietly drifted after a well-meaning fix that never got applied everywhere else. Nobody deliberately decides to run inconsistent SQL Server configuration across a fleet. It just accumulates, one exception at a time, until an audit or an incident forces someone to find out what's actually out there.

Policy-Based Management (PBM) is SQL Server's built-in answer to that drift. Instead of manually checking whether every instance has backups configured, memory limits set sensibly, and `TRUSTWORTHY` turned off, you define the rule once as a policy and let SQL Server evaluate it — on demand, on a schedule, or in response to the change that would have violated it in the first place. This article covers PBM's core components, a worked example end to end, a categorized catalog of the policies that matter most in production, and how to export and reuse policies across a fleet of instances.

---

## Why This Exists: Governance, Not Just Convenience

The value of PBM isn't that it saves typing — it's that it turns "we have a standard" into something SQL Server actually enforces or at least actively reports on, rather than something written in a wiki page nobody rereads. Three practical reasons this matters:

**Compliance and audit evidence.** When an auditor asks "how do you ensure backups run on every production database," the honest answer without PBM is usually "someone checks, we think." With PBM, the answer is a scheduled policy evaluation with a queryable history in `msdb` — the checking is not a person's memory, it's a repeatable, timestamped process.

**Preventing configuration drift across a fleet.** As the number of instances grows, the gap between "how we intend to configure SQL Server" and "how it's actually configured" grows with it. PBM closes that gap by making the intended state explicit and machine-checkable, rather than tribal knowledge that erodes as the team changes.

**Catching bad changes before they land, not after.** The strongest evaluation mode doesn't just report a violation after the fact — it blocks the change outright. That turns a policy from a monitoring tool into an actual guardrail.

## Core Components

PBM is built from three layered concepts, and understanding the layering is what makes the rest of this article make sense.

### 1. Facets

A **Facet** is a category of SQL Server objects whose properties can be inspected or enforced — `Login`, `Database`, `Server`, `Backup`, and dozens more. A facet is the *thing being described*: it exposes a set of properties (like `PasswordExpirationEnabled` on the `Login` facet, or `AutoShrink` on the `Database` facet) that a condition can then test.

### 2. Conditions

A **Condition** is a logical expression written against one or more facet properties. It's the *rule itself*, independent of what it applies to or when it runs.

```
Facet: Login
Condition: PasswordExpirationEnabled = True
```

### 3. Policies

A **Policy** is what makes a condition operational — it binds the condition to a set of targets and defines how and when evaluation happens:

| Evaluation Mode | Behavior |
|---|---|
| On Demand | Run manually, typically from SSMS, for a point-in-time check |
| On Schedule | Runs automatically via a SQL Server Agent job |
| On Change – Prevent | Enforced in real time; blocks the non-compliant change from happening at all |
| On Change – Log Only | Logs the violation without blocking it — useful for rolling out a new policy without breaking existing workflows |

The progression matters operationally: start a new policy in **Log Only** to see what it would have caught without disrupting anyone, then graduate it to **Prevent** once you're confident the rule is correct and the fallout of blocking violations is understood.

## Putting It Together: a Password Hygiene Example

Here's the full path from facet to enforced policy, using password expiration as a concrete walkthrough.

| Component | Value | Purpose |
|---|---|---|
| Facet | `Login` | The category of object being managed — SQL Server logins |
| Condition | `PasswordExpirationEnabled = True` | The rule: password expiration must be turned on |
| Policy | "Enforce Password Expiration" | Applies the condition to all logins, evaluated daily |

The flow in SSMS:

1. **Select the facet** — `Login`, since password expiration is a login-level property.
2. **Create the condition** — `PasswordExpirationEnabled = True`.
3. **Create the policy** — target all logins (or a filtered subset, if service accounts are meant to be exempt), set evaluation mode to On Schedule with a daily SQL Server Agent job.
4. **Result** — the policy runs daily, and any login found with password expiration disabled shows up in the policy report. Switching the evaluation mode to Prevent would instead block the `ALTER LOGIN` statement that tries to disable expiration in the first place.

This same shape — facet, condition, policy, evaluation mode — is the template for every policy in the catalog below. The categories differ; the mechanism doesn't.

## Policy Catalog by Category

This is a working reference of the policies that consistently pay off in production. Treat it as a starting checklist for what a well-governed fleet of instances should have covered, not an exhaustive list.

### Configuration and Settings

| Policy | Why It Matters |
|---|---|
| Max Server Memory is Set | An unset or too-high `max server memory` starves the OS and other processes on the box |
| Auto Shrink is Off | Auto-shrink causes recurring fragmentation and I/O spikes — it should never be a standing setting |
| Remote Access is Disabled | Removes a legacy connectivity surface that's rarely needed and rarely reviewed |
| CLR Integration is Disabled | Blocks unapproved .NET assemblies from running inside the engine unless explicitly needed |
| Backup Compression Default is Enabled | Enforces a sensible default rather than relying on every backup job to set it explicitly |

### Security and Compliance

| Policy | Why It Matters |
|---|---|
| No Database Has TRUSTWORTHY Set to ON | `TRUSTWORTHY ON` is a known privilege-escalation vector and should be an exception, not a default |
| Cross-Database Ownership Chaining is Disabled | Prevents one database's permissions from silently leaking access into another |
| Logins Must Have Password Expiration Enabled | The password hygiene example above, generalized as a standing rule |
| SQL Authentication is Disabled | Enforces Windows/Entra-only authentication where policy requires it |
| Public Role Has No Permissions | The `public` role applies to every principal by default — any permission granted to it is granted to everyone |

### Database-Level

| Policy | Why It Matters |
|---|---|
| All User Databases Must Have Auto Close Disabled | Auto-close causes the database to shut down and reopen repeatedly, degrading performance |
| All Databases Must Use Full Recovery Model | Enforces the recovery strategy required for point-in-time restore on critical systems |
| All Databases Must Have a Backup Within Last 24 Hours | Directly verifies the thing every DR plan assumes is true |
| All Databases Must Have Page Verify = CHECKSUM | Detects page-level corruption early instead of discovering it during a restore |
| File Growth Must Be in Megabytes | Percentage-based autogrowth causes increasingly large, slow growth events as a file grows — fixed MB growth avoids that |

### Instance-Level Maintenance

| Policy | Why It Matters |
|---|---|
| SQL Agent Must Be Running | If the Agent is down, scheduled backups, index maintenance, and monitoring jobs silently stop running |
| Policy Purge Job Exists and Is Scheduled | Validates that `syspolicy_purge_history` itself is scheduled, so PBM's own history doesn't grow unbounded |
| MAXDOP is Properly Configured | Prevents a default MAXDOP setting from causing excessive parallelism on OLTP workloads |

### Monitoring and Health

| Policy | Why It Matters |
|---|---|
| No Failed SQL Server Agent Jobs in the Last 24 Hours | Surfaces failing jobs — including failed backups — before they're discovered by an outage |
| System Databases Are On Fast Storage | Validates that `master`, `msdb`, and `tempdb` placement hasn't drifted onto slow storage |
| TempDB Has Multiple Data Files | Avoids allocation contention, especially relevant on instances with more than four CPUs |

## Custom Policies

The built-in facets cover most common checks, but PBM also supports custom conditions built from T-SQL expressions or WMI classes for server-wide settings that don't map cleanly to an existing facet.

A common example — enforcing that stored procedures aren't left with `WITH RECOMPILE` baked in, which defeats plan caching:

```sql
OBJECTPROPERTY(object_id, 'ExecIsRecompile') = 1
```

This is written the same way as any other condition — bound to the relevant facet, wrapped in a policy, given an evaluation mode — but it lets you extend PBM to organization-specific standards that Microsoft's built-in facet catalog doesn't anticipate. If a rule exists only in a wiki page or a tribal "we always do it this way," a custom policy is usually how to get it out of the wiki and into something enforced.

---

## Exporting and Reusing Policies

A policy defined on one instance is only useful there unless it's shared. PBM policies export to XML, which is what makes a fleet-wide standard practical instead of a manual, per-instance re-creation exercise:

- Export a policy from SSMS as an XML file, then import that same file on every other instance that should follow the standard — this is the mechanism for DevOps pipelines, CI/CD gates on new instance provisioning, and compliance audits that need to show the same policy is actually deployed everywhere it's supposed to be.
- SQL Server ships with built-in sample policies covering many of the categories above, typically found at:

```
C:\Program Files\Microsoft SQL Server\NNN\Tools\Policies\
```

These sample policies are a reasonable starting point — import the ones relevant to your environment, adjust the conditions to match your actual standards, and layer custom policies on top for anything organization-specific.

## Key Takeaways

- **PBM turns "we have a standard" into something SQL Server actually checks** — evaluations log to `msdb`, giving you queryable, timestamped compliance evidence instead of relying on memory
- **Facet → Condition → Policy is the core layering** — a facet exposes properties, a condition is a rule against those properties, a policy binds the condition to targets and an evaluation mode
- **Evaluation mode determines how strict enforcement is** — On Demand and On Schedule report; On Change – Prevent actively blocks the violating action; start new policies in Log Only before graduating to Prevent
- **The policy catalog spans configuration, security, database-level, instance maintenance, and monitoring** — treat the categories above as a starting checklist for a well-governed fleet
- **Custom policies extend PBM past the built-in facets** using T-SQL expressions or WMI classes for organization-specific standards
- **Export to XML for fleet-wide consistency** — this is what makes PBM a governance tool across many instances rather than a per-instance convenience
