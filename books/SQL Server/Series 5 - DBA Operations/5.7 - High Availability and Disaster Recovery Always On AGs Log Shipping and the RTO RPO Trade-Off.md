# High Availability and Disaster Recovery: Always On AGs, Log Shipping, and the RTO/RPO Trade-Off

*Series 5 — DBA Operations | The SQL Server Deep Dive*

---

A node goes offline at 3 AM. How long until the database is back? How much data did you lose? If you can't answer both questions with a number, you don't have a recovery strategy — you have a hope.

High Availability (HA) and Disaster Recovery (DR) are two different problems that are often confused because they both involve redundancy. HA is about surviving failures automatically without human intervention, usually in seconds. DR is about recovering from a catastrophic event — a data center fire, a region outage, a corrupted backup chain — usually in minutes to hours. Most production systems need both, and they require different tools.

This article covers the technical implementation of HA with Always On Availability Groups and DR with log shipping, including the real trade-offs between them.

---

## RTO and RPO: The Two Numbers That Drive Every Decision

Before choosing a technology, define your targets:

- **RTO (Recovery Time Objective):** How long can the system be unavailable before the business is impacted? If your SLA is 99.9% uptime, your RTO is about 8 hours per year. If it's 99.99%, it's 52 minutes.
- **RPO (Recovery Point Objective):** How much data loss is acceptable? An RPO of 5 minutes means you can lose at most 5 minutes of transactions.

These two numbers constrain your architecture:

| RTO | RPO | Solution |
|-----|-----|---------|
| Hours | Hours | Backup + restore |
| 30–60 minutes | Minutes | Log shipping |
| < 60 seconds | ~0 | Always On AG (synchronous commit) |
| < 60 seconds | Minutes | Always On AG (asynchronous) + log shipping for DR |

Lowering RTO or RPO costs money — faster recovery requires more infrastructure. The goal is to match your architecture to your actual requirements, not to over-engineer for scenarios that will never happen.

## High Availability: Always On Availability Groups

Always On Availability Groups (AOAG) is SQL Server's primary HA technology since SQL Server 2012. An AG is a group of databases that fail over together as a unit, with automatic promotion of a secondary replica to primary when the primary fails.

### The Components

**Primary replica:** The instance accepting reads and writes. Only one replica is primary at a time.

**Secondary replicas:** Copies of the databases that receive changes from the primary. Depending on configuration, they can serve read workloads or be kept in a warm standby state.

**Availability Group Listener:** A virtual network name and IP address that always points to the current primary. Applications connect to the listener — they never need to know which node is currently primary.

**Windows Server Failover Cluster (WSFC):** The underlying cluster service that manages node health and drives failover decisions. AOAG requires WSFC.

### Synchronous vs. Asynchronous Commit

This is the most consequential configuration decision:

**SYNCHRONOUS_COMMIT:** A transaction on the primary does not complete until the secondary has hardened the log record to disk. Both nodes are guaranteed to have every committed transaction.

```sql
ALTER AVAILABILITY GROUP [AG-Production]
MODIFY REPLICA ON N'NODE2' WITH (
    AVAILABILITY_MODE = SYNCHRONOUS_COMMIT,
    FAILOVER_MODE     = AUTOMATIC
);
```

- RPO: zero — no committed transaction is ever lost
- Cost: every write waits for the secondary to acknowledge, adding network latency to each transaction
- Appropriate for: same-datacenter or same-region replicas where round-trip is < 5ms

**ASYNCHRONOUS_COMMIT:** The primary completes the transaction without waiting for the secondary. The secondary catches up asynchronously.

```sql
ALTER AVAILABILITY GROUP [AG-Production]
MODIFY REPLICA ON N'NODE3-DR' WITH (
    AVAILABILITY_MODE = ASYNCHRONOUS_COMMIT,
    FAILOVER_MODE     = MANUAL
);
```

- RPO: nonzero — transactions committed on the primary since the last acknowledgment can be lost
- Cost: no write latency overhead
- Appropriate for: cross-region DR replicas where round-trip is 60–80ms

**Why you can't use synchronous commit cross-region:** A write that takes 2ms locally now takes 62ms waiting for a cross-region acknowledgment. That's a 30× performance multiplier on every write. Production workloads cannot absorb this — cross-region replicas must be asynchronous.

### Quorum and the File Share Witness

A WSFC cluster needs a quorum — a majority of votes — before it takes action. This prevents "split-brain" scenarios where both nodes think they're primary.

With two SQL Server nodes, the vote count is 2. If Node 1 fails, Node 2 has 1 of 2 votes — not a majority. The cluster refuses to fail over.

**The File Share Witness (FSW)** adds a third vote. It's a small instance whose only job is to host a shared folder the cluster uses as a tiebreaker:

```
Node 1 (1 vote) + Node 2 (1 vote) + FSW (1 vote) = 3 total votes

Node 1 fails:
  Node 2 (1) + FSW (1) = 2/3 → majority → automatic failover ✓

Without FSW:
  Node 2 (1) = 1/2 → no majority → cluster enters RESOLVING state ✗
```

Without the FSW, a two-node cluster will not automatically fail over — it will stop accepting connections and wait for an administrator.

### Creating an Availability Group

```sql
-- Step 1: Enable AOAG on both nodes (requires restart)
-- Enable-SqlAlwaysOn -ServerInstance NODE1 -Force

-- Step 2: Create the AG on the primary replica
CREATE AVAILABILITY GROUP [AG-Production]
WITH (
    AUTOMATED_BACKUP_PREFERENCE = PRIMARY,
    FAILURE_CONDITION_LEVEL     = 3,
    HEALTH_CHECK_TIMEOUT        = 30000
)
FOR DATABASE [SalesDB], [OrdersDB]
REPLICA ON
    N'NODE1' WITH (
        ENDPOINT_URL          = 'TCP://NODE1:5022',
        AVAILABILITY_MODE     = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE         = AUTOMATIC,
        SEEDING_MODE          = AUTOMATIC,
        SECONDARY_ROLE        (ALLOW_CONNECTIONS = NO)
    ),
    N'NODE2' WITH (
        ENDPOINT_URL          = 'TCP://NODE2:5022',
        AVAILABILITY_MODE     = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE         = AUTOMATIC,
        SEEDING_MODE          = AUTOMATIC,
        SECONDARY_ROLE        (ALLOW_CONNECTIONS = READ_ONLY)
    );

-- Step 3: Create the listener
ALTER AVAILABILITY GROUP [AG-Production]
ADD LISTENER N'AG-Production-Listener' (
    WITH IP ((N'10.0.1.50', N'255.255.255.0')),
    PORT = 1433
);

-- Step 4: Join the secondary (run on NODE2)
ALTER AVAILABILITY GROUP [AG-Production] JOIN;
ALTER AVAILABILITY GROUP [AG-Production] GRANT CREATE ANY DATABASE;
```

`SEEDING_MODE = AUTOMATIC` (direct seeding) lets SQL Server seed the secondary databases directly over the mirroring endpoint without requiring a manual backup/restore. This is the modern approach for initial setup.

### Monitoring AOAG Health

```sql
-- Replica health and synchronization state
SELECT
    ar.replica_server_name,
    ars.role_desc,
    ars.operational_state_desc,
    ars.synchronization_health_desc,
    ars.connected_state_desc,
    ars.last_commit_time
FROM sys.dm_hadr_availability_replica_states AS ars
JOIN sys.availability_replicas AS ar
    ON ars.replica_id = ar.replica_id;

-- Per-database synchronization state
SELECT
    db_name(drs.database_id) AS database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.redo_queue_size,        -- KB of log waiting to be applied on secondary
    drs.log_send_queue_size,    -- KB of log waiting to be sent to secondary
    drs.last_hardened_time
FROM sys.dm_hadr_database_replica_states AS drs
WHERE drs.is_local = 0;
```

`log_send_queue_size` tells you how far behind the secondary is in receiving log from the primary. `redo_queue_size` tells you how far behind it is in applying received log. Both should trend toward zero in a healthy AG under normal load.

### Manual and Automatic Failover

Automatic failover triggers when the WSFC health check detects the primary is unresponsive and quorum is maintained. For planned maintenance, initiate a manual failover:

```sql
-- Planned failover (run on the target secondary you want to promote)
-- This preserves the log chain and causes no data loss
ALTER AVAILABILITY GROUP [AG-Production] FAILOVER;
```

For unplanned failover when the primary is not reachable (forced failover with potential data loss):

```sql
-- Forced failover — use only when primary is confirmed down and cannot be recovered
ALTER AVAILABILITY GROUP [AG-Production] FORCE_FAILOVER_ALLOW_DATA_LOSS;
```

After a forced failover, the old primary must rejoin as a secondary before it can be promoted back. Never force failover and then restart the old primary without understanding the LSN gap — you may have two nodes that believe they're each primary.

## Disaster Recovery: Log Shipping

Log shipping is the oldest DR technology in SQL Server — and still one of the most practical. It copies transaction log backups from a source instance to one or more standby servers and applies them, keeping the standby continuously updated.

### How Log Shipping Works

```
Primary server
  └── SQL Agent: BACKUP LOG every N minutes
        └── Backup file written to shared folder or S3
              └── Copy job: transfers to standby location
                    └── SQL Agent on standby: RESTORE LOG WITH NORECOVERY
                          └── Standby database (RESTORING/STANDBY state)
```

The standby database is never fully recovered — it stays in RESTORING (unreadable) or STANDBY (read-only) mode so subsequent logs can be applied. This is intentional: applying a log backup requires the database to be in a state where it can accept log records.

**RPO = frequency of log backups.** If logs are shipped every 5 minutes, you can lose at most 5 minutes of transactions.

**RTO = time to apply the remaining logs + bring the database online.** A database that's been applying logs continuously has very little log to apply at failover time — the DR procedure is mostly just executing `WITH RECOVERY` on the last log.

### Setting Up Log Shipping (T-SQL)

```sql
-- On the primary: configure log shipping for the source database
EXEC master.dbo.sp_add_log_shipping_primary_database
    @database                = N'SalesDB',
    @backup_directory        = N'\\SQLBACKUP\LogShipping\SalesDB',
    @backup_share            = N'\\SQLBACKUP\LogShipping\SalesDB',
    @backup_job_name         = N'LSBackup_SalesDB',
    @backup_retention_period = 4320,    -- minutes (3 days)
    @backup_threshold        = 60,      -- alert if no backup in 60 minutes
    @threshold_alert_enabled = 1,
    @history_retention_period= 5760,    -- minutes (4 days)
    @backup_job_id           = @ls_backup_jobid OUTPUT,
    @primary_id              = @ls_primary_id OUTPUT,
    @overwrite               = 1;

-- On the standby: configure the restore job
EXEC master.dbo.sp_add_log_shipping_secondary_database
    @secondary_database      = N'SalesDB',
    @primary_server          = N'SQLPRIMARY',
    @primary_database        = N'SalesDB',
    @restore_delay           = 0,
    @restore_all             = 1,
    @restore_mode            = 0,       -- 0 = NORECOVERY, 1 = STANDBY
    @disconnect_users        = 0,
    @restore_threshold       = 45,      -- alert if no restore in 45 minutes
    @threshold_alert_enabled = 1,
    @history_retention_period= 5760;
```

`@restore_mode = 1` (STANDBY) allows read-only access to the standby between log applications. Useful for reporting workloads on the DR server. `@restore_mode = 0` (NORECOVERY) keeps the database fully in restoring state — slightly faster log apply because there's no undo phase.

### Log Shipping to RDS via S3

When the DR target is Amazon RDS for SQL Server, traditional UNC path log shipping doesn't work — RDS has no accessible filesystem. The workaround uses `BACKUP TO URL` (SQL Server writes directly to S3) and the RDS-native stored procedure `msdb.dbo.rds_restore_log`.

```sql
-- On the primary: backup log directly to S3
DECLARE @timestamp NVARCHAR(20) = CONVERT(NVARCHAR(20), GETUTCDATE(), 112)
    + '_' + REPLACE(CONVERT(NVARCHAR(8), GETUTCDATE(), 108), ':', '');

-- Only run on the primary replica (AOAG-aware check)
IF (
    SELECT role_desc
    FROM sys.dm_hadr_availability_replica_states
    WHERE is_local = 1
) = 'PRIMARY'
BEGIN
    BACKUP LOG [SalesDB]
    TO URL = 's3://backup-bucket/logs/SalesDB_' + @timestamp + '.bak'
    WITH COMPRESSION, CHECKSUM;
END
```

Running a log backup on the secondary replica would create an LSN gap in the primary's log chain. The `is_local = 1` check ensures backups only run on the current primary regardless of which node that is after a failover.

```python
# Lambda function: apply T-logs to RDS as they arrive via S3 CRR + SQS
def handler(event, context):
    for record in event["Records"]:
        s3_key = record["s3"]["object"]["key"]
        s3_arn = f"arn:aws:s3:::destination-bucket/{s3_key}"

        conn = pymssql.connect(host=RDS_ENDPOINT, user=USER, password=PWD)
        cur  = conn.cursor()

        # @with_norecovery=1 keeps DB in RESTORING state for subsequent logs
        cur.execute("""
            EXEC msdb.dbo.rds_restore_log
                @restore_db_name        = %s,
                @s3_arn_to_restore_from = %s,
                @with_norecovery        = 1;
        """, (DB_NAME, s3_arn))
        conn.commit()
```

Transaction logs must be applied in strict LSN order. Processing one log at a time (`batch_size=1` on the SQS trigger) ensures ordering. A Dead Letter Queue captures failures so no log is silently skipped — a skipped log breaks the restore chain, and the next log after the gap will fail to apply.

### Monitoring Log Shipping Lag

```sql
-- Check how far behind the standby is
SELECT
    primary_server,
    primary_database,
    last_backup_date,
    last_backup_file,
    last_restored_date,
    last_restored_file,
    last_restored_latency    -- minutes
FROM msdb.dbo.log_shipping_monitor_secondary
WHERE secondary_database = 'SalesDB';
```

If `last_restored_latency` exceeds your RPO target, investigate: the copy job may be slow, the network share may be full, or the restore job may have failed and require manual restart.

### Failing Over from Log Shipping

When a DR failover is needed:

```sql
-- On the standby: apply any remaining logs and bring the database online
-- First, apply the last available log backup manually if there's a gap

-- Bring the database fully online (terminates log shipping relationship)
RESTORE DATABASE SalesDB WITH RECOVERY;

-- Verify
SELECT state_desc FROM sys.databases WHERE name = 'SalesDB';
-- Should return: ONLINE
```

After recovery, the database is read/write and log shipping is terminated. Rebuilding the log shipping relationship in the other direction (if you want the original primary to become the standby) requires starting over from a fresh full backup of the new primary.

## Choosing Between HA and DR Technologies

These are not mutually exclusive. Production systems typically layer them:

```
Same-region HA:
  Primary node ──(synchronous, automatic failover)──→ Secondary node
       │
       │  Every 5 minutes
       ↓
  Cross-region DR:
  S3 log backups ──(async, 5-minute RPO)──→ DR replica
```

The same-region AOAG provides sub-minute RTO with zero RPO for local failures. The cross-region log shipping provides a warm standby for regional disasters, with a 5-minute RPO and 30–60 minute RTO (time to apply remaining logs and promote).

**RDS Multi-AZ** is the managed alternative to a self-managed AOAG for teams running on AWS. AWS synchronously replicates every write to a hidden standby in a second Availability Zone. Failover is automatic, the connection string endpoint doesn't change (AWS updates the DNS CNAME), and there's nothing to configure — but you give up OS access, readable secondaries, and control over failover timing.

| | Self-managed AOAG | RDS Multi-AZ |
|--|--|--|
| Automatic failover | Yes (WSFC-driven) | Yes (AWS-driven) |
| RTO | < 60 seconds | ~40 seconds |
| RPO | Zero (synchronous) | Zero (synchronous) |
| Readable secondary | Yes (configure) | No |
| OS access | Full | None |
| IaC complexity | High | Low |
| Cost control | Granular | Fixed by instance class |

## The Trap

**Configuring HA/DR but never testing failover.** AOAG replicas can appear `SYNCHRONIZED` while having a latent issue that prevents failover — a misconfigured endpoint, a certificate that expired, a quorum that won't form without a specific node online. Log shipping that looks healthy on the monitor screen can have a broken restore chain that only surfaces when you try to apply the last log during an actual event.

Run quarterly failover tests:

1. Stop or isolate the primary node in a non-production window
2. Verify the secondary was promoted automatically (AOAG) or initiate `RESTORE DATABASE WITH RECOVERY` (log shipping)
3. Connect applications to the new primary through the listener or updated connection string
4. Measure the actual time from failure to "applications operational"
5. Restart the old primary, confirm it rejoins as secondary

That elapsed time is your real RTO.

## Key Takeaways

- **HA and DR solve different problems** — HA is automatic sub-minute recovery from local failures; DR is recovery from regional or catastrophic events, measured in minutes to hours
- **RTO and RPO are the decision drivers** — define both before choosing a technology; match architecture to requirements, not to what's most impressive
- **Synchronous commit = zero RPO, but only within a region** — cross-region replicas must use asynchronous commit or write latency becomes a 30× multiplier
- **The File Share Witness is mandatory for two-node WSFC clusters** — without it, a single node failure leaves the cluster without quorum and prevents automatic failover
- **Log shipping RPO equals backup frequency** — every 5 minutes of log backup frequency means at most 5 minutes of data loss; the standby stays in NORECOVERY or STANDBY until a failover is needed
- **BACKUP LOG must only run on the primary replica** — running it on a secondary breaks the log chain on the primary and makes the next restore fail with an LSN gap
- **Test failover quarterly in a non-production window** — synchronized-looking replicas and healthy-looking monitors don't prove failover works; only an actual failover test does
