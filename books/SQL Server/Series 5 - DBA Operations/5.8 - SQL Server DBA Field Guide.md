# SQL Server DBA Field Guide
### Monitoring · Performance Troubleshooting · Logs, Events & Diagnostics

A working reference, not a textbook. Every section leans toward what you actually run and read at 2 a.m. when something's on fire. T-SQL throughout. Tested patterns favored over exhaustive option lists.

---

## Part 0 — The Mental Model

Before any tool: SQL Server is a thread scheduler on top of a storage engine. At any instant a worker thread is in one of three states — **running** (on CPU), **runnable** (ready, waiting for CPU), or **suspended** (waiting for a resource: a lock, a page from disk, a memory grant, the log to flush). When a thread suspends, SQL Server records *why* as a **wait type**. That record is the single most honest signal in the engine.

This gives you the spine of all troubleshooting — **wait-based methodology**:

> Don't guess where the bottleneck is. Read the waits. The engine already knows why threads aren't running; your job is to listen, not theorize.

Everything below hangs off this. Monitoring = capturing waits and their context over time. Troubleshooting = reading waits to pick which subsystem to drill into. Logs = the record of discrete events the waits can't tell you about (a failed login, a corruption, a deadlock victim).

Three rules that prevent most wasted hours:
1. **Measure before optimizing.** "Slow" is a symptom, not a diagnosis.
2. **Diff cumulative counters; never read them raw.** Most DMVs accumulate since restart — a single snapshot tells you about uptime, not about now.
3. **Confirm the fix moved the waits, not the wall clock.** A faster run could be a warm cache. Re-measure the same way you diagnosed.

# PART 1 — MONITORING

## 1.1 The Three Time Horizons

Conflating these is the most common monitoring mistake. Each needs different tools:

| Horizon | Question it answers | Primary tools |
|---|---|---|
| **Real-time** | What's happening *right now*? | `sp_WhoIsActive`, `dm_exec_requests`, `dm_os_waiting_tasks` |
| **Cumulative** | What's been expensive *since restart*? | `dm_os_wait_stats`, `dm_exec_query_stats`, `dm_io_virtual_file_stats` |
| **Historical** | How has this *trended* over days/weeks? | Query Store, external TSDB (Prometheus/Grafana) |

A good monitoring posture covers all three. Most shops over-invest in real-time (someone watching Activity Monitor) and under-invest in historical (no baseline, so "is this normal?" is unanswerable).

## 1.2 Real-Time DMVs

The live picture. These reflect the current instant and don't accumulate.

**The core join — what's executing right now:**

```sql
select
    r.session_id,
    r.status,
    r.command,
    r.wait_type,
    r.wait_time,
    r.last_wait_type,
    r.blocking_session_id,
    r.cpu_time,
    r.total_elapsed_time,
    r.reads,
    r.writes,
    r.logical_reads,
    db_name(r.database_id) as database_name,
    substring(t.text, (r.statement_start_offset / 2) + 1,
        ((case r.statement_end_offset
            when -1 then datalength(t.text)
            else r.statement_end_offset
          end - r.statement_start_offset) / 2) + 1) as running_statement,
    qp.query_plan
from sys.dm_exec_requests as r
inner join sys.dm_exec_sessions as s
    on r.session_id = s.session_id
cross apply sys.dm_exec_sql_text(r.sql_handle) as t
cross apply sys.dm_exec_query_plan(r.plan_handle) as qp
where r.session_id <> @@spid       -- exclude this query itself
    and s.is_user_process = 1;     -- exclude system sessions
```

The `statement_start/end_offset` math extracts the *currently running statement* out of a batch — critical, because `sql_text` returns the whole batch but you usually want the one line that's stuck.

**Live blocking / waiting — what's suspended and on what:**

```sql
select
    wt.session_id,
    wt.wait_type,
    wt.wait_duration_ms,
    wt.blocking_session_id,
    wt.resource_description,
    r.command,
    db_name(r.database_id) as database_name
from sys.dm_os_waiting_tasks as wt
left join sys.dm_exec_requests as r
    on wt.session_id = r.session_id
where wt.session_id > 50            -- skip most system sessions
order by wt.wait_duration_ms desc;
```

`dm_os_waiting_tasks` is your live blocking-chain source: `blocking_session_id` points at whoever's holding what you need. Chase it up the chain to the lead blocker (the one with a NULL/0 blocker that's itself blocking others).

**Session-level overview without a current request** (idle-but-holding sessions — a frequent blocking culprit):

```sql
select
    s.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    s.status,
    s.last_request_end_time,
    s.open_transaction_count,
    db_name(s.database_id) as database_name
from sys.dm_exec_sessions as s
where s.is_user_process = 1
    and s.open_transaction_count > 0
order by s.last_request_end_time;
```

An idle session with `open_transaction_count > 0` and an old `last_request_end_time` is the classic "someone left a transaction open in SSMS" blocker.

## 1.3 sp_WhoIsActive

Adam Machanic's procedure. Install it on every instance — it's the single highest-leverage thing in your toolkit. It collapses the DMV joins above into one coherent, sorted snapshot: who's running what, blocking chains, waits, tempdb allocation, reads/writes, the plan.

```sql
-- Baseline: everything active, sorted by who's been running longest
exec sp_WhoIsActive;

-- The full picture for troubleshooting
exec sp_WhoIsActive
    @get_plans = 1,            -- include the execution plan
    @get_locks = 1,            -- include lock detail (XML)
    @find_block_leaders = 1,   -- compute and surface blocking chains
    @get_task_info = 2,        -- detailed wait info per task
    @get_additional_info = 1;  -- session settings, etc.

-- Sort by tempdb usage to find the spiller
exec sp_WhoIsActive @sort_order = '[tempdb_current] desc';

-- Sort by CPU
exec sp_WhoIsActive @sort_order = '[CPU] desc';
```

Key columns to read: `blocking_session_id` and the `blocked_session_count` (with `@find_block_leaders=1` the lead blocker shows a high blocked count and zero blocker), `wait_info` (aggregated wait types with durations), `tempdb_current` / `tempdb_allocations`, and `sql_command` / `query_plan`.

A common production pattern: log it to a table on a schedule for a lightweight "what was happening" history.

```sql
-- One-time: build the destination with the exact schema sp_WhoIsActive emits
declare @schema nvarchar(max);
exec sp_WhoIsActive @return_schema = 1, @schema = @schema output;
set @schema = replace(@schema, '<table_name>', 'dbo.WhoIsActive_Log');
exec (@schema);

-- Then schedule this every 30–60s via Agent
exec sp_WhoIsActive @destination_table = 'dbo.WhoIsActive_Log';
```

## 1.4 Cumulative DMVs (Aggregate Health)

These accumulate from instance start. **Always diff two snapshots** for a meaningful window, or read them right after a restart for "since when it last mattered."

**`sys.dm_exec_query_stats` — top queries by cost.** Your "what's eating the server" source.

```sql
select top (25)
    qs.execution_count,
    qs.total_worker_time / 1000 as total_cpu_ms,
    (qs.total_worker_time / qs.execution_count) / 1000 as avg_cpu_ms,
    qs.total_logical_reads,
    qs.total_logical_reads / qs.execution_count as avg_logical_reads,
    qs.total_elapsed_time / 1000 as total_elapsed_ms,
    qs.last_execution_time,
    substring(t.text, (qs.statement_start_offset / 2) + 1,
        ((case qs.statement_end_offset
            when -1 then datalength(t.text)
            else qs.statement_end_offset
          end - qs.statement_start_offset) / 2) + 1) as statement_text,
    qp.query_plan
from sys.dm_exec_query_stats as qs
cross apply sys.dm_exec_sql_text(qs.sql_handle) as t
cross apply sys.dm_exec_query_plan(qs.plan_handle) as qp
order by qs.total_worker_time desc;   -- swap to total_logical_reads, total_elapsed_time as needed
```

Change the `order by` to pivot your hunt: CPU (`total_worker_time`), I/O (`total_logical_reads`), duration (`total_elapsed_time`), or frequency (`execution_count`). The cheap-but-run-a-million-times query often outweighs the one slow report.

Caveat: this only holds plans currently in cache. A plan evicted under memory pressure, or marked `RECOMPILE`, vanishes here — which is exactly why Query Store exists.

**`sys.dm_io_virtual_file_stats` — the cleanest proof of a storage problem.** Per-file read/write latency.

```sql
select
    db_name(vfs.database_id) as database_name,
    mf.name as logical_name,
    mf.type_desc,
    vfs.num_of_reads,
    vfs.num_of_writes,
    case when vfs.num_of_reads = 0 then 0
         else vfs.io_stall_read_ms / vfs.num_of_reads end as avg_read_latency_ms,
    case when vfs.num_of_writes = 0 then 0
         else vfs.io_stall_write_ms / vfs.num_of_writes end as avg_write_latency_ms,
    vfs.io_stall_read_ms,
    vfs.io_stall_write_ms,
    cast(vfs.num_of_bytes_read / 1048576.0 as decimal(18,2)) as mb_read,
    cast(vfs.num_of_bytes_written / 1048576.0 as decimal(18,2)) as mb_written,
    mf.physical_name
from sys.dm_io_virtual_file_stats(null, null) as vfs
inner join sys.master_files as mf
    on vfs.database_id = mf.database_id
    and vfs.file_id = mf.file_id
order by (vfs.io_stall_read_ms + vfs.io_stall_write_ms) desc;
```

Rule of thumb on latency (sustained, not spikes): **data files < 10–20 ms/read** is healthy, 20–50 ms is suspect, >50 ms is a problem. **Log files want < 5 ms/write** — log writes are synchronous on the commit path, so log latency throttles every write transaction.

**`sys.dm_db_index_usage_stats` — seeks/scans/updates per index.** Finds unused indexes (pure write overhead) and write-heavy ones.

```sql
select
    db_name() as database_name,
    object_name(i.object_id) as table_name,
    i.name as index_name,
    ius.user_seeks,
    ius.user_scans,
    ius.user_lookups,
    ius.user_updates,
    ius.last_user_seek,
    ius.last_user_scan
from sys.indexes as i
left join sys.dm_db_index_usage_stats as ius
    on i.object_id = ius.object_id
    and i.index_id = ius.index_id
    and ius.database_id = db_id()
where objectproperty(i.object_id, 'IsUserTable') = 1
    and i.type_desc <> 'HEAP'
order by ius.user_updates desc;     -- high updates + zero reads = drop candidate
```

This resets on restart and on index rebuild — judge it only over a representative uptime (a full business cycle, including month-end jobs).

## 1.5 Query Store — The Flight Recorder

Turn it on everywhere (2016+; on by default in 2022 and Azure). It persists query text, plans, and runtime stats *into the user database*, surviving restarts and cache eviction. It's the backbone of regression detection — "this query got slow after Tuesday's deploy" becomes a 30-second query instead of an archaeology project.

```sql
alter database [YourDB] set query_store = on;
alter database [YourDB] set query_store (
    operation_mode = read_write,
    max_storage_size_mb = 2048,
    data_flush_interval_seconds = 900,
    interval_length_minutes = 15,           -- aggregation granularity; 15–60 typical
    query_capture_mode = auto,              -- skip trivial/infrequent queries
    max_plans_per_query = 200,
    size_based_cleanup_mode = auto,
    cleanup_policy = (stale_query_threshold_days = 30)
);
```

**Regressed queries** — the killer feature. This finds queries that got measurably slower between two time windows:

```sql
select top (25)
    q.query_id,
    qt.query_sql_text,
    rs.avg_duration / 1000.0 as avg_duration_ms,
    rs.avg_cpu_time / 1000.0 as avg_cpu_ms,
    rs.avg_logical_io_reads,
    rs.count_executions,
    p.plan_id,
    rsi.start_time,
    rsi.end_time
from sys.query_store_runtime_stats as rs
inner join sys.query_store_runtime_stats_interval as rsi
    on rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
inner join sys.query_store_plan as p
    on rs.plan_id = p.plan_id
inner join sys.query_store_query as q
    on p.query_id = q.query_id
inner join sys.query_store_query_text as qt
    on q.query_text_id = qt.query_text_id
where rsi.start_time >= dateadd(day, -7, sysutcdatetime())
order by rs.avg_duration desc;
```

**Multiple plans for one query** — the parameter-sniffing fingerprint. If `query_id` X has two `plan_id`s with wildly different `avg_duration`, you've found a sniffing problem:

```sql
select
    p.query_id,
    p.plan_id,
    rs.avg_duration / 1000.0 as avg_duration_ms,
    rs.count_executions,
    p.is_forced_plan
from sys.query_store_plan as p
inner join sys.query_store_runtime_stats as rs
    on p.plan_id = rs.plan_id
where p.query_id = 12345     -- from the regressed-queries result
order by rs.avg_duration desc;
```

**Force the good plan** — Query Store's escape hatch for plan instability:

```sql
exec sp_query_store_force_plan @query_id = 12345, @plan_id = 67890;
-- and to release it later:
-- exec sp_query_store_unforce_plan @query_id = 12345, @plan_id = 67890;
```

Mostly you'll use the SSMS Query Store reports (Regressed Queries, Top Resource Consumers, Queries With Forced Plans) for the visual diff, then drop to T-SQL to force/unforce. The built-in views are the canonical interface.

## 1.6 Wait Statistics — The Methodology

`sys.dm_os_wait_stats` is the aggregate of every wait since restart. This is where wait-based tuning lives. The raw DMV is noisy with benign system waits, so the standard practice is Paul Randal's filtered query that excludes the harmless ones and ranks by percentage:

```sql
with waits as (
    select
        wait_type,
        wait_time_ms / 1000.0 as wait_s,
        (wait_time_ms - signal_wait_time_ms) / 1000.0 as resource_s,
        signal_wait_time_ms / 1000.0 as signal_s,
        waiting_tasks_count as wait_count,
        100.0 * wait_time_ms / sum(wait_time_ms) over () as pct,
        row_number() over (order by wait_time_ms desc) as rn
    from sys.dm_os_wait_stats
    where waiting_tasks_count > 0
        and wait_type not in (
            -- benign / idle waits to ignore (abbreviated; the full Randal list is longer)
            'BROKER_TASK_STOP', 'CLR_AUTO_EVENT', 'CLR_MANUAL_EVENT', 'CLR_SEMAPHORE',
            'DIRTY_PAGE_POLL', 'DISPATCHER_QUEUE_SEMAPHORE', 'FT_IFTS_SCHEDULER_IDLE_WAIT',
            'HADR_FILESTREAM_IOMGR_IOCOMPLETION', 'LAZYWRITER_SLEEP', 'LOGMGR_QUEUE',
            'ONDEMAND_TASK_QUEUE', 'PWAIT_ALL_COMPONENTS_INITIALIZED', 'QDS_PERSIST_TASK_MAIN_LOOP_SLEEP',
            'QDS_ASYNC_QUEUE', 'REQUEST_FOR_DEADLOCK_SEARCH', 'SLEEP_TASK', 'SLEEP_SYSTEMTASK',
            'SP_SERVER_DIAGNOSTICS_SLEEP', 'SQLTRACE_INCREMENTAL_FLUSH_SLEEP', 'WAIT_XTP_HOST_WAIT',
            'WAITFOR', 'XE_DISPATCHER_WAIT', 'XE_TIMER_EVENT', 'CXCONSUMER'
        )
)
select
    wait_type,
    cast(wait_s as decimal(18,2)) as wait_s,
    cast(resource_s as decimal(18,2)) as resource_s,
    cast(signal_s as decimal(18,2)) as signal_s,
    wait_count,
    cast(pct as decimal(5,2)) as pct,
    cast(wait_s / nullif(wait_count, 0) as decimal(18,4)) as avg_wait_s
from waits
where rn <= 15
order by wait_s desc;
```

Note **`signal_s`**: that's time spent *runnable* (waiting for CPU after the resource was ready). High signal time relative to resource time across the board is a CPU-pressure tell on its own.

**Reset the counters** when you want a clean window (e.g., before a load test):

```sql
dbcc sqlperf('sys.dm_os_wait_stats', clear);
```

For a true point-in-time window without resetting, snapshot the DMV into a temp table, wait N seconds, snapshot again, and subtract. That's what good monitoring tools do under the hood.

### Wait Type Catalog — recognize these on sight

| Wait type | What it means | First move |
|---|---|---|
| `PAGEIOLATCH_SH` / `_EX` | Waiting on a data page being read from disk | Check `dm_io_virtual_file_stats`; could be I/O *or* memory pressure forcing re-reads |
| `WRITELOG` | Transaction log flush latency | Log disk latency; or too many tiny commits (batch them) |
| `LCK_M_*` | Blocking — waiting to acquire a lock | Chase the blocking chain; find the long transaction |
| `PAGELATCH_*` (no IO) | In-memory page contention | Classic tempdb allocation contention (PFS/GAM/SGAM) or hot-page inserts |
| `CXPACKET` | Parallelism exchange — uneven work distribution | Tune MAXDOP + cost threshold; often a symptom, not the disease |
| `CXCONSUMER` | Benign parallelism consumer wait (2017+) | Usually ignore; split out from CXPACKET deliberately |
| `SOS_SCHEDULER_YIELD` | Threads yielding the CPU voluntarily | CPU pressure or large scans burning cycles |
| `RESOURCE_SEMAPHORE` | Query waiting for a memory grant | Memory pressure; oversized grants from bad estimates |
| `RESOURCE_SEMAPHORE_QUERY_COMPILE` | Waiting to compile (compile memory gate) | Plan-cache thrash, lots of ad-hoc compiles |
| `ASYNC_NETWORK_IO` | Server waiting for the client to consume rows | Almost always the *app*, not SQL — row-by-row consumption, no pagination |
| `THREADPOOL` | No worker threads available | Severe blocking exhausting the pool, or genuinely too many sessions — dangerous |
| `HADR_SYNC_COMMIT` | Sync-mode Availability Group commit latency | Network/secondary replica latency |
| `BACKUPIO` / `BACKUPBUFFER` | Backup throughput | Backup target speed, compression, striping |
| `OLEDB` | Linked server or DMV that uses OLE DB internally | Often DBCC CHECKDB or linked-server calls |

The discipline: a top wait points at a subsystem, not a fix. `PAGEIOLATCH` says "I/O subsystem" — but the cure might be more RAM (so pages stay cached), a missing index (so you read fewer pages), or actually faster disk. Waits direct the investigation; they don't end it.

## 1.7 External Monitoring — Prometheus / Grafana

This is where your homelab stack earns its keep over people stuck in SSMS. The standard path:

- **Exporter:** the community `sql_exporter` (free, config-driven, runs arbitrary T-SQL collectors and exposes them as Prometheus metrics) or a vendor agent. Point it at the instance with a least-privilege monitoring login (`VIEW SERVER STATE`, `VIEW ANY DEFINITION`).
- **Prometheus** scrapes on an interval; you write recording rules for the diffs (wait-stat deltas, file-stat deltas) so the dashboards show *rates*, not since-restart totals.
- **Grafana** dashboards: batch requests/sec, compilations/sec, page life expectancy, buffer cache hit ratio, top waits over time, file latency, blocked process count, tempdb usage, log flush rate.
- **Alerting** off Prometheus or Grafana with thresholds tied to *your* baseline, not generic numbers.

The thing to internalize: the DMVs are point-in-time or since-restart. To get **trend**, something external has to sample and store them on a clock. Query Store gives you per-query trend inside one DB; Prometheus/Grafana gives you instance- and host-level trend across everything, with retention you control and correlation against OS metrics (CPU, disk queue, network) on the same timeline.

## 1.8 Baselines & Alerting

You cannot answer "is this normal?" without a baseline. Capture, on a schedule, into a history table or your TSDB:
- Wait-stat deltas (top 15) per interval
- File latency deltas
- Batch requests/sec, compiles/sec, recompiles/sec
- Page Life Expectancy (per NUMA node on big boxes — the aggregate lies)
- Memory grants pending, `RESOURCE_SEMAPHORE` waits
- Active/blocked session counts, longest-running transaction age

Then alert on *deviation from baseline* and on discrete events (severity 17+ in the error log, blocked process report firing, failed jobs, log file growth, AG not synchronizing). Generic threshold alerts ("CPU > 80%") generate noise; baseline-relative alerts ("waits shifted to `RESOURCE_SEMAPHORE` and grants-pending is non-zero, which never happens here") generate signal.

# PART 2 — PERFORMANCE TROUBLESHOOTING

## 2.1 The Triage Order

A repeatable sequence beats poking around. My default when a ticket lands:

**Step 1 — Instance-wide or single query?**
Run `sp_WhoIsActive @find_block_leaders=1`. If you see a blocking chain, chase the lead blocker. If many sessions wait on the *same* resource (all `PAGEIOLATCH`, all `RESOURCE_SEMAPHORE`), it's systemic — go to the relevant subsystem section. If it's one fat query and everyone else is fine, it's a query problem.

**Step 2 — Characterize by waits.**
Diff `dm_os_wait_stats` over the bad window, or read Query Store's per-query wait categories. The top wait tells you which section below to open.

**Step 3 — Drill into the culprit** (sections 2.2–2.12).

**Step 4 — Confirm the fix changed the *waits*, not just the clock.** Re-measure identically.

The whole of "the database is slow" almost always resolves to one of: **blocking, a plan regression, stale statistics, a missing index, tempdb contention, or I/O.** The waits tell you which before you open a single plan.

## 2.2 Blocking & Locking

Blocking is one session holding a lock another needs. Normal in bursts; a problem when held long.

**Find the blocking chain and the lead blocker:**

```sql
select
    r.session_id,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time,
    r.wait_resource,
    db_name(r.database_id) as database_name,
    t.text as blocked_statement,
    s.host_name,
    s.program_name,
    s.login_name
from sys.dm_exec_requests as r
inner join sys.dm_exec_sessions as s
    on r.session_id = s.session_id
cross apply sys.dm_exec_sql_text(r.sql_handle) as t
where r.blocking_session_id <> 0;

-- What is the lead blocker actually doing / holding?
-- (sql_handle of an idle blocker comes from dm_exec_connections.most_recent_sql_handle)
select
    c.session_id,
    t.text as last_statement,
    s.open_transaction_count,
    s.last_request_start_time,
    s.last_request_end_time
from sys.dm_exec_connections as c
inner join sys.dm_exec_sessions as s
    on c.session_id = s.session_id
cross apply sys.dm_exec_sql_text(c.most_recent_sql_handle) as t
where c.session_id = <lead_blocker_session_id>;
```

**Inspect the locks themselves:**

```sql
select
    tl.request_session_id,
    tl.resource_type,
    tl.resource_database_id,
    db_name(tl.resource_database_id) as database_name,
    tl.resource_associated_entity_id,
    tl.request_mode,
    tl.request_status        -- GRANT vs WAIT
from sys.dm_tran_locks as tl
where tl.request_session_id <> @@spid
order by tl.request_session_id, tl.request_status;
```

Long-held locks almost always trace to one of: a **long-running transaction** (someone's batch, or an open transaction left idle), a **missing index** forcing a scan that takes broad locks, an **unindexed foreign key** causing parent updates to lock children, or a **wrong isolation level** (someone running everything serializable, or holding shared locks under repeatable read).

**Last resort to clear it:** `kill <session_id>;` — but understand the rollback cost. Killing a transaction that's modified a million rows triggers a rollback that can take *longer* than letting it finish, and you can't interrupt the rollback. Check `KILL <id> WITH STATUSONLY` to watch rollback progress.

**Structural fixes** beyond the immediate kill: shorten transactions, add the missing index, consider **Read Committed Snapshot Isolation (RCSI)** so readers don't block writers (it shifts the cost to tempdb version store — a real tradeoff, not free, but often the right call for read-heavy OLTP).

## 2.3 Deadlocks

Two sessions each holding a lock the other needs, in opposite order — the engine picks a victim and rolls it back (error 1205). Deadlocks are *not* blocking; they resolve themselves. Your job is to read the graph and prevent recurrence.

The good news: **`system_health` already captures every deadlock graph** (see 3.4). You rarely need to set up capture — you need to read what's already there:

```sql
-- Pull deadlock graphs out of the system_health session
with sh as (
    select cast(xet.target_data as xml) as target_data
    from sys.dm_xe_session_targets as xet
    inner join sys.dm_xe_sessions as xes
        on xet.event_session_address = xes.address
    where xes.name = 'system_health'
        and xet.target_name = 'ring_buffer'
)
select
    xer.value('(@timestamp)[1]', 'datetime2') as event_time,
    xer.query('.') as deadlock_graph
from sh
cross apply target_data.nodes('//RingBufferTarget/event[@name="xml_deadlock_report"]') as t(xer)
order by event_time desc;
```

Reading the graph: it shows two (or more) **process nodes** and the **resource nodes** they're fighting over, with arrows for owner vs. requester. Find the two resources locked in opposite order — that ordering is the bug. The `inputbuf` in each process node is the statement each session was running.

Prevention patterns, in rough order of preference: **access objects in a consistent order** everywhere (the root cause is usually inconsistent ordering); **shorten transactions** to narrow the window; **add indexes** so operations take fewer, narrower locks instead of scanning; consider **RCSI** to remove reader/writer deadlocks entirely; and only as a tactical measure, **retry logic** in the app on 1205 (deadlocks are by definition transient, so a retry often just succeeds — but treat it as a band-aid, not a fix).

## 2.4 Reading Query Plans

When waits point at a query, the plan is the evidence. Pull it live (`dm_exec_query_plan`), from cache (`dm_exec_query_stats`), or from Query Store. The usual suspects, in the order I scan for them:

- **Scans where seeks belong** — a clustered/table scan on a big table with a selective predicate means a missing or unusable index (or a non-sargable predicate, below).
- **Fat arrows / estimate vs. actual mismatch** — hover the operators; when *estimated rows* and *actual rows* diverge by orders of magnitude, the optimizer was working from bad cardinality. Cause is stale statistics, a non-sargable predicate, a local variable the optimizer can't sniff, or a multi-statement TVF (which estimates a fixed row count).
- **Spills** (hash warning / sort warning, the yellow triangle) — the operator needed more memory than its grant and spilled to tempdb. Traces to bad estimates undersizing the grant.
- **Key Lookups** — a nonclustered index seek followed by a lookup into the clustered index for columns it didn't cover. Fix by widening the index with `INCLUDE` columns *if* the query is hot enough to justify it.
- **Implicit conversions** — `CONVERT_IMPLICIT` in the plan, usually from comparing a column to a mismatched type (the classic: `NVARCHAR` parameter against a `VARCHAR` column, or a string against an int). It silently kills index usage because the column side gets converted. Fix the types.

**Non-sargable predicates** are the recurring own-goal — wrapping the indexed column in a function or expression makes the index unusable:

```sql
-- non-sargable: function on the column -> scan
where year(o.OrderDate) = 2026

-- sargable: range on the bare column -> seek
where o.OrderDate >= '2026-01-01'
    and o.OrderDate < '2027-01-01'
```

Same trap with leading wildcards (`like '%foo'`), arithmetic on the column (`where Col + 1 = @x`), and implicit conversions. Keep the indexed column bare on one side of the predicate.

## 2.5 Parameter Sniffing

The optimizer compiles a plan using the parameter values from the *first* execution, then caches and reuses it. When the data is skewed, the plan that's optimal for the sniffed value is terrible for others. Symptom: **"fast sometimes, slow other times, same query, same parameters-shaped input."**

Diagnosis: Query Store shows one `query_id` with **multiple plans** of divergent performance (the query in 1.5). Or you flush the plan and it's suddenly fast — that's sniffing confirmed.

Fixes, from least to most blunt:
- `OPTION (RECOMPILE)` — compile every time with the actual values. Best plan per execution, at compile cost. Fine for queries run occasionally; wrong for high-frequency ones.
- `OPTION (OPTIMIZE FOR (@p = <typical_value>))` — pin the plan to a value you choose.
- `OPTION (OPTIMIZE FOR UNKNOWN)` — compile for the average density, ignoring the sniffed value. Gives a stable mediocre plan instead of a bimodal one.
- **Query Store forced plan** — when you've identified the good plan and want it pinned without touching code.
- Rewrite into separate code paths (e.g., branch on the parameter and call distinct procedures) for genuinely bimodal workloads.

There's no free option — recompiling costs CPU, pinning a plan accepts it's wrong for some inputs. Pick based on frequency and skew.

## 2.6 Statistics & Cardinality

The optimizer's cost estimates are only as good as its statistics — histograms of column value distribution. Stale stats are behind a huge share of "the plan went bad" incidents.

```sql
-- When were stats last updated, and how stale by row churn?
select
    object_name(s.object_id) as table_name,
    s.name as stats_name,
    sp.last_updated,
    sp.rows,
    sp.rows_sampled,
    sp.modification_counter,         -- rows changed since last update
    cast(100.0 * sp.modification_counter / nullif(sp.rows, 0) as decimal(5,2)) as pct_modified
from sys.stats as s
cross apply sys.dm_db_stats_properties(s.object_id, s.stats_id) as sp
where objectproperty(s.object_id, 'IsUserTable') = 1
order by sp.modification_counter desc;

-- Update with full scan when auto-update sampling isn't cutting it
update statistics dbo.YourTable with fullscan;
```

The default **auto-update** threshold (roughly 20% + 500 rows pre-2016, dynamic/sqrt-based with TF2371 or on 2016+) is too lazy for large tables — a billion-row table needs hundreds of millions of changes before auto-update fires, by which point the histogram is fiction. For big or fast-churning tables, schedule explicit `UPDATE STATISTICS` (or a maintenance solution like Ola Hallengren's) rather than trusting auto-update.

Also know the **Cardinality Estimator (CE) version** matters: the 2014+ "new CE" changed estimates and occasionally regresses plans that were fine under the legacy CE. It's tied to the database compatibility level. If a plan regresses right after a compat-level bump, the new CE is a prime suspect — you can revert per-query (`OPTION (USE HINT('FORCE_LEGACY_CARDINALITY_ESTIMATION'))`) or database-wide, and Query Store gives you the before/after evidence.

## 2.7 Indexing

**Find missing indexes the optimizer wished it had** (use as a *hint*, never blindly — it suggests wide, overlapping indexes):

```sql
select
    mid.statement as table_name,
    migs.user_seeks,
    migs.avg_total_user_cost,
    migs.avg_user_impact,
    migs.user_seeks * migs.avg_total_user_cost * (migs.avg_user_impact / 100.0) as improvement_measure,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
from sys.dm_db_missing_index_group_stats as migs
inner join sys.dm_db_missing_index_groups as mig
    on migs.group_handle = mig.index_group_handle
inner join sys.dm_db_missing_index_details as mid
    on mig.index_handle = mid.index_handle
order by improvement_measure desc;
```

Treat these as candidates, not commands. The DMV reports each missing index in isolation, so it'll suggest five overlapping indexes when one well-designed composite covers all five. Design by hand: key columns by selectivity, `INCLUDE` for covering, and account for the write cost — every index is maintained on every insert/update/delete.

**Find unused and duplicate indexes** to drop (write overhead with no read benefit) — that's `dm_db_index_usage_stats` from 1.4: high `user_updates`, zero/near-zero seeks/scans, judged over a full business cycle.

**Fragmentation** matters less than people think on modern storage (SSD/NVMe make the random-vs-sequential gap small), but page density still matters for cache efficiency. Reorganize vs. rebuild on the usual thresholds (reorg 5–30%, rebuild >30%), and prefer Ola Hallengren's `IndexOptimize` over hand-rolled maintenance — it factors in fragmentation *and* page count so you don't rebuild tiny indexes pointlessly.

## 2.8 I/O

When `PAGEIOLATCH_*` or `WRITELOG` tops the waits, go to `dm_io_virtual_file_stats` (the query in 1.4). Sustained read latency >20 ms or log write latency >5 ms points at storage. But before blaming the SAN, rule out the cheaper causes:

- **Memory pressure** — if data won't stay cached (low Page Life Expectancy, high lazy-writer activity), you re-read from disk constantly and it *looks* like an I/O problem. Adding RAM can fix "I/O" waits.
- **Missing index / bad plan** — a scan reads orders of magnitude more pages than a seek. The cheapest way to cut I/O is often to read less, not to buy faster disk.
- **Implicit conversions / non-sargable predicates** forcing scans (2.4).

Only after ruling those out is it genuinely the storage layer — and then it's a real conversation about latency, queue depth, and layout.

## 2.9 tempdb

tempdb is shared by the whole instance — temp tables, table variables, sort/hash spills, version store (RCSI/snapshot), online index builds. Two distinct problems:

**Allocation contention** — `PAGELATCH_*` (note: latch, *not* IO latch) on pages like `2:1:1`, `2:1:3` (PFS/GAM/SGAM allocation pages). Many sessions creating temp objects simultaneously serialize on these in-memory allocation structures.

```sql
-- Live tempdb latch contention check
select
    wt.session_id,
    wt.wait_type,
    wt.wait_duration_ms,
    wt.resource_description
from sys.dm_os_waiting_tasks as wt
where wt.wait_type like 'PAGELATCH%'
    and wt.resource_description like '2:%';   -- database_id 2 = tempdb
```

Fix: **multiple equally-sized tempdb data files** (start at 4, or one per logical core up to 8, all the same size with the same autogrowth). On 2016+ this is largely handled by setup defaults plus the always-on round-robin allocation; pre-2016 you also needed trace flags **1117** (grow all files together) and **1118** (uniform extents) — both are default behavior for tempdb on 2016+, so don't bother setting them on modern versions.

**Space blowout** — a runaway query spilling or a huge version-store buildup fills tempdb. Find the consumer:

```sql
select
    ssu.session_id,
    ssu.user_objects_alloc_page_count,
    ssu.internal_objects_alloc_page_count,
    t.text as current_statement
from sys.dm_db_session_space_usage as ssu
left join sys.dm_exec_requests as r on ssu.session_id = r.session_id
outer apply sys.dm_exec_sql_text(r.sql_handle) as t
where ssu.user_objects_alloc_page_count + ssu.internal_objects_alloc_page_count > 0
order by (ssu.user_objects_alloc_page_count + ssu.internal_objects_alloc_page_count) desc;
```

`internal_objects` ballooning = spills (fix the query's estimates); version store ballooning = a long-open transaction under RCSI preventing cleanup (find and kill the long transaction).

## 2.10 Memory & Memory Grants

Each query that sorts or hashes gets a **memory grant** estimated at compile time. Underestimate → spill to tempdb (slow). Overestimate → fewer concurrent queries, `RESOURCE_SEMAPHORE` waits as queries queue for grants.

```sql
-- Queries waiting for grants right now, and what's outstanding
select
    mg.session_id,
    mg.requested_memory_kb,
    mg.granted_memory_kb,
    mg.required_memory_kb,
    mg.used_memory_kb,
    mg.grant_time,
    mg.wait_time_ms,
    mg.dop,
    t.text as statement_text
from sys.dm_exec_query_memory_grants as mg
cross apply sys.dm_exec_sql_text(mg.sql_handle) as t
order by mg.requested_memory_kb desc;
```

`granted` ≫ `used` repeatedly means inflated grants from bad estimates — fix the cardinality (stats, sargability) rather than throwing RAM at it. SQL Server 2017+ has **Memory Grant Feedback**, which self-corrects grants across executions; if you're on a recent version, Query Store may show the grant settling over runs on its own.

Instance-level memory health: **Page Life Expectancy** (per NUMA node — the aggregate hides a starved node), buffer cache hit ratio (less useful than people think), and whether `max server memory` is set sanely (it should be — leaving it at the default 2 PB lets SQL starve the OS).

## 2.11 CPU

`SOS_SCHEDULER_YIELD` topping waits, or high `signal_wait_time`, means CPU pressure. Confirm and find the burners:

```sql
-- CPU by recent query (from cache)
select top (20)
    qs.total_worker_time / 1000 as total_cpu_ms,
    qs.execution_count,
    (qs.total_worker_time / qs.execution_count) / 1000 as avg_cpu_ms,
    t.text as statement_text
from sys.dm_exec_query_stats as qs
cross apply sys.dm_exec_sql_text(qs.sql_handle) as t
order by qs.total_worker_time desc;

-- Scheduler-level pressure: runnable tasks queued behind the CPU
select
    scheduler_id,
    cpu_id,
    current_tasks_count,
    runnable_tasks_count,       -- sustained > 0 means threads queuing for CPU
    work_queue_count
from sys.dm_os_schedulers
where scheduler_id < 255;       -- user schedulers only
```

Sustained `runnable_tasks_count > 0` across schedulers is direct evidence of CPU starvation. Causes are usually the same handful: heavy scans (missing indexes), excessive compilation (ad-hoc unparameterized SQL thrashing the plan cache — check `compilations/sec` vs `batch requests/sec`), bad plans burning cycles, or genuinely undersized hardware. Implicit conversions and spills also show up as CPU. As always: cut the work before buying cores.

## 2.12 Parallelism — MAXDOP & Cost Threshold

`CXPACKET` high in the waits is the parallelism tell — but it's usually a *symptom* of something else (a big scan that shouldn't be parallel because it shouldn't be a scan). Don't just clamp MAXDOP and call it done.

Two knobs:
- **Cost Threshold for Parallelism** — the plan-cost above which SQL considers a parallel plan. The default **5** is a 1990s relic; raise it (25–50 is a common starting range) so trivial queries stay serial and only genuinely expensive ones parallelize.
- **MAXDOP** — max cores per parallel query. Microsoft's guidance keys off NUMA/core count (commonly 8, or the cores-per-NUMA-node, whichever is lower). 0 (unlimited) on a many-core box invites one query to monopolize every scheduler.

The right sequence when you see `CXPACKET`: first ask *why is this query parallel at all* — frequently the answer is a missing index turning a seek into a parallel scan. Fix that and the parallelism wait evaporates without touching the settings. Tune the settings for the workload as a whole, not in reaction to one query.

# PART 3 — LOGS, EVENTS & DEBUGGING

Three distinct logging systems. Knowing which one holds the answer saves the most time.

## 3.1 SQL Server Error Log

The instance's own log — startup, recovery, failed logins, backup/restore, severity 17+ errors, I/O-longer-than-15-seconds warnings, deadlock info (if TF1222 is on). **Read this first when something broke at a specific point in time.**

```sql
-- Read current error log (0 = current; 1, 2... = archived)
exec sys.sp_readerrorlog 0;

-- Search: param 3 and 4 are two AND-ed search strings
exec sys.sp_readerrorlog 0, 1, N'Login failed';
exec sys.sp_readerrorlog 0, 1, N'error', N'17';

-- The extended version exposes date filtering and result ordering
exec sys.xp_readerrorlog 0, 1, N'I/O', NULL, '2026-06-01', '2026-06-25', N'desc';
```

**Operational hygiene:** the log cycles on restart, and the default keeps only **6** archived files — on a busy instance that's nowhere near enough history. Raise the retention (SSMS → SQL Server Logs → Configure, or the registry/`xp_instance_regwrite` path) to 30+, and cycle it on a schedule so no single file grows enormous:

```sql
exec sys.sp_cycle_errorlog;   -- schedule daily via Agent; pairs with higher retention count
```

## 3.2 Windows Event Log (Application Log)

SQL Server also writes to the Windows **Application** log. This is where you look for things *outside* SQL's own world: service crash/restart, OS-level disk errors, cluster and Availability Group failovers, OS-side memory pressure, and startup failures where SQL never got far enough to write its own log. **When the SQL error log is silent but something's clearly wrong, check here.** (Read it with Event Viewer, or `Get-WinEvent` / `Get-EventLog` from PowerShell — your stack.)

```powershell
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'MSSQLSERVER' } -MaxEvents 100 |
    Where-Object { $_.LevelDisplayName -in 'Error','Warning' } |
    Select-Object TimeCreated, Id, LevelDisplayName, Message
```

## 3.3 Extended Events (XEvents)

The modern tracing engine. It replaces the deprecated **SQL Trace / Profiler** — lighter weight, more granular, and the only forward-looking option (Profiler still ships but is on the deprecation path; don't build new tooling on it). Invest here.

**Anatomy of a session:** *events* (what to capture) + *actions* (extra columns to attach, like sql_text/session_id) + *predicates* (filters — apply them hard) + *targets* (where output goes: `ring_buffer` for live in-memory, `event_file` for persisted to disk).

**A practical session — capture slow statements over 1 second, persisted to file:**

```sql
create event session [slow_statements] on server
add event sqlserver.sql_statement_completed (
    action (
        sqlserver.sql_text,
        sqlserver.session_id,
        sqlserver.database_name,
        sqlserver.client_app_name,
        sqlserver.username
    )
    where duration > 1000000        -- microseconds; 1,000,000 us = 1 second
        and sqlserver.database_name = N'YourDB'
)
add target package0.event_file (
    set filename = N'slow_statements',
        max_file_size = 256,        -- MB per rollover file
        max_rollover_files = 5
)
with (
    max_dispatch_latency = 5 seconds,
    track_causality = on,
    startup_state = off
);

alter event session [slow_statements] on server state = start;
```

**Read the captured events back:**

```sql
select
    object_name as event_name,
    event_data.value('(event/@timestamp)[1]', 'datetime2') as event_time,
    event_data.value('(event/data[@name="duration"]/value)[1]', 'bigint') / 1000 as duration_ms,
    event_data.value('(event/action[@name="sql_text"]/value)[1]', 'nvarchar(max)') as sql_text,
    event_data.value('(event/action[@name="database_name"]/value)[1]', 'nvarchar(128)') as database_name,
    event_data.value('(event/action[@name="session_id"]/value)[1]', 'int') as session_id
from (
    select object_name, cast(event_data as xml) as event_data
    from sys.fn_xe_file_target_read_file('slow_statements*.xel', null, null, null)
) as x
order by event_time desc;
```

**Predicate discipline matters:** XEvents is cheap but not free. `sql_statement_completed` with no filter on a busy OLTP instance generates a firehose and adds real overhead. Always filter to a database, an app name, a duration threshold, a session — capture the narrowest thing that answers your question. For ad-hoc work the SSMS XEvents **Watch Live Data** viewer is fine; for anything you'll analyze later, use `event_file` and query it.

Common events worth knowing: `sql_statement_completed` / `rpc_completed` (statement timing), `wait_info` (per-session waits — wait analysis at the query level), `lock_acquired` / `lock_released`, `blocked_process_report` (3.6), `query_post_execution_showplan` (actual plans — *expensive*, filter hard), `xml_deadlock_report` (3.4).

## 3.4 system_health — The Free Black Box

A `system_health` XEvents session **runs by default on every instance**, and most people don't know they're already sitting on a black-box recorder. It captures, automatically: every **deadlock graph**, severe errors (severity ≥ 20, and 17–19 memory-related), sessions hitting long lock/latch waits (>15s), `RESOURCE_SEMAPHORE` waits, and the periodic `sp_server_diagnostics` health output.

Before you build any new session, **query what's already captured.** The deadlock-extraction query is in 2.3. More generally:

```sql
-- Dump recent system_health events from its event_file target
select
    object_name as event_name,
    cast(event_data as xml) as event_data,
    file_name,
    file_offset
from sys.fn_xe_file_target_read_file('system_health*.xel', null, null, null)
order by file_offset desc;
```

The ring-buffer target gives you the most recent in-memory slice (faster, smaller); the event_file target gives you more history on disk. For deadlocks and recent severe errors, this is usually all the capture you need.

## 3.5 The Default Trace

A lightweight SQL Trace that's *still running* on most instances unless explicitly disabled (it predates XEvents and lingers for back-compat). It captures schema/DDL changes, config changes (`sp_configure`), file growth/shrink events, and a few others — low volume, useful for "who changed what."

```sql
-- Is it on, and where's the file?
select * from sys.configurations where name = 'default trace enabled';

select top (200)
    te.name as event_name,
    t.DatabaseName,
    t.NTUserName,
    t.HostName,
    t.ApplicationName,
    t.StartTime,
    t.TextData
from sys.fn_trace_gettable(
        (select cast(value as nvarchar(260))
         from sys.fn_trace_getinfo(default)
         where property = 2), default) as t
inner join sys.trace_events as te
    on t.EventClass = te.trace_event_id
order by t.StartTime desc;
```

It's the quickest answer to "when did this table get altered / when did the data file last autogrow?" without having set up anything.

## 3.6 The Blocked Process Report

A fire-on-threshold event: when a session is blocked longer than N seconds, SQL emits a report with both the blocked and blocking statements. You enable it by setting the threshold, then capture it via XEvents (or the default-off SQL Trace event).

```sql
-- Set the threshold (seconds). 0 = off. 5–20 is typical.
exec sp_configure 'show advanced options', 1; reconfigure;
exec sp_configure 'blocked process threshold', 10; reconfigure;

-- Capture it
create event session [blocked_process] on server
add event sqlserver.blocked_process_report
add target package0.event_file (set filename = N'blocked_process');
alter event session [blocked_process] on server state = start;
```

The report is XML showing the blocked process and the blocking process with their input buffers — exactly the "who's holding what" you'd otherwise reconstruct by hand, but captured automatically the moment blocking crosses your threshold. Pairs perfectly with alerting: fire a notification when this event lands.

## 3.7 Severity Levels — The Triage Key

Every SQL Server error carries a severity. It's how you decide what pages someone:

| Severity | Meaning | Action |
|---|---|---|
| 0–10 | Informational | Ignore for alerting |
| 11–16 | User-correctable (constraint violation, bad object name, deadlock victim 1205) | App/dev concern; log, don't page |
| 17 | Insufficient resources (out of memory, disk full, locks) | Alert — server is stressed |
| 18 | Non-fatal internal error | Alert |
| 19 | Internal resource limit exceeded | Alert |
| **20–25** | **Fatal** | **Page someone** |

The 20–25 band is where you stop reading and start acting: 20–22 are fatal errors in the current process/statement; **23–24 frequently mean corruption** (24 is the media/hardware-error signal — go straight to `DBCC CHECKDB`); 25 is a fatal system error. Anything 20+ in the error log warrants immediate investigation and almost always an alert.

```sql
-- DBCC CHECKDB when corruption is suspected (severity 23/24, 823/824 errors)
dbcc checkdb ('YourDB') with no_infomsgs, all_errormsgs;
```

Also watch for errors **823, 824, 825** specifically — these are I/O integrity errors (823 = OS-level I/O failure, 824 = logical consistency / checksum failure, 825 = read-retry succeeded, an early warning the disk is going). 825 in particular is the canary: it means a read *failed and then succeeded on retry*, so the data's fine *this time* but the storage is failing. Alert on it.

## 3.8 Reading a Deadlock Graph

The graph (from system_health, 2.3/3.4) has two parts:

**Process nodes** (`<process-list>`) — one per session in the deadlock. Each shows the `spid`, the `isolationlevel`, the `inputbuf` (the statement it was running), and which resource it *owns* vs. *waits on*. The victim is flagged (`victim` attribute on the deadlock report).

**Resource nodes** (`<resource-list>`) — the locked objects (keys, pages, objects, RIDs), each listing its `owner` (who holds it) and `waiter` (who wants it) with the lock modes.

To diagnose: trace the cycle. Process A owns resource 1, waits on resource 2; process B owns resource 2, waits on resource 1. That **opposite ordering** is the bug — A and B touch the same two objects in different order. Map the resources back to tables/indexes (the `objectname` in the resource node), look at the two `inputbuf` statements, and you've found the two code paths to reconcile (usually by enforcing a consistent access order, or by indexing so the operations take narrower locks).
