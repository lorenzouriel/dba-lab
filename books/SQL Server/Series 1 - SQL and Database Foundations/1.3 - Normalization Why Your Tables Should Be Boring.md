# Normalization: Why Your Tables Should Be Boring

*Series 1 — SQL & Database Foundations | The SQL Server Deep Dive*

---

You have a `sales` table. Every row has the product name, product description, and product category alongside the sale data. Then someone renames "Product A" to "Widget Pro." You update it in one row. Three months later, you discover 847 rows still say "Product A" and 23 say "Widget Pro." Your reports are now inconsistent, and nobody knows which name is correct.

This is the kind of problem normalization was designed to prevent — not in theory, but in practice, in production.

---

## What Normalization Is

**Normalization** is the process of structuring your tables to eliminate redundancy and prevent data anomalies. It's a set of rules — called Normal Forms — that you apply progressively to push a messy table toward a clean, consistent structure.

The problems it prevents fall into three categories:

- **Insertion anomalies:** You can't insert data for one thing without inserting data for something else (e.g., you can't add a new product without also creating a sale)
- **Update anomalies:** Changing one piece of information requires updating it in multiple rows (the "Widget Pro" problem above)
- **Deletion anomalies:** Deleting one thing accidentally deletes something else (removing the last sale for a product removes the product's existence from the database)

The mechanism behind normalization is **functional dependency** — understanding which columns *determine* the values of other columns. If you change the primary key, which columns must change with it? Those are functionally dependent on the key. If a non-key column is functionally dependent on another non-key column, you have a problem.

---

## The Normal Forms (What You Actually Need to Know)

### 1NF — First Normal Form: No Repeating Groups

Each column must hold a single, atomic value. No lists. No comma-separated values. No `phone_1`, `phone_2`, `phone_3` columns.

```sql
-- Violates 1NF: multiple phone numbers in one column
CREATE TABLE dbo.Customers (
    customer_id   INT          PRIMARY KEY,
    first_name    VARCHAR(100),
    phone_numbers VARCHAR(500) -- "555-1234, 555-5678, 555-9999"
);

-- 1NF-compliant: one value per row
CREATE TABLE dbo.CustomerPhones (
    phone_id    INT          PRIMARY KEY,
    customer_id INT          NOT NULL REFERENCES dbo.Customers(customer_id),
    phone       VARCHAR(20)  NOT NULL
);
```

The practical test: can you add a `WHERE phone_numbers = '555-1234'` and get a reliable result? If not, you're not in 1NF.

### 2NF — Second Normal Form: Every Non-Key Column Depends on the Full Key

This only applies to tables with composite primary keys (PKs made of multiple columns). Every non-key column must depend on *all* parts of the key, not just part of it.

In `OrderDetails`, the PK is (order_id, product_id). `quantity` depends on the full combination — it's how many of *this product* in *this order*. But `product_name` only depends on `product_id`, not on `order_id`. That's a partial dependency — a 2NF violation.

```sql
-- Violates 2NF: product_name depends only on product_id, not on (order_id, product_id)
CREATE TABLE dbo.OrderDetails (
    order_id      INT,
    product_id    INT,
    product_name  VARCHAR(200), -- partial dependency!
    quantity      INT,
    unit_price    DECIMAL(10,2),
    PRIMARY KEY (order_id, product_id)
);

-- 2NF-compliant: product_name lives in Products, not here
CREATE TABLE dbo.OrderDetails (
    order_detail_id INT            PRIMARY KEY,
    order_id        INT            NOT NULL REFERENCES dbo.Orders(order_id),
    product_id      INT            NOT NULL REFERENCES dbo.Products(product_id),
    quantity        INT            NOT NULL,
    unit_price      DECIMAL(10,2)  NOT NULL
);
```

### 3NF — Third Normal Form: No Transitive Dependencies

No non-key column should depend on another non-key column. If column C depends on column B, which depends on the primary key A, that's a transitive dependency — C doesn't belong in this table.

Classic example: a table with `employee_id`, `department_id`, and `department_name`. `department_name` depends on `department_id`, which depends on `employee_id`. Remove `department_name` from the employees table; it belongs in a `Departments` table.

```sql
-- Violates 3NF: department_name transitively depends on employee_id via department_id
CREATE TABLE dbo.Employees (
    employee_id     INT          PRIMARY KEY,
    name            VARCHAR(100),
    department_id   INT,
    department_name VARCHAR(100) -- should live in Departments table
);

-- 3NF-compliant
CREATE TABLE dbo.Departments (
    department_id   INT          PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

CREATE TABLE dbo.Employees (
    employee_id   INT PRIMARY KEY,
    name          VARCHAR(100),
    department_id INT REFERENCES dbo.Departments(department_id)
);
```

---

## 4NF: When You Have Independent Multivalued Facts

If a table has two independent sets of repeating values for the same entity, split them. A `project_id` that can be associated with multiple employees *and* multiple clients has two independent multivalued facts — separate them into `ProjectEmployees` and `ProjectClients` tables.

In practice, most production databases only need to reach 3NF. 4NF comes up in specific modeling scenarios with complex many-to-many relationships.

---

## The Trap

**Over-normalizing for reporting.** Normalization is the right tool for your operational (OLTP) database — the one that gets written to constantly. But reporting databases (OLAP/data warehouses) often *deliberately denormalize* — joining 15 tables on every query is slow, and flattening the data into fewer, wider tables can be the right call.

Know where you're operating: normalize your transactional system, and decide consciously whether to denormalize for read-heavy analytics workloads.

---

## Key Takeaways

- **1NF eliminates repeating groups** — each column holds one atomic value
- **2NF removes partial dependencies** — in composite-key tables, every column must depend on the *whole* key
- **3NF removes transitive dependencies** — non-key columns can only depend on the primary key, not on each other
- **Normalization is for OLTP databases** — reporting databases often intentionally trade normalization for read performance
- **The goal is boring tables** — small, focused, single-purpose tables are easier to maintain and trust
