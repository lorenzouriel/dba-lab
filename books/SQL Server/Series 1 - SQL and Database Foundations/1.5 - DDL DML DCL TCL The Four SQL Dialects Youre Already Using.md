# DDL, DML, DCL, TCL: The Four SQL Dialects You're Already Using

*Series 1 — SQL & Database Foundations | The SQL Server Deep Dive*

---

Every SQL command you write belongs to one of four categories. You've probably used all four without knowing their names — and most developers don't learn them until an interviewer asks, or until they need to explain to someone else why a `TRUNCATE` behaves differently from a `DELETE`. Knowing the categories is knowing the mental model behind the whole language.

---

## Why SQL Has Subsets

SQL is described as a query language, but it does much more than retrieve data. It creates tables, inserts rows, grants permissions, and manages transactions. These are fundamentally different kinds of operations — structurally defining a table has nothing to do with filtering its rows. The four SQL subsets exist to name these distinct concerns.

Each subset answers a different question:
- **DDL** — "What structure does the data live in?"
- **DML** — "What data exists and how do I work with it?"
- **DCL** — "Who is allowed to do what?"
- **TCL** — "How do I group operations into atomic units?"

---

## DDL — Data Definition Language

DDL commands define and modify the *structure* of database objects: tables, indexes, views, schemas. They don't touch the data — they define the containers that hold the data.

The four core DDL commands:

```sql
-- CREATE: build a new object
CREATE TABLE dbo.Products (
    product_id   INT            PRIMARY KEY,
    product_name VARCHAR(200)   NOT NULL,
    unit_price   DECIMAL(10, 2) NOT NULL
);

-- ALTER: modify an existing object
ALTER TABLE dbo.Products
ADD category VARCHAR(100) NULL;

-- DROP: permanently delete an object and all its data
DROP TABLE dbo.Products;

-- TRUNCATE: delete all rows but keep the table structure
TRUNCATE TABLE dbo.Products;
```

The `DROP` vs `TRUNCATE` distinction matters: `DROP` removes the table entirely (you'd need a `CREATE` to use it again). `TRUNCATE` wipes all rows but the table structure remains. Both are logged differently and behave differently with foreign key constraints.

---

## DML — Data Manipulation Language

DML commands work with the *data itself*: reading, writing, updating, and deleting rows. This is where most day-to-day SQL work lives.

```sql
-- SELECT: retrieve data (yes, SELECT is DML in SQL Server's classification)
SELECT
    customer_id,
    first_name,
    email
FROM dbo.Customers
WHERE created_at >= DATEADD(DAY, -30, GETDATE());

-- INSERT: add new rows
INSERT INTO dbo.Orders (order_id, customer_id, status)
VALUES (1001, 42, 'Pending');

-- UPDATE: modify existing rows
UPDATE dbo.Orders
SET status = 'Completed'
WHERE order_id = 1001;

-- DELETE: remove specific rows (unlike TRUNCATE, you can add a WHERE clause)
DELETE FROM dbo.Orders
WHERE status = 'Cancelled'
  AND order_date < DATEADD(YEAR, -2, GETDATE());
```

A common debate: is `SELECT` DML or its own subset (DQL — Data Query Language)? In SQL Server's official documentation, `SELECT` is classified as DML. DQL doesn't appear in the SQL Server docs. The logic: SQL is already a Query Language — adding a "Query" sublanguage would be redundant.

---

## DCL — Data Control Language

DCL manages *permissions* — who can read, write, or execute what. In production environments, DCL is how you enforce least-privilege access: an application user reads from views but never touches base tables directly.

```sql
-- GRANT: give a user or role specific permissions
GRANT SELECT ON dbo.Orders TO [reporting_user];
GRANT EXECUTE ON dbo.usp_GetCustomerOrders TO [api_user];

-- REVOKE: remove a previously granted permission
REVOKE SELECT ON dbo.Orders FROM [reporting_user];

-- DENY: explicitly block a permission (overrides GRANT even via role membership)
DENY DELETE ON dbo.Customers TO [junior_dev];
```

The difference between `REVOKE` and `DENY` is important: `REVOKE` removes a permission that was previously granted. `DENY` actively blocks it — even if the user belongs to a role that has the permission, `DENY` wins.

---

## TCL — Transaction Control Language

TCL manages *transactions* — groups of DML operations that should succeed or fail together. TCL is the enforcement layer for ACID's Atomicity guarantee.

```sql
-- A money transfer: both operations must succeed or both must fail
BEGIN TRANSACTION;

BEGIN TRY
    UPDATE dbo.Customers
    SET credit_balance = credit_balance - 100
    WHERE customer_id = 1;

    UPDATE dbo.Customers
    SET credit_balance = credit_balance + 100
    WHERE customer_id = 2;

    COMMIT TRANSACTION; -- both updates written permanently
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION; -- both updates undone
    THROW;
END CATCH;
```

`SAVE TRANSACTION` adds a savepoint within a transaction — you can roll back to the savepoint without undoing the entire transaction, which is useful for long operations where you want partial recovery options.

## The Trap

**Using `DELETE` when you need `TRUNCATE`, and vice versa.** `DELETE FROM Orders` without a `WHERE` clause and `TRUNCATE TABLE Orders` look similar but behave very differently:

| Behavior | DELETE | TRUNCATE |
|----------|--------|----------|
| Can use WHERE | Yes | No |
| Transaction log | Logs each row | Minimal logging |
| Speed on large tables | Slow | Fast |
| Resets IDENTITY | No | Yes |
| Fires DELETE triggers | Yes | No |
| Respects FK constraints | Yes | Yes (will fail if referenced) |

When you need to empty a large table fast for a reload, `TRUNCATE` is almost always the right tool. When you need to remove specific rows or need the operation to fire triggers, use `DELETE`.

---

## Key Takeaways

- **DDL defines structure** — `CREATE`, `ALTER`, `DROP`, `TRUNCATE` work on tables and objects, not data
- **DML manipulates data** — `SELECT`, `INSERT`, `UPDATE`, `DELETE`; SQL Server classifies `SELECT` as DML
- **DCL controls access** — `GRANT`, `REVOKE`, `DENY`; `DENY` always wins over `GRANT`
- **TCL manages transactions** — `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVE`; the enforcement layer for ACID atomicity
- **TRUNCATE ≠ DELETE** — `TRUNCATE` is minimal-log, resets identity, fires no triggers; `DELETE` is row-level, auditable, and filterable
