# Database Patterns Every Developer Should Know: Indexing, Partitioning, ACID, CAP

*Series 1 — SQL & Database Foundations | The SQL Server Deep Dive*

---

You're not designing a database from scratch every week. But you will make decisions that depend on understanding these patterns: whether to add an index, how to handle a large table that's getting slow, how to think about consistency when you're distributing reads across servers. The developers who make the wrong call here are the ones who say "the database is slow" without knowing why — and the ones who make the right call are the ones who understood these patterns before they needed them.

---

## Indexing: The Most Common Lever

An **index** is a separate data structure the database maintains alongside your table to make lookups faster. Without an index, finding a row means scanning every row in the table. With an index, the database can skip directly to the right location — like a book index that tells you "B-Trees: page 47" instead of making you read every page.

The two main index types in SQL Server:

**Clustered Index** — determines the physical order of data in the table. There can only be one per table, and it's automatically created when you define a `PRIMARY KEY`. Data rows are stored in clustered index order.

**Non-clustered Index** — a separate structure with a sorted copy of the indexed columns, plus pointers back to the actual rows. A table can have many non-clustered indexes.

```sql
-- Clustered index (created automatically with PRIMARY KEY)
CREATE TABLE dbo.Orders (
    order_id    INT PRIMARY KEY,   -- clustered index on order_id
    customer_id INT,
    order_date  DATETIME2,
    status      VARCHAR(50)
);

-- Non-clustered index for queries that filter by customer
CREATE NONCLUSTERED INDEX ix_Orders_customer_id
    ON dbo.Orders (customer_id);

-- Composite index for queries filtering by customer AND status
CREATE NONCLUSTERED INDEX ix_Orders_customer_status
    ON dbo.Orders (customer_id, status);
```

Indexes make reads faster but writes slower — every insert, update, or delete must also update the index. Index thoughtfully: start with columns used in `WHERE`, `JOIN`, and `ORDER BY` clauses on high-traffic queries.

## Partitioning: Dividing a Large Table

**Partitioning** divides a single large table into smaller, more manageable pieces called *partitions* — all within the same database instance. From the outside, it still looks like one table. Under the hood, SQL Server can prune searches to only relevant partitions.

The most common strategy is **range partitioning** — dividing rows by date range. An `Orders` table with 5 years of data can be partitioned by year: queries for 2024 orders only touch the 2024 partition, not all 5 years.

```text
dbo.Orders (logical view)
├── Partition 2020 → rows where order_date in 2020
├── Partition 2021 → rows where order_date in 2021
├── Partition 2022 → rows where order_date in 2022
├── Partition 2023 → rows where order_date in 2023
└── Partition 2024 → rows where order_date in 2024
```

Partitioning is different from **sharding** — sharding distributes data across *separate database instances* (completely different servers), while partitioning keeps everything in one instance. Sharding is a distributed systems strategy; partitioning is a storage optimization within SQL Server.

---

## Replication: Copying Data Across Servers

**Replication** copies data from one server (the primary) to one or more others (secondaries). It's the foundation of high availability and read scaling.

Two main models:

- **Primary-Secondary (Master-Slave):** All writes go to the primary. Secondaries replicate from primary and handle reads. If the primary goes down, a secondary can be promoted.
- **Multi-Primary (Multi-Master):** Multiple servers can accept writes. Powerful but complex — maintaining consistency between masters is a hard problem.

SQL Server's Always On Availability Groups build on this concept for enterprise high availability.

## ACID: The Reliability Guarantee

You've already seen ACID in article 1.1, but it's worth revisiting here as a pattern decision, not just a database property.

**ACID** (Atomicity, Consistency, Isolation, Durability) is the contract SQL Server makes about every transaction:

| Property | The Promise | The Real-World Meaning |
|----------|-------------|----------------------|
| **Atomicity** | All or nothing | A transfer of $100 either completes fully or doesn't happen at all |
| **Consistency** | Only valid states | Constraints and rules are enforced — you can't end in an invalid state |
| **Isolation** | Transactions don't see each other's in-progress changes | Two concurrent queries get consistent results |
| **Durability** | Committed = permanent | A confirmed transaction survives a server crash |

ACID is what makes relational databases trustworthy for financial systems, medical records, and any scenario where data integrity is non-negotiable.

## CAP Theorem: The Distributed Trade-Off

When you distribute a database across multiple servers or data centers, you face a fundamental constraint known as the **CAP Theorem**: a distributed system can guarantee at most two of three properties simultaneously.

- **Consistency (C):** Every read returns the most recent write, or an error
- **Availability (A):** Every request receives a response (possibly with stale data)
- **Partition Tolerance (P):** The system keeps functioning even when network partitions occur

The catch: **partition tolerance is non-negotiable** in any real distributed system — networks do fail. So the actual choice is between C and A when a partition happens:

- **Choose Consistency:** Some requests fail during a partition to ensure all reads are current (banking systems, inventory)
- **Choose Availability:** Requests always get a response, but data might be slightly stale (shopping carts, social feeds)

SQL Server with synchronous Always On replicas prioritizes Consistency. NoSQL systems like Cassandra often prioritize Availability. Neither is wrong — it depends on what your system needs to guarantee.

## The Trap

**Adding indexes to fix everything.** When a query is slow, the instinct is to add an index. Sometimes that's right. But over-indexed tables are slow on writes (every index must be maintained on every insert/update/delete), waste disk space, and confuse the query optimizer with too many choices. Before adding an index, look at the execution plan — the optimizer will tell you what it's missing. And periodically audit your indexes: unused ones are pure overhead.

---

## Key Takeaways

- **Indexes make reads faster and writes slower** — index columns used in `WHERE`, `JOIN`, and `ORDER BY` on your most-queried paths
- **Partitioning and sharding solve different problems** — partitioning is within one SQL Server instance; sharding is across multiple database instances
- **ACID is SQL Server's default guarantee** — every transaction is protected; you don't opt in
- **CAP forces a choice in distributed systems** — SQL Server chooses consistency by default; you trade availability for it during network failures
- **Don't over-index** — review execution plans before adding indexes, and audit unused ones regularly
