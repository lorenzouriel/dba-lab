# Data Modelling: How to Design a Database That Won't Haunt You

*Series 1 — SQL & Database Foundations | The SQL Server Deep Dive*

---

Six months into a project, a developer asks for a new report. You write the query, run it, and the results are wrong. Not because the SQL is wrong — but because the data model is wrong. The structure baked into the database three months ago, when nobody thought about this use case, is now impossible to query correctly without contorting every JOIN into something unrecognizable. Fixing it means migrating data, rewriting queries, and having an uncomfortable conversation about "we should have thought about this earlier."

Data modelling is how you avoid that conversation.

---

## What Data Modelling Actually Is

**Data modelling** is the process of deciding how your data will be structured before you write a single table. It's not a technical task in the first place — it's a communication task. The goal is to translate business reality into a database structure that makes sense, is consistent, and can evolve without collapsing.

The process has four phases, and each one removes a layer of ambiguity:

```text
1. Requirements Analysis  →  What data do we need and why?
2. Conceptual Model (ERD) →  What are the entities and how do they relate?
3. Logical Model          →  What are the tables, columns, and foreign keys?
4. Physical Model         →  What are the data types, indexes, and constraints?
```

Skip any of these phases and you're guessing. The database that results from guessing is the one that haunts you six months later.

---

## Phase 1: Requirements Analysis

Before drawing a single box or writing a single `CREATE TABLE`, talk to the people who will use the data. Not about column types — about *what they need to know*.

"We need to track customer orders" is a requirement. "We need to know which customers placed more than five orders in the last 30 days" is a *specific* requirement that changes how you model the `Orders` table. "We need to send promotional emails only to customers who haven't ordered in 90 days" tells you that `created_at` on the `Customers` table needs to be reliable and queryable.

The goal is not to capture every possible future need — that way lies over-engineering. The goal is to understand the core domain well enough that the model won't fight you on day-one use cases.

---

## Phase 2: The Conceptual Model (ERD)

The Entity-Relationship Diagram (ERD) is the high-level sketch. No column types, no SQL — just entities (things you're tracking), their attributes (what you know about them), and their relationships (how they connect).

**Entities** are the nouns of your domain: `Customer`, `Order`, `Product`. They become tables. Each entity can be **strong** (exists independently) or **weak** (depends on a parent entity).

**Relationships** describe how entities interact. The most important thing to define here is **cardinality** — how many instances of one entity relate to how many instances of another:

| Cardinality | Example |
|-------------|---------|
| One-to-One (1:1) | A customer has exactly one billing address |
| One-to-Many (1:N) | A customer can have many orders |
| Many-to-Many (N:M) | An order can contain many products; a product can appear in many orders |

Many-to-Many relationships need special attention — they always require a **junction table**. In SalesDB, a single order can have multiple products, and a product can appear in multiple orders. The `OrderDetails` table is that junction: it holds one row per (order, product) combination, resolving the many-to-many into two one-to-many relationships.

```text
Customers ──────< Orders ──────< OrderDetails >────── Products
  (1:N)                (1:N)                  (N:1)
```

---

## Phase 3: The Logical Model

The logical model takes the ERD and turns it into tables, columns, and foreign keys — still without thinking about SQL Server specifics. This is where cardinality becomes foreign key direction and entity attributes become column names.

Key decisions to make here:
- **What is the primary key for each table?** (natural key or surrogate integer?)
- **Which tables reference which other tables?** (foreign key placement)
- **Are there optional relationships?** (nullable foreign keys)

In SalesDB, `OrderDetails` holds foreign keys to both `Orders` and `Products`. Neither is optional — an order detail without an order or without a product is meaningless. Both foreign keys are `NOT NULL`.

---

## Phase 4: The Physical Model

The physical model is what actually goes into SQL Server — `CREATE TABLE` statements with specific data types, constraints, default values, and indexes.

```sql
-- Physical model for SalesDB OrderDetails
CREATE TABLE dbo.OrderDetails (
    order_detail_id INT            NOT NULL IDENTITY(1,1) PRIMARY KEY,
    order_id        INT            NOT NULL REFERENCES dbo.Orders(order_id),
    product_id      INT            NOT NULL REFERENCES dbo.Products(product_id),
    quantity        INT            NOT NULL CHECK (quantity > 0),
    unit_price      DECIMAL(10, 2) NOT NULL CHECK (unit_price >= 0)
);
```

Every decision here is deliberate: `IDENTITY(1,1)` for auto-increment primary key, `NOT NULL` on both foreign keys, `CHECK` constraints to prevent negative quantities or prices. The database will now enforce these rules on every insert and update — permanently.

---

## Referential Integrity: The Enforcement Layer

A well-modelled database doesn't just describe relationships — it *enforces* them. **Referential integrity** means the database guarantees that foreign key values always point to a real row in the referenced table.

Practical consequences:
- You can't insert an `Order` for a `customer_id` that doesn't exist in `Customers`
- You can't delete a `Customer` who still has `Orders` (unless you've configured cascade behavior)
- Updates to primary keys propagate according to the `ON UPDATE` rule you define

The `ON DELETE` and `ON UPDATE` options give you control over what happens when a referenced row changes:

```sql
-- Cascade: delete orders when a customer is deleted
REFERENCES dbo.Customers(customer_id) ON DELETE CASCADE

-- Restrict: prevent deletion if orders exist (default behavior)
REFERENCES dbo.Customers(customer_id)

-- Set NULL: allow the order to remain but clear the customer reference
REFERENCES dbo.Customers(customer_id) ON DELETE SET NULL
```

Choose based on your domain. A sales system probably shouldn't cascade-delete orders when a customer is deleted — historical records matter. An audit log probably should cascade. Think it through at modelling time.

---

## The Trap

**Designing the model in the database tool instead of on paper.** The moment you open SQL Server Management Studio and start creating tables, you've skipped requirements and conceptual modelling. The result is a physical model that made sense one table at a time but doesn't hold together as a system.

Spend 30 minutes with a whiteboard (or Miro, or even a napkin) drawing boxes and arrows before touching SQL. The ERD forces you to think about the whole picture before committing to structure. Every hour you spend at the whiteboard saves two hours of migration scripts later.

---

## Key Takeaways

- **Model the domain, not the queries** — design for what the data *is*, and the queries you need will follow naturally
- **Many-to-many always needs a junction table** — never resolve it with comma-separated values in a single column
- **Referential integrity is enforced by the database, not by application code** — use foreign keys; don't trust the app layer to maintain consistency
- **Go through all four phases** — skipping conceptual or logical modelling creates physical models that look fine until requirements change
