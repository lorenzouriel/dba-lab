# RAISERROR vs THROW: The Right Way to Handle Errors in T-SQL

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

Forget `PRINT`. It prints a message to the output window and does nothing to stop execution, nothing to communicate to the caller that something went wrong, and nothing that TRY/CATCH can catch. It's fine for debugging in a query window. In production code — stored procedures, triggers, batch scripts — it's not error handling.

`RAISERROR` and `THROW` are. Both generate real errors that stop execution, can be caught by TRY/CATCH blocks, and propagate meaningful information to the caller. The question is which one to use, and when.

---

## RAISERROR: The Legacy Approach

`RAISERROR` has been in SQL Server since the early versions. It generates an error with a configurable severity level and message.

```sql
RAISERROR (message_string, severity, state [, argument [, ...n]]);
```

- `message_string` — the error text (can use printf-style formatting with arguments)
- `severity` — integer 0 to 25 controlling how serious the error is
- `state` — integer 1 to 127, user-defined (used to distinguish where in the code an error originated)

The severity levels determine behavior:

| Severity | Behavior |
|----------|----------|
| 0–10 | Informational; execution continues |
| 11–16 | User-correctable error; batch stops if unhandled |
| 17–19 | Software or resource errors (use caution) |
| 20–25 | Fatal; connection is terminated |

```sql
-- Input validation with RAISERROR
CREATE PROCEDURE dbo.usp_UpdateProductPrice
    @product_id INT,
    @new_price  MONEY
AS
BEGIN
    IF @new_price < 0
    BEGIN
        RAISERROR('Price cannot be negative. Received: %f', 16, 1, @new_price);
        RETURN;  -- RAISERROR doesn't automatically stop execution; you must RETURN
    END

    UPDATE dbo.Products
    SET unit_price = @new_price
    WHERE product_id = @product_id;
END;
```

Notice the `RETURN` after `RAISERROR`. This is important: severity levels below 20 don't automatically stop execution. If you forget `RETURN`, the UPDATE runs even after the error is raised.

---

## THROW: The Modern Replacement

`THROW` was introduced in SQL Server 2012. It's simpler, safer, and designed to work seamlessly with TRY/CATCH.

```sql
THROW [error_number, message, state];
```

- `error_number` — must be 50000 or higher (user-defined range)
- `message` — error message string (up to 2048 characters)
- `state` — integer 0 to 255

```sql
-- Same validation with THROW
CREATE PROCEDURE dbo.usp_UpdateProductPrice
    @product_id INT,
    @new_price  MONEY
AS
BEGIN
    IF @new_price < 0
        THROW 50001, 'Price cannot be negative.', 1;
        -- No RETURN needed: THROW always stops execution

    UPDATE dbo.Products
    SET unit_price = @new_price
    WHERE product_id = @product_id;
END;
```

`THROW` always raises severity 16 — you can't change it. That sounds like a limitation, but it's actually a feature: it removes the footgun of accidentally raising a fatal severity 20+ error or forgetting that severity 10 doesn't stop execution.

---

## Re-Throwing: The Most Important Difference

`THROW` without parameters, used inside a `CATCH` block, **re-raises the original error exactly** — same error number, same message, same state, same severity.

```sql
BEGIN TRANSACTION;
BEGIN TRY
    INSERT INTO dbo.OrderDetails (order_id, product_id, quantity, unit_price)
    VALUES (@order_id, @product_id, @quantity, @unit_price);

    COMMIT;
END TRY
BEGIN CATCH
    ROLLBACK;
    THROW;  -- Re-raises the original SQL Server error intact
END CATCH;
```

This is crucial for observability: the caller gets the original error. Logs capture the original error. The call stack preserves the original context. Nothing is lost.

With `RAISERROR`, re-raising means calling `RAISERROR` with `ERROR_NUMBER()`, `ERROR_MESSAGE()`, `ERROR_SEVERITY()`, and `ERROR_STATE()` — manually rebuilding the error, and sometimes losing fidelity in the process.

---

## When to Use Each

**Use `THROW` for all new code.** It's simpler, safer, stops execution automatically, re-raises cleanly, and integrates well with TRY/CATCH. There's no reason to prefer `RAISERROR` in new stored procedures or scripts.

**Use `RAISERROR` when:**
- You need to control severity levels (severity 10 informational messages that don't stop execution)
- You're working with legacy code that already uses `RAISERROR` and consistency matters
- You need printf-style argument formatting in older SQL Server versions where `FORMATMESSAGE` isn't available

```sql
-- RAISERROR with formatting (legacy pattern)
RAISERROR('Order %d cannot be processed: insufficient stock (%d units available).', 16, 1, @order_id, @stock);

-- THROW with FORMATMESSAGE (modern equivalent)
THROW 50002, FORMATMESSAGE('Order %d cannot be processed: insufficient stock (%d units available).', @order_id, @stock), 1;
```

## Four Real Use Cases

**1. Parameter validation in stored procedures**

```sql
CREATE PROCEDURE dbo.usp_CreateOrder
    @customer_id INT,
    @quantity    INT
AS
BEGIN
    IF @quantity <= 0
        THROW 50001, 'Quantity must be greater than zero.', 1;

    IF NOT EXISTS (SELECT 1 FROM dbo.Customers WHERE customer_id = @customer_id)
        THROW 50002, 'Customer not found.', 1;

    -- Proceed with order creation
END;
```

**2. Enforcing business rules**

```sql
CREATE PROCEDURE dbo.usp_ProcessOrder
    @order_id INT
AS
BEGIN
    DECLARE @stock INT;

    SELECT @stock = p.stock
    FROM dbo.Orders o
    INNER JOIN dbo.OrderDetails od ON o.order_id = od.order_id
    INNER JOIN dbo.Products p ON od.product_id = p.product_id
    WHERE o.order_id = @order_id;

    IF @stock < 1
        THROW 50003, 'Insufficient stock to process order.', 1;

    -- Process the order
END;
```

**3. Transaction error handling with re-raise**

```sql
BEGIN TRANSACTION;
BEGIN TRY
    -- Multiple operations
    UPDATE dbo.Products SET stock = stock - @quantity WHERE product_id = @product_id;
    INSERT INTO dbo.Orders (customer_id, status) VALUES (@customer_id, 'Pending');

    COMMIT;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK;
    THROW;  -- Caller gets original error
END CATCH;
```

**4. Triggers blocking unauthorized operations**

```sql
CREATE TRIGGER trg_PreventOrderDelete
ON dbo.Orders
INSTEAD OF DELETE
AS
BEGIN
    IF EXISTS (SELECT 1 FROM deleted WHERE status = 'Completed')
        THROW 50004, 'Completed orders cannot be deleted.', 1;

    DELETE o FROM dbo.Orders o
    INNER JOIN deleted d ON o.order_id = d.order_id;
END;
```

## The Trap

**Swallowing errors in CATCH blocks.** The most dangerous pattern is a CATCH block that handles the error silently:

```sql
-- DANGEROUS: error disappears, caller has no idea something went wrong
BEGIN TRY
    INSERT INTO dbo.Orders (customer_id, status) VALUES (@customer_id, 'Pending');
END TRY
BEGIN CATCH
    ROLLBACK;
    -- Nothing here: error is swallowed
END CATCH;
```

If the INSERT fails, the caller gets no indication. The application proceeds as if the order was created. This leads to data inconsistencies that are impossible to debug because there's no error trail.

Always re-raise with `THROW` (or `RAISERROR`) in the CATCH block. Log the error if your system has a logging mechanism, but always propagate it upward.

---

## Key Takeaways

- **Use `THROW` for all new code** — simpler syntax, always stops execution, re-raises the original error cleanly
- **`RAISERROR` requires an explicit `RETURN`** — severities below 11 don't stop execution automatically; forget RETURN and the code continues
- **`THROW` without parameters re-raises the original error exactly** — error number, message, and state are preserved for callers and logs
- **Use `RAISERROR` for severity control** — when you need informational messages (severity ≤10) that don't stop execution, or for legacy code consistency
- **Never swallow errors in CATCH blocks** — always re-raise; a silent failure is worse than a visible one
