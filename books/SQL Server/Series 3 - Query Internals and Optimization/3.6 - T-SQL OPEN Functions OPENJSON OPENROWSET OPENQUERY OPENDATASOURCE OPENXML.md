# T-SQL OPEN Functions: OPENJSON, OPENROWSET, OPENQUERY, OPENDATASOURCE, OPENXML

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

SQL Server doesn't live in isolation. In real environments, it needs to talk to other servers, import files, parse API responses, and integrate with systems that speak different data formats. The OPEN* family of functions is how SQL Server reaches outside its own walls — pulling data from JSON payloads, CSV files, remote servers, and XML documents directly into T-SQL queries.

Each function solves a different integration problem. Choosing the right one comes down to where your data lives and whether you need a one-time operation or a production pipeline.

---

## OPENDATASOURCE: Ad-Hoc Cross-Server Queries

`OPENDATASOURCE` connects to a remote data source on the fly, without configuring a linked server. It's an OLE DB connection embedded directly in the query.

```sql
-- Query a table on a remote SQL Server instance
SELECT *
FROM OPENDATASOURCE(
    'SQLNCLI',
    'Server=RemoteServer;Trusted_Connection=yes;'
).SalesDB.dbo.Orders;
```

**Best for:** One-off cross-server queries, ad-hoc data validation, or one-time migrations where you don't want to configure a persistent linked server.

**Not for:** Production pipelines with frequent execution. `OPENDATASOURCE` pulls all data to the local server before filtering — no query pushdown. For frequent cross-server queries, configure a linked server and use `OPENQUERY` instead.

**Requires:** `Ad Hoc Distributed Queries` enabled in SQL Server configuration (`sp_configure`).

---

## OPENJSON: Parsing JSON Into Rows

`OPENJSON` converts a JSON string into a relational rowset. This is how SQL Server integrates with APIs, modern application logs, and any system that produces JSON output.

```sql
-- Basic parsing: returns key-value pairs
DECLARE @json NVARCHAR(MAX) = N'{
    "order_id": 1001,
    "customer": "Ana Costa",
    "status": "Completed"
}';

SELECT [key], [value], [type]
FROM OPENJSON(@json);
```

The `WITH` clause maps JSON properties to typed columns:

```sql
-- Structured parsing with WITH clause
DECLARE @order_json NVARCHAR(MAX) = N'{
    "order_id": 1001,
    "customer_id": 42,
    "status": "Completed",
    "items": [
        {"product_id": 5, "quantity": 2, "unit_price": 29.99},
        {"product_id": 8, "quantity": 1, "unit_price": 149.00}
    ]
}';

-- Parse the header fields
SELECT order_id, customer_id, status
FROM OPENJSON(@order_json)
WITH (
    order_id    INT         '$.order_id',
    customer_id INT         '$.customer_id',
    status      VARCHAR(50) '$.status'
);

-- Parse the nested array
SELECT product_id, quantity, unit_price
FROM OPENJSON(@order_json, '$.items')
WITH (
    product_id INT            '$.product_id',
    quantity   INT            '$.quantity',
    unit_price DECIMAL(10, 2) '$.unit_price'
);
```

**Best for:** Ingesting API responses stored in a column, processing JSON payloads passed to stored procedures, shredding JSON into relational tables.

**Performance note:** Works well for small to medium JSON documents. Very large JSON (tens of MB) is CPU-intensive to parse. For bulk JSON ingestion, stage documents and shred in batches.

## OPENQUERY: Pushdown Queries to Linked Servers

`OPENQUERY` executes a query directly on a linked server. Unlike `OPENDATASOURCE`, the SQL string is sent to the remote server and executed there — only results come back over the network.

```sql
-- Execute a query on a linked server (defined in sp_addlinkedserver)
SELECT *
FROM OPENQUERY(LinkedServerName, 'SELECT customer_id, email FROM SalesDB.dbo.Customers WHERE email LIKE ''%@gmail.com''');
```

**The key advantage over OPENDATASOURCE:** Query pushdown. Filtering, aggregation, and joins happen on the remote server. Only the filtered result set travels across the network. For large remote tables, this can be the difference between a 2-second query and a 2-minute one.

**Best for:** Frequent, production cross-server queries where network efficiency matters.

**Limitations:** Requires a pre-configured linked server. The query string must be a literal string — you can't use variables directly inside `OPENQUERY`. For parameterized queries, use `EXEC` with `sp_executesql` on the linked server.

## OPENROWSET: Ad-Hoc External Queries and Bulk File Import

`OPENROWSET` serves two distinct purposes.

**As an ad-hoc query tool** (similar to OPENDATASOURCE but with the query embedded):

```sql
SELECT *
FROM OPENROWSET(
    'SQLNCLI',
    'Server=RemoteServer;Trusted_Connection=yes;',
    'SELECT name, unit_price FROM SalesDB.dbo.Products'
);
```

**As a bulk file importer** (`OPENROWSET BULK`):

```sql
-- Import a CSV file into a query
SELECT *
FROM OPENROWSET(
    BULK 'C:\Data\products_import.csv',
    FORMATFILE = 'C:\Data\products_import.fmt'
) AS DataFile;

-- Or use SINGLE_BLOB to read raw file content
SELECT BulkColumn
FROM OPENROWSET(BULK 'C:\Data\order_payload.json', SINGLE_BLOB) AS JsonFile;
```

The BULK option is optimized for high-volume file imports. It bypasses row-by-row insert overhead and is one of the fastest ways to load external data into SQL Server.

**Best for:** ETL processes, staging table loads from CSV/JSON/XML files, one-off data imports.

## OPENXML: Parsing XML Into Rows (Legacy)

`OPENXML` converts an XML document into a relational rowset. It works by loading the XML into an in-memory DOM representation and querying it with XPath patterns.

```sql
DECLARE @xml_doc XML = N'
<Orders>
    <Order id="1001" status="Completed">
        <Customer id="42" name="Ana Costa" />
    </Order>
    <Order id="1002" status="Pending">
        <Customer id="15" name="Carlos Lima" />
    </Order>
</Orders>';

DECLARE @doc_handle INT;
EXEC sp_xml_preparedocument @doc_handle OUTPUT, @xml_doc;

SELECT order_id, status, customer_id, customer_name
FROM OPENXML(@doc_handle, '/Orders/Order', 2)
WITH (
    order_id      INT          '@id',
    status        VARCHAR(50)  '@status',
    customer_id   INT          'Customer/@id',
    customer_name VARCHAR(100) 'Customer/@name'
);

EXEC sp_xml_removedocument @doc_handle;  -- Always release the DOM handle
```

**Important:** Always call `sp_xml_removedocument` after using `OPENXML`. The DOM representation is allocated in memory and not freed automatically — leaving it unreleased is a memory leak.

**For new code:** Prefer native XML methods (`nodes()`, `value()`, `query()`) over `OPENXML`. They're faster, more memory-efficient, and don't require the prepare/remove document ceremony.

```sql
-- Modern equivalent using native XML methods
DECLARE @xml XML = N'<Orders>...</Orders>';

SELECT
    o.value('@id', 'INT')         AS order_id,
    o.value('@status', 'VARCHAR(50)') AS status
FROM @xml.nodes('/Orders/Order') AS t(o);
```

## Which One to Use

| Function | Where data lives | Use in production? | Notes |
|----------|-----------------|-------------------|-------|
| `OPENDATASOURCE` | Remote server (ad-hoc) | Rarely | No pushdown; good for one-off queries |
| `OPENJSON` | JSON string/column | Yes | Best for API ingestion and JSON storage |
| `OPENQUERY` | Linked server | Yes | Best cross-server option; pushes query to remote |
| `OPENROWSET` | Remote server or files | For ETL | Ad-hoc version of OPENDATASOURCE; BULK option is excellent for file imports |
| `OPENXML` | XML string | Legacy only | Use native XML methods for new code |

---

## The Trap

**Using `OPENDATASOURCE` or `OPENROWSET` for frequent production queries.** Both pull full datasets to the local server before applying any filtering — the WHERE clause in your local query is applied after all the remote data has been fetched. For a 50-million-row table on the remote server, your `WHERE status = 'Active'` filter runs locally on 50 million fetched rows.

The correct pattern for frequent cross-server queries: configure a linked server, use `OPENQUERY`, and put the WHERE clause inside the quoted query string so it executes on the remote server.

Also: `Ad Hoc Distributed Queries` must be enabled for OPENDATASOURCE and OPENROWSET to work. This is disabled by default for security reasons. Enable it deliberately, audit who has permission to use it, and consider whether a linked server is more appropriate for your use case.

---

## Key Takeaways

- **`OPENJSON` is the modern standard for JSON integration** — use the `WITH` clause to map to typed columns; keep documents reasonably sized
- **`OPENQUERY` pushes execution to the remote server** — the right choice for frequent linked-server queries; filters run on the remote side
- **`OPENROWSET BULK` is the fastest way to load files** — optimized for high-volume CSV/JSON/XML imports into staging tables
- **`OPENDATASOURCE` and bare `OPENROWSET` are for ad-hoc queries only** — don't use them in production pipelines on large tables
- **`OPENXML` is legacy** — use native XML methods (`nodes()`, `value()`) for new code; always free the document handle with `sp_xml_removedocument`
