# Window Functions, JSON, Regex, Fuzzy Matching, and Graph Queries: Advanced T-SQL

*Series 3 — Query Internals and Optimization | The SQL Server Deep Dive*

---

There's a failure mode every data team eventually pays for. A query is "too complex for SQL," so a developer pulls a few hundred thousand rows across the network and loops over them in application code. Now the data has been moved instead of computed on, something the engine already does has been reimplemented badly, and set-based execution has been thrown away for row-by-row processing over a network connection.

Most of the time the reason is that nobody on the team knew the T-SQL feature that made it a one-statement problem. This article closes that gap: window functions, correlated subqueries, JSON, regular expressions, fuzzy matching, and graph queries. Several of these tools can produce the same result as each other, or as things already covered in this series — CTEs (2.4), subqueries (2.5), and `THROW`/`RAISERROR` error handling (3.3). The real skill isn't memorizing syntax. It's knowing which of two or three overlapping tools is cheapest at production scale.

---

## A Brief Word on CTEs

Recursive CTEs — walking a hierarchy with an anchor member and a recursive member joined by `UNION ALL` — are already covered in full in 2.4, including the `MAXRECURSION` cap and the trap of CTEs not being materialized. One addition worth knowing: on SQL Server 2022+, Azure SQL, and Fabric, generating a number or date series is better done with `GENERATE_SERIES(start, stop, step)` than with a hand-rolled recursive CTE — it's set-based and meaningfully faster than the row-by-row recursive approach for that specific job.

```sql
-- Generate the last 12 month-start dates, set-based
SELECT DATEADD(MONTH, -value, CAST(GETDATE() AS DATE)) AS month_start
FROM GENERATE_SERIES(0, 11);
```

## Window Functions: Beyond Ranking

2.8 already introduced `OVER()` and the basic ranking functions. What's worth adding here is the detail that actually causes bugs in production: frame semantics, and the two analytical functions that don't get as much attention as `ROW_NUMBER`.

`NTILE(n)` is the ranking function most people forget exists. It buckets rows into `n` roughly equal groups — the tool for quartiles, deciles, or any "split my customers into 4 tiers by revenue" question.

```sql
SELECT
    c.customer_id,
    SUM(od.quantity * od.unit_price) AS lifetime_value,
    NTILE(4) OVER (ORDER BY SUM(od.quantity * od.unit_price) DESC) AS value_quartile
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY c.customer_id;
```

### The ROWS vs. RANGE Gotcha

This is worth tattooing somewhere. When you specify `ORDER BY` inside `OVER()` without an explicit frame, the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. `RANGE` groups **peers** — rows with equal `ORDER BY` values — together. That means two orders placed on the exact same date get the *same* running total instead of two distinct incremental values, which is almost never what you meant. `RANGE` also tends to force a spool internally and runs slower than the alternative.

What you almost always want is `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which counts physical rows regardless of ties and behaves the way people intuitively expect a running total to behave.

```sql
-- Default RANGE frame: same-day orders share one running total (surprising)
SELECT
    o.order_date,
    SUM(od.quantity * od.unit_price) AS line_total,
    SUM(SUM(od.quantity * od.unit_price)) OVER (ORDER BY o.order_date) AS running_total_range
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY o.order_date;

-- Explicit ROWS frame: each row gets its own incremental total
SELECT
    o.order_date,
    SUM(od.quantity * od.unit_price) AS line_total,
    SUM(SUM(od.quantity * od.unit_price)) OVER (
        ORDER BY o.order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total_rows
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY o.order_date;
```

Be explicit with the frame clause every time you write a running calculation. The default is the surprise waiting to happen in production.

### FIRST_VALUE, LAST_VALUE, and the Frame Trap

`LAG()` and `LEAD()` reach backward and forward a fixed number of rows — the standard tool for period-over-period comparisons, with an optional default value for the edge rows where there's nothing to reach for.

`FIRST_VALUE()` and `LAST_VALUE()` pull from the *boundary* of the current frame rather than a fixed offset. `FIRST_VALUE()` usually behaves as expected with the default frame. `LAST_VALUE()` is the one that trips people up: with the default frame (`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`), the frame's upper boundary *is* the current row — so `LAST_VALUE()` just returns the current row's own value, not the last value in the partition. To get the actual last value across the whole partition, you need an explicit frame that extends to the end:

```sql
SELECT
    o.order_id,
    o.order_date,
    SUM(od.quantity * od.unit_price) AS order_total,
    FIRST_VALUE(SUM(od.quantity * od.unit_price)) OVER (
        PARTITION BY o.customer_id ORDER BY o.order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS first_order_total,
    LAST_VALUE(SUM(od.quantity * od.unit_price)) OVER (
        PARTITION BY o.customer_id ORDER BY o.order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS most_recent_order_total
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
GROUP BY o.customer_id, o.order_id, o.order_date;
```

`PERCENT_RANK()` and `CUME_DIST()` round out the set — both give a row's relative position within its partition (0 to 1), useful for percentile-style reporting without a self-join.

## Correlated Subqueries: Powerful, and the Slow Option More Often Than Not

A correlated subquery references a column from the outer query, so conceptually it runs once per outer row — like a nested loop. That model is exactly right for some jobs and quietly expensive for others.

Where it earns its place is `EXISTS` / `NOT EXISTS`. The engine can stop at the first matching row, so an existence check is cheap regardless of how many matching rows there might actually be. `EXISTS` also dodges a real correctness bug that `IN` has: `NOT IN` against a subquery whose result contains even one `NULL` returns an empty result set entirely — not "everything that doesn't match," but nothing. `NOT EXISTS` doesn't have this problem. Default to `EXISTS` over `IN` for both reasons.

```sql
-- Customers with no orders at all
SELECT c.customer_id, c.first_name, c.last_name
FROM dbo.Customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM dbo.Orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Correlated subqueries also work fine in a `SELECT` list for a one-value-per-row calculation, and for top-N-per-group patterns via `IN (SELECT TOP n ...)`. They're readable, and for existence checks specifically, they're usually the right tool.

But notice the overlap with what's already in this article and elsewhere in the series. Running totals, rankings, and previous/next-row comparisons can all technically be written as correlated subqueries — and a window function will almost always be faster and clearer for those jobs, because a scalar correlated subquery evaluated once per row in a `SELECT` list carries the same per-row execution tax as a scalar UDF in a `WHERE` clause (see 2.8). So the decision framework worth keeping:

- **Existence test or genuinely per-row complex logic** → correlated subquery (`EXISTS`/`NOT EXISTS`)
- **Pulling columns from a related table** → join
- **Running totals, ranking, previous/next row** → window function
- **Naming and reusing an intermediate result** → CTE (2.4)

When a correlated subquery is on the critical path, index the correlation columns — a composite index covering the join column plus whatever the subquery filters or aggregates on — then check the actual execution plan. The optimizer frequently rewrites a correlated subquery into a join internally, but "frequently" isn't "always," and it's worth confirming on production-sized data rather than assuming.

## JSON: Extraction and Construction

3.6 already covers `OPENJSON` — shredding a JSON array or object into a relational rowset with a typed `WITH` clause — in full detail, including the `CROSS APPLY` pattern for parsing JSON stored per-row. What's worth adding here is the rest of the JSON toolkit: scalar extraction, document construction, and validation.

**Extraction splits two ways** depending on what you're pulling out. `JSON_VALUE` extracts a scalar (returns `NVARCHAR(4000)`, cast as needed for numeric or date comparisons). `JSON_QUERY` extracts an object or array and preserves it as valid JSON rather than flattening it to text. Using the wrong one silently returns `NULL` instead of erroring, which makes this an easy mistake to miss in testing.

```sql
-- Products table with a JSON column holding variable attributes
SELECT
    product_id,
    product_name,
    JSON_VALUE(attributes, '$.color')        AS color,      -- scalar
    JSON_QUERY(attributes, '$.dimensions')    AS dimensions  -- object, stays JSON
FROM dbo.Products
WHERE JSON_VALUE(attributes, '$.category') = 'Electronics';
```

**Construction goes the other direction** — building JSON output from relational columns, which is how you produce API-shaped payloads directly from a normalized schema without an application-layer serialization step. `JSON_OBJECT` and `JSON_ARRAY` build documents with correct escaping and can be nested for hierarchical output. `JSON_ARRAYAGG` rolls multiple rows into a single JSON array, aggregate-style. These three are SQL Server 2022+; on older versions, `FOR JSON PATH` (with dotted column aliases to express nesting, plus `ROOT(...)` to name the top-level element) covers the same ground.

```sql
-- Build one JSON object per order, with a nested array of line items (2022+)
SELECT
    o.order_id,
    JSON_OBJECT(
        'orderId': o.order_id,
        'orderDate': o.order_date,
        'items': (
            SELECT JSON_ARRAYAGG(
                JSON_OBJECT('productId': od.product_id, 'quantity': od.quantity)
            )
            FROM dbo.OrderDetails AS od
            WHERE od.order_id = o.order_id
        )
    ) AS order_json
FROM dbo.Orders AS o;

-- Equivalent shape with FOR JSON PATH, available on older versions
SELECT
    o.order_id AS [orderId],
    o.order_date AS [orderDate]
FROM dbo.Orders AS o
FOR JSON PATH, ROOT('orders');
```

**Validation** is the part people skip and regret later. `ISJSON` confirms a string is well-formed JSON before you attempt to parse it — critical for any column that accepts JSON from an external source. `JSON_PATH_EXISTS` checks whether a path is present before you read it. Path expressions run in `lax` mode by default, where a missing path simply returns `NULL`, or `strict` mode, where a missing path raises an error — use `strict` when an absent property genuinely means the incoming data is broken and you want to know immediately rather than silently getting `NULL`s downstream.

The performance rule carries over from 3.6's OPENJSON coverage: parsing JSON on every row of a large table is a full scan with a parse bolted on top. If a specific JSON property is queried frequently, extract it into a `PERSISTED` computed column and index that column — the parse happens once, on write, and the query becomes a seek instead of a scan-and-parse.

```sql
ALTER TABLE dbo.Products
ADD product_category AS JSON_VALUE(attributes, '$.category') PERSISTED;

CREATE INDEX IX_Products_Category ON dbo.Products(product_category);
```

## Regular Expressions: Where LIKE Runs Out

`LIKE` gives you `%` and `_` and nothing else. Email validation, phone-format normalization, product codes with a fixed structural shape, repeated-character detection — none of those fit a wildcard pattern. SQL Server 2025 and Fabric add ECMAScript-syntax regex functions, meaning the patterns are the same ones already familiar from Python or JavaScript.

The function set is predictable: `REGEXP_LIKE` for validation and filtering in a `WHERE` clause, `REGEXP_REPLACE` for cleansing and standardization (with capture groups and `$1`-style backreferences for reshaping a string, such as masking all but the last four digits of a card number), `REGEXP_SUBSTR` and `REGEXP_INSTR` for extracting and locating a match, `REGEXP_COUNT` for counting occurrences, and two table-valued functions — `REGEXP_SPLIT_TO_TABLE` and `REGEXP_MATCHES` — that turn matches into rows you can join against.

```sql
-- Standardize inconsistent phone formats to (XXX) XXX-XXXX
SELECT
    customer_id,
    REGEXP_REPLACE(
        REGEXP_REPLACE(phone, '[^\d]', ''),
        '^(\d{3})(\d{3})(\d{4})$', '($1) $2-$3'
    ) AS standardized_phone
FROM dbo.Customers
WHERE phone IS NOT NULL
  AND REGEXP_LIKE(phone, '\d{10}');
```

Two practical notes. There's an `'i'` flag for case-insensitive matching, passed as an extra argument to most of these functions. And regex predicates don't use indexes — `REGEXP_LIKE` in a `WHERE` clause means a scan with per-row pattern evaluation, no matter how selective the pattern looks. Filter down with sargable, indexable predicates first wherever possible, and treat the regex function as the thing that runs only on the rows that survive that first filter.

## Fuzzy Matching: Cheap to Write, Expensive to Run

Real-world data is misspelled, abbreviated, and inconsistent. SQL Server 2025, Azure SQL, and Fabric add string-similarity functions built for deduplication, fuzzy search, and general data-quality work.

`EDIT_DISTANCE` returns the Levenshtein distance between two strings — a count of single-character edits needed to turn one into the other, where lower means closer. `EDIT_DISTANCE_SIMILARITY` normalizes that distance to a 0–100 score, which is easier to threshold consistently across strings of different lengths. `JARO_WINKLER_DISTANCE` is tuned specifically for names: it weights matching prefixes more heavily, which makes it the better choice for person names and other short strings, where a score above roughly 0.9 is generally a strong match.

The detail that matters for using any of these in production: they're O(string length) per comparison, and none of them can use an index. Running one unfiltered against a million-row table means a million character-by-character comparisons. The entire performance technique is the same one that applies to regex — shrink the candidate set first with cheap, indexed, sargable predicates, and apply the fuzzy function only to what's left.

```sql
-- Pre-filter with sargable LIKE on indexed columns, then fuzzy-match the survivors
SELECT customer_id, first_name, last_name
FROM dbo.Customers
WHERE first_name LIKE 'Jo%'
  AND last_name  LIKE 'Sm%'
  AND JARO_WINKLER_DISTANCE('John',  first_name) > 0.85
  AND JARO_WINKLER_DISTANCE('Smith', last_name)  > 0.85;
```

## Graph Queries: When the Relationships Are the Point

Some data is fundamentally a network — social connections, org hierarchies with variable depth, recommendation chains, fraud rings. You can model any of that with foreign keys and self-joins, but multi-hop traversal turns into nested-join soup fast, and a "how many hops away" question becomes unanswerable without knowing the depth in advance.

SQL Server's graph feature adds node and edge tables and the `MATCH` operator, which expresses a relationship pattern almost like ASCII art. You create tables `AS NODE` and `AS EDGE`; the engine adds a hidden `$node_id` to nodes and `$edge_id`/`$from_id`/`$to_id` to edges, and edges can carry their own properties (a connection date, a weight, a relationship type). You insert an edge by selecting the `$node_id` of each endpoint node.

```sql
-- Two-hop traversal: "friends of friends"
SELECT DISTINCT Person1.name AS person, Person3.name AS friend_of_friend
FROM dbo.Person AS Person1, dbo.Knows AS k1, dbo.Person AS Person2,
     dbo.Knows AS k2, dbo.Person AS Person3
WHERE MATCH(Person1-(k1)->Person2-(k2)->Person3)
  AND Person1.name = 'Ana Costa'
  AND Person3.name <> Person1.name;
```

For variable-depth traversal — "everyone reachable from this node within three hops," where the exact depth isn't known ahead of time — there's `SHORTEST_PATH`, used with `FOR PATH` and quantifiers like `{1,3}`. `MATCH` has been available since SQL Server 2017; `SHORTEST_PATH` requires 2019+.

The honest decision framework: reach for graph tables when relationships are the primary subject of the query, the traversal depth is variable or unknown ahead of time, the data is genuinely network-shaped, or the relational alternative would require writing many chained self-joins. Stick with a standard relational design when relationships are fixed-depth, the query is mostly filtering and aggregating attributes rather than traversing, and indexed foreign keys already answer the question directly — a single-level parent-child relationship does not need a graph table.

The most common graph bug is worth knowing before it costs debugging time: if a `MATCH` query returns nothing, check that the arrow direction in the pattern matches the direction the edge was actually inserted in (`$from_id` to `$to_id`). Reversing the direction in the query silently returns zero rows instead of an error.

## Error Handling: A Pointer, Not a Repeat

Everything above can fail mid-statement, and in a database, a half-finished multi-step operation leaves orphaned rows and broken totals — not just a stack trace. `TRY...CATCH`, `THROW` vs. `RAISERROR`, the `@@TRANCOUNT` rollback guard, and `SET XACT_ABORT ON` are all covered in full in 3.3, including the four production use cases and the trap of silently swallowing errors in a `CATCH` block. That coverage applies directly to every technique in this article — a trigger doing JSON validation, a stored procedure running a graph traversal, a batch job applying fuzzy matching — so there's no separate error-handling story here. If you're wiring any of the above into a stored procedure or trigger, go back to 3.3 for the pattern.

One addition worth knowing for the specific case of a doomed transaction: `XACT_STATE()` tells you whether the current transaction is committable (`1`), already doomed and rollback-only (`-1`), or absent entirely (`0`). That third state matters when an error has left the transaction in a state where even a `ROLLBACK` needs to be handled carefully.

## Key Takeaways

- **Be explicit with window frames** — the default `RANGE` frame groups tied `ORDER BY` values together, which surprises people; use `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for running totals
- **`LAST_VALUE()` needs an explicit frame to the end of the partition** — otherwise its default frame stops at the current row and it just returns that row's own value
- **`EXISTS` beats `IN` for existence checks** — both on performance (stops at first match) and correctness (`NOT IN` breaks silently on `NULL`s in the subquery)
- **A correlated subquery, window function, join, and CTE often solve the same problem** — pick by execution cost: window function for running totals/ranking, join for pulling related columns, `EXISTS` for existence, CTE for naming and reuse
- **`JSON_VALUE` for scalars, `JSON_QUERY` for objects/arrays** — using the wrong one returns `NULL` silently instead of erroring
- **Regex and fuzzy-matching functions can't use indexes** — pre-filter with sargable predicates first, then apply the expensive per-row function only to the survivors
- **Graph queries earn their place when traversal depth is variable** — a fixed-depth relationship is still better served by a plain foreign key and a join
