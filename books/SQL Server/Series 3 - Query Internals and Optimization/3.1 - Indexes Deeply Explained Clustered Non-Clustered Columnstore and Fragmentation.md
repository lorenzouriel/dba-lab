# Indexes, Deeply Explained: Clustered, Non-Clustered, Columnstore, and Fragmentation

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

A query that ran in 200ms last month now takes 8 seconds. Nobody changed the query. Nobody changed the data model. The table grew from 500,000 rows to 5 million, and suddenly the index that used to help isn't helping anymore.

This is how index problems usually announce themselves — not dramatically, but gradually, until one day performance collapses and nobody can explain why. Understanding indexes means understanding what's happening under the surface before that moment arrives.

---

## How Indexes Work: The B-Tree

An index is a separate data structure SQL Server maintains alongside your table. Its purpose is to let the database locate rows without reading every row.

All standard SQL Server indexes use a **B-Tree (Balanced Tree)** structure. The tree has a root node, intermediate levels, and leaf nodes. When you search for a specific value, SQL Server traverses the tree from root to leaf — navigating down levels until it reaches the target rows. The "balanced" part means the path from root to any leaf is always the same length, keeping lookups consistently fast regardless of where in the tree the target value lives.

Without an index, SQL Server must scan every page of the table — every row, every time. With an index, it can jump directly to the relevant location.

---

## Clustered Indexes: The Table IS the Index

A clustered index determines the **physical order** of data in the table. It defines how rows are stored on disk. Because of this:

- Every table can have only **one** clustered index
- SQL Server automatically creates a clustered index when you define a PRIMARY KEY
- The leaf level of the clustered index contains the actual data rows (not just pointers)

```sql
-- A clustered index is created automatically with PRIMARY KEY
CREATE TABLE dbo.Orders (
    order_id    INT          NOT NULL PRIMARY KEY,  -- clustered index on order_id
    customer_id INT          NOT NULL,
    order_date  DATETIME2    NOT NULL DEFAULT GETDATE(),
    status      VARCHAR(50)  NOT NULL DEFAULT 'Pending'
);

-- You can also create one explicitly
CREATE CLUSTERED INDEX cix_Orders_order_id ON dbo.Orders (order_id ASC);
```

Think of the clustered index as the book itself — the pages are physically sorted by chapter (the index key). Finding chapter 15 means going straight to page 150, not scanning every page.

---

## Non-Clustered Indexes: The Index at the Back of the Book

A non-clustered index is a **separate structure** with sorted copies of the indexed column values, plus pointers back to the actual data rows in the clustered index.

- A table can have **many** non-clustered indexes
- The leaf level contains index keys + row locators (pointers to the clustered index)
- They don't affect physical data order

```sql
-- Index for queries that filter by customer_id
CREATE NONCLUSTERED INDEX ix_Orders_customer_id
    ON dbo.Orders (customer_id);

-- Composite index for queries filtering by customer AND status
CREATE NONCLUSTERED INDEX ix_Orders_customer_status
    ON dbo.Orders (customer_id, status);

-- INCLUDE: add extra columns to cover a query without putting them in the key
-- Queries that need customer_id, status, AND order_date can be served from this index alone
CREATE NONCLUSTERED INDEX ix_Orders_customer_status_include_date
    ON dbo.Orders (customer_id, status)
    INCLUDE (order_date);
```

The `INCLUDE` clause is powerful: columns added via INCLUDE appear in the leaf-level pages of the index. A query that needs those columns can get everything it needs from the index without touching the base table — a "covering index" that eliminates the additional lookup step.

## Columnstore Indexes: Built for Analytics

Rowstore indexes (clustered and non-clustered) organize data by rows. **Columnstore indexes** organize data by columns. Each column is stored and compressed independently.

This makes columnstore indexes dramatically faster for analytical queries that aggregate large amounts of data:

```sql
-- Clustered columnstore: entire table stored column-oriented
-- Best for data warehouse tables where every query is analytical
CREATE CLUSTERED COLUMNSTORE INDEX cix_OrderDetails_columnstore
    ON dbo.OrderDetails
    WITH (DROP_EXISTING = ON);

-- Non-clustered columnstore on an OLTP table
-- Adds analytical acceleration without changing the row store
CREATE NONCLUSTERED COLUMNSTORE INDEX ncix_Orders_analytics
    ON dbo.Orders (customer_id, order_date, status);
```

| | Rowstore | Columnstore |
|---|---|---|
| Best for | OLTP (point lookups, small updates) | OLAP (aggregations, large scans) |
| Storage | Row-oriented | Column-oriented, compressed |
| Index per table | 1 clustered, many non-clustered | 1 clustered or 1 non-clustered |
| Compression | Standard page compression | High compression (similar values per column) |

Use rowstore indexes for transactional workloads with many small read/write operations. Use columnstore indexes for analytical workloads that run `SUM`, `AVG`, `MIN`, `MAX` over millions of rows.

## Index Fragmentation

When you create an index, fragmentation is 0%. As inserts, updates, and deletes happen, the B-Tree pages become disordered. Fragmentation accumulates over time and degrades performance.

**External fragmentation**: pages are out of logical order. SQL Server has to jump around the disk to read them sequentially.

**Internal fragmentation**: pages have unused space. Rows were deleted, leaving gaps. More pages need to be read to scan the same amount of data.

Check current fragmentation levels:

```sql
SELECT
    OBJECT_NAME(ips.object_id)       AS table_name,
    i.name                           AS index_name,
    ips.index_type_desc,
    ROUND(ips.avg_fragmentation_in_percent, 1) AS fragmentation_pct
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED'
) AS ips
INNER JOIN sys.indexes AS i
    ON i.object_id = ips.object_id
    AND i.index_id = ips.index_id
WHERE OBJECT_NAME(ips.object_id) NOT LIKE '[_]%'
  AND ips.index_type_desc != 'HEAP'
ORDER BY fragmentation_pct DESC;
```

## REBUILD vs REORGANIZE

Once you know fragmentation levels, the question is what to do about them.

**REORGANIZE** — defragments the existing index pages in place. Online operation; doesn't lock the index for reads. Use for light to moderate fragmentation (typically 10–30%).

```sql
ALTER INDEX ix_Orders_customer_id ON dbo.Orders REORGANIZE;
```

**REBUILD** — drops and recreates the index from scratch. Completely eliminates fragmentation and updates statistics. Historically offline (locks the table), though Enterprise edition supports `ONLINE = ON`. Use for heavy fragmentation (>30%) or after bulk data operations.

```sql
-- Rebuild a specific index
ALTER INDEX ix_Orders_customer_id ON dbo.Orders REBUILD;

-- Rebuild all indexes on a table
ALTER INDEX ALL ON dbo.Orders REBUILD;

-- Online rebuild (Enterprise edition)
ALTER INDEX ALL ON dbo.Orders REBUILD WITH (ONLINE = ON);
```

The practical maintenance schedule: check fragmentation weekly, REORGANIZE indexes between 10–30% fragmented, REBUILD above 30%. Schedule REBUILDs during off-peak hours.

## The Trap

**Too many indexes.** Every index speeds up reads and slows down writes — because every INSERT, UPDATE, and DELETE must also update every index on the table. A table with 15 non-clustered indexes on it will be slow to insert into.

The warning signs:
- Index fragmentation climbing unusually fast (too many writes on an over-indexed table)
- Long-running INSERT/UPDATE batches on tables with many indexes
- `sys.dm_db_index_usage_stats` showing indexes with zero seeks and zero scans — unused indexes burning write overhead for no benefit

```sql
-- Find unused indexes (seek + scan + lookup count = 0)
SELECT
    OBJECT_NAME(i.object_id) AS table_name,
    i.name AS index_name,
    ius.user_seeks + ius.user_scans + ius.user_lookups AS total_reads,
    ius.user_updates AS total_writes
FROM sys.indexes AS i
LEFT JOIN sys.dm_db_index_usage_stats AS ius
    ON i.object_id = ius.object_id
    AND i.index_id = ius.index_id
    AND ius.database_id = DB_ID()
WHERE OBJECT_NAME(i.object_id) NOT LIKE '[_]%'
  AND i.type_desc != 'HEAP'
ORDER BY total_reads ASC;
```

Start with the execution plan before adding any index. The Missing Index hints in the plan tell you exactly what the optimizer wishes it had.

## Key Takeaways

- **Clustered indexes define physical data order** — one per table, created automatically with PRIMARY KEY; the leaf level IS the data
- **Non-clustered indexes are separate pointer structures** — many allowed; INCLUDE adds columns to cover queries without key bloat
- **Columnstore indexes store data column-by-column** — optimal for aggregations and analytics (DW/OLAP), not for high-frequency OLTP writes
- **Fragmentation degrades performance over time** — check with `sys.dm_db_index_physical_stats`; REORGANIZE for <30%, REBUILD for >30%
- **Over-indexing hurts write performance** — audit unused indexes with `sys.dm_db_index_usage_stats` and drop what isn't being used
