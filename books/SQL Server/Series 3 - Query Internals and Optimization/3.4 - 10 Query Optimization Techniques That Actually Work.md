# 10 Query Optimization Techniques That Actually Work

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

A slow query is almost never just "the database is slow." It's a specific operation — a scan where a seek should be, a missing index, a function wrapper disabling index use, a DISTINCT hiding a join problem. The fix is almost always precise.

Before reaching for any of the techniques below, open the execution plan (Ctrl+M in SSMS). The plan shows you what SQL Server actually does with your query, where it spends the most time, and what it wishes it had. These techniques are most valuable when you understand what they're fixing and why.

---

## 1. Use SELECT TOP to Limit Early

When you only need a subset of recent data, TOP limits the rows SQL Server needs to process. Combined with an ORDER BY on an indexed column, this can mean a tiny index seek instead of a full scan.

```sql
-- Get the 100 most recent orders
SELECT TOP 100
    order_id,
    customer_id,
    order_date,
    status
FROM dbo.Orders
ORDER BY order_date DESC;
```

This is also useful for quick diagnostic checks — `SELECT TOP 1000` instead of `SELECT *` gives you a data preview without potentially fetching millions of rows.

---

## 2. Always Specify Columns — Never `SELECT *`

`SELECT *` forces SQL Server to fetch every column from disk, even the wide VARCHAR(MAX) columns you don't need. On tables with many or large columns, the I/O difference is significant. It also prevents covering index use.

```sql
-- Bad: fetches every column, prevents index covering
SELECT * FROM dbo.Orders WHERE status = 'Pending';

-- Good: only the columns needed, potentially served from an index
SELECT order_id, customer_id, order_date
FROM dbo.Orders
WHERE status = 'Pending';
```

---

## 3. Use IN Instead of Multiple OR Conditions

`IN` is logically equivalent to multiple `OR` conditions on the same column, but the optimizer handles it more efficiently — it can evaluate multiple values in a single, optimized pass.

```sql
-- Less efficient: multiple OR conditions
WHERE status = 'Pending' OR status = 'Processing' OR status = 'Shipped'

-- More efficient: IN with indexed column
WHERE status IN ('Pending', 'Processing', 'Shipped')
```

The difference becomes noticeable with larger value lists and on non-indexed columns where scan behavior differs.

---

## 4. Filter with WHERE Before Grouping, HAVING After

`WHERE` eliminates rows before aggregation begins. `HAVING` filters after all rows are grouped and aggregated. On large tables, a `WHERE` clause that removes 90% of rows means aggregation happens on 10% of the data.

Use `HAVING` only when you must filter on an aggregated value (`SUM`, `COUNT`, etc.). Everything else belongs in `WHERE`.

```sql
-- Good: WHERE eliminates rows first, then GROUP BY + HAVING
SELECT
    customer_id,
    COUNT(*) AS order_count,
    SUM(od.quantity * od.unit_price) AS total_value
FROM dbo.Orders AS o
INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
WHERE o.order_date >= '2024-01-01'          -- Eliminates old rows early
  AND o.status = 'Completed'               -- Eliminates non-completed rows early
GROUP BY customer_id
HAVING SUM(od.quantity * od.unit_price) > 500;  -- Filters after aggregation
```

---

## 5. Index Columns Used in WHERE, JOIN, and ORDER BY

The execution plan's "Missing Index" warnings are your starting point. Columns that appear frequently in WHERE filters, JOIN conditions, and ORDER BY clauses are index candidates.

```sql
-- Check existing indexes on a table
EXEC sp_helpindex 'dbo.Orders';

-- Index on a high-cardinality filter column
CREATE NONCLUSTERED INDEX ix_Orders_status_date
    ON dbo.Orders (status, order_date DESC)
    INCLUDE (customer_id);
```

The column order in a composite index matters. Put the most selective column (or the equality filter) first. Date columns used in range queries often benefit from `DESC` ordering if you're usually fetching the most recent records.

---

## 6. Don't Wrap Filter Columns in Functions

Wrapping a column in a function in a WHERE clause makes the expression non-sargable — SQL Server can't use an index on the column because the function is applied to every row.

```sql
-- Non-sargable: function on column, full scan required
WHERE YEAR(order_date) = 2024
WHERE LOWER(email) = 'ana@email.com'
WHERE LEN(product_name) > 10

-- Sargable: range condition, index can be used
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
WHERE email = 'ana@email.com'    -- store consistently lowercase in the table
```

The fix for date functions is always a range condition. The fix for LOWER/UPPER is consistent storage — lowercase or case-insensitive collation at the column or database level.

---

## 7. Use EXISTS Instead of COUNT for Existence Checks

`EXISTS` stops as soon as one matching row is found. `COUNT(*)` scans every matching row and returns a number. When you only care about whether something exists, `EXISTS` can be an order of magnitude faster on large tables.

```sql
-- Inefficient: counts all matching rows
IF (SELECT COUNT(*) FROM dbo.Orders WHERE customer_id = @customer_id) > 0

-- Efficient: stops at first match
IF EXISTS (SELECT 1 FROM dbo.Orders WHERE customer_id = @customer_id)
```

---

## 8. AVOID DISTINCT as a Crutch

`DISTINCT` is used to remove duplicates. In many queries, duplicates appear because of an incorrect join — joining to a table that has multiple rows per parent produces duplicate parent rows, and `DISTINCT` masks that by deduplicating the result.

The correct fix is fixing the join, not adding DISTINCT.

```sql
-- Symptom: DISTINCT is needed because the join multiplies rows
SELECT DISTINCT c.customer_id, c.first_name
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id;

-- Fix: if you just need customers who have at least one order, use EXISTS
SELECT c.customer_id, c.first_name
FROM dbo.Customers AS c
WHERE EXISTS (SELECT 1 FROM dbo.Orders WHERE customer_id = c.customer_id);
```

DISTINCT causes an expensive sort-and-dedup operation. If your query legitimately needs deduplication across a large result set, consider the root cause first.

---

## 9. Understand NOLOCK — and Use It Cautiously

`WITH (NOLOCK)` makes a SELECT read dirty (uncommitted) data. It's widely used as a "performance hint" to avoid waiting for locks.

```sql
-- Read without acquiring shared locks
SELECT order_id, status
FROM dbo.Orders WITH (NOLOCK)
WHERE customer_id = @customer_id;
```

The tradeoff: you may read rows that are being written and haven't been committed, rows that will be rolled back, or even rows twice (for large table scans where page splits occur during the read).

`NOLOCK` is appropriate for truly non-critical reads where slight staleness or occasional duplicates are acceptable — like dashboard aggregate queries that run frequently and don't need perfect precision. It is not appropriate for any query whose results drive financial decisions, regulatory reporting, or data modifications.

For most scenarios requiring reduced locking, the proper answer is the `READ COMMITTED SNAPSHOT ISOLATION` (RCSI) database setting — it provides a consistent read without dirty reads, without locking.

---

## 10. Use Stored Procedures for Frequently-Run Queries

Ad-hoc queries are compiled every time they run — the optimizer produces an execution plan, which is discarded when the connection closes. Stored procedures cache their execution plans after the first execution. Subsequent runs skip compilation.

```sql
CREATE PROCEDURE dbo.usp_GetCustomerOrderHistory
    @customer_id INT,
    @start_date  DATE = NULL,
    @end_date    DATE = NULL
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        o.order_id,
        o.order_date,
        o.status,
        p.product_name,
        od.quantity,
        od.unit_price
    FROM dbo.Orders AS o
    INNER JOIN dbo.OrderDetails AS od ON o.order_id = od.order_id
    INNER JOIN dbo.Products AS p ON od.product_id = p.product_id
    WHERE o.customer_id = @customer_id
      AND (@start_date IS NULL OR o.order_date >= @start_date)
      AND (@end_date IS NULL OR o.order_date <= @end_date)
    ORDER BY o.order_date DESC;
END;
```

Besides plan caching, stored procedures benefit from security isolation (EXECUTE permission without direct table access) and centralized maintenance.

## The Meta-Tip: Read the Execution Plan First

Every technique above is a fix for a specific problem. The execution plan tells you which problem you have.

In SSMS: enable "Include Actual Execution Plan" (Ctrl+M) and run the query. Look for:
- **Table Scan** or **Clustered Index Scan** on large tables — often indicates a missing index
- **Missing Index** hint (yellow warning icon) — the optimizer's suggestion
- **Sort** operations on large data sets — may indicate a missing ordered index
- High **Cost %** nodes — where most of the query time is spent
- **Key Lookup** operations — non-clustered index found the row, then had to go back to the clustered index for other columns (INCLUDE can fix this)

Optimize what the plan shows you, not what you assume is slow.

---

## Key Takeaways

- **Start with the execution plan** — it shows what's actually slow and what indexes are missing
- **Non-sargable filters kill index performance** — don't wrap filter columns in functions; use range conditions instead
- **`WHERE` beats `HAVING` for pre-aggregation filtering** — eliminate rows early, filter aggregates late
- **`EXISTS` beats `COUNT(*)` for existence checks** — stops at first match instead of scanning all matches
- **`DISTINCT` often masks a bad join** — fix the join instead of deduplicating the result
- **`NOLOCK` is not a free performance upgrade** — it trades consistency for speed; use RCSI instead for production reads
