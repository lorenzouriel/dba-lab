# Transactions, COMMIT, and ROLLBACK: How SQL Server Keeps Your Data Consistent

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

You're transferring $500 from one account to another. The debit succeeds. Then the database crashes before the credit can run.

When the server comes back up, one account is $500 lighter and the other is unchanged. The money is gone — not to fraud, not to a bug in the query, but to a failure of atomicity. Two operations that should have been one weren't.

This is exactly the problem that transactions were designed to solve.

---

## What a Transaction Is

A **transaction** is a sequence of SQL statements executed as a single logical unit of work. All statements inside the transaction succeed together, or none of them do.

The three control commands:

- `BEGIN TRANSACTION` — marks the start. SQL Server starts recording changes in the transaction log.
- `COMMIT` — finalizes all changes. Makes them permanent.
- `ROLLBACK` — undoes all changes since `BEGIN TRANSACTION`. Returns the database to its state before the transaction started.

Every SQL statement in SQL Server runs inside a transaction, even if you don't write one explicitly. When you run a bare `INSERT`, SQL Server wraps it in an implicit transaction: it either succeeds entirely or rolls back entirely. `BEGIN TRANSACTION` is how you group multiple statements into one atomic unit.

---

## A Simple COMMIT

```sql
BEGIN TRANSACTION;

-- Insert new customer
INSERT INTO dbo.Customers (first_name, last_name, email)
VALUES ('Ana', 'Costa', 'ana.costa@email.com');

-- Insert their first order
INSERT INTO dbo.Orders (customer_id, status)
VALUES (SCOPE_IDENTITY(), 'Pending');

COMMIT;
```

Both inserts succeed together and are written permanently to disk. If the server crashes between COMMIT and writing to disk, the Write-Ahead Log (more on this below) ensures the committed data survives.

---

## COMMIT + ROLLBACK with TRY/CATCH

In production, you never write a bare transaction without error handling. The pattern is `BEGIN TRANSACTION` → `TRY` block → `COMMIT` → `CATCH` block → `ROLLBACK`.

```sql
BEGIN TRANSACTION;

BEGIN TRY
    -- Debit customer 1
    UPDATE dbo.Customers
    SET credit_balance = credit_balance - 100
    WHERE customer_id = 1;

    -- Credit customer 2
    UPDATE dbo.Customers
    SET credit_balance = credit_balance + 100
    WHERE customer_id = 2;

    COMMIT;
END TRY
BEGIN CATCH
    ROLLBACK;
    THROW;  -- Re-raise the original error to the caller
END CATCH;
```

If the second UPDATE fails — constraint violation, deadlock, anything — control transfers to `CATCH`, the transaction rolls back, and both accounts remain unchanged. The error is then re-raised with `THROW` so the caller knows what happened.

This pattern is the non-negotiable standard for any multi-statement operation. Never rely on implicit transaction behavior when you need atomicity.

## A Real Production Example: Creating an Order

```sql
CREATE PROCEDURE dbo.usp_CreateOrder
    @customer_id INT,
    @product_id  INT,
    @quantity    INT
AS
BEGIN
    SET NOCOUNT ON;

    -- Validate before entering transaction (keep transactions short)
    IF NOT EXISTS (SELECT 1 FROM dbo.Customers WHERE customer_id = @customer_id)
        THROW 50001, 'Customer not found.', 1;

    DECLARE @unit_price DECIMAL(10,2);
    SELECT @unit_price = unit_price FROM dbo.Products WHERE product_id = @product_id;

    IF @unit_price IS NULL
        THROW 50002, 'Product not found.', 1;

    BEGIN TRANSACTION;
    BEGIN TRY
        DECLARE @order_id INT;

        INSERT INTO dbo.Orders (customer_id, order_date, status)
        VALUES (@customer_id, GETDATE(), 'Pending');

        SET @order_id = SCOPE_IDENTITY();

        INSERT INTO dbo.OrderDetails (order_id, product_id, quantity, unit_price)
        VALUES (@order_id, @product_id, @quantity, @unit_price);

        UPDATE dbo.Products
        SET stock = stock - @quantity
        WHERE product_id = @product_id;

        COMMIT;

        SELECT @order_id AS new_order_id;
    END TRY
    BEGIN CATCH
        ROLLBACK;
        THROW;
    END CATCH;
END;
```

Three DML operations — order header, order line, stock decrement — committed as one. If stock goes negative (violating a CHECK constraint), all three roll back.

## How This Works Internally: Write-Ahead Logging

SQL Server uses the **Write-Ahead Logging (WAL)** algorithm. Before any data modification reaches the actual data files (`.mdf`), the change is written to the transaction log (`.ldf`) first.

The sequence:
1. `BEGIN TRANSACTION` — SQL Server marks a transaction start point in the log
2. Each statement writes changes to the log *and* to the Buffer Pool (in-memory pages)
3. `COMMIT` — SQL Server writes a commit record to the log; at this point the transaction is durable
4. Modified pages flush to disk asynchronously via the checkpoint process

If the server crashes after step 3, the log contains a complete record of the committed transaction. SQL Server replays it on recovery — the data is not lost. If the crash happened before `COMMIT`, SQL Server rolls back the incomplete transaction during recovery — partial changes don't persist.

This is the Durability guarantee from ACID. The log is the source of truth.

## SAVE TRANSACTION: Savepoints

For long, complex transactions, you can create named savepoints that allow partial rollbacks without abandoning the entire transaction.

```sql
BEGIN TRANSACTION;

INSERT INTO dbo.Orders (customer_id, status)
VALUES (42, 'Pending');

SAVE TRANSACTION order_created;  -- Savepoint

BEGIN TRY
    -- Risky operation
    INSERT INTO dbo.OrderDetails (order_id, product_id, quantity, unit_price)
    VALUES (SCOPE_IDENTITY(), 99, 1, 25.00);

    COMMIT;
END TRY
BEGIN CATCH
    -- Roll back only to the savepoint, not the whole transaction
    ROLLBACK TRANSACTION order_created;

    -- Can continue with other logic here, then commit or rollback
    COMMIT;
END CATCH;
```

Savepoints are rarely needed in typical application code but appear in complex batch operations where partial recovery is meaningful.

---

## The Trap

**Long-running transactions block everything.** A transaction holds locks on the rows and pages it touches. While the transaction is open, other transactions that need those same resources must wait — or receive a deadlock error.

The most common cause: `BEGIN TRANSACTION` in code that then makes an external call (API request, file write, user input), leaving the transaction open for seconds or minutes while the lock holds.

```sql
-- DANGEROUS pattern: transaction open across a slow external operation
BEGIN TRANSACTION;
INSERT INTO dbo.AuditLog (event) VALUES ('Processing started');

-- API call that takes 3 seconds... transaction holds locks for 3 seconds
EXEC dbo.usp_CallExternalService;

COMMIT;
```

Rules for keeping transactions short:
- Validate and fetch all data you need *before* `BEGIN TRANSACTION`
- Keep only DML operations inside the transaction
- Never put user interaction, API calls, or waits inside a transaction
- COMMIT or ROLLBACK as soon as the critical section is complete

---

## Key Takeaways

- **A transaction groups multiple statements into one atomic unit** — all succeed or all fail; no partial state
- **Always pair `BEGIN TRANSACTION` with TRY/CATCH** — `COMMIT` in the TRY block, `ROLLBACK` in the CATCH block, re-raise with `THROW`
- **Write-Ahead Logging is what makes durability work** — the log file is written before the data file; committed transactions survive crashes
- **SAVE TRANSACTION creates partial rollback points** — useful for complex batches where you want to recover from one step without undoing everything
- **Keep transactions as short as possible** — every open transaction holds locks; long transactions cause blocking and deadlocks
