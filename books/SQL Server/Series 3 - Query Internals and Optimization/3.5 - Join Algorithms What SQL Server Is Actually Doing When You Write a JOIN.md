# Join Algorithms: What SQL Server Is Actually Doing When You Write a JOIN

*Series 3 — Query Internals & Optimization | The SQL Server Deep Dive*

---

When you write `JOIN`, you specify what to join and on what condition. You don't specify how to join. That decision belongs to the query optimizer — and it makes it based on table sizes, available indexes, data distribution statistics, and cost estimates.

The optimizer's choice shows up in the execution plan as one of three physical join algorithms: Nested Loops, Merge Join, or Hash Join. Knowing which one was chosen — and why — is often the difference between understanding your execution plan and just staring at it.

---

## The Problem Each Algorithm Solves

All three algorithms produce the same result: matched rows from two tables. They differ in how they find the matches:

- **Nested Loops** — take each row from the outer table and look it up in the inner table
- **Merge Join** — walk both sorted inputs simultaneously, matching as you go
- **Hash Join** — build a hash table from the smaller input, probe it with the larger input

---

## Nested Loops Join

**How it works:** SQL Server takes the first row from the outer (driving) table, scans or seeks the inner table for matching rows, moves to the next outer row, and repeats. It's literally a nested for-loop.

**When the optimizer chooses it:**
- The outer input is small (few rows)
- The inner table has an index on the join key (so each lookup is a fast seek, not a scan)
- High selectivity — only a few rows match per outer row

**Example:**

```sql
-- Small Customers result (filtered), large indexed Orders table
SELECT
    c.customer_id,
    c.first_name,
    o.order_id,
    o.order_date
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
WHERE c.email = 'ana.costa@email.com';   -- Returns 1 customer
```

SQL Server finds one customer, then seeks into the Orders index for `customer_id = 42`. The seek is O(log n). This is extremely efficient when the outer result is small.

**When it performs badly:** Both tables are large and unfiltered. 1 million outer rows × index lookups into a 1 million row inner table = potentially catastrophic performance.

In the execution plan: **Nested Loops (Inner Join)**

---

## Merge Join

**How it works:** Both inputs must be sorted on the join key. SQL Server walks through both sorted inputs simultaneously with a "zipper" approach — advance the pointer on whichever side has the smaller current key, match when both pointers are on the same value.

**When the optimizer chooses it:**
- Both inputs are already sorted (clustered indexes on the join key, or an upstream ORDER BY)
- Both inputs are large
- Equality join condition (`=`)

**Example:**

```sql
-- Both tables clustered on customer_id — data is pre-sorted
SELECT
    c.customer_id,
    COUNT(o.order_id) AS order_count
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o ON c.customer_id = o.customer_id
GROUP BY c.customer_id;
```

If both `Customers` and `Orders` have clustered indexes on `customer_id`, SQL Server can walk both in ascending order, matching as it goes. O(n + m) — one pass through each table.

**When it performs badly:** Inputs aren't sorted. SQL Server must sort them first, which is expensive on large sets. Merge Join also doesn't work with non-equality conditions (`>`, `BETWEEN`, `LIKE`).

In the execution plan: **Merge Join (Inner Join)**

---

## Hash Join

**How it works:** SQL Server builds a hash table in memory from the smaller input (the "build" side). It then scans the larger input (the "probe" side) and for each row, hashes the join key and looks it up in the hash table.

**When the optimizer chooses it:**
- Large, unsorted inputs
- No useful indexes on either join key
- Equality joins
- Common in data warehouse queries and large analytical operations

**Example:**

```sql
-- Large tables without useful join-key indexes
SELECT
    p.category,
    SUM(od.quantity * od.unit_price) AS category_revenue
FROM dbo.OrderDetails AS od
INNER JOIN dbo.Products AS p ON od.product_id = p.product_id
GROUP BY p.category;
```

If neither `OrderDetails.product_id` nor `Products.product_id` has a supporting index, the optimizer builds a hash table of `Products` (smaller) and probes it with `OrderDetails` (larger).

**When it performs badly:** If the hash table doesn't fit in the memory grant, SQL Server spills it to tempdb. This is called a "hash spill" or "hash bail" — the query continues but performance degrades significantly. Watch for "tempdb spills" in execution plans.

In the execution plan: **Hash Match (Inner Join)**

---

## Comparison

| Algorithm | Best Case | Worst Case | Memory | Parallelism |
|-----------|-----------|------------|--------|------------|
| Nested Loops | Small outer + indexed inner | Both sides large, no index | Low | Limited |
| Merge Join | Both inputs sorted, large sets | Inputs unsorted (sort cost) | Medium | Good |
| Hash Join | Large unsorted inputs, no indexes | Hash spill to tempdb | High | Good |

## Reading the Execution Plan

In SSMS, enable "Include Actual Execution Plan" (Ctrl+M). Each join operator shows:

- The algorithm chosen (Nested Loops, Merge Join, Hash Match)
- The estimated and actual row counts (large discrepancies indicate stale statistics)
- The cost percentage relative to the total query cost
- For Hash Match: whether a spill occurred (orange warning icon)

**Yellow warning icons** often indicate:
- Missing index hints
- High estimated vs. actual row count discrepancy (statistics need updating)
- Hash spills

**What to do with this information:**
- Nested Loops on large inputs → add an index to make the inner lookup a seek
- Merge Join with an expensive Sort operator before it → add an ordered index so the sort is pre-baked
- Hash Match with a spill warning → investigate why the build side is larger than expected; check statistics or add an index

## Hint Overrides (Use Sparingly)

You can force a specific join algorithm with query hints. This is almost always the wrong approach — the optimizer usually knows better — but it's useful for testing and diagnosis.

```sql
-- Force Nested Loops
SELECT ...
FROM dbo.Customers c
INNER JOIN dbo.Orders o ON c.customer_id = o.customer_id
OPTION (LOOP JOIN);

-- Force Merge Join
OPTION (MERGE JOIN);

-- Force Hash Join
OPTION (HASH JOIN);
```

Use hints to understand the performance difference between algorithms on your data. Don't leave them in production code unless you have a specific, well-understood reason — they prevent the optimizer from adapting as your data changes.

---

## The Trap

**Assuming that INNER JOIN always means the same algorithm.** Two queries with identical join syntax can use different physical algorithms depending on data volume, index state, and cardinality estimates. A query that used Nested Loops efficiently in development (on a small table) may switch to Hash Join in production (on millions of rows) — or worse, to Nested Loops with no useful index, causing a catastrophic full scan per outer row.

The solution is to understand your data volume and check execution plans in production-like conditions. What performs well on 10,000 rows may perform very differently on 10 million.

---

## Key Takeaways

- **SQL Server chooses join algorithms automatically** — you write INNER/LEFT/RIGHT JOIN; the optimizer picks Nested Loops, Merge, or Hash based on cost estimation
- **Nested Loops** — best for small outer inputs with indexed inner lookups; disastrous when both sides are large
- **Merge Join** — best for large, already-sorted inputs; requires a sort step if inputs aren't ordered
- **Hash Join** — best for large, unsorted inputs without indexes; watch for hash spills to tempdb in execution plans
- **Read the execution plan** — the algorithm shown tells you what the optimizer decided and why; spill warnings and missing index hints are actionable signals
- **Forcing join hints** is for diagnosis, not production — the optimizer adapts; hardcoded hints don't
