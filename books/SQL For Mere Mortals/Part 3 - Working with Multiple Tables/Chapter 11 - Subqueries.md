# Chapter 11: Subqueries

Subquery == a SELECT expression embedded inside a clause of another SELECT statement.

Big idea: there's (almost) always more than one way to solve a SQL problem — this chapter re-solves several problems from Chapters 8/9 using subqueries instead of JOINs, plus unlocks filters that JOINs alone can't express correctly (see "Why not just JOIN?" below).

## Three Kinds of Subquery (SQL Standard)

1. **Row subquery** — returns more than one column, no more than one row.
2. **Table subquery** — returns one-or-more columns, zero-to-many rows. (This is what you've already been using inside a FROM clause since Chapter 8.)
3. **Scalar subquery** — returns exactly one column, no more than one row. Usable anywhere a single value expression is legal (SELECT list, WHERE comparison).

### Row subqueries

Pairs with a **row value constructor** — comparing a tuple of columns against a tuple of literals/subquery output:

```sql
SELECT SKUClass, SKUNumber, ProductName
FROM Products
WHERE (SKUClass, SKUNumber) >= ('DSK', 9775);
```

Equivalent to `WHERE SKUClass > 'DSK' OR (SKUClass = 'DSK' AND SKUNumber >= 9775)`. Barely any commercial database supports this syntax — nice to know it exists, not worth relying on.

## Subqueries as Column Expressions

A scalar subquery can sit directly in the SELECT list, pulling a value from a table that isn't in the outer query's FROM clause at all.

```sql
SELECT o.OrderNumber, o.OrderDate, o.ShipDate,
       (SELECT c.CustLastName FROM Customers c WHERE c.CustomerID = o.CustomerID)
FROM Orders o
WHERE o.ShipDate = '2017-10-03';
```

This particular example is better written as a plain INNER JOIN — the subquery form only pays off once an **aggregate function** is involved, because there's no other way to get "one row per outer row, plus one summary value" without grouping (covered fully in Ch. 13).

```sql
SELECT CustFirstName, CustLastName,
       (SELECT COUNT(*) FROM Orders WHERE Orders.CustomerID = Customers.CustomerID) AS CountOfOrders
FROM Customers;
```

1. `COUNT(*)` == count of rows. `COUNT(column)` == count of non-Null values in that column. Add `DISTINCT` to count only unique values.
2. `MAX(column)` == largest value (numeric/character-collation/date, depending on type).

🤯 If you instead `INNER JOIN Customers to Orders` to get this same count, a customer with 3 orders produces 3 duplicate output rows — a subquery is the *only* clean way to get exactly one row per customer with a related count/max tacked on, short of GROUP BY.

Always give the subquery column an alias (`AS CountOfOrders`) — otherwise the engine invents an ugly name like `Expr1`.

## Subqueries as Filters

A scalar subquery can also be the right-hand side of a WHERE comparison — most useful when the comparison value must itself be computed per outer row (a **correlated subquery**: the inner query references a column from the outer query, so it re-evaluates for every outer row).

```sql
SELECT c.CustFirstName, c.CustLastName, o.OrderNumber, o.OrderDate
FROM Customers c
INNER JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE o.OrderDate = (SELECT MAX(o2.OrderDate) FROM Orders o2 WHERE o2.CustomerID = c.CustomerID);
```

Alias the inner copy of a self-referenced table (`o2`) even when the engine could infer it — the Standard resolves unqualified names from the innermost query first, but an explicit alias keeps the intent readable months later.

### Special Predicate Keywords

**IN** — compare against a list generated by a table subquery (one column, many rows):

```sql
SELECT RecipeTitle FROM Recipes
WHERE RecipeID IN (
  SELECT RecipeID FROM Recipe_Ingredients
  WHERE IngredientID IN (
    SELECT IngredientID FROM Ingredients
    INNER JOIN Ingredient_Classes ON Ingredients.IngredientClassID = Ingredient_Classes.IngredientClassID
    WHERE IngredientClassDescription = 'Seafood'));
```

Subqueries can nest arbitrarily deep — doesn't mean they should. A single IN plus a JOIN inside the subquery reads better than IN-inside-IN-inside-IN.

**Quantified: `ALL` / `SOME` / `ANY`** — compare against every value (`ALL`) or at least one value (`SOME`/`ANY`, the Standard treats them as synonyms) returned by a table subquery.

```sql
SELECT ProductName, RetailPrice
FROM Products INNER JOIN Categories ON Products.CategoryID = Categories.CategoryID
WHERE CategoryDescription = 'Accessories'
  AND RetailPrice > ALL (
    SELECT RetailPrice FROM Products
    INNER JOIN Categories ON Products.CategoryID = Categories.CategoryID
    WHERE CategoryDescription = 'Clothing');
```

Gotchas:
1. `= ANY` behaves like `IN`.
2. If the subquery returns **zero rows**: any `ALL` comparison is **true**; any `SOME`/`ANY` comparison is **false**. Easy to get backwards.

**EXISTS** — true if the subquery returns at least one row at all; doesn't care what columns it returns (`SELECT *` is idiomatic).

```sql
SELECT c.CustomerID, c.CustFirstName, c.CustLastName
FROM Customers c
WHERE EXISTS (
  SELECT * FROM Orders o
  INNER JOIN Order_Details od ON o.OrderNumber = od.OrderNumber
  INNER JOIN Products p ON p.ProductNumber = od.ProductNumber
  WHERE p.CategoryID = 2 AND o.CustomerID = c.CustomerID);
```

### Why not just JOIN? (fan-out duplicates)

If a related table can have many rows per outer row (e.g. Recipe_Ingredients has many rows per Recipe), filtering with a JOIN + WHERE on the related table's attribute returns the *filter column* correctly but corrupts everything else you select alongside it: you only get the columns that passed the filter, not the full sibling set.

```sql
-- Wrong: only returns the seafood ingredients themselves, not the full ingredient list
SELECT r.RecipeTitle, i.IngredientName
FROM Recipes r
INNER JOIN Recipe_Ingredients ri ON r.RecipeID = ri.RecipeID
INNER JOIN Ingredients i ON ri.IngredientID = i.IngredientID
INNER JOIN Ingredient_Classes ic ON i.IngredientClassID = ic.IngredientClassID
WHERE ic.IngredientClassDescription = 'Seafood';

-- Right: JOIN fetches all ingredients; subquery just selects which recipes qualify
SELECT r.RecipeTitle, i.IngredientName
FROM Recipes r
INNER JOIN Recipe_Ingredients ri ON r.RecipeID = ri.RecipeID
INNER JOIN Ingredients i ON ri.IngredientID = i.IngredientID
WHERE r.RecipeID IN (
  SELECT ri2.RecipeID FROM Recipe_Ingredients ri2
  INNER JOIN Ingredients i2 ON ri2.IngredientID = i2.IngredientID
  INNER JOIN Ingredient_Classes ic ON i2.IngredientClassID = ic.IngredientClassID
  WHERE ic.IngredientClassDescription = 'Seafood');
```

This is the chapter's central "why bother" point: using a subquery as a *row filter* while a separate JOIN fetches the *full* related data is the only way to get "all details for rows that satisfy some condition elsewhere," without a stray DISTINCT papering over duplicate rows (and DISTINCT-based views are never updatable, since DISTINCT hides which underlying row is which).

✨ **Side learning:** the book notes that Standard SQL barely gets implemented consistently here — one vendor's saved view silently rewrote an `= ANY` into an `IN` under the hood. Don't assume the SQL you wrote is the SQL that runs.

## Uses for Subqueries

Two buckets, matching the two subsections above:
1. **Column expression** — pull a per-row aggregate (COUNT, MAX, ...) from a related table without a JOIN-induced fan-out. ("List vendors and a count of products they sell," "customers and the date of their last booking.")
2. **Filter** — IN / NOT IN / SOME / ANY / ALL / EXISTS in a WHERE clause, especially when you need "all sibling data for rows that satisfy some condition on a *different* related table" (the fan-out problem above), or a simple "give me the max/min-matching row per group" comparison.

`NOT IN` is the natural way to phrase negative existence ("products never ordered," "students who never withdrew," "agents who never booked anyone") — same shape as `EXISTS`/`NOT EXISTS`, more readable for a plain single-column check.

## Summary

- Three subquery flavors: row (rare, tuple comparisons), table (FROM clause or IN list), scalar (single value, usable as a column or in a WHERE comparison).
- A scalar subquery in the SELECT list is the clean way to attach a per-row aggregate from a related table without duplicating rows the way a JOIN would.
- A correlated subquery re-runs per outer row by referencing an outer column inside its WHERE clause; alias self-joined tables explicitly for clarity.
- `IN` compares against a subquery-built list; `= ANY` is equivalent to `IN`.
- `ALL`/`SOME`/`ANY` quantify a comparison across every/at-least-one row of a subquery — watch the true/false flip when the subquery returns zero rows.
- `EXISTS` only cares whether the subquery returns any row at all.
- Use a subquery filter (`IN`/`EXISTS`) instead of a JOIN+WHERE filter whenever you need the *full* set of related rows for qualifying outer rows, not just the ones matching the filter — a plain JOIN+WHERE fan-out silently drops sibling data or forces an unwanted DISTINCT.
